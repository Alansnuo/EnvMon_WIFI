## 2.1 这块代码要解决什么问题

### 问题：字节来了，CPU 不一定在

STM32F1 的 USART 接收端**只有一个字节的寄存器**（叫 RDR），**没有 FIFO**。
意思是：

```
字节到 → RDR 满了 → 下一个字节到 → 前一个字节被覆盖 → 丢
```

CPU 必须在下一个字节到来之前把 RDR 读走，否则就丢数据。115200 波特率下，
**一个字节的时间是 87 微秒**。

而这个项目里有个东西会**关中断 4 毫秒**：

```c
/* BSP/dht11/dht11.c:163 —— DHT11 读位流期间 */
__disable_irq();
...  /* 收发 40 bit，约 4ms */
__enable_irq();
```

4 毫秒 = **46 个字节的时间**。也就是说，只要 DHT11 在读数，串口来的字节
**在中断方式下必丢无疑**。

更早的实现是在 `WaitResponse()` 里这样收的：

```c
/* 旧实现（已删除），esp8266.c:15-20 有记录 */
while (HAL_GetTick() - start < timeout)
{
    if (HAL_UART_Receive(&ESP8266_UART, &buf[len], 1, 10) == HAL_OK)
    {
        ...
    }
}
```

两个毛病：

1. **丢字节** —— 上面说的，关中断那 4ms 里来的全没了。
2. **忙等** —— `HAL_UART_Receive(..., 10)` 空读时要等 10ms 才返回。
   一条 512 字节的响应要轮询 512 次 → 这个循环会把低优先级任务**饿死十几秒**。

### 约束

| 约束 | 从哪来 | 对设计的影响 |
|---|---|---|
| 字节不能丢 | DHT11 关中断 4ms | 收字节的活儿必须**全交给硬件**（DMA），CPU 参不参与都不影响 |
| 不能忙等 | FreeRTOS 下要能切任务 | 轮询循环里必须有让出 CPU 的点 |
| **BSP 层不能依赖 FreeRTOS** | `bsp_delay.h` 的约定 | 没法在中断里调 `...FromISR` API，所以**不能走中断 + 信号量那条路** |
| RAM 很紧 | 芯片只有 20KB，FreeRTOS 堆已经占了 10KB | 缓冲区要精打细算，见 §2.9 |

第三条是**整个架构的决定性约束**，展开说：

如果想用"IDLE 中断 + 信号量"的方案（串口空闲时触发中断，中断里
`xSemaphoreGiveFromISR` 唤醒任务），那 `esp8266.c` 就得 `#include "FreeRTOS.h"`。
而这个项目的分层规矩是 **BSP 层是"裸机驱动"，RTOS 是可选的**——
同一个驱动理论上能拿到没有 RTOS 的工程里用。

所以最终选了**轮询 CNDTR**：不用中断、不依赖 RTOS，代价是**最多 1ms 的发现延迟**
（轮询间隔），而 AT 响应本身是几十毫秒级的，这点延迟完全无所谓。

## 2.2 整体结构

### ⚠️ 先纠正一个常见的误解

很多介绍会把这个架构画成"三级流水线"：

```
DMA → DmaBuf → RxBuf → 调用方        ← 错！RxBuf 不是必经之路
```

**实际不是流水线，是"一条环形队列 + 两个互斥的消费者"**：

```
                    ┌──────────────────────────────┐
   USART2 ──DMA──写──▶   ESP8266_DmaBuf[256]        │
                    │   （环形，永不停止）           │
                    │   写指针 = CNDTR 算出来的      │
                    │   读指针 = ESP8266_DmaTail     │
                    └───────────┬──────────────────┘
                                │
                    ESP8266_RxPop()  ← 唯一推进读指针的地方
                                │
                ┌───────────────┴───────────────┐
                │                               │
        消费者 A                          消费者 B
        ESP8266_RxDrain()                 ESP8266_RxPop() 直接用
                │                               │
                ▼                               ▼
        ESP8266_RxBuf[512]                 调用方的 buf
        （线性累积，strstr 匹配）           （MQTT 的 rx[]）
                │                               ▲
                ▼                               │
        ESP8266_WaitResponse()          ESP8266_TCPRecvRaw()
        ← 只处理 AT 文本应答            ← 只处理 +IPD 数据
```

**关键点：`TCPRecvRaw` 完全绕过 `RxBuf`。** MQTT 的数据一个字节都不会进
`RxBuf`，也不会被 `strstr` 扫到。

这一点为什么重要？因为**所有"数据会不会丢"的分析都取决于它**。如果
`TCPRecvRaw` 是"先把数据 drain 进 `RxBuf` 再从里面挑"，那 `RxBuf` 满
（512 字节）的时候就会丢数据，而 `RxBuf` 是给 AT 文本用的——两个消费者
抢一块地，麻烦就大了。实际设计里它们各走各的，`RxBuf` 满不影响 MQTT 数据。

> 但"两个消费者抢**同一条队列**"这件事本身仍然有代价，见 §2.7。

## 2.3 接收层逐段

### 2.3.1 `ESP8266_RxStart()` —— 挂上 DMA

`esp8266.c:44-77`。只在 `ESP8266_Init()` 里调一次（`esp8266.c:181`），
之后 DMA 就在环形模式里**永远转下去**，再也不停。

```c
    (void)HAL_UART_DMAStop(&ESP8266_UART);

    ESP8266_DmaTail = 0;

    if (HAL_UART_Receive_DMA(&ESP8266_UART, ESP8266_DmaBuf,
                             ESP8266_DMA_BUF_SIZE) != HAL_OK)
    {
        return ESP8266_ERR_AT;
    }
```

**`HAL_UART_DMAStop()` 这一行不能省。** 原因是 HAL 自己的状态机：

`HAL_UART_Receive_DMA()` 开头有一句判断——如果 `huart->RxState != HAL_UART_STATE_READY`
就直接返回 `HAL_BUSY`。第一次调用时 `RxState` 是 `READY`，没问题；
但 `ESP8266_Init()` 会被上层**反复调用**（连不上就重试，`task_wifi.c:243`），
第二次进来时 `RxState` 还停在 `BUSY_RX`——因为 DMA 在环形模式下从没结束过。

于是第二次起 `HAL_UART_Receive_DMA` 直接失败，`RxStart` 返回 `ERR_AT`，
`Init()` 立刻返回**连模块都不复位了**。

> **症状非常有迷惑性**：第一次失败之后**永远**失败。而且从第二次起报的是
> `ESP8266 Init Failed!`，看起来像模块坏了、接触不良、供电不够 ——
> 其实只是漏了 `HAL_UART_DMAStop()` 这一行。
> `HAL_UART_DMAStop()` 内部会调 `UART_EndRxTransfer()`，那里把 `RxState`
> 复位成 `READY`，重开就能成功。

#### 关中断那一步的真相

```c
    __HAL_DMA_DISABLE_IT(ESP8266_UART.hdmarx, DMA_IT_TC);
```

这是**只关掉了传输完成（TC）中断**。`esp8266.c:69-73` 的注释说
"环形模式下 HAL 的回调本来也什么都不做……那这个中断就是纯浪费，关掉" ——
**对 TC 来说完全正确**：

```c
/* stm32f1xx_hal_uart.c:3042 —— UART_DMAReceiveCplt 的开头 */
if ((hdma->Instance->CCR & DMA_CCR_CIRC) == 0U)   /* ← 这一行在 :3047 */
{
    ...  /* 环形模式下整段跳过，什么都不做 */
}
```

> ⚠️ **但是半传输（HT）中断并没有被关掉，它到现在仍然在触发。**
>
> 原因在 HAL 内部：`HAL_UART_Receive_DMA()` 会走到
> `UART_Start_Receive_DMA()`，那里设了
> `huart->hdmarx->XferHalfCpltCallback = UART_DMARxHalfCplt;`
> （`stm32f1xx_hal_uart.c:3285`）。而 `HAL_DMA_Start_IT()` 看到这个回调非空，
> 就会走"三个中断全开"的分支：
>
> ```c
> /* stm32f1xx_hal_dma.c:385-388 */
> if (NULL != hdma->XferHalfCpltCallback)
> {
>     __HAL_DMA_ENABLE_IT(hdma, (DMA_IT_TC | DMA_IT_HT | DMA_IT_TE));
> }
> ```
>
> 我们的 `__HAL_DMA_DISABLE_IT(..., DMA_IT_TC)` 在这之后执行，**只关掉了 TC**。
> HT 和 TE 还开着。结果是：**每收满 128 字节（256 的一半）就进一次
> `DMA1_Channel6_IRQHandler`**，环形模式下 128 字节一到就重来一次，
> 数据不停就一直进。
>
> 这次中断做了什么？`HAL_DMA_IRQHandler` 清标志，然后调
> `UART_DMARxHalfCplt`（`stm32f1xx_hal_uart.c:3104`）。那个函数检查
> `ReceptionType`——我们是 `HAL_UART_Receive_DMA` 不是 `ReceiveToIdle_DMA`，
> 所以走 `HAL_UART_RxHalfCpltCallback`，而**那是个空的弱函数**。
> 所以后果只是"白进一次中断"，不影响正确性。
>
> 但如果想真的做到"一个中断都不要"，得再补一行：
> ```c
> __HAL_DMA_DISABLE_IT(ESP8266_UART.hdmarx, DMA_IT_HT);
> ```
>
> **顺带纠正一处过时的说法**：`Core/Src/dma.c:46-53` 的注释说
> "优先级设成 5 是为了让 USART2 的 DMA 完成中断能给任务发信号量"。
> 全工程**没有任何一处真的调用 `...FromISR` API**——那条理由已经不成立了
> （优先级 5 本身没问题，只是理由过时了）。见 §2.9。

### 2.3.2 `ESP8266_RxHead()` —— 算出 DMA 写到哪了

`esp8266.c:82-86`：

```c
static uint16_t ESP8266_RxHead(void)
{
    return (uint16_t)(ESP8266_DMA_BUF_SIZE -
                      __HAL_DMA_GET_COUNTER(ESP8266_UART.hdmarx));
}
```

`CNDTR` 是 DMA 的**剩余计数**寄存器：DMA 每搬一个字节它就减 1。
环形模式下搬到 0 会自动回绕成 `DMA_BUF_SIZE`，继续减。

所以 `缓冲区大小 - 剩余计数` **恒等于当前写位置**，而且因为回绕的关系，
这个减法天然就是在做取模，不需要额外处理。

> **为什么读一次 CNDTR 是安全的？**
> CNDTR 是单个 16 位寄存器，读一次就是**原子的**，不会被 DMA 撕裂。
> 但要注意：**不能连续读两次再做运算**——两次读之间 DMA 可能又搬了字节，
> 算出来的差值就没意义了。这里的写法只读一次，然后直接做减法。
>
> 另外还有一个**固有的竞态**：如果 DMA 恰好在这个函数返回之后、`RxPop`
> 读 `DmaBuf` 之前把环形缓冲区追上了读指针（转了一整圈），读到的就是
> 被覆盖的新数据。这需要两次轮询之间来 256 个字节（1ms 内 256 字节 =
> 2Mbps，远超 115200）才会发生，实际触发不了。

### 2.3.3 `ESP8266_RxPop()` —— 唯一推进读指针的地方

`esp8266.c:90-107`：

```c
static uint16_t ESP8266_RxPop(uint8_t *dst, uint16_t max)
{
    uint16_t head  = ESP8266_RxHead();
    uint16_t moved = 0;

    while (ESP8266_DmaTail != head && moved < max)
    {
        dst[moved++] = ESP8266_DmaBuf[ESP8266_DmaTail];

        ESP8266_DmaTail++;
        if (ESP8266_DmaTail >= ESP8266_DMA_BUF_SIZE)
        {
            ESP8266_DmaTail = 0;
        }
    }

    return moved;
}
```

这个函数的地位很特殊：**`DmaTail` 只在三个地方被写**——这里是
"正常搬走数据"，`RxDiscard` 是"扔掉不要"，`RxStart` 是"重新开始"。除此之外
没有别的地方碰它。所以想理清"字节都去哪了"，只要盯住这一个变量。

`head` **只算一次**（在循环外面）。这是刻意的：如果写成
`while (DmaTail != ESP8266_RxHead())`，那么 DMA 一边搬、这边一边追，
理论上可以永远追不上，循环退不出来。先把水位线拍下来，**最多搬到这里为止**。

### 2.3.4 `ESP8266_RxDrain()` —— 搬进解析缓冲区

`esp8266.c:112-119`：

```c
static uint16_t ESP8266_RxDrain(void)
{
    uint16_t room  = (uint16_t)(ESP8266_RX_BUF_SIZE - 1 - ESP8266_RxLen);
    uint16_t moved = ESP8266_RxPop(&ESP8266_RxBuf[ESP8266_RxLen], room);

    ESP8266_RxLen = (uint16_t)(ESP8266_RxLen + moved);
    return moved;
}
```

**`-1` 是给结尾的 `'\0'` 留位置**：`RxBuf` 要直接交给 `strstr()` 用，
必须以 `'\0'` 结尾。`RxLen` 到 `SIZE-1` 就停，`strstr` 才不会越界读。

**房间不够时也照样搬**（能搬多少搬多少）。`esp8266.c:109-111` 的注释解释了
为什么不能"装不下就不搬"：

> 关键是读指针不能卡住，卡住就永远追不上 DMA 了。

如果这里因为 `room == 0` 就返回 0，`DmaTail` 就停住不动；而 DMA 还在往里写。
两边速度差得太远时，环形缓冲区会被 DMA 转一整圈追上来，**旧数据被新数据覆盖**，
而且读指针还会以为自己读的是老数据——彻底乱套。

所以策略是：**搬，哪怕搬不下也要搬**。装不下的部分由 `WaitResponse` 那边
发现 `RxLen >= SIZE-1` 然后返回 `ERR_BUF_FULL` 报错。**宁可报错，不能卡住。**

### 2.3.5 `ESP8266_RxDiscard()` —— 扔掉环形缓冲区里的存货

`esp8266.c:123-126`：

```c
static void ESP8266_RxDiscard(void)
{
    ESP8266_DmaTail = ESP8266_RxHead();
}
```

一句话，但是**必须有**。因为 `ClearRxBuf()` 要表达"清空接收缓冲区"，
而缓冲区其实有两块（DMA 环形的那块 + `RxBuf` 那块）。只清 `RxBuf` 的话，
下次 `RxDrain` 又会把环形里剩下的存货灌进来，看起来就像"清了但没清干净"。

`esp8266.c:133-136` 的注释把这件事写清楚了：

> 两处都要清，语义才是"清空接收缓冲区"

### 2.3.6 `ESP8266_ClearRxBuf()` —— 清缓冲区（**但漏了一样东西**）

`esp8266.c:131-140`：

```c
void ESP8266_ClearRxBuf(void)
{
    ESP8266_RxDiscard();
    memset(ESP8266_RxBuf, 0, sizeof(ESP8266_RxBuf));
    ESP8266_RxLen = 0;
}
```

三件事都做了：环形缓冲丢掉、`RxBuf` 清掉、长度归零。

**但是它没有清 `+IPD` 状态机的状态**（`IpdHdrLen` / `IpdLeft`）。
这是个真问题，单独放到 §2.6 讲。

## 2.4 `ESP8266_WaitResponse()` —— 等一条 AT 应答

`esp8266.c:241-288`。这是 AT 命令的"等"字诀：

```c
    while ((HAL_GetTick() - startTick) < timeout)
    {
        if (ESP8266_RxDrain() > 0)
        {
            // 先判响应, 再判缓冲满。顺序不能反: 若最后一个字节恰好凑齐响应,
            // 先判满就会把成功误报成失败。
            if (strstr((char *)ESP8266_RxBuf, expected) != NULL)
            {
                return ESP8266_OK;
            }

            // 检查是否收到错误响应
            if (strstr((char *)ESP8266_RxBuf, "ERROR") != NULL ||
                strstr((char *)ESP8266_RxBuf, "FAIL") != NULL)
            {
                return ESP8266_ERR_AT;
            }

            if (ESP8266_RxLen >= ESP8266_RX_BUF_SIZE - 1)
            {
                return ESP8266_ERR_BUF_FULL;
            }
        }
        else
        {
            BSP_DelayMs(1);
        }
    }
```

### 三个判断的**顺序**决定了返回哪个错误码

顺序是：**期望 → ERROR/FAIL → 缓冲满**。这个顺序不能动，理由有二：

1. **期望排在前面**：如果最后一个字节刚好凑齐了 `expected`，同时缓冲区也满了，
   先判满就会把**成功误报成失败**。这个 bug 只在"响应刚好填满缓冲区"时出现，
   平时测不出来，非常难查。
2. **ERROR/FAIL 排在缓冲满前面**：所以"缓冲区满且末尾是 ERROR"会报
   `ERR_AT` 而不是 `ERR_BUF_FULL`。这是有意的——`ERR_AT` 是更具体的原因。

### `BSP_DelayMs(1)` 是这套架构的收口

没有新字节的时候让出 CPU 1ms。

这一行就是"忙等饿死低优先级任务"那个毛病的解法。而它能成立的前提是
**DMA 保证字节一个不丢**——两件事各归各的：

- **收**字节：DMA 全权负责，CPU 睡多久都不影响
- **处理**字节：CPU 这边可以让出，反正东西在内存里跑不掉

旧实现里这两件事是耦合的（要处理就得守着串口，守着就没法让出），所以怎么改都别扭。

### 到处都在用 `strstr`——这是把双刃剑

`expected` 传的是一些很短的字符串（`"OK"`、`"CONNECT"`、`">"`、`"SEND OK"`），
`strstr` 是**子串**匹配。已知的几个咬人点：

| 场景 | 后果 |
|---|---|
| 模块回 `ALREADY CONNECTED` | 命中 `"CONNECT"`，被当成 `AT+CIPSTART` 成功 |
| 回显没关掉（`ATE0` 之前或 `RESTORE` 之后） | 命令原文里就带着 `AT`…… 一般不会命中 `OK`，但 `CWJAP` 那类命令的原文可能带 |
| 扫描名单里恰好有含 `FAIL` 的热点名 | 被当成 AT 错误 |

目前靠两个东西兜着：① 每次 `SendCmd` 开头都 `ESP8266_ClearRxBuf()`
（`esp8266.c:300`），历史文本不会残留；② `ESP8266_Init()` 里发 `ATE0`
关掉回显（`esp8266.c:213`）。

**改这块代码时的铁律：`expected` 越短越危险。** 能写 `"SEND OK"` 就别写 `"OK"`。

## 2.5 `+IPD` 状态机 —— 全项目最复杂的 130 行

### 2.5.1 先看它要处理什么

ESP8266 在默认模式下，会把服务器发来的 TCP 数据**包装**一下再吐给你：

```
\r\n+IPD,5:hello\r\n
    └──头──┘└payload┘
```

所以从环形缓冲区里取出来的字节流是"**AT 包装 + 真数据**"混在一起的。
而 `APP/mqtt.c` 要的是**纯 MQTT 字节**——它不该知道 `+IPD` 长什么样。

**这个剥离动作放在驱动层**，理由和分层有关：`+IPD` 是 AT 协议的事，
换一个 WiFi 模块（NB-IoT、以太网）就没有这个包装了。剥在驱动里，
上面 MQTT 层一行都不用改。

### 2.5.2 为什么必须留状态？

**不能"攒够一整包再剥"。** 因为串口是**流**，头有可能被分两次取出来：

```
第一次 RxPop 拿到：  "+IPD,5"
第二次 RxPop 拿到：  ":hello"
```

头有 7~11 个字节，115200 波特率下要发约 1ms —— **正好跨过一次轮询**
（轮询间隔就是 `BSP_DelayMs(1)`）。所以必须有地方记着"头攒到哪了"。

三个状态变量（`esp8266.c:577-579`）：

```c
static char     ESP8266_IpdHdr[ESP8266_IPD_HDR_MAX];    // 正在攒的 +IPD 头
static uint8_t  ESP8266_IpdHdrLen = 0;
static uint16_t ESP8266_IpdLeft = 0;                    // 本包 payload 还欠多少字节
```

加起来十几个字节的状态，省掉的是"在上层自己攒缓冲区"——那是把 AT 协议的
复杂度泄漏到 MQTT 层去，不划算。

### 2.5.3 状态一：攒头

`esp8266.c:617-664`。进这个分支的条件是 `IpdLeft == 0`（没有欠着的 payload）。

```c
        if (ESP8266_IpdLeft == 0)
        {
            if (ESP8266_RxPop(&b, 1) == 0)
            {
                /* 手上有货就先交出去, 别为了等一个头把已经拿到的数据押着 */
                if (copied > 0) { return copied; }
                BSP_DelayMs(1);
                continue;
            }
```

> ⚠️ **那句 `if (copied > 0) { return copied; }` 是走不到的死代码。**
>
> 进 `IpdLeft == 0` 分支的前提是"本包已经收完了"或者"还没开始收"。
> 而一旦进过 payload 分支，出口只有两个：`room == 0` 返回、`IpdLeft == 0` 返回
> ——**没有任何路径能回到头状态**。`copied` 是本次调用的局部变量，入口恒为 0。
>
> 所以这是**防御性代码**，不是活路径。写在这里是为了将来万一加了
> "一包收完继续收下一包"的逻辑时不至于把数据押住。**别删，但也别以为它在干活。**

接着是三条过滤规则，**每一条都对应一个具体的坑**：

#### 规则一：换行重置（`esp8266.c:627-635`）

```c
            if (b == '\r' || b == '\n')
            {
                ESP8266_IpdHdrLen = 0;
                continue;
            }
```

合法头 `+IPD,<数字>:` 里**不可能出现 `\r` 或 `\n`**，所以这么做不会误伤真头。

它的作用是**兜住半截头**：模块复位时可能吐了个 `+IPD` 就没下文了，
这个残缺的头会一直占着 `IpdHdrLen`，把后面**真正的**头挡在门外。
换行一到就清零，状态机自己恢复。

#### 规则二：只认 `'+'` 开头（`esp8266.c:637-642`）

```c
            if (ESP8266_IpdHdrLen == 0 && b != '+') { continue; }
```

**这一条最关键，去掉它整个状态机就废了。**

因为 AT 固件在 `+IPD` 前面会先发一对 `\r\n`。如果不过滤：
`\r\n` 先进了 `IpdHdr`（因为换行重置只在 `b` **是**换行时触发，
而这里是 `\r` 已经是头的一部分了……不对，`\r` 会触发重置）。

让我把过程走一遍更准确：`\r` 进来 → 规则一命中，`IpdHdrLen = 0`，跳过。
`\n` 进来 → 同样。然后 `+` 进来 → `IpdHdrLen == 0` 且 `b == '+'`，开始攒。
看起来没问题？

**问题出在"`\r\n` 和 `+` 之间还夹了别的东西"的时候**，以及——
真正要防的是这种循环：

假设过滤条件写成 `if (ESP8266_IpdHdrLen == 0 && b != '+')` 但**改成**
"不检查直接攒"，那 `\r\n` 会被攒进 `IpdHdr[0]`、`IpdHdr[1]`。等 `:` 来了
去 `ParseIpdLen`，一看 `hdr[0] != '+'` 直接返回 0 判失败，`IpdHdrLen` 清零。
下一轮又攒一遍 `\r\n`……**数据永远解析不出来**。

而且这一条**顺手把 `CLOSED` 这类通知也滤掉了**——`C` 不是 `+`，直接跳过。

#### 规则三：攒满 12 字节还没见到 `:`（`esp8266.c:657-662`）

```c
            else if (ESP8266_IpdHdrLen >= ESP8266_IPD_HDR_MAX)
            {
                ESP8266_IpdHdrLen = 0;
            }
```

兜底。比如 `CLOSED` 这种以 `+` 开头、又一直不出现 `:` 的通知，
靠这条把状态清掉，不让它把状态机卡死。

> **一个数字上的细节**：`ESP8266_IPD_HDR_MAX = 12`，而最长合法头是
> `+IPD,65535:` = **11 字符**。留了 1 字节余量。如果哪天 `+IPD` 支持
> 更长的长度字段，这个常量要跟着改。

### 2.5.4 认头：`ESP8266_ParseIpdLen()`

`esp8266.c:582-600`：

```c
static uint8_t ESP8266_ParseIpdLen(const char *hdr, uint8_t hdrLen, uint16_t *len)
{
    uint16_t v = 0;
    uint8_t  i;

    if (hdrLen < 7) { return 0; }               /* 最短也得多于 "+IPD,0:" */
    if (hdr[0] != '+' || hdr[1] != 'I' || hdr[2] != 'P' ||
        hdr[3] != 'D' || hdr[4] != ',') { return 0; }

    /* 末尾那个 ':' 之前应该全是数字 */
    for (i = 5; i < (uint8_t)(hdrLen - 1); i++)
    {
        if (hdr[i] < '0' || hdr[i] > '9') { return 0; }
        v = (uint16_t)(v * 10 + (uint16_t)(hdr[i] - '0'));
    }

    *len = v;
    return 1;
}
```

- `hdrLen < 7`：`+IPD,0:` 正好 7 个字符。比这短的不可能是合法头。
- 逐个字符比对前缀 + 逐位累加数字。**没有用 `atoi`**，因为它不校验
  "后面全是数字"，`+IPD,12ab:` 这种坏头会被它算成 12。
- **返回 0 时 `*len` 不被写**——调用方（`esp8266.c:649-655`）靠返回值判断，
  不靠 `*len`。

### 2.5.5 状态二：收 payload

`esp8266.c:666-680`：

```c
        room = (uint16_t)(max - copied);
        if (room == 0) { return copied; }       /* 装满了, 剩下的下次再来 */

        want = (ESP8266_IpdLeft < room) ? ESP8266_IpdLeft : room;
        got  = ESP8266_RxPop(&buf[copied], want);

        copied          = (uint16_t)(copied + got);
        ESP8266_IpdLeft = (uint16_t)(ESP8266_IpdLeft - got);

        /* 一包收完就返回: MQTT 按包解析, 攒两包混在一起反而要在上层拆 */
        if (ESP8266_IpdLeft == 0) { return copied; }

        if (got == 0) { BSP_DelayMs(1); }        /* 没新数据, 让出 CPU */
```

**这一段是"按长度盲取"，不做任何扫描。** 这是整个状态机最重要的性质：

> payload 里的字节**原封不动**搬给调用方。所以哪怕 MQTT 数据里
> 恰好奇妙地出现了 `+IPD,` 这几个字，也**不会被误判成包头**——
> 因为我们根本不去看 payload 的内容，只数够 `IpdLeft` 个字节就走。

如果反过来写成"扫描缓冲区找 `+IPD,` 然后从那里切开"，那 MQTT 的
JSON 里出现一篇文章、或者二进制数据里恰好有这几个字节，就误切了。
**按长度取是这个设计唯一正确的做法。**

#### 两个出口，各有各的用途

| 出口 | 条件 | 含义 |
|---|---|---|
| `return copied` | `room == 0`（调用方的缓冲区装满了） | 本包**还没收完**，`IpdLeft > 0`。下次调用接着收 |
| `return copied` | `IpdLeft == 0`（本包收完） | 干净的一包，正好交给上层 |

**"一包收完就返回"是有意为之**：MQTT 是按包解析的，如果一次调用里
攒了两包混在一起返回，上层还得自己切分——那是把协议分帧的活儿从
该干的地方挪到了不该干的地方。

#### 没能收满的时候

注意 `want` 可能是**大于**实际能拿到的字节数的——因为 `IpdLeft` 说的是
"这一包还有多少"，而环形缓冲区里其实只有一部分。这时候 `RxPop` 返回的
`got` 小于 `want`，`IpdLeft` 相应减少，循环继续（`got == 0` 时让出 1ms）。

**所以 `TCPRecvRaw` 返回 0 只代表"这次没拿到"，不等于出错。**
这个契约很重要，`APP/mqtt.c` 是靠**循环多次调用来兜半包**的：

```c
/* APP/mqtt.c:162-174 —— 等 CONNACK */
    while (rxLen < 4)
    {
        got = ESP8266_TCPRecvRaw(&rx[rxLen], (uint16_t)(sizeof(rx) - rxLen),
                                 CFG_MQTT_TIMEOUT_MS);
        if (got == 0)
        {
            printf("[MQTT] no CONNACK (timeout) - check Remaining Length\r\n");
            return 0;
        }
        rxLen = (uint16_t)(rxLen + got);
    }
```

`MQTT_Ping` 里的 `while (rxLen < 2)`（`mqtt.c:230`）是同一个套路。
**这两处和 §2.5.5 是同一份契约的两端**，改一边就要想另一边。

### 2.5.6 一个容易被忽略的代价

头状态是**一次一字节**取的（`esp8266.c:619`）：

```c
            if (ESP8266_RxPop(&b, 1) == 0)
```

`+IPD,5:` 这 7 个字符要 **7 次函数调用 + 7 次 `DmaTail` 推进**。

在 1ms 轮询粒度下这完全无所谓（7 次调用是微秒级的），但这个写法值得知道——
如果哪天要处理高频小包，这里是第一个要考虑优化的地方。

## 2.6 ⚠️ `ClearRxBuf()` 与 `+IPD` 状态机不同步

**这是本文发现的唯一一个会静默破坏协议分帧的真问题，改这块代码时优先看它。**

### 问题

`ESP8266_ClearRxBuf()`（`esp8266.c:131-140`）清了：

- ✅ DMA 环形缓冲区（`RxDiscard`）
- ✅ `ESP8266_RxBuf`（`memset`）
- ✅ `ESP8266_RxLen`

**没清**：

- ❌ `ESP8266_IpdHdrLen`
- ❌ `ESP8266_IpdLeft`

### 怎么咬人

设想这样一串事件：

```
1. 某次 TCPRecvRaw 半途返回了 —— 因为调用方缓冲区满了(room==0), 或者超时了
   → 此时 IpdLeft = 37（这一包还有 37 字节没取走）

2. 链路断了(或平台主动断开), TaskWifi 判定连续失败, 回到外层重连

3. 重连过程中会调 WifiConnect() → ESP8266_Init() → 大量 SendCmd
   → 每次都调 ClearRxBuf(), 但 IpdLeft 一直是 37

4. 重连成功, MQTT_Connect() 发出 CONNECT, 然后调用 TCPRecvRaw 等 CONNACK
   → TCPRecvRaw 一进来看到 IpdLeft == 37 != 0, 直接跳到"收 payload"分支
   → 从新数据流里盲取 37 个字节当作"上一包的残渣"!
   → CONNACK 那 4 个字节被吃掉一部分
   → rx[0] != 0x20 → "[MQTT] unexpected reply" → 这一轮 MQTT 连接失败
   → 多花一轮重连
```

**为什么难查**：它只在"上一次连接是**半包状态**结束的"+"这次重连"同时满足时
才发生。也就是说设备大部分时候工作正常，偶尔要多重连一轮。看日志只会觉得
"咦，怎么连着两次 CONNACK 失败"，很难联想到是驱动里的状态泄漏。

### 修法

```c
void ESP8266_ClearRxBuf(void)
{
    ESP8266_RxDiscard();
    memset(ESP8266_RxBuf, 0, sizeof(ESP8266_RxBuf));
    ESP8266_RxLen = 0;

    /* "清空接收缓冲区"在语义上应该包括放弃当前这一包 ——
     * 否则半包状态会跨过重连, 把下一轮的协议数据错位吃掉 */
    ESP8266_IpdHdrLen = 0;
    ESP8266_IpdLeft   = 0;
}
```

或者更保守一点：只在 `ESP8266_Init()` 里清（因为那才意味着"整条链路重来"）。
但放在 `ClearRxBuf` 里语义更自洽 —— **"清空接收缓冲区"就该包括
"当前这包不要了"**。

> 本次只记录，未修改代码。

## 2.7 一条流，两个消费者的三种代价

`DmaBuf` 里的字节有两条去路，它们**互相看不见对方**。这是"两个消费者"
这个设计的必然代价，具体有三个表现：

### 代价一：`SendCmd` 会静默丢弃在途的 `+IPD`

每个 `ESP8266_SendCmd` 开头都清缓冲区（`esp8266.c:300`）。
如果这时候环形缓冲区里正躺着一包没取的 `+IPD` 数据，**它就被扔了**。

现在的代码之所以没事：所有 AT 命令都在"一问一答"的同步流程里，
发命令的时候没有人在等 `+IPD` 数据。**做了 MQTT 订阅之后这里会出事**——
服务器随时可能推消息，而这边每发一个 PINGREQ 就清一次缓冲区。

### 代价二：进了 `RxBuf` 的字节，`TCPRecvRaw` 再也拿不到

反过来也一样：`WaitResponse` 把字节搬进 `RxBuf` 之后，`TCPRecvRaw`
**永远看不到它们**（它只从 `DmaBuf` 取）。

所以如果在等 AT 应答的过程中来了 `+IPD`，那份数据会被卷进 `RxBuf`
当文本搜掉，然后跟着下一次 `ClearRxBuf` 一起消失。

### 代价三：`CLOSED` 被滤掉 ⇒ 驱动没有"断链感知"能力

`esp8266.c:642` 的 `if (ESP8266_IpdHdrLen == 0 && b != '+') { continue; }`
把 `CLOSED` 这类通知**静默丢掉了**。

后果是：**服务器把 TCP 断掉的时候，驱动完全不知道**。

这和 `app_config.h:96-99` 记的那个坑是同一件事的两端：

> ⚠️ 主题不对时 OneNET **不报错，直接断掉 TCP** —— 而设备这边收到的
> `SEND OK` 是 ESP8266 自己回的（"我塞进 TCP 了"），**不是平台回执**。
> 于是日志会呈现"第一条上报成功，后面全失败"。

"后面全失败"是怎么变成失败的？因为 TCP 断了之后 `ESP8266_TCPSend` 里的
`AT+CIPSEND` 拿不到 `>`、等不到 `SEND OK`，超时返回错误——**而不是**因为
驱动检测到了 `CLOSED`。断链的感知是**被动超时**出来的，不是主动发现的。

### 这三条现在为什么都不发作

| 代价 | 为什么现在没事 | 什么时候会发作 |
|---|---|---|
| 一 | 没有订阅，服务器不会主动推数据 | **做订阅时** |
| 二 | 同上 | **做订阅时** |
| 三 | 断链靠超时也能被发现，只是慢 | 一直存在，只是表现为"慢"而不是"错" |

**结论：这三条是同一个根因——驱动用的是"同步问答"模型，而订阅需要
"异步收推送"模型。** 做订阅之前，这里的架构要先改。

## 2.8 已知局限与注意事项

| 局限 | 触发条件 | 现象 | 能否自愈 | 修法 |
|---|---|---|---|---|
| **半包状态跨重连泄漏** | 上次 `TCPRecvRaw` 半途返回 + 重连 | 重连后第一次 `TCPRecvRaw` 错吃字节，多花一轮重连 | 能（下一轮就好） | §2.6，在 `ClearRxBuf` 里清 `IpdLeft` |
| **DMA 传输错误后接收永久停摆** | DMA 传输出错（TE） | 接收彻底停，`RxHead()` 恒等于旧值，**无任何日志** | 能，但要几十秒 | 见下 |
| **HT 中断仍然在触发** | 每收满 128 字节 | 白进一次中断（回调是空的） | 不影响正确性 | 补一行 `__HAL_DMA_DISABLE_IT(..., DMA_IT_HT)` |
| **AT 应答与 `+IPD` 共用一条流** | 做 MQTT 订阅后 | 推送数据被当文本搜掉 | 不能 | 见 §2.7，需改架构 |
| **断链靠超时发现** | 服务器主动断开 | 要等到下一次 POST/PING 超时才知道 | 能 | 解析 `CLOSED` 通知 |
| **`strstr` 子串匹配** | 响应里恰好含期望串 | 误判成功/失败 | 不能 | 用更长的 `expected`，见 §2.4 |

### 展开说：DMA 传输错误之后会发生什么

这一条值得单独讲，因为它的**症状特别像"模块坏了"**。

TE（Transfer Error）中断触发链：

```
DMA1_Channel6_IRQHandler        (Core/Src/stm32f1xx_it.c:225)
  → HAL_DMA_IRQHandler(&hdma_usart2_rx)
      → stm32f1xx_hal_dma.c:659  关掉全部 DMA 中断 (TC|HT|TE)
      → 调 XferErrorCallback = UART_DMAError
          → stm32f1xx_hal_uart.c  UART_DMAError
              → UART_EndRxTransfer()  把 huart->RxState 复位成 READY
```

注意 **`UART_EndRxTransfer` 只是复位了 UART 的状态，没有重新挂 DMA**，
也没有把 `RxState` 之外的东西恢复。而 `HAL_UART_ErrorCallback`
（那个弱回调）是空的 —— 驱动里没有实现它。

所以此后：

- DMA 不再搬字节了
- `ESP8266_RxHead()` 返回 `DMA_BUF_SIZE - CNDTR`，而 `CNDTR` 停在某个值不动
  → **`RxHead()` 恒定**
- `RxPop` 里 `DmaTail != head` 永远不成立 → 一直返回 0
- `WaitResponse` 一直拿不到数据 → 超时
- **串口上一句提示都没有**

从外面看就是"模块突然不回话了"。唯一的恢复路径是 TaskWifi 连续失败 3 次
后回到外层重连，`ESP8266_Init()` → `ESP8266_RxStart()` 重新挂 DMA。

**耗时**：上报路径 2 秒一条 × 3 次 = 约 6 秒；但如果走的是心跳路径
（30 秒一次），最长要 **90 秒**才触发重连。

> 本次只记录，未修改代码。想改善的话有两条路：① 实现
> `HAL_UART_ErrorCallback` 打一句日志（至少让人看得见）；
> ② 在 `RxHead()` 里加一个"连续 N 次没变化就重新 RxStart"的看门狗。
> ①成本低、收益大，建议先做①。

## 2.9 动手改这里

### 想加大缓冲区

**改哪几行**：`esp8266.h:33-34` 的 `ESP8266_RX_BUF_SIZE` / `ESP8266_DMA_BUF_SIZE`

**连带要改的**：没有，但**要算 RAM 账**。

当前 RAM 预算（`MDK-ARM/build.log`）：
```
Code=18720  RO-data=524  RW-data=164  ZI-data=12828    芯片总共 20480 字节
```
`ZI-data` 12828 里，**FreeRTOS 堆占 10240**（`FreeRTOSConfig.h:290`）。
剩下约 2.5KB 要装：`.bss` 里的 `RxBuf`(512) + `DmaBuf`(256) + `s_MqttTxBuf`(256)
+ 主栈 `Stack_Size`(0x400 = 1024) + C 库堆 `Heap_Size`(0x200 = 512)……

**已经差不多满了。** 加 256 字节的缓冲区，就得从别处减 256。

**怎么验证改对了**：`RxBuf` 改大了看 `AT+CWLAP` 扫描是否不再报
`ERR_BUF_FULL`；`DmaBuf` 改大了看长时间运行有没有丢字节。改小了则相反——
故意改小到 32 跑一遍，能复现"热点列表截断"的现象。

### 想真的关掉所有 DMA 中断

**改哪几行**：`esp8266.c:74` 后面加一行

```c
    __HAL_DMA_DISABLE_IT(ESP8266_UART.hdmarx, DMA_IT_TC);
    __HAL_DMA_DISABLE_IT(ESP8266_UART.hdmarx, DMA_IT_HT);   /* 补这行 */
```

**连带要改的**：`Core/Src/dma.c:45-53` 那段注释的理由已经过时
（见 §2.3.1 末尾），顺手改掉。`NVIC.DMA1_Channel6_IRQn` 的优先级
**在 `.ioc:48` 里已经是 5，重新生成不会丢**——`dma.c:50-52` 的
"WARNING: CubeMX regenerates this file..." 是个过时的警告。

**怎么验证改对了**：在 `DMA1_Channel6_IRQHandler` 里下一个断点，
或者在里面翻一个计数器然后打印——补上这行之后应该**永远不进**。

### 想加 "IDLE 中断" 判帧

**别急着改。** 先读 `esp8266.c:26-30` 的注释，那里写了为什么**刻意不用**：

> 那要多开一个 USART2 中断，还得纠结"中断里能不能调 FromISR 的 RTOS API"
> ——一碰 RTOS，BSP 就破了"不认识 FreeRTOS"这条规矩。

而且当前实现在功能上**没有缺失**：轮询虽然最多慢 1ms 发现数据，但 AT 响应
都是几十毫秒级的。IDLE 中断能省的只有那 1ms 延迟。

**唯一值得考虑加它的场景**：真要做 MQTT 订阅、且要求低延迟收推送。
那时候要改的不止是加个中断，而是 §2.7 讲的整个模型。

### 想做 MQTT 订阅

这不是"改几行"的事，是架构改动。要动的地方：

1. **`CLOSED` 通知要能被上层看到** —— 现在被 `esp8266.c:642` 滤掉了
2. **`SendCmd` 不能无脑清缓冲区** —— `esp8266.c:300` 会把在途推送丢掉
3. **要给"等 AT 应答"和"收推送"分优先级** —— 现在的两个消费者互不知情
4. **MQTT 层要加 SUBSCRIBE 报文**（`0x82`）和 `SUBACK`（`0x90`）解析
   → 见 [详解 03](10-mqtt报文拼装.md) 的魔数表

**怎么验证**：用 MQTTX 往设备订阅的主题发一条消息，看设备串口能不能
原样打出来，且**期间不断线**。

## 2.10 其余函数速览

`esp8266.c` 还有一批"发命令等应答"的函数，它们**结构都一样**
（`SendCmd` 包一层，业务参数拼进去），本文不逐段讲。
需要细节看《ESP8266 思路知识点代码对照》。

| 函数 | 行号 | 发的命令 | 期望应答 | 备注 |
|---|---|---|---|---|
| `ESP8266_Reset` | 320 | 拉低 RST 100ms → 释放 → 等 1s | 无 | **硬复位**，是重连能救回一切的根据 |
| `ESP8266_Test` | 337 | `AT` | `OK` | 确认模块活着 |
| `ESP8266_SetWiFiMode` | 347 | `AT+CWMODE=<n>` | `OK` | **`no change` 也算成功**（359 行） |
| `ESP8266_ConnectWiFi` | 372 | `AT+CWQAP` → `AT+CWJAP` | `OK` | 先清残留关联，见 381-384 的注释 |
| `ESP8266_ScanAP` | 417 | `AT+CWLAP` | `OK` | **`ERR_BUF_FULL` 不算失败**，见下 |
| `ESP8266_TCPConnect` | 485 | `AT+CIPMUX=0` → `AT+CIPSTART` | `CONNECT` | 传域名也行，模块自己做 DNS |
| `ESP8266_TCPDisconnect` | 512 | `AT+CIPCLOSE` | `OK` | **非幂等**：没连的时候会失败 |
| `ESP8266_TCPSend` | 523 | `AT+CIPSEND=<n>` → 等 `>` → 裸数据 | `SEND OK` | 两步式，见下 |
| `ESP8266_GetStatus` | 689 | `AT+CIPSTATUS` | `OK` | **只返回状态码，不解析内容** |
| `ESP8266_GetIPAddress` | 700 | `AT+CIFSR` | `OK` | 兼容 v1.x / v2.x 两种固件格式 |
| `ESP8266_ParseRssi` | 396 | — | — | 内部：从 `+CWLAP` 行里抠 RSSI |

### 两个值得单独说的

**`ESP8266_ScanAP` 把 `ERR_BUF_FULL` 当成功**（`esp8266.c:428-434`）：

```c
    /* ERR_BUF_FULL 不当失败: 邻居热点太多时 512 字节装不下后半截名单, 但
     * 已经收上来的那部分照样能查。而且 +CWLAP 是按信号强度从强到弱排的 ——
     * 真要找的那个就在跟前的话, 必然排在名单最前面, 一定收进来了。 */
    if (st != ESP8266_OK && st != ESP8266_ERR_BUF_FULL)
```

这个论证很漂亮：**因为模块按信号强度排序，所以"要找的那个"必然在最前面，
一定在 512 字节之内**。所以缓冲区满不影响这次诊断的结论。

**`ESP8266_TCPSend` 是两步式命令**（`esp8266.c:523-551`）：
先发 `AT+CIPSEND=<n>` 等 `>` 提示符，然后**裸发** `n` 个字节（不走 AT 格式），
再等 `SEND OK`。

注意最后一行的写法（`esp8266.c:548-550`）：

```c
    // 只等响应, 不再发命令。原来用 SendCmd("") 时, HAL_UART_Transmit 在
    // Size==0 时直接返回 HAL_ERROR, 那次调用其实是个空操作。
    return ESP8266_WaitResponse("SEND OK", ESP8266_TIMEOUT);
```

这里调的是 `WaitResponse` 而**不是** `SendCmd("")`。因为 `SendCmd` 会先清
缓冲区再发数据——而 `SEND OK` 是**数据发出去之后**才回的，用 `SendCmd`
会先把缓冲区清掉（虽然在这个时序下无害），并且 `HAL_UART_Transmit(size=0)`
会直接返回错误。用 `WaitResponse` 语义才正确。

> ⚠️ **`AT+CIPSEND` 有 2048 字节的上限**，代码里**没检查**。
> 当前最大报文是 CONNECT 的 158 字节，用不到上限，所以没暴露。
> 如果哪天要发大报文（比如批量上报），这里要先加上限判断。

## 2.11 一句话总结

**把"收字节"这件事整个托给 DMA 环形缓冲区（永不停止、CPU 参不参与都不丢），
CPU 只轮询 CNDTR 知道收到哪了；环形里的字节被两个互不相识的消费者按需取走
—— AT 文本走 `RxBuf` 供 `strstr` 匹配，MQTT 数据走 `+IPD` 状态机按长度盲取
直接交给上层，两条路各走各的、互不阻塞。**

这个设计里最值得记住的一条：**payload 按长度取、不做扫描**。
只要违背它去"搜 `+IPD,` 然后切开"，二进制数据早晚会把它咬穿。
