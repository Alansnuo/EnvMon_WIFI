## 20.1 这块代码要解决什么问题

### 一句话

**把"用 AT 指令让模块联上网、把一条数据发到 OneNET"这件事，收成 5 个函数；每个函数返回时，事情已经有了结果。**

驱动是**顺序阻塞**写法：每个接口内部就是"发一条 AT 指令 → 等模块回话 → 再发下一条"，
函数返回时要么成功、要么已经判定失败（超时 / 模块回 ERROR）。

### 问题：五件必须解决的事

| 要解决的事 | 难在哪 |
| --- | --- |
| 收得到模块的每一句话 | 读 DHT11 时要关中断约 4 ms，用中断收串口必丢字节（见 20.3.2） |
| 发得出完整的一条 AT 指令 | 命令最长 256 字节，要保证发送期间那块内存不被改写 |
| 判断"这条命令成了没有" | 模块回的可能是 `OK`、`ERROR`、`FAIL`、`+MQTTPUB:FAIL`，还有超时 |
| 用户数据能安全塞进指令 | SSID / Token / JSON 里含 `"`、`\`、`,`，不转义模块会切错参数 |
| 等待时不能拖累别的任务 | 一次连不上要等一分多钟（见 20.2 超时账），不能让采集和灯停摆 |

第 5 条是这套设计最要紧的一条：驱动靠 `BSP_DelayMs()` 让出 CPU，所以**必须跑在一个独立任务里**（本项目的 WiFi 任务），不能放进裸机主循环。

### 约束

| 约束 | 后果 |
| --- | --- |
| AT 指令单条上限 **256 字节**（模块文档写死） | 主题 + 载荷加起来太大就发不出去，本地直接报 `ERR_PARAM` 更清楚 |
| 模块固件是特定的 ESP-AT 版本 | 指令名以固件为准：老资料里的 `AT+MQTTCFG` 在这版里**不存在** |
| 模块内存不够 TLS | 只能用明文 1883，鉴权靠 OneNET 的 Token |
| FreeRTOS 的中断优先级门槛 = 5 | `USART2_IRQn` 抢占比 5，和 DMA1_Channel6 一致 |
| 驱动的等待是整毫秒级（`BSP_DelayMs(1)`） | 做不了精细的 tick 比较；换来的是驱动能在任何工程里直接用 |

### 本文不讲什么

- **任务层的策略**：什么时候连、失败几次重连、报文长什么样 —— 见 [详解 19](19-FreeRTOS任务入门-以WiFi任务为例.md) 与 `APP/task_wifi.c`。
- **MQTT 协议本身**：报文格式、QoS、keepalive 的语义。这里只讲"模块的 AT 指令怎么用"。
- **OneNET 平台的配置**：产品、设备、物模型、Token 怎么生成。

## 20.2 整体结构

### 五个接口与一次上报的调用链

| 接口 | 底下发的 AT 指令 | 成功判据 | 超时 |
| --- | --- | --- | --- |
| `ESP8266_Init()` | 复位引脚时序 + `AT` + `ATE0` + `AT+CWAUTOCONN=0` | 每条回 `OK` | 5 s / 条 |
| `ESP8266_ConnectAP(ssid, pwd)` | `AT+CWMODE=1` + `AT+CWQAP` + `AT+CWJAP="…","…"` | 回 `OK` | 前两条 5 s，CWJAP 15 s |
| `ESP8266_MQTT_SetParam(cid, user, token, keepalive)` | `AT+MQTTUSERCFG` + `AT+MQTTPASSWORD` + `AT+MQTTCONNCFG` | 每条回 `OK` | 5 s / 条 |
| `ESP8266_MQTT_ConnectBroker(host, port)` | `AT+MQTTCONN=0,"host",port,0` | 收到 `+MQTTCONNECTED` | 15 s |
| `ESP8266_MQTT_Publish(topic, data)` | `AT+MQTTPUB=0,"主题","载荷",0,0` | 回 `OK` | 5 s |

返回类型统一是 `ESP8266_Status`：`ESP8266_OK` / `ERR_TIMEOUT`（超时）/ `ERR_AT`（模块回了 ERROR/FAIL）/
`ERR_PARAM`（参数错或命令超长）/ `ERR_BUF_FULL`（应答太长，缓冲塞满）。

驱动自己不打印、不重试、不知道"什么叫失败策略" —— 那些都在任务层（`APP/task_wifi.c`）。

一次上报走完全程是这样：

```
TaskWifi 从队列取到数据
   → snprintf 拼 JSON
   → ESP8266_MQTT_Publish(主题, payload)
        → 拼 AT+MQTTPUB（转义主题和载荷）
        → 清接收缓冲 → HAL_UART_Transmit_IT 发出 → 等发完
        → 轮询 DMA 搬字节, 匹配 "OK" / "ERROR|FAIL" / 超时
   → 拿到 ESP8266_OK 就完成一次上报; 失败则 failStreak++
```

### 硬件连接与外设配置

| 项 | 配置 | 配在哪 |
| --- | --- | --- |
| 串口 | USART2，115200-8-N-1 | `MX_USART2_UART_Init()` |
| TX / RX | PA2 / PA3 | 同上 |
| **RST** | **PB1，推挽输出** | **驱动自己配**（`ESP8266_Init()` 里，CubeMX 没配这个脚） |
| 接收 DMA | DMA1_Channel6，**环形模式 (CIRCULAR)**，字节对齐，优先级 Low | `usart.c` 的 `HAL_UART_MspInit()` |
| 串口中断 | `USART2_IRQn`，抢占优先级 **5**，使能 | 同上 |
| 中断服务函数 | `USART2_IRQHandler()` → `HAL_UART_IRQHandler(&huart2)` | `stm32f1xx_it.c` |

两个关键点：

- **为什么中断优先级必须是 5**：FreeRTOS 规定"会调用 RTOS API 的中断"优先级数值必须 ≥ `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`（本工程 = 5）。本驱动在中断里不调任何 FreeRTOS API，取 5 和 DMA1_Channel6 保持一致，最省事也最安全。
- **串口中断是给"发送"用的**：`HAL_UART_Transmit_IT()` 靠 TXE 中断一个字节一个字节往外送。接收那条路根本不经过串口中断（见 20.3.2）。这也是 `usart.c` 里那两行 NVIC 配置和 `stm32f1xx_it.c` 里那个 `USART2_IRQHandler` 存在的唯一理由。

### 关键常量：超时账与缓冲大小

**超时账**（最坏情况，每一步都失败到超时）：

| 阶段 | 最坏耗时 |
| --- | --- |
| `Init` | 0.1 + 1.0 + 3×5 = **16.1 s** |
| `ConnectAP` | 5 + 5 + 15 = **25 s** |
| `MQTT_SetParam` | 3×5 = **15 s** |
| `MQTT_ConnectBroker` | **15 s** |
| 合计 | **约 71 s** |

这就是"驱动只能跑在独立任务里"的量化依据：**一次彻底连不上的流程最坏能连续占住调用者一分多钟**。本项目的 WiFi 任务就是专门用来扛这个的 —— 它卡住的时候，采集任务、灯照跑（长时间等待都发生在 `BSP_DelayMs()` 里，那会让出 CPU）。

**缓冲**（都在 `esp8266.h` 里定大小）：

| 缓冲 | 大小 | 角色 |
| --- | --- | --- |
| `s_DmaBuf` | 256 字节 | **环形**，DMA 直接往里写。只要装得下"两次搬运之间的突发"：1 ms @115200 才 11 字节，256 是绰绰有余的余量 |
| `s_RxBuf` | 512 字节 | **直线**，CPU 把新字节搬进来累积，直到能匹配出整条应答。要装得下最长的一条回复（CWJAP 的回应里带 AP 信息，比较长） |
| `s_Cmd` | 288 字节 | 命令区。比 256 多留 32，给拼完字符串后接的数字尾巴 |

**其余超时宏**：`ESP8266_TX_TIMEOUT = 100 ms`（中断发送兜底，正常 22 ms 发完）；`ESP8266_TIMEOUT = 5000`（一般命令）；`ESP8266_AP_TIMEOUT` / `ESP8266_MQTT_TIMEOUT = 15000`。

## 20.3 逐段详解

### 20.3.1 发送路径：中断发送 + 轮询 `gState`

驱动内部所有命令都走同一个函数 `ESP8266_Exec()`，发送部分就这几行：

```c
if (HAL_UART_Transmit_IT(&ESP8266_UART, (uint8_t *)s_Cmd, len) != HAL_OK)
{
    return ESP8266_ERR_AT;
}

/* 判"发完没有"只能看 gState */
tick = HAL_GetTick();
while (ESP8266_UART.gState != HAL_UART_STATE_READY)
{
    if ((HAL_GetTick() - tick) > ESP8266_TX_TIMEOUT) { return ESP8266_ERR_TIMEOUT; }
    BSP_DelayMs(1);      /* 让出 CPU, 别的任务接着跑 */
}
```

三个"为什么"：

- **为什么用中断发送而不是 DMA 发送**：一条 AT 指令最多 256 字节，115200 波特下 22 ms 就发完，中断完全够用。DMA 发送要多占一个通道、多一套中断，收益为零。以后真要换，只是把 `Transmit_IT` 换成 `HAL_UART_Transmit_DMA` 一处的事。
- **为什么判断"发完"要看 `huart2.gState`，不能用 `HAL_UART_GetState()`**：接收 DMA 一直挂着，`RxState` 恒为 `BUSY_RX`，`HAL_UART_GetState()` 会把"发送完成"和"正在接收"一起看，**永远等不到 READY**。`gState` 只管发送状态，才是干净的判据。
- **`ESP8266_TX_TIMEOUT = 100 ms` 是兜底值**：正常 22 ms 发完，100 ms 还没发完说明串口出问题了，不必再等。

命令必须放在 RAM 里（`static char s_Cmd[]`），因为 `HAL_UART_Transmit_IT` 要的是可写指针，且异步发送期间那块内存不能被改写 —— 所以驱动里所有命令都是先拼进 `s_Cmd` 再发，不用字符串字面量。

### 20.3.2 接收路径：DMA 环形缓冲 + 轮询 CNDTR

#### 为什么接收非用 DMA 不可

两个硬约束叠在一起：

1. STM32F1 的串口**只有一个字节的接收寄存器，没有 FIFO**。用 RXNE 中断收，CPU 必须在下一个字节到来之前把 DR 读走。
2. 本项目读 DHT11 时要**关中断约 4 ms**（时序要求）。这 4 ms 里来的串口字节，用中断收必丢。

DMA 在 CIRCULAR 模式下自己搬字节，CPU 关不关中断都不影响它 —— 这是唯一能同时满足两边的方案。

#### 两级缓冲各干什么

搬运方向只有一个：`s_DmaBuf` →（`RxPop`）→ `s_RxBuf`。读指针 `s_DmaTail` 只在 `RxPop` 里推进。

```c
/* DMA 写到哪了: 环形模式下 "缓冲大小 - CNDTR" 就是写指针 */
static uint16_t ESP8266_RxHead(void)
{
    return (uint16_t)(ESP8266_DMA_BUF_SIZE - __HAL_DMA_GET_COUNTER(ESP8266_UART.hdmarx));
}
```

`RxDrain()` 每次把 DMA 里攒下的新字节尽量搬进 `s_RxBuf`；搬不下的部分**不阻塞、直接放弃**（读指针不能卡住，卡住就永远追不上 DMA 的写指针了），缓冲满不满由 `Exec()` 判 `ERR_BUF_FULL`。

#### `RxStart()` 里四件必须做的事

```c
(void)HAL_UART_DMAStop(&ESP8266_UART);           /* ① 先停 */
s_DmaTail = 0;
HAL_UART_Receive_DMA(&ESP8266_UART, s_DmaBuf, ESP8266_DMA_BUF_SIZE);   /* ② 重挂 */
__HAL_DMA_DISABLE_IT(ESP8266_UART.hdmarx, DMA_IT_TC);                  /* ③ 关 DMA 完成中断 */
__HAL_UART_DISABLE_IT(&ESP8266_UART, UART_IT_ERR);                     /* ④ 关串口错误中断 ★ */
```

- **① 先停再开不能省**：`HAL_UART_Receive_DMA()` 要求 `RxState == READY`，而重连时 DMA 还在环形模式里跑（`RxState == BUSY_RX`），不停掉就永远失败。症状很迷惑人：**第一次失败之后永远失败**，看着像模块坏了。
- **③** 环形模式下 HAL 的传输完成回调什么都不做，我们靠轮询 CNDTR，这个中断白开。
- **④ ★ 这是全驱动最不能删的一句**：HAL 在 `HAL_UART_Receive_DMA()` 里会顺手打开串口的**错误中断**（`CR3.EIE`）。一旦 `USART2_IRQHandler` 生效，帧错/噪声/溢出任何一个标志都会被 HAL 当成致命错误，**直接中止 DMA 接收** —— 接收就此彻底哑掉。而 ESP8266 每次复位都会吐一段 **74880 波特**的启动日志，我们按 115200 收它就是一连串帧错，正好踩中。我们靠轮询，根本不需要这个中断。

#### `ClearRxBuf()`：为什么两处都要清

```c
static void ESP8266_ClearRxBuf(void)
{
    s_DmaTail = ESP8266_RxHead();     /* DMA 里还没搬走的, 直接跳过 */
    memset(s_RxBuf, 0, sizeof(s_RxBuf));
    s_RxLen = 0;
}
```

只清 `s_RxBuf` 是不够的：DMA 里没搬走的那部分，下一次 `RxDrain()` 又会灌回来（上一次命令的尾巴会被当成这一次的应答）。
`memset` 除了清内容还有一个作用 —— 后面追加的字节后面永远是 `'\0'`，`strstr()` 才不会越界读。

每次发命令之前都会清一次，所以**空闲期间模块主动上报的消息（URC，比如 `+MQTTDISCONNECTED`）会被丢掉**，现在不解析它们（见 20.5 的盲区）。

### 20.3.3 等应答的判定顺序（顺序不能反）

`Exec()` 等应答的循环里，四条判断的**先后顺序是刻意的**：

```c
ESP8266_RxDrain();

if (strstr(s_RxBuf, ack) != NULL)              { return ESP8266_OK; }        /* ① 先看期望的应答 */
if (strstr(s_RxBuf, "ERROR") || strstr(s_RxBuf, "FAIL")) { return ESP8266_ERR_AT; }  /* ② 再看失败 */
if (s_RxLen >= ESP8266_RX_BUF_SIZE - 1U)       { return ESP8266_ERR_BUF_FULL; } /* ③ 缓冲满 */
if ((HAL_GetTick() - tick) > timeoutMs)        { return ESP8266_ERR_TIMEOUT; }  /* ④ 最后判超时 */
BSP_DelayMs(1);
```

- ①必须在④前面：最后一个字节恰好凑齐应答的那一瞬间，如果先判超时，会把一个成功报成失败。
- ②在①后面：像 `+MQTTPUB:FAIL` 这种回复里既有 FAIL 又没有期望的 OK，两条判断不冲突；但先看期望值能避免"回复里恰好含 OK 又含 FAIL"时判错。
- 超时用 `HAL_GetTick()` 做**差值比较**，不是"看时间戳多大"：`HAL_GetTick()` 是 1 ms 递增的 32 位计数器，差值是自然的无符号运算，`tick` 溢出回绕也不会出错。

### 20.3.4 拼命令与转义

用户数据（SSID、密码、设备名、Token、主题、JSON 载荷）里可能含 `"`、`\`、`,` 三种字符，**必须转义**：

- AT 指令按**逗号**切参数，载荷里的内层逗号不转义就会被切成多余的参数，模块回 `ERROR`（发布时是 `+MQTTPUB:FAIL`）；
- 引号不转义会提前结束字符串。

```c
if (*src == '"' || *src == '\\' || *src == ',') { s_Cmd[n++] = '\\'; }   /* 前面补一个反斜杠 */
s_Cmd[n++] = *src++;
```

两个细节：

- **三种字符必须一趟处理完**。分两趟会把第一趟刚补上的 `\` 再转义一次，得到 `\\\"` 这种鬼东西。
- **有余量上限**：`AppendEsc()` 最多拼到 `256 - 16` 字节（`ESP8266_CMD_TAIL_ROOM = 16` 是给后面 `",0,0\r\n"` 这类收尾字面量留的位置）。拼不下时返回 `0`，调用者直接返回 `ESP8266_ERR_PARAM`。
  这条限制的现实含义：**主题 + 载荷加起来不能太大**，否则 `AT+MQTTPUB` 整条超过模块的 256 字节上限。当前 JSON 报文（约 90 字节）离上限还很远，但要往里塞更多字段时得留意。

`Exec()` 还会再检查一次总长度（`len > 256` 直接返回 `ERR_PARAM`）—— 半条命令发给模块只会换来一句含义模糊的 `ERROR`，甚至被静默截断，不如在本地就报清楚。

### 20.3.5 `ESP8266_Init()` —— 复位 + 探活

整个函数是一条直线：**配引脚 → 挂 DMA → 拉复位 → 三条 AT**，没有分支、没有状态。分三段看。

**第 ① 段：RST 引脚（CubeMX 那边没配这个脚，驱动自己配）**

```c
    GPIO_InitTypeDef GPIO_InitStruct = {0};
    ESP8266_Status   st;

    /* RST 引脚由驱动自己配 (CubeMX 那边没配这个脚): PB1 推挽输出 */
    __HAL_RCC_GPIOB_CLK_ENABLE();
    GPIO_InitStruct.Pin   = ESP8266_RST_PIN;
    GPIO_InitStruct.Mode  = GPIO_MODE_OUTPUT_PP;
    GPIO_InitStruct.Pull  = GPIO_NOPULL;
    GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_LOW;
    HAL_GPIO_Init(ESP8266_RST_PORT, &GPIO_InitStruct);
```

- **`= {0}` 不能省**：`GPIO_InitTypeDef` 里除了 Pin/Mode/Pull/Speed 还有 `Alternate` 字段，不整体清零就是拿栈上的随机值去配寄存器。
- **`__HAL_RCC_GPIOB_CLK_ENABLE()` 不能省**：外设时钟没开的时候写它的寄存器是**静默无效**的 —— 不报错，但引脚一直停在默认的浮空输入，RST 根本拉不动。本项目在 `MX_DMA_Init()` 的位置上踩过同一个坑（时钟没开就去写 DMA 寄存器）。
- 推挽输出 + 低速：RST 只是个开关信号，不需要速度和开漏。引脚定义在 `esp8266.h`（`ESP8266_RST_PIN = GPIO_PIN_1`、`ESP8266_RST_PORT = GPIOB`），换板子只改这两个宏。

**第 ② 段：先挂 DMA 接收，再复位**

```c
    /* 先挂上 DMA 接收再复位: 从这一刻起不管 CPU 在忙什么(哪怕在关中断读
     * DHT11), 串口来的字节都不丢 */
    if (ESP8266_RxStart() != ESP8266_OK)
    {
        return ESP8266_ERR_AT;
    }
```

顺序是刻意的：**先把接水的桶摆好，再让模块开始说话**。模块一被复位就会吐一段启动日志，DMA 早挂上就一个字节都不丢。
`RxStart()` 内部做了四件事（先 `DMAStop`、重挂 `Receive_DMA`、关 DMA 完成中断、关串口错误中断），详见 20.3.2 —— 它是全驱动最不能乱动的地方。

**第 ③ 段：复位时序 + 三条 AT**

```c
    /* 复位: 拉低 100ms 再放开. 模块的启动日志是 74880 波特, 收进来是一串乱码,
     * 不用管它 —— 真正算数的是下面 AT 回 OK */
    HAL_GPIO_WritePin(ESP8266_RST_PORT, ESP8266_RST_PIN, GPIO_PIN_RESET);
    BSP_DelayMs(100);
    HAL_GPIO_WritePin(ESP8266_RST_PORT, ESP8266_RST_PIN, GPIO_PIN_SET);
    BSP_DelayMs(1000);
```

- 拉低 100 ms 是给它一个明确的复位脉冲，放开后等 1000 ms 是等它自己启动完（内部 flash、射频校准都要时间）。
- 这两处延时用 `BSP_DelayMs()` 而不是 `HAL_Delay()`：在 RTOS 里这 1.1 秒是**挂着让出 CPU** 的，采集、灯照跑。

```c
    /* 探活: 回 OK 就是活着 */
    st = ESP8266_SendCmd("AT\r\n", "OK", ESP8266_TIMEOUT);
    if (st != ESP8266_OK)
    {
        return st;
    }

    /* 关回显, 后面匹配应答才干净 */
    st = ESP8266_SendCmd("ATE0\r\n", "OK", ESP8266_TIMEOUT);
    ...
```

- 三条 AT 的写法完全同构：`ESP8266_SendCmd(命令, "OK", 超时)`。返回不是 `ESP8266_OK` 就**把这个错误码原样 `return`** 给调用者 —— 超时就是 `ERR_TIMEOUT`，模块回 ERROR 就是 `ERR_AT`。驱动不翻译、不重试、不打印，判断全交给任务层。
- 第 2、3 条与第 1 条唯一的差别就是命令字串：`ATE0`、`AT+CWAUTOCONN=0`。后两条不再单独开 `if`，写成 `return ESP8266_SendCmd(...)`。
- 三条指令各自的理由：**探活**（`AT` 回 `OK` 就是模块活着）、**关回显**（不关的话模块会把每条命令原样回显一遍，匹配应答时容易撞上自己发出去的内容）、**关自动重连**（模块默认会自己重连上次的 AP，在后台跟我们抢射频状态，症状是最气人的那种 —— **扫得到、信号满格，但 `CWJAP` 就是连不上**）。
- 启动日志按 115200 收是一串乱码（它是 74880 波特发的），不用管，真正算数的是 `AT` 有没有回 `OK`。
- **每次重连都重新走一遍这个函数**，所以它同时承担了"把模块整个复位到干净状态"的职责：不管之前是卡死、半连还是 socket 半开，拉一次 RST 就都归零了。这是全项目唯一的"清理手段"。

### 20.3.6 `ESP8266_ConnectAP()` —— 关联热点

**开头：判空**

```c
ESP8266_Status ESP8266_ConnectAP(const char *ssid, const char *password)
{
    ESP8266_Status st;

    if (ssid == NULL || password == NULL)
    {
        return ESP8266_ERR_PARAM;
    }
```

两个指针后面都会被 `strlen` / 逐字节读，所以第一步先挡住空指针 —— 这是驱动里唯一"防御性"的地方，不花钱。

**第 ① 步：设成 Station 模式**

```c
    /* CWMODE 是掉电保存的, 每次重发一遍不费事, 也省得依赖模块 flash 里存了什么 */
    st = ESP8266_SendCmd("AT+CWMODE=1\r\n", "OK", ESP8266_TIMEOUT);
    if (st != ESP8266_OK)
    {
        return st;
    }
```

`CWMODE=1` = Station 模式（3 = AP+STA）。这个设置模块会存进 flash，但**每次连接都重发一遍**：不依赖模块里到底存了什么，少一个"上次跑别的程序改过它"的隐患。这一步失败就直接返回 —— 模式不对，后面 CWJAP 必然失败。

**第 ② 步：清掉可能残留的关联**

```c
    /* 先清掉可能残留的关联: 模块卡在"半连不连"时不先清干净会一直连不上, 表现
     * 得很像密码错. 没连的时候它是空操作, 所以失败也接着往下走 */
    (void)ESP8266_SendCmd("AT+CWQAP\r\n", "OK", ESP8266_TIMEOUT);
```

注意这里**没有 `if`，只有 `(void)`** —— 这就是"这一步不要紧"的代码化表达：返回值故意丢掉，编译不报警告，读代码的人一眼看出"失败了也往下走"。
理由：模块卡在"半连不连"的状态时，不先断开重来就会一直连不上，**表现得很像密码错**（让人白查半天）；而没关联的时候它本来就是空操作，失败没有意义。

**第 ③ 步：关联热点（唯一带用户数据的一步）**

```c
    /* AT+CWJAP="<名字>","<密码>": 名字和密码都是用户数据, 里面的 " \ , 都得转义 */
    (void)strcpy(s_Cmd, "AT+CWJAP=\"");
    if (ESP8266_AppendEsc(ssid) == 0U)
    {
        return ESP8266_ERR_PARAM;
    }
    (void)strcat(s_Cmd, "\",\"");
    if (ESP8266_AppendEsc(password) == 0U)
    {
        return ESP8266_ERR_PARAM;
    }
    (void)strcat(s_Cmd, "\"\r\n");

    /* 这一步包含关联 + DHCP, 要留够时间 */
    return ESP8266_Exec("OK", ESP8266_AP_TIMEOUT);
```

- **为什么不能一句 `SendCmd` 了事**：SSID 和密码是用户数据，可能含 `"`、`\`、`,`，必须先转义（见 20.3.4）。所以命令要**分五次拼出来**：`strcpy` 开头 → `AppendEsc(ssid)` → `strcat` 中间那段 `","` → `AppendEsc(password)` → `strcat` 收尾 `"\r\n`。
- **`AppendEsc` 返回 `0` = 拼不下**（超过 256−16 字节）。这时 `s_Cmd` 里是**半条命令**，绝不能发出去，所以立刻返回 `ERR_PARAM`。
- **`(void)strcpy` / `(void)strcat` 的 `(void)` 是另一回事**：它们返回的是指针，不是错误码；这里丢掉返回值只是因为"用不上"，`(void)` 的写法消掉编译警告。别把它和上面 `CWQAP` 那个"故意不管返回值"混了。
- **`\"` 是 C 语言的转义，不是 AT 的转义**：`"AT+CWJAP=\""` 拼出来的真实字节是 `AT+CWJAP="`。发给模块后，AT 那条规则（`"` `\` `,` 补反斜杠）才轮到 `AppendEsc` 管。这两层容易看混。
- **最后一步用 `ESP8266_Exec()` 而不是 `ESP8266_SendCmd()`**：命令已经拼好躺在 `s_Cmd` 里了，`Exec` 就是"发 `s_Cmd` 里现成的东西"，而 `SendCmd` 的作用是"先覆盖 `s_Cmd` 再发"。
- **超时 15 秒（`ESP8266_AP_TIMEOUT`）**：这一步不只是关联，还包含 DHCP 拿 IP 的过程，按 5 秒算不够。

### 20.3.7 `ESP8266_MQTT_SetParam()` —— 配鉴权与连接参数

这个函数发**三条**命令，少一条都不行：

```c
① AT+MQTTUSERCFG=0,1,"<设备名>","<产品ID>","",0,0,""
② AT+MQTTPASSWORD=0,"<Token>"
③ AT+MQTTCONNCFG=0,<keepalive>,0,"","",0,0
```

**开头的判空和 `st` 声明**

```c
ESP8266_Status ESP8266_MQTT_SetParam(const char *clientId, const char *username,
                                     const char *password, uint16_t keepalive)
{
    ESP8266_Status st;

    if (clientId == NULL || username == NULL || password == NULL)
    {
        return ESP8266_ERR_PARAM;
    }
```

三个字符串都要逐字节扫（转义），所以先挡住空指针。`st` 提到开头声明是因为下面要**用两次**：第 ① 条和第 ② 条发完都得看结果。

**第 ① 条：USERCFG（设备名 + 产品 ID）**

```c
    /* 设备名和产品 ID; scheme=1 = MQTT over TCP (明文 1883); 证书 ID 和 path
     * 只有 WebSocket 用 */
    (void)strcpy(s_Cmd, "AT+MQTTUSERCFG=0,1,\"");
    if (ESP8266_AppendEsc(clientId) == 0U)
    {
        return ESP8266_ERR_PARAM;
    }
    (void)strcat(s_Cmd, "\",\"");
    if (ESP8266_AppendEsc(username) == 0U)
    {
        return ESP8266_ERR_PARAM;
    }
    (void)strcat(s_Cmd, "\",\"\",0,0,\"\"\r\n");

    st = ESP8266_Exec("OK", ESP8266_TIMEOUT);
    if (st != ESP8266_OK)
    {
        return st;
    }
```

参数含义逐个对：`link_id = 0`（模块只开一路 MQTT，固定 0）；`scheme = 1` = MQTT over TCP，就是明文 1883 —— 本项目不用 TLS，模块内存也不够；接着是 client_id（OneNET 的设备名，会转义）、username（产品 ID，会转义）；然后 **password 位留空**（`\"\"`）—— 不是忘了填，是故意留空：Token 有 124 字节，塞不进这个字段，下一段讲；最后 `0,0` 是证书 ID 和 CA ID、`\"\"` 是 path，**这两样只有 WebSocket 用**，TCP 直连给 0 和空串。

注意命令的**收尾是 `strcat` 一次性拼上**的：`\",\"\",0,0,\"\"\r\n` —— 客户端 ID 和用户名的转义结果后面，接的是 `",""` 加一串固定参数，中间那个空 password 就是这里的 `\"\"`。

拼完马上 `Exec`，**且必须检查结果**：这条失败后面两条毫无意义（没有 client_id 和 username，连也连不上）。这种"前一条失败就 `return st`"的写法在这个函数里出现两次，和 20.3.6 里对 `CWQAP` 那种 `(void)` 放行形成对照 —— 判据只有一条：**这条失败以后，后面的步骤还有没有意义**。

**第 ② 条：Token 单独发**

```c
    /* 密码单独发: Token 124 字节 > MQTTUSERCFG 里 password 字段的 64 字节上限
     * (文档要求这条放在 USERCFG 之后) */
    (void)strcpy(s_Cmd, "AT+MQTTPASSWORD=0,\"");
    if (ESP8266_AppendEsc(password) == 0U)
    {
        return ESP8266_ERR_PARAM;
    }
    (void)strcat(s_Cmd, "\"\r\n");

    st = ESP8266_Exec("OK", ESP8266_TIMEOUT);
    if (st != ESP8266_OK)
    {
        return st;
    }
```

**为什么密码不能写在 ① 里**：OneNET 的 Token 有 **124 字节**，而 `AT+MQTTUSERCFG` 的 password 字段上限是 **64 字节**。塞进 ① 只会被截断或直接报错。模块另有一条 `AT+MQTTPASSWORD`，没有这个长度限制，**但文档规定它必须放在 USERCFG 之后** —— 所以不是"拆成两条都行"，顺序是被固定的。

写法上和第 ① 条一模一样（`strcpy` 开头 → `AppendEsc` → `strcat` 收尾），因为转义规则不认参数是第几个。

**第 ③ 条：连接参数**

```c
    /* 连接参数. keepalive 必须显式给: 模块把 0 强制改成 120 秒.
     * disable_clean_session=0 = 开清洁会话 (关掉会留下旧会话, 表现成"连上了但
     * 发布没反应"); 后面是遗嘱, 不用 */
    (void)sprintf(s_Cmd, "AT+MQTTCONNCFG=0,%u,0,\"\",\"\",0,0\r\n", (unsigned)keepalive);

    return ESP8266_Exec("OK", ESP8266_TIMEOUT);
}
```

- **这条没有用户数据（都是数字和空串），所以不用 `AppendEsc`、不用拼**，一句 `sprintf` 直接覆盖 `s_Cmd`。
- **`%u` + `(unsigned)keepalive`**：`keepalive` 是 `uint16_t`，C 里会做整型提升成 `int`，而 `%u` 要的是 `unsigned`，所以显式转一次。驱动里所有 `%u` 都这么写。
- **`keepalive` 必须显式给**（本项目 `CFG_MQTT_KEEPALIVE_S = 60`）：**模块会把 0 强制改成 120 秒**，想让心跳按自己的值来就必须写进去。
- **`disable_clean_session = 0`** = 开清洁会话。关掉它（写 1）会保留旧会话，症状是"连上了但发布没反应"—— 一个很难查的坑。
- 后面四个是遗嘱（lwt）相关，本项目不用，全给空串 / 0。
- **最后一条直接 `return ESP8266_Exec(...)`**：不用 `st`，因为它就是本函数的返回值了。

**三条的固定顺序**：USERCFG → MQTTPASSWORD → MQTTCONNCFG，不能换。前两条失败立刻返回，第三条的结果就是函数结果。

> 注意指令名：老资料里常见的 `AT+MQTTCFG` 在这版固件里**不存在**，它对外的名字是 `AT+MQTTUSERCFG` + `AT+MQTTCONNCFG`（扫固件里的字符串表确认过）。

### 20.3.8 `ESP8266_MQTT_ConnectBroker()` —— 连 broker

```c
AT+MQTTCONN=0,"<域名>",<端口>,0        → 等 "+MQTTCONNECTED", 超时 15 秒
```

**全部代码只有五处**

```c
ESP8266_Status ESP8266_MQTT_ConnectBroker(const char *host, uint16_t port)
{
    if (host == NULL)
    {
        return ESP8266_ERR_PARAM;
    }

    /* AT+MQTTCONN=0,"<host>",<port>,0
     * 最后的 <reconnect> 传 0: 不让模块自己闷头重连, 重连交给任务层那套
     * "连续失败 N 次就整个重来"(它会复位模块 + 重接热点, 更彻底) */
    (void)strcpy(s_Cmd, "AT+MQTTCONN=0,\"");
    if (ESP8266_AppendEsc(host) == 0U)
    {
        return ESP8266_ERR_PARAM;
    }
    (void)sprintf(&s_Cmd[strlen(s_Cmd)], "\",%u,0\r\n", (unsigned)port);

    /* 等 "+MQTTCONNECTED" 而不是 "CONNECTED": 后者是 "+MQTTDISCONNECTED" 的
     * 子串, 用短的会把"已经断开"读成"连上了" */
    return ESP8266_Exec("+MQTTCONNECTED", ESP8266_MQTT_TIMEOUT);
}
```

- **`sprintf(&s_Cmd[strlen(s_Cmd)], ...)` 是"接在尾巴后面"的写法**：`&s_Cmd[strlen(s_Cmd)]` 就是当前字符串末尾那个 `\0` 的地址，从那儿 `sprintf` 相当于 `strcat` 一个格式化结果。C 里没有"`strcatf`"，所以只能这么写。
  有用户数据的段（`host`）走 `AppendEsc`，纯数字的段（端口）直接 `sprintf` —— 和 20.3.7 里第 ③ 条是同一个判据。
- **这里不能整条一次 `sprintf` 出来**：那样 `host` 就没法转义了。`sprintf("%s", host)` 遇到 host 里的 `"` 或 `,` 会原样吐出来，模块就会当成多余参数。
- **传域名的话模块自己做 DNS**，所以 15 秒（`ESP8266_MQTT_TIMEOUT`）里包含 **DNS + TCP 握手 + MQTT CONNACK** 三步，比一条普通 AT 命令慢得多。
- **最后那个 `reconnect = 0`**：不让模块自己闷头重连。重连交给任务层那套"连续失败 3 次就整个重来"—— 它会复位模块 + 重接热点，比模块自己重连彻底得多，也不会出现"模块在偷偷重连、任务层以为一切正常"的两套逻辑打架。
- **成功判据是 `+MQTTCONNECTED`，不能图省事写 `CONNECTED`**：`+MQTTDISCONNECTED`（断开上报）里正好含 `CONNECTED` 这个子串，用短的会把"已经断开"读成"连上了"。这个坑是**踩过的**，别改回去。

### 20.3.9 `ESP8266_MQTT_Publish()` —— 发布一条消息

```c
AT+MQTTPUB=0,"<主题>","<载荷>",0,0     → 等 OK, 超时 5 秒
```

**代码**

```c
ESP8266_Status ESP8266_MQTT_Publish(const char *topic, const char *data)
{
    if (topic == NULL || data == NULL)
    {
        return ESP8266_ERR_PARAM;
    }

    /* AT+MQTTPUB=0,"<主题>","<载荷>",0,0
     * 两段都要转义 —— JSON 载荷里全是逗号和引号, 不转义模块会当成多余的参数,
     * 回一句 +MQTTPUB:FAIL */
    (void)strcpy(s_Cmd, "AT+MQTTPUB=0,\"");
    if (ESP8266_AppendEsc(topic) == 0U)
    {
        return ESP8266_ERR_PARAM;
    }
    (void)strcat(s_Cmd, "\",\"");
    if (ESP8266_AppendEsc(data) == 0U)
    {
        return ESP8266_ERR_PARAM;
    }
    (void)strcat(s_Cmd, "\",0,0\r\n");

    return ESP8266_Exec("OK", ESP8266_TIMEOUT);
}
```

结构和 20.3.6 的 `CWJAP` 完全一样（两段用户数据夹在中间），只是参数不同。**这个函数是被调用得最频繁的一个**（本任务 2 秒一次），载荷最长，所以它是最容易撞上"拼不下"上限的那个。

**转义到底长什么样**

假设要上报一帧：

```json
{"id":"12","version":"1.0","params":{"Temp":{"value":25.0},"Hum":{"value":60.0}}}
```

`AppendEsc` 会给每个 `"` 和 `,` 前面补一个反斜杠，拼出来的命令实际是：

```
AT+MQTTPUB=0,"$sys/<产品ID>/<设备名>/thing/property/post","{\"id\":\"12\"\,\"version\":\"1.0\"\,\"params\":{\"Temp\":{\"value\":25.0}\,\"Hum\":{\"value\":60.0}}}",0,0
```

注意**逗号也补了反斜杠**（`\"12\"\,`）—— 这是这套 AT 固件的规定，不是笔误。这也解释了 20.3.4 为什么必须**一趟处理三个字符**：转义 `"` 的时候顺手把 `\` 和 `,` 也处理掉，就不会出现"补进去的反斜杠又被下一次转义再补一遍"的连锁。

**这个转义是驱动干的，调用者不用管**：`task_wifi.c` 里照常拼合法 JSON，直接传给 `ESP8266_MQTT_Publish(CFG_MQTT_PUB_TOPIC, payload)` 就行。自己预先转一遍会得到 `\\\"` 这种东西，模块解析不了。

**返回值的含义**

- `qos = 0`（最多一次）、`retain = 0`（不保留）。
- 成功时模块回 `OK`（有的固件回 `+MQTTPUB:OK`，同样含 `OK`）；失败回 `+MQTTPUB:FAIL`，含 `FAIL`，被判定成 `ERR_AT`（判定顺序见 20.3.3：先找 ack，再找 `ERROR`/`FAIL`，最后才判超时 —— 所以 `FAIL` 不会被误读成"这就是我要的 ack"）。
- ⚠️ **`OK` 只代表模块把这条消息收下了、发出去了，不代表 OneNET 收到了**。平台侧收没收到得去控制台看数据点。这是 MQTT QoS 0 的固有性质，不是驱动的问题。真要知道通道死没死，靠的是任务层"连续 3 次失败就重连"（见 [详解 19](19-FreeRTOS任务入门-以WiFi任务为例.md) 的 19.3.3）。

## 20.4 关键设计决策

### 决策一：顺序阻塞，不做状态机

驱动是"发一条等一条"的：接口返回时事情已经有结果。代价是**一次彻底连不上的流程最坏能占住调用者约 71 秒**（见 20.2 超时账）。

这个取舍成立的前提有三条：**有独立的 WiFi 任务**、**该任务卡 5~15 秒无所谓**（别的传感器、灯跑在别的任务里）、**流程是线性的**（复位 → 连 WiFi → 连 MQTT → 循环发布，没有"一边跑网络一边干别的"的需求）。

**想把这套驱动搬进裸机主循环，或者塞进一个还要干别的事的任务，就必须把状态机请回来**（接口只发起、`Process()` 推进那套写法）—— 那正是改写成阻塞式时明确接受掉的东西。

### 决策二：接收用 DMA，发送用中断 —— 不对称是故意的

| | 接收 | 发送 |
| --- | --- | --- |
| 用什么 | DMA1_Channel6，CIRCULAR | `HAL_UART_Transmit_IT` |
| 为什么 | 关中断 4 ms 读 DHT11 期间也不能丢字节（20.3.2） | 一条命令最多 256 字节，22 ms 发完，中断足够；DMA 要多占一个通道、多一套中断，收益为零 |

### 决策三：一切都靠轮询，不用回调、不用接收中断

- 发送完没完：轮询 `huart2.gState`（不能用 `HAL_UART_GetState()`，理由见 20.3.1）。
- 收到多少字节：轮询 DMA 的 CNDTR（`RxHead()`）。
- 应答出现了没：在 `Exec()` 的循环里每 1 ms 搬一次字节再 `strstr`。
- 因此**不需要** `HAL_UART_TxCpltCallback`（那是全局弱符号，多个串口都用会打架），也**不需要**串口的接收中断和错误中断（错误中断还必须主动关掉，见 20.3.2 ★）。

### 决策四：驱动不打印、不重试、不认识 FreeRTOS

| | 驱动 `BSP/ESP8266/` | 任务层 `APP/task_wifi.c` |
| --- | --- | --- |
| 管什么 | AT 指令怎么拼、怎么发、应答怎么匹配、超时怎么算 | 什么时候连、失败几次重连、隔多久重试、发什么内容 |
| 打印 | **一句都不打** | 只打"连上了/没连上"这类结论 |
| 重试 | 不重试，一次不行就返回错误码 | 连续失败 3 次 → 回外层复位模块重连；连不上时每 5 秒重试一次 |
| 依赖 | HAL + `BSP_DelayMs()`（**不认识 FreeRTOS**） | FreeRTOS 任务、队列、`printf` |

分界线的判据很简单：**"这条 AT 指令该怎么写"属于驱动，"什么时候发、失败了怎么办"属于任务。**

驱动不认识 FreeRTOS 是靠 `BSP_DelayMs()` 的弱/强符号实现的（弱定义在 `BSP`，强定义在 `APP/app_delay.c`），详见 [详解 19](19-FreeRTOS任务入门-以WiFi任务为例.md) 的 19.2。

### 决策五：命令先拼进 RAM 里的 `s_Cmd`

`HAL_UART_Transmit_IT` 要的是**可写指针**，而且异步发送期间那块内存不能被改写。所以驱动里没有一处直接把字符串字面量发出去：所有命令都先拼进 `static char s_Cmd[288]`，再发 `s_Cmd`。这样也避开了"把 `const char *` 强转成 `uint8_t *`"那种脏写法。

代价：**驱动不是可重入的**，同一个模块只能有一个"当前命令"。本项目只有一个 WiFi 任务碰它，够用。

### 决策六：每条命令之前都清一次接收缓冲

好处：上一次命令的尾巴不会被当成这一次的应答，`strstr` 匹配永远只看本次。

代价：**模块空闲时主动上报的 URC（`+MQTTDISCONNECTED` 之类）被一并丢掉**，驱动不解析它们（见 20.5）。这是"简单"换来的，不是做不到。

## 20.5 已知局限与注意事项

### 不能删 / 不能改的地方（都是踩过坑留下的）

1. **`RxStart()` 里的 `__HAL_UART_DISABLE_IT(&ESP8266_UART, UART_IT_ERR)`** —— 删了接收早晚全哑（原因见 20.3.2）。
2. **判断发送完成只能看 `huart2.gState`**，不能用 `HAL_UART_GetState()`。
3. **`RxStart()` 开头必须先 `HAL_UART_DMAStop()`** —— 否则重连时接收永远挂不上。
4. **`+MQTTCONNECTED` 不能简写成 `CONNECTED`**。
5. **Token 必须走 `AT+MQTTPASSWORD`**，不能塞进 `AT+MQTTUSERCFG`（64 字节上限）。
6. **`keepalive` 必须显式给**，否则模块把 0 改成 120。
7. **转义三种字符必须一趟处理完**，且要守住 256 字节上限。
8. **`ClearRxBuf()` 里两处都要清**（DMA 里没搬走的 + 已搬进解析缓冲的），`memset` 不能省（`strstr` 靠它保证结尾是 `'\0'`）。
9. **等待应答的四条判断顺序不能调**（期望应答 → ERROR/FAIL → 缓冲满 → 超时）。
10. **驱动里不要用 `vsnprintf`**：它会把浮点版 `printf` 一整套格式化代码链进来（多约 2.5 KB Flash）。现在只用 `sprintf` 打 `%u` 和 `%s`，一个浮点都不带。
11. **所有等待都要经过 `BSP_DelayMs()`**，不要在驱动里直接调 `HAL_Delay()` 或 `vTaskDelay()` —— 前者会把别的任务饿死，后者会让驱动编不进裸机工程。

### 已知的空白（现在的设计里没有的东西）

- **没有链路探活**。驱动里没有 `AT+MQTTCONN?` 之类的"查一下还连着没"的接口，模块主动上报的 `+MQTTDISCONNECTED` 也不解析（每次发命令前会清接收缓冲，顺手丢掉）。
  现在的"自愈"是两条粗粒度路径：连不上时每 5 秒重试；上报连续失败 3 次退回重连。
  **盲区**：采集停了、队列空着的时候，WiFi 任务一直阻塞在 `xQueueReceive`，没有发送尝试就没有失败计数 —— 此时 broker 那边断了不会被发现。
- **没有 TLS**（明文 1883）：ESP8266 的内存扛不住 TLS 握手，OneNET 的鉴权靠 Token 本身。搭在热点上做课程设计可以，正式产品不行。
- **解析缓冲 512 字节**：应答超过它直接报 `ERR_BUF_FULL`（不是解析出错，而是这条回复我们不认识了）。CWJAP 的回复是最长的那条，目前够用。
- **`ESP8266_Init()` 是唯一的"清理"手段**：想回到干净状态，就是把它再跑一遍（拉 RST）。所以任务层的重连逻辑里第一步永远是它。
- **驱动不可重入**：只有一个 `s_Cmd`、一套接收缓冲，同时只能有一个任务用它（见 20.4 决策五）。

## 20.6 动手改这里

**换板子 / 换接线**：只改 `esp8266.h` 顶部的三个宏 —— `ESP8266_UART`（用哪个串口）、`ESP8266_RST_PIN`、`ESP8266_RST_PORT`。接收 DMA 换通道要去 `usart.c` 的 `HAL_UART_MspInit()` 改。

**改超时**：`esp8266.h` 里的四个超时宏。别把 `ESP8266_TX_TIMEOUT` 往下调到 30 ms 以下 —— 256 字节 @115200 就要 22 ms，会误判。反过来，把 `ESP8266_AP_TIMEOUT` 调到 10 s 以下，热点信号差的时候会误报失败（DHCP 有时真慢）。

**改上报内容**：改 `task_wifi.c` 里的 `snprintf` 和 `app_config.h` 里的主题。**加字段前先算一下长度**：整条 `AT+MQTTPUB` 不能超过 256 字节，主题 + 载荷的转义结果不能超过 240（256 − 16）。现在的报文约 90 字节，还有余量，但不是无限的。

**想加一个接口**（比如"查一下模块还连着没"）：
1. 先在 `esp8266.h` 里声明，枚举不够就加值。
2. 没有用户数据的命令最简单：一句 `ESP8266_SendCmd("AT+…\r\n", "OK", ESP8266_TIMEOUT)`。
3. 带用户数据的，照 `CWJAP` 的模子拼（`strcpy` → `AppendEsc` → `strcat`），最后用 `ESP8266_Exec` 发。
4. **不要**在驱动里写 `printf`、不要加重试循环 —— 打印和策略留给任务层（20.4 决策四）。

**想回到非阻塞**：那是重写，不是改参数。要加回"接口只发起 + `Process()` 推进 + `WaitDone()` 收敛"那一套，同时任务层要改成轮询式。**动手前先确认真的出现了新需求**（比如要在同一个任务里一边跑网络一边干别的），否则只是把简单的东西复杂化。

## 20.7 一句话总结

**驱动只干一件事：把一条 AT 指令发出去、把应答收回来、告诉调用者成没成；接收靠 DMA 环 + 轮询 CNDTR，发送靠中断 + 轮询 `gState`，等待靠 `BSP_DelayMs()` 让出 CPU —— 于是它必须跑在独立的 WiFi 任务里，换来的是全驱动没有一个状态机、没有一个回调。**

三件最容易被误解的事：

1. **"顺序阻塞"是有代价的选择**：一次彻底连不上最坏占住调用者约 71 秒。成立的前提是本项目有独立的 WiFi 任务；搬进裸机主循环就得把状态机请回来。
2. **接收和发送不对称是故意的**：接收非用 DMA 不可（关中断 4 ms 读 DHT11 不能丢字节），发送用中断就够（256 字节 22 ms 发完）。
3. **`OK` ≠ 平台收到了**：它只代表模块把消息发出去了。QoS 0 下没有回执，真正的自愈是任务层"连续失败 3 次就整个重连"。
