## 〇、最终能跑的配置（抄这个）

```c
/* ---- WiFi：手机热点 ---- */
CFG_WIFI_SSID      "奈何神明耍诈"          /* 名字里带中文，没问题，见 3.2 */
CFG_WIFI_PASSWORD  "G123456789"

/* ---- MQTT 端点：明文，不是 TLS ---- */
CFG_MQTT_HOST      "mqtts.heclouds.com"    /* 域名里的 s 不代表加密！见 6.4 */
CFG_MQTT_PORT      1883
CFG_MQTT_CLIENT_ID "test1"                 /* = 设备名称 */
CFG_MQTT_USERNAME  "v9cSbzDFqr"            /* = 产品 ID */
CFG_MQTT_PASSWORD  "version=2018-10-31&res=products%2Fv9cSbzDFqr%2Fdevices%2Ftest1&et=1821308308&method=sha1&sign=9Cyhm1fn76GI5cURLVvT6AV4XCg%3D"
```

⚠️ **Token 整串必须写在同一行。** 这不是排版讲究 —— C 里换行会把它断成两个字符串
字面量，**拼起来是错的**（`APP/app_config.h:63` 就是这么写警告的）。上面这条以前被
笔记折成了两行，照抄编译出来的 Token 里会混进第二行的**缩进空格**
（`...devices%2Ftest1                    &et=...`），服务器验签当然过不去，
而平台只会回那个含义模糊的 `code 4`。**换 Token 时去控制台整串复制，别手动折行。**

**上报主题**（物模型产品）：

```
$sys/v9cSbzDFqr/test1/thing/property/post
```

**上报报文**：

```json
{"id":"1","version":"1.0","params":{"Temp":{"value":27.0},"Hum":{"value":98.0}}}
```

⚠️ **主题和报文是配套的一对**，换一个必须同时换另一个。详见 [6.1](#61-主题和-json-是配套的一对)。

## 一、贯穿全篇的一条方法论

### 1.1 平台和模块几乎不给你有效报错

这一天踩的所有坑，表面症状和真实原因**全都是错位的**：

| 你看到的 | 你以为 | 实际上 |
|---|---|---|
| `CONNACK code 4: 用户名或密码错误` | 密码写错了 | Token **验签失败**（`et` 多了个数字）|
| `SEND OK` | 平台收下了 | ESP8266 **自己**回的"我塞进 TCP 了" |
| 上报失败，平台"设备离线" | 模块坏了 / 代码写错了 | **主题不对**，平台直接断链，不报错 |
| `AT+CWLAP` 扫得到热点，信号满格 | 热点就在跟前，是模块的问题 | 热点把板子**拉黑了**，黑名单不挡 beacon |
| 串口打印 `濂堜綍绁炴槑鑰嶈瘓` | 编码错了，固件里存的是乱码 | 字节是对的，**串口助手按 GBK 显示 UTF-8** |
| IDE 红线报 `未定义标识符` | 代码有错 | IDE 拿的是**过期快照**，编译器 0 错误 |

**结论：不要相信任何一条单一的报错。** 尤其是"密码错误"和"发送成功"这两个，
它们的实际含义和字面意思差得最远。

### 1.2 二分法：把设备排除在外

遇到"设备连不上/发不出去"，**先别动固件**。把设备上用的**同一串凭据**
拿到 PC 端（MQTTX 或 python paho）连一次：

```
PC 端也失败  →  凭据 / Token / 主题 / 属性名的问题。别碰固件，改了也是白改
PC 端成功    →  这才轮到查代码和硬件
```

**这一步在本次排障里省掉了绝大部分时间。** 两个死结（Token 验签、主题不匹配）
都是靠它定性的：

- Token 那次：把代码里的 Token 抄进 MQTTX → **MQTTX 也连不上** →
  立刻证明"不是 STM32 的问题"，方向从"查固件"转到"查凭据字节"
- 主题那次：反过来，MQTTX 能发、板子不能发 → 说明链路是好的，问题在报文内容

### 1.3 判断"成功"的唯一标准

> **控制台上出现数据点。**

不是"设备在线"（那只是 CONNACK 过了），不是 `SEND OK`（那是模块的回执），
不是 `uploaded` 那行日志（那只是 `ESP8266_TCPSend` 返回了 OK）。

**中间任何一环说自己成功了，都不算数。**

## 二、工具链层的坑

### 2.1 `printf` 里的中文会报警告 #870-D

**现象**：编译报 `warning #870-D: invalid multibyte character sequence`。

**原因**：ARM Compiler 5 按**系统码页**读源文件（中文 Windows 上是 GBK），
而工程里所有 `.c/.h` 都是 UTF-8。字符串字面量里的中文就被当成非法多字节序列。

**约定**：注释用中文，`printf` 等字符串字面量一律英文。

```c
/* 这样写：中文只在注释里 */
printf("[WiFi] connect failed, retry in %d s\r\n", 5);

/* 不要这样写 */
printf("WiFi 连接失败, %d 秒后重试\r\n", 5);   /* ← 警告 */
```

还有个副作用：源文件是 UTF-8，串口助手常用 GBK，两端不匹配会显示乱码。
全英文两头都省事。

### 2.2 但 AC5 不会转换字节（我在这儿白绕了一轮）

**这是我在本次排障里判断错了、走了弯路的地方，记下来免得再犯。**

当时 SSID 连不上，我怀疑是"源文件是 UTF-8，AC5 按 GBK 读，所以编译进固件的
SSID 是 GBK 的，跟热点广播的 UTF-8 对不上"。

**这个假说是错的。** 用 hex 核对过：

```
源文件里 "奈何神明耍诈"  = e5 a5 88 e4 bd 95 ...     ← 18 字节 UTF-8
project.axf 里           = e5 a5 88 e4 bd 95 ...     ← 同一串，一个字节没变
```

**AC5 不做字符集转换，字面量里的字节原样进 `.rodata`。**

所以：
- 看到串口打出 `濂堜綍绁炴槑鑰嶈瘓`，**字节是对的**，只是**终端用 GBK 在显示 UTF-8**
- 别再为此去查编译器、查源文件编码 —— 那条路是死的

### 2.3 IDE 的红线可能是过期快照

**现象**：IDE 报 `未定义标识符 "msgId"`、标识符被截断成 `ESP8266_TX_TIMEO` 之类，
但代码明明是刚写好的。

**处理**：**以编译器为准。** 每次改完跑一遍：

```bash
"D:/Download/kile5/PACK/UV4/UV4.exe" -b project.uvprojx -j0 -o build.log
```

看到 `0 Error(s), 0 Warning(s)` 就是好的，IDE 那边过一会儿自己会刷新。

## 三、WiFi 关联层的坑

### 3.1 手机热点把板子拉黑了 —— 本次最坑的一个

**现象**：

```
AT+CWLAP                    → +CWLAP:(3,"奈何神明耍诈",-20,...)   ← 扫得到，满格
AT+CWJAP="奈何神明耍诈","..." → +CWJAP:4  FAIL                    ← 就是连不上
```

**看起来像模块坏了**：能扫到、信号满格、命令也发得出去，就是关联不上。

**真实原因**：手机热点把这个板子的 MAC 地址**加进了黑名单**（"已阻止的设备"）。

**为什么这么有迷惑性**：

> **黑名单只拒绝"关联"，但不挡 beacon。**

而 `AT+CWLAP` 是靠**被动接收 beacon** 来列热点的 —— 所以被拉黑的设备照样
扫得到这个热点，信号强度也照常显示满格。**"扫得到"根本不代表"连得上"。**

**排查顺序**（以后再遇到"扫得到但连不上"，按这个顺序查）：

1. **热点黑名单 / "已阻止的设备"** ← 先查这个
2. 热点客户端数满了，或开了"仅允许已添加的设备"
3. 密码值不对
4. 模块天线 / 供电

**代码里留的取证工具**：`APP/task_wifi.c` 的 `WifiDiagScan()`，只挂在 CWJAP
失败分支上，正常路径一次都不跑。它会把扫码结果和热点在模块眼里的**原文名字**
都打出来，用来区分"热点不在跟前"和"热点主动拒绝"这两种情况。

> 💡 这个信息是用户自己找到的，不是我。我先前猜的是"热点关了/太远"和
> "3.3V 供电塌陷"，方向都错了 —— 因为扫描已经证明热点在跟前、信号满格，
> 那个证据当时被我忽略了。

### 3.2 SSID 里有中文不是问题

热点名字 `奈何神明耍诈` 是 UTF-8 中文，`AT+CWJAP` 直接传就行。

**别再怀疑这个。** 见 [2.2](#22-但-ac5-不会转换字节我在这儿白绕了一轮) —— 字节是原样进固件的。

### 3.3 残留关联和模块的后台重连会来抢

**两个隐患**，都会让 `AT+CWJAP` 莫名其妙失败：

| 隐患 | 处理 |
|---|---|
| 上一次的关联还残留着 | 连之前先发 `AT+CWQAP` 断开 |
| 模块自己后台重连（`CWAUTOCONN` 默认=1），跟我们的 CWJAP 抢射频状态 | 初始化时发 `AT+CWAUTOCONN=0` 关掉 |

**症状很有迷惑性**：扫描能扫到、信号满格，但 CWJAP 就是失败，
而且响应里会先冒一条 `WIFI DISCONNECT` —— 那是模块后台重连失败留下的。

**已加在代码里**：
- `ESP8266_Init()` 里发 `AT+CWAUTOCONN=0`（持久化设置，每次开机重发一遍不费事）
- `ESP8266_ConnectWiFi()` 里，`CWJAP` 之前先发 `AT+CWQAP`

### 3.4 逃生开关：`ESP8266_FACTORY_RESET_ON_BOOT`

`BSP/ESP8266/esp8266.h` 里有个开关，默认 `0`。打开后每次开机发 `AT+RESTORE`
恢复出厂，清掉模块 flash 里存的那份 AP 配置。

**什么时候用**：遇到"以前能连，现在怎么都连不上"，且怀疑模块内部存了脏状态时。

⚠️ **RESTORE 会把波特率也恢复成 115200** —— 本项目正好就是 115200，所以没事；
别的项目开这个开关前先确认波特率。另外记得**用完关掉**。

## 四、ESP8266 驱动层的坑

### 4.1 `HAL_UART_Receive_DMA` 第二次调用返回 `HAL_BUSY`

**这是个"一次失败，永远失败"的坑。**

**原因**：`HAL_UART_Receive_DMA()` 要求 `huart->RxState == HAL_UART_STATE_READY`，
否则直接返回 `HAL_BUSY`。第一次调用时是 READY，没问题；但 DMA 一直在环形模式里
跑、从来没"结束"过，所以第二次进来时 `RxState` 还停在 `BUSY_RX`。

**症状极具迷惑性**：第一次失败之后**永远**失败，而且从第二次起报的是
`ESP8266 Init Failed!`，看起来像模块坏了或者接触不良。

**处理**：进函数先 `HAL_UART_DMAStop()` —— 它内部会把 `RxState` 复位成 READY。

```c
static ESP8266_Status ESP8266_RxStart(void)
{
    (void)HAL_UART_DMAStop(&ESP8266_UART);   /* ← 这一行不能省 */
    ESP8266_DmaTail = 0;
    if (HAL_UART_Receive_DMA(&ESP8266_UART, ESP8266_DmaBuf,
                             ESP8266_DMA_BUF_SIZE) != HAL_OK) { ... }
    ...
}
```

**这个坑和后面的"自动重连"直接相关** —— 重连就是反复调 `ESP8266_Init()`，
没有这一行的话，第二次重连就再也起不来了。

### 4.2 一条 DMA 环形队列 + 两个互斥的消费者

> ⚠️ **这一节以前写的是"驱动里有两套收数据的地方，是已知隐患"——那个说法是错的。**
> 收数据的地方**只有一个**：DMA 环形缓冲区。下面按实际架构重写。

AT 的文本应答和 `+IPD` 里的协议数据，是**同一条队列里的同一批字节**，
区别只在"谁来取、怎么取"：

```
DMA1_CH6 ──写──> DmaBuf[256]（环形）
                     ├── RxDrain ──> RxBuf[512]（线性，strstr 匹配 AT 文本应答）
                     └── RxPop ────> 调用方 buf  ← TCPRecvRaw 走这条，完全绕过 RxBuf
```

| 取法 | 谁在用 | 字节去哪 | 干什么 |
|---|---|---|---|
| `ESP8266_RxDrain()`<br>（`esp8266.c:112`） | `ESP8266_WaitResponse()` | `ESP8266_RxBuf`（512 字节线性） | 累积整条 AT 应答，`strstr` 搜 `OK` / `ERROR` / `FAIL` |
| `ESP8266_RxPop()`<br>（`esp8266.c:90`） | `ESP8266_TCPRecvRaw()` | 调用方自己的 buf | 剥掉 `+IPD,<len>:` 包装，只交出 MQTT 字节 |

**两条路是互斥的** —— 都推进同一个读指针（`ESP8266_DmaTail`），
字节被一边取走，另一边就再也看不到。所以不是"两份数据"，是
**"一条队列、两个出口"**。

**`+IPD` 剥离状态机早就实现了**（`esp8266.c:553-683`，出口是
`ESP8266_TCPRecvRaw()`，声明在 `esp8266.h:163`），连"头被切成两半"的情况都处理了。
MQTT 层的应答（CONNACK / PINGRESP）走的就是 `TCPRecvRaw`，
**不经过 `WaitResponse`**。

**现在仍然成立的风险只剩一条**：将来做 MQTT **订阅**时，服务器主动推来的
订阅数据如果正好落在"我们在等 AT 应答"的那段时间里，会被 `WaitResponse`
经 `RxDrain` 卷进 `RxBuf` 当文本搜掉。本项目只上报、不订阅，所以触发不了
（这条风险跟"缓冲区分几块"无关 —— 就算没有 `RxBuf`，等应答期间没人去取的字节
也一样会被吞掉，只是吞在别处）。

> 逐行原理见新笔记 [详解/02-ESP8266接收架构与+IPD剥离](09-ESP8266接收架构与+IPD剥离.md)。

### 4.3 多任务 `printf` 有竞态（已知隐患，还没爆）

多个任务都在用 `printf`，而 `printf` 内部不是原子的。

**今天没事**，因为输出量小、且都阻塞在别的地方。但严格说这是个隐患，
真要长期跑得给 `printf` 加锁，或者改成各自往队列里丢、由一个任务统一输出。

## 五、MQTT 协议层的坑

### 5.1 `CONNACK code 4` 的字面意思是骗人的

```
[WiFi] to MQTT CONNACK refused: code 4, bad username or password (Token expired?)
```

**"用户名或密码错误"这个名字会把你直接带偏。** 它实际覆盖的情况包括：

- 用户名/密码值真的写错了
- **Token 的签名验不过**（← 本次的真实原因）
- Token 过期了

**关键点**：OneNET 的 Token 不是一串随机字符，是**算出来的**：

```
sign  = base64( HMAC-SHA1( 设备密钥, "{et}\n{method}\n{res}\n{version}" ) )
Token = "version=...&res=...&et=...&method=...&sign=..."
```

👉 **`sign` 覆盖了 `et` / `method` / `res` / `version` 这四个字段。
这四个里任何一个被手改过，`sign` 立刻失效。**

而平台只会回一个含义模糊的 `4`，看起来像密码写错了。

### 5.2 `et` 是 **10 位**数字，多一位必错

**本次的真实病因**：抄 Token 时在 `et` 里**多打了一个 `1`**。

```
错:  et=18211308308     ← 11 位
对:  et=1821308308      ← 10 位
```

`et` 是 Unix 时间戳（秒）。**10 位能表示到 2286 年**（32 位有符号整数上限
2147483647 对应 2038-01-19，还更早），而实际生成的 Token 都在近几年 ——
所以：

> **正常情况下 `et` 永远是 10 位。看到 11 位，换算出来是两千多年后，必然是打错了。**

**排查提示**：这种错误**在 MQTTX 上能原样复现**（同一串 Token 拿去 MQTTX 也连不上），
所以一旦复现成功，就别再怀疑模块和代码了，去逐字节比对凭据。

> ⚠️ 这里我一开始判断错了方向。我看到 `et=18211308308` 换算过来是 2547 年，
> 猜是用户**有意**改成"永不过期"。实际上只是**打字多了一位**。
> **结论（Token 失效）蒙对了，但原因说错了。** 教训：不要替别人的错误编动机。

### 5.3 百分号编码**不是必须的**

Token 里 `%2F`（`/`）和 `%3D`（`=`）这种百分号编码，**编码版和字面版都能过鉴权**
（2026-09-20 直连 broker 验过）。

用编码版只是因为它就是控制台"复制"出来的样子，照抄不易错。

### 5.4 QoS 选 0

选 QoS 1 要多实现 PUBACK 确认和重传逻辑，对 2 秒一次的温湿度上报不值得。

**代价**：所以"发出去了"和"平台收到了"之间**没有任何协议层的保证** ——
这就是 [`SEND OK` 是本地回执](#63-send-ok-是本地回执不是平台回执) 的根源之一。

### 5.5 Keep Alive 会强制改变任务结构

`xQueueReceive(..., portMAX_DELAY)` 意味着队列一直没数据就永远不醒。
但 Keep Alive 要求**每 60 秒至少发一次报文**，否则服务器（OneNET 是 1.5 倍
Keep Alive，即 90 秒）会主动断开。

**必须改成带超时的等待**，超时取 Keep Alive 的**一半**：

```c
xQueueReceive(g_xDht11Queue, &dht,
              pdMS_TO_TICKS(CFG_MQTT_KEEPALIVE_S * 500))   /* 30 秒 */
```

留一半余量，这样即使某次心跳丢了，下一个周期还能补上，不会踩到 90 秒的线。

## 六、OneNET 平台层的坑

### 6.1 主题和 JSON 是配套的一对

**换主题必须同时换报文格式，只改一个等于没改。**

| 产品类型 | 主题 | JSON |
|---|---|---|
| **物模型**（本项目） | `$sys/{产品ID}/{设备名}/thing/property/post` | `{"id":"1","version":"1.0","params":{"Temp":{"value":27.0}}}` |
| 数据流 | `$sys/{产品ID}/{设备名}/dp/post/json` | `{"datastreams":[{"id":"temp","datapoints":[{"value":27}]}]}` |

⚠️ 注意是 **`thing/property/post`**，**不是 `thing/event/property/post`** ——
后者是 OneNET 另一套接口，发过去平台不认。

⚠️ 主题**不对时平台不报错，直接断掉 TCP**。这就是那个"第一条上报成功、
后面全失败"现象的根源，详见 [6.3](#63-send-ok-是本地回执不是平台回执)。

### 6.2 属性名大小写敏感，必须和控制台一字不差

本产品的属性名是 **`Temp` / `Hum`**（首字母大写），不是 `temp` / `humi`。

**必须去控制台的"功能定义"页核对。** 名字对不上平台不收数据，
而且**不一定报错**。

还有一个细节：属性在平台上定义的是**浮点**类型，所以值要补 `.0`：

```c
"\"Temp\":{\"value\":%d.0}"      /* 27 → 27.0 */
```

DHT11 本身只给整数，补个 `.0` 两边都满足。**用 `%d.0` 而不是 `%f`** ——
不用把 float 版的 `printf` 链进来，省 flash。

### 6.3 `SEND OK` 是本地回执，不是平台回执

**这是最容易被骗的一处。**

```
ESP8266 收到 AT+CIPSEND  →  把字节塞进 TCP  →  回 "SEND OK"
                                                 ↑
                                    这只表示"我发出了"，仅此而已
```

**服务器的反应在后面。** 所以：

```c
if (MQTT_Publish(CFG_MQTT_PUB_TOPIC, payload))
    printf("[WiFi] uploaded: ...\r\n");    /* ← 这行不代表平台收下了！ */
```

**典型的骗局现场**：

```
[MQTT] CONNECTED - device is online now
[WiFi] uploaded: Temp 27 C, Humi 98%      ← 看着成功，其实是假的
（后面两条静默失败 —— 逐条的失败现在不打印了）
[WiFi] 3 failures in a row - link is dead, reconnecting    ← 平台早把连接踢了
```

> ⚠️ **日志文本变了，行为没变。** 逐条的失败现在**不打印**（`task_wifi.c:300-303`，
> 那句注释写的就是"不在这儿打印"：真断线时会连着打好几条，刷屏没意义），
> 只在退出上报循环时统一汇报一句
> `[WiFi] %u failures in a row - link is dead, reconnecting`（`task_wifi.c:322-323`）。
> **所以别因为串口变干净了就以为没问题** —— 判成功的标准还是去控制台看数据点。

**真实过程**：第一条 PUBLISH 发出去 → 平台不认这个主题 → **直接断掉 TCP** →
之后每一条 `AT+CIPSEND` 都被模块回 `ERROR` → 全失败。

而第一条的 `SEND OK` 是模块在平台翻脸**之前**回出来的。

> **判成功的唯一标准：控制台上出现数据点。**

### 6.4 `mqtts.heclouds.com` 里的 `s` **不代表加密**

**OneNET 的历史命名，坑过很多人。**

| 用途 | MQTTX 里选 | 域名 | 端口 |
|---|---|---|---|
| **本项目用这个** | `mqtt://` | `mqtts.heclouds.com` | **1883**（明文）|
| 不用 | `mqtts://` | `mqttstls.heclouds.com` | 8883（TLS）|

**判断明文还是加密，看「端口 + 协议头」，不是域名。**
加密的域名是 `mqttstls`（多一个 `tls`）。

**为什么不用 TLS**：TLS 握手要跑 RSA/ECC、要缓存证书链，而 ESP8266 可用堆
通常只有 40~50KB，还要留给自己跑 WiFi 协议栈。实测容易报 `0x6009 TLS config error`。

⚠️ **代价**：Token 会明文过网络。做 demo 可以接受，**要做产品必须回来上 TLS**。

### 6.5 同一个 Client ID 只能有一个在线

`Client ID = 设备名`。OneNET 同一个 Client ID **只允许一个连接**，
**谁后连上谁就把对方踢下线**。

**调试时的直接后果**：

> **板子和 MQTTX 都用 `test1`。所以测板子之前必须先把 MQTTX 断开。**

否则：板子刚连上 → 你点开 MQTTX 连接 → 板子被踢 → 上报开始连续失败
（逐条不打日志，大约 6 秒后才打一句 `link is dead, reconnecting`）。
你会以为是板子的问题，其实是自己把它踢了。

### 6.6 端点和账号版本要对上

OneNET 有新旧两套，**凭据格式完全不同**：

| | Client ID | 用户名 | 密码 |
|---|---|---|---|
| **新版 Studio**（本项目） | 设备名称 | 产品 ID | Token |
| 旧版多协议 | 设备 ID | （空）| APIKey |

**搞混了必然连不上，而且报的还是那个模糊的 `code 4`。**

## 七、排查决策树

按**层次**从下往上查，**每一层都有明确的成功标志**，不要跳步：

```
① 模块活着吗？
   AT  →  OK ?
   ✗ 查供电（3.3V 带载会不会塌）、TX/RX 有没有接反、波特率

② 热点在跟前吗？
   AT+CWLAP  →  名单里有目标 SSID 吗？
   ✗ 热点关了 / 走远了 / 模块天线有问题
   ✓ 但 CWJAP 还是失败  →  ⚠️ 先翻热点的黑名单！（见 3.1）

③ 关联上了吗？
   AT+CWJAP  →  OK / WIFI GOT IP ?
   ✗ 先发 AT+CWQAP 清残留关联，再确认 AT+CWAUTOCONN=0（见 3.3）

④ TCP 通了吗？
   AT+CIPSTART="TCP","mqtts.heclouds.com",1883  →  CONNECT ?
   ✗ DNS Fail → 域名写错 / 没通外网
     ERROR    → 端口错 / 被防火墙挡了

⑤ MQTT 会话建起来了吗？
   CONNACK 第 4 字节  →  0x00 ?
   ✗ code 4 → ⚠️ 先拿这串 Token 去 MQTTX 复现（见 1.2）
              能复现 = 凭据问题（查 et 是不是 10 位）；不能复现 = 报文拼装问题

⑥ 数据上去了吗？
   ⚠️ 不看 SEND OK，不看"设备在线" —— 去控制台看有没有数据点
   ✗ 查主题和 JSON 格式是否配套（见 6.1）、属性名大小写（见 6.2）
```

**核心原则：每一层验过再往上走。** 跳步的结果就是被上层那个含义模糊的报错
带偏，然后在错误的方向上查半天。

**关于 1**：重连的实现是给 `TaskWifi` 套了一层外层循环 ——
连不上就一直重试，连上之后连续失败 3 次就退回去重跑 `WifiConnect()`。
用**连续**计数（成功一次归零）而不是累计计数，偶发抖动不会触发重连。

拉 RST 引脚**硬复位模块**，所以模块卡死、socket 半开、WiFi 掉了，走一遍都能
回到干净状态（这也是 [4.1](#41-hal_uart_receive_dma-第二次调用返回-hal_busy) 那个坑必须修好的原因）。

**关于 3**：`WifiConnect()` / 上报循环期间是"一问一答"，服务器不会主动推数据，
所以现在触发不了。等真要做 MQTT 订阅（`AT+CIPSUB` / MQTT SUBSCRIBE）时，
先回来处理这一条。

## 九、一句话总结

**这一天踩的坑，没有一个在代码里，也一个都不在硬件上 —— 全是配置和平台侧的
字节不匹配。**

而它们之所以难查，是因为**每一层的报错都在说谎**：`code 4` 说密码错、`SEND OK`
说发送成功、"扫得到热点"说信号没问题。**照着报错查，只会越查越远。**

所以真正管用的不是"更仔细地看报错"，而是两个动作：

1. **拿同一串凭据去 PC 端复现** —— 一次操作就能把设备、代码、硬件全部排除
2. **只认最终结果** —— 中间的每一环说自己成功，都不算数，去控制台看数据点

这两条不只适用于 OneNET。**任何"嵌入式设备连云平台"的调试，都是这个套路。**
