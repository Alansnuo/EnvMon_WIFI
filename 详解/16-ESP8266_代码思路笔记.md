## 一、驱动在系统中的位置

ESP8266 不是"一个芯片"，而是一个**跑着固件的完整子系统**。我们写的驱动本质上是
一个"翻译官"：把 C 函数调用翻译成 AT 文本命令，再把模块回的文本解析成状态码。

```
        STM32F103                          ESP8266
   ┌─────────────────┐                ┌──────────────────┐
   │  APP/ 应用层    │                │                  │
   │  DHT11 采集     │                │   AT 固件        │
   │       ↓         │                │   (自带 TCP/IP   │
   │  esp8266.c 驱动 │                │    协议栈)       │
   │       ↓         │   UART2        │        ↓         │
   │   USART2 外设   │◄──────────────►│    WiFi 射频     │
   └─────────────────┘  PA2/PA3       └──────────────────┘
                        115200             ↓
                                     无线路由器 → 服务器
```

**关键认知**：TCP/IP 协议栈跑在 ESP8266 内部，不在 STM32 上。
所以 STM32 不需要 LWIP，只需要"发命令、等回复"。这决定了整个驱动的形态是
**请求-应答（request-response）**，而不是"组包-发送"。

## 二、核心设计模式：请求-应答

这是理解全部代码的钥匙。每一条 AT 命令都遵循同一个三段式：

```
① STM32 发命令      "AT+CWJAP=\"ssid\",\"pwd\"\r\n"
                              ↓
② ESP8266 执行      连接路由器（可能耗时数秒）
                              ↓
③ ESP8266 回结果    "WIFI CONNECTED\r\nWIFI GOT IP\r\n\r\nOK\r\n"
                              ↑
                    驱动在这里匹配 "OK" → 成功
```

**两条铁律：**

1. **每条命令都必须有超时**。ESP8266 可能因为信号差、密码错、模块死机而永远不回。
   没有超时，程序就永久卡死。
2. **发命令前必须清空接收缓冲区**。否则上一条命令的残留响应会串台，
   导致把上一条的 "OK" 误判成本次的成功。

这两条铁律直接对应代码里 `ESP8266_SendCmd()` 的两行：

```c
ESP8266_ClearRxBuf();                    // 铁律 2
...
ESP8266_WaitResponse(expected, timeout); // 铁律 1（timeout 参数）
```

## 三、代码分层

驱动分三层，依赖方向单向向下：

```
┌──────────────────────────────────────────────────────┐
│  业务接口层                                           │
│  ESP8266_ConnectWiFi()  ESP8266_TCPSend()            │
│  ESP8266_GetIPAddress() ...                          │
│  —— 知道具体 AT 指令怎么拼，知道要等什么响应          │
├──────────────────────────────────────────────────────┤
│  命令层                                               │
│  ESP8266_SendCmd()      ESP8266_WaitResponse()       │
│  —— 只知道"发一串字符、等一串字符"，不懂 AT 语义      │
├──────────────────────────────────────────────────────┤
│  收发层（HAL 库 + DMA）                              │
│  HAL_UART_Transmit()  HAL_UART_Receive_DMA()         │
│  —— 只知道字节；接收靠 DMA 环形缓冲区（见第八章）    │
└──────────────────────────────────────────────────────┘
```

> 收发层比以前多了一块：`HAL_UART_Receive_DMA()` 只挂一次，之后 DMA 在
> **环形模式**下自己把字节搬进内存，驱动靠 `__HAL_DMA_GET_COUNTER()` 问进度
> —— 这里已经没有 `HAL_UART_Receive()` 了（第八章细讲）。

**为什么这样分？**

`SendCmd` 完全不懂 AT 协议 —— 它不关心发的是 `AT+CWJAP` 还是 `AT+RST`，
只负责"发出去、等回来、超时报警"。AT 语义全部上浮到业务接口层。

好处：新增一条 AT 命令时，只需要在业务层加一个函数，**中间层一行都不用改**。
这就是为什么 `ESP8266_Test()`、`ESP8266_GetStatus()`、`ESP8266_TCPDisconnect()`
都只有一行 —— 它们只是给 `SendCmd` 传不同的字符串。

```c
ESP8266_Status ESP8266_Test(void)
{
    return ESP8266_SendCmd("AT\r\n", "OK", ESP8266_TIMEOUT);
}
```

## 四、几个关键设计决策

### 4.1 用"单缓冲 + strstr"而不是状态机

**两条路可选：**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 状态机 | 逐字节解析，识别 `\r\n` 分行，按行匹配 | 精确、省内存 | 代码复杂，AT 响应格式多变时难维护 |
| **单缓冲 + strstr** | 全部收进一个缓冲区，直接子串查找 | 极简单、直观 | 需要足够大的缓冲区 |

**选了后者**，理由：

- AT 响应格式不规整，同一个意思可能出现在不同位置（比如 `OK` 可能在一堆
  `WIFI CONNECTED` 中间）。子串查找天然容错。
- 代码量少一个数量级，调试时直接 `printf` 出缓冲区就能看到模块说了什么 ——
  **可调试性是嵌入式开发的第一生产力**。
- STM32F103C8 有 20KB RAM，512 字节缓冲区完全负担得起。

代价：缓冲区必须够大。所以 `ESP8266_RX_BUF_SIZE` 定为 512。

### 4.2 缓冲区末尾永远保留一个 `'\0'`

**问题**：`strstr()` 要求字符串以 `'\0'` 结尾。但串口收到的是**裸字节流**，
不含结尾符。如果直接对满缓冲区调 `strstr`，它会一直往后读，
读到栈上别的内容，轻则误判，重则硬件错误。

**方案**：`ESP8266_ClearRxBuf()` 用 `memset` 把**整个缓冲区清零**。
现在的实现要多做一步 —— 把 DMA 那边还没搬过来的字节也扔掉
（`esp8266.c:131`，为什么要扔两处见第八章）：

```c
void ESP8266_ClearRxBuf(void)
{
    /* 两处都要清, 语义才是"清空接收缓冲区":
     *   ① DMA 环形缓冲区里还没搬走的那部分
     *   ② 已经搬进 RxBuf 的那部分
     * 只清②的话, 下次 Drain 又会被①灌进来, 看起来就像"清了但没清干净". */
    ESP8266_RxDiscard();
    memset(ESP8266_RxBuf, 0, sizeof(ESP8266_RxBuf));
    ESP8266_RxLen = 0;
}
```

清零之后，只要写入位置不超过 `SIZE-1`，末尾那个字节**永远还是 `'\0'`**，
`strstr` 就永远安全。（`RxLen` 到 `SIZE-1` 就停，是 `ESP8266_RxDrain()`
里用 `ESP8266_RX_BUF_SIZE - 1 - ESP8266_RxLen` 算出"还剩多少空位"做到的。）

这就解释了为什么接收时判断的是 `ESP8266_RxLen >= ESP8266_RX_BUF_SIZE - 1`
而不是 `>= ESP8266_RX_BUF_SIZE` —— **那留出来的 1 个字节就是给 `'\0'` 的**。

### 4.3 判断顺序：先判响应，再判缓冲满

代码里有一段看起来可以随便调换顺序，其实不行（`esp8266.c:249`，这里的
`ESP8266_RxDrain()` 就是"把 DMA 的新字节搬进 `RxBuf`"，第八章细讲）：

```c
        if (ESP8266_RxDrain() > 0)
        {
            // 先判响应, 再判缓冲满。顺序不能反: 若最后一个字节恰好凑齐响应,
            // 先判满就会把成功误报成失败。
            // RxBuf 末尾恒为 '\0'(由 ClearRxBuf 清零, 且 RxLen 到 SIZE-1 就停),
            // strstr 不会越界。
            if (strstr((char *)ESP8266_RxBuf, expected) != NULL)
            {
                return ESP8266_OK;
            }

            // 检查是否收到错误响应
            if (strstr((char *)ESP8266_RxBuf, "ERROR") != NULL ||
                strstr((char *)ESP8266_RxBuf, "FAIL") != NULL)
            {
                return ESP8266_ERR_AT;
            }

            if (ESP8266_RxLen >= ESP8266_RX_BUF_SIZE - 1)
            {
                return ESP8266_ERR_BUF_FULL;
            }
```

**反例会怎样**：假如第 511 个字节恰好是 `"OK"` 里的 `'K'`，此刻
`RxLen` 正好等于 511（= SIZE-1），缓冲同时"满了"也同时"匹配成功"。
如果先判满，就会直接返回错误 —— **明明成功了却报失败**，而且这种 bug
只在特定长度下偶发，极难排查。

### 4.4 为什么要把 `WaitResponse` 单独抽出来

有的 AT 交互是**两步式**的，不能简单地"发一条、等一条"。
最典型的是发送 TCP 数据：

```
AT+CIPSEND=5\r\n       ← 第一步：告诉模块"我要发 5 字节"
       ↓
>                      ← 模块回一个 '>' 提示符，表示"可以发了"
       ↓
HELLO                  ← 第二步：把真正的数据发出去（这一步不是 AT 命令！）
       ↓
SEND OK                ← 模块确认
```

**难点**：第二步发的是**裸数据**，不是 AT 命令。数据发完后要等 `SEND OK`，
但此时**不能再发任何 AT 命令**。

原代码的写法是 `ESP8266_SendCmd("", "SEND OK", ...)` —— 传了个空串。
这能跑，但其实是**巧合**：`HAL_UART_Transmit()` 在 `Size == 0` 时直接返回
`HAL_ERROR`，根本没发东西。代码忽略了这个返回值，所以"碰巧"行为正确。

这属于**依赖未定义行为的巧合**，一旦 HAL 版本变化、或者有人加了返回值检查，
就会突然出错。所以把"只等、不发"这个语义显式抽成独立函数：

```c
ESP8266_Status ESP8266_WaitResponse(const char *expected, uint32_t timeout);
```

`SendCmd` 此时退化为"发 + 等"，`cmd` 为空时自动跳过发送。

### 4.5 超时为什么要分级

`.h` 里定义了**五个**不同用途的超时，不是随便定的（`esp8266.h:14`）：

| 常量 | 值 | 为什么是这个量级 |
|---|---|---|
| `ESP8266_TX_TIMEOUT` | 1 秒 | 只管"把命令串塞进串口"这半截，115200 波特率下几十字节是毫秒级的活，1 秒纯属兜底 |
| `ESP8266_TIMEOUT` | 5 秒 | 普通命令（AT、CWMODE、CIPSTATUS），模块本地执行，瞬间完成 |
| `ESP8266_TCP_TIMEOUT` | 10 秒 | 建立 TCP 连接要经过三次握手 + DNS，比本地命令慢 |
| `ESP8266_WIFI_TIMEOUT` | 15 秒 | **连接路由器最慢**，要扫描、认证、DHCP 拿 IP，信号差时可能十几秒 |
| `ESP8266_SCAN_TIMEOUT` | 15 秒 | 扫描周边热点（`AT+CWLAP`）要把所有信道过一遍，也慢 —— `ESP8266_ScanAP()`（`esp8266.c:417`）专用，只在排查时走 |

如果全用一个 5 秒超时，连 WiFi 会频繁误报超时 —— 尤其在信号弱的环境。
如果全用 15 秒，`AT` 命令失败时要白等 15 秒才发现。

**超时值本质上是"对最坏情况的估计"**，需要按操作类型区分。

### 4.6 缓冲区设为 static

```c
static uint8_t ESP8266_RxBuf[ESP8266_RX_BUF_SIZE];
static uint16_t ESP8266_RxLen = 0;
```

变量本身设为 `static`（文件作用域私有），但**对外仍然可用** —— 通过
`ESP8266_GetRxBuf()` 和 `ESP8266_GetRxBufLen()` 两个访问函数。

这是 C 语言里实现"私有成员"的常规手法：数据隐藏 + 受控访问。
好处是命名空间干净（不会和别的模块的 `RxBuf` 撞名），
而且以后想改内部结构（比如换成环形缓冲），只要访问函数签名不变，
外部代码一行都不用改。

这句话后来应验了：接收层改成 DMA 环形缓冲（`ESP8266_DmaBuf`）之后，
`ESP8266_RxBuf` 和两个访问函数的对外样子**一个字都没动** ——
`RxBuf` 的定位也没变，还是"给 `strstr` 搜的那块直线缓冲区"（见第八章）。

## 五、初始化流程

`ESP8266_Init()` 是一条**自适应流水线**：每一步都依赖上一步成功，
任何一步失败就立刻返回，不继续往下做。

```
  上电
   ↓
① 配置 RST 引脚为推挽输出（PB1）
   ↓
①.5 把 DMA 接收挂上（ESP8266_RxStart）   ← 必须在复位之前，见下面
   ↓
② 拉低 RST 100ms → 拉高 → 等 1000ms     ← 硬复位，确保从干净状态开始
   ↓
③ 发 "AT"，期待 "OK"                    ← 签到：模块活着吗？串口通吗？
   ↓
④ (可选) 发 "AT+RESTORE"，期待 "ready"  ← 恢复出厂，默认关（开关在 .h 里）
   ↓
⑤ 发 "ATE0"，期待 "OK"                  ← 关回显（必须在 RESTORE 之后）
   ↓
⑥ 发 "AT+CWAUTOCONN=0"，期待 "OK"       ← 关掉模块自己的自动重连
   ↓
  就绪
```

**几个设计要点：**

**为什么第 ①.5 步要在复位之前把 DMA 挂上？**（`esp8266.c:181`）
一旦挂上，从这一刻起不管 CPU 在忙什么（哪怕正在为 DHT11 关中断跑那 4ms
的位流），串口来的字节都由 DMA 搬进内存，一个都不会丢。
复位后 ESP8266 会吐一串启动日志，也能顺手收下来，后面的 `AT` 测试正好对上。

**为什么要硬复位？** 模块可能因为上次运行异常、或热插拔而处于未知状态。
拉低 RST 是唯一能保证"回到已知初始状态"的手段，比发 `AT+RST` 更可靠
（因为 `AT+RST` 依赖串口当前是通的，而硬复位不依赖）。

**为什么复位后等 1000ms？** ESP8266 上电要加载固件、初始化射频，
这段时间串口是没有响应的。不等的话，后面的 `AT` 必然超时。
（顺带一提：`ESP8266_Reset()` 里自己已经等过一个 1000ms 了，`Init` 里
又等了一个 —— 两次加起来约 2 秒，这也是 `task_wifi.c` 里说"每次重连
多花约 2 秒复位"的来源。）

**为什么要关回显（ATE0）？** 回显开着时，你发 `AT` 模块会先原样回一个 `AT`
再回 `OK`。这会让接收缓冲区里混进我们发出去的内容 —— 比如你发
`AT+CWJAP=...`，回显里就有这串字符，如果密码里恰好含 "OK"
就会**误判成功**。关掉回显可以让接收缓冲区只包含模块真正的回复。
放在 `AT+RESTORE` **之后**发，是因为恢复出厂会把回显重新打开
（`esp8266.c:212` 那句注释就是提醒这个顺序）。

**第 ④ 步的 RESTORE 是可选开关。** `ESP8266_FACTORY_RESET_ON_BOOT`
（`esp8266.h:30`）默认是 0。什么时候打开：**"以前连得上，现在同一套代码
连不上了"** —— 模块 flash 里存着上次连过的 AP，密码一改它就一直连不上。
⚠️ 用完记得改回 0，这条命令要好几秒，每次开机都做没必要。

**为什么要关掉自动重连（CWAUTOCONN=0）？**（`esp8266.c:230`）
模块 flash 里存着上次连过的 AP，而 `AT+CWAUTOCONN` 默认是 1 ——
一上电它自己就往那儿连。那个 AP 要是密码改了或者不在了，它就在后台
没完没了地重试，跟我们发的 `AT+CWJAP` **抢同一套射频状态**。
症状很有迷惑性：**扫描能扫到、信号满格，但 CWJAP 就是失败**，
而且响应里会先冒一条 `WIFI DISCONNECT` —— 那是它后台重连失败留下的。

**注意**：`AT+CWMODE` 和 `AT+CWJAP` 不在 `Init` 里，而是在
**`APP/task_wifi.c` 的 `WifiConnect()`** 里单独调用（`task_wifi.c:144` 和
`task_wifi.c:153`）—— main.c 里一次都没出现过 ESP8266 的函数。
这是**刻意的职责划分** —— `Init` 只负责"让模块可用"，
"连哪个 WiFi"属于业务配置，应该由应用决定。

## 六、数据发送流程（两步式）

`ESP8266_TCPSend()` 是驱动里唯一一个不用 `SendCmd` 一步到位的函数，
因为它对应的是上面 4.4 说的两步式交互：

```
ESP8266_TCPSend(data, len)
   │
   ├─ ① snprintf 拼出 "AT+CIPSEND=<len>\r\n"
   │     用 len 而不是数据本身，是为了让模块知道要收多少字节
   │
   ├─ ② SendCmd(..., ">", ESP8266_TIMEOUT)
   │     等 '>' 提示符 —— 这是"模块已准备好接收裸数据"的信号
   │
   ├─ ③ HAL_UART_Transmit(data, len)      ← 裸数据，不是 AT 命令
   │
   └─ ④ WaitResponse("SEND OK", ...)      ← 只等，不再发
```

**核心约束**：①②之间、③④之间**顺序不能乱**。
`>` 没等到就发数据，数据会被模块当成 AT 命令解析，直接报错。

## 七、当时提出的三个局限

> ⚠️ **本节结论未被采用，不要照着它改代码。**
> 下面这三个"局限"和它们的"改进方向"，是针对**更早那一版**驱动写的 ——
> 那时候 `ESP8266_WaitResponse()` 里是逐字节
> `HAL_UART_Receive(..., 1, 10)` 轮询。那套实现在本工程里已经不存在了：
> `HAL_UART_Receive()` 现在**一次都找不到**，接收全部走 DMA。
>
> 当时提的解法是"换成 `HAL_UARTEx_ReceiveToIdle_DMA` + IDLE 中断 +
> `HAL_UARTEx_RxEventCallback` + 信号量"。**实际采用的不是它** ——
> DMA 确实用上了，但走的是 **CIRCULAR 环形模式 + 轮询写指针**，
> 一个串口中断都没开（为什么这么选，见 `esp8266.c:26` 那段注释和第八章）。
> 所以本章保留下来当**历史记录**看：它说清了旧实现差在哪。
> 真实实现见[第八节](#八真实的接收架构dma-环形队列)和
> [详解/02-ESP8266接收架构与+IPD剥离](09-ESP8266接收架构与+IPD剥离.md)。

这套设计**适合简单场景**（偶尔上报一次传感器数据），但有明确的天花板：

### 7.1 接收是阻塞轮询，浪费 CPU

**（当时的实现）** `ESP8266_WaitResponse()` 每次调 `HAL_UART_Receive()`
只收 **1 个字节**，且空读时要等 10ms 才返回。收 512 字节要循环 512 次，
期间 CPU 完全被占住，什么也干不了。

**改进方向（提了，但没被采用）**：工程其实**已经为 USART2 配好了 DMA 接收**
（`usart.c` 里的 `hdma_usart2_rx`，DMA1_Channel6），但当时驱动完全没用它。
当时想改成 `HAL_UARTEx_ReceiveToIdle_DMA()` —— DMA 在后台收，
检测到串口空闲（IDLE）中断才通知 CPU 处理。

> **实际走的路**：DMA 用上了，但是**环形模式 + 轮询 `CNDTR` 写指针**，
> 不碰 IDLE 中断。为什么不碰、代价是什么，见[第八节](#八真实的接收架构dma-环形队列)。
> 有一点结论仍然成立：这不是"降一个数量级"的问题 —— 连 WiFi 那 15 秒里，
> 旧实现是 **CPU 接近 100% 空转**，现在至少不再被空转烧掉了。

### 7.2 阻塞式设计无法与 FreeRTOS 友好共存

**（当时的问题）** `HAL_Delay(1000)` 和轮询循环都会**独占 CPU**。
在 FreeRTOS 下，一个任务卡在 `HAL_Delay` 里，同优先级的其他任务就得不到执行。

**改进方向（提了两条，一条做到了、一条没走）**：

- ✅ `HAL_Delay` → `vTaskDelay`：**做到了**。驱动里现在**一个 `HAL_Delay`
  都没有**，全换成了 `BSP_DelayMs()` —— 裸机下它是 `HAL_Delay`，
  上了 FreeRTOS 就被 `APP/app_delay.c` 的强符号顶替成 `vTaskDelay`
  （机制见 `bsp_delay.h` 的注释），等待期间任务真的睡下、让出 CPU。
- ❌ 轮询等待 → 信号量 + `xSemaphoreTake`：**没有采用**。
  等待仍然是"同步等"，只是空读的每一轮都 `BSP_DelayMs(1)` 让一次 CPU
  （`esp8266.c:283`）。为什么不上中断和信号量，见第八章 8.2。

所以现在的情况是：别的任务不会被拖慢，但**发起 AT 命令的那个任务**
在 `AT+CWJAP` 那十几秒里确实一直卡在 `WaitResponse()` 里出不来。
对本项目够用 —— 联网阶段本来也没别的事要它做。

### 7.3 `+IPD` 主动上报没有处理

**（当时的情况）** TCP 模式下，服务器主动推来的数据会以
`+IPD,<长度>:<数据>` 的形式**不请自来**地出现在串口上。当时的驱动只在
"发完命令后"才读串口，所以这些主动上报的数据会被丢掉或误当成某条命令的响应。

**✅ 这条后来真解决了。** `ESP8266_TCPRecvRaw()`（`esp8266.c:605`）
已经实现了**完整的 `+IPD` 剥离状态机**，连"头被切成两半、跨两次收上来"
的情况都处理了 —— MQTT 层的 CONNACK / PINGRESP 全靠它。
怎么做到的见第八章 8.6，逐行原理见
[详解/02-ESP8266接收架构与+IPD剥离](09-ESP8266接收架构与+IPD剥离.md)。

> 当初说"这个改进方向和 7.1 是同一个方向"，其实**不是**：
> +IPD 能处理，靠的是"有东西一直在收字节"（DMA 环形缓冲），
> 不需要 IDLE 中断。剩下的那条风险写在第八章 8.8。

## 八、真实的接收架构（DMA 环形队列）

> ✅ 这一节讲**代码里真实存在**的接收架构，不是设想。
> 第七章那三个局限最后是这么解的：**DMA 开成环形 + 轮询写指针**，
> 从头到尾**没有开过任何一个会干活的串口中断**。
> 逐行原理见 [详解/02-ESP8266接收架构与+IPD剥离](09-ESP8266接收架构与+IPD剥离.md)；
> 当年那套"DMA + IDLE 中断 + 信号量"的方案存档在 8.9，看看就好，**别照抄**。

### 8.1 一张图：一条队列，两条消费路径

```
DMA1_Channel6 ──►  ESP8266_DmaBuf[256]（环形，永不停机）
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
      ESP8266_RxDrain()        ESP8266_RxPop()
      （搬进 RxBuf[512]）      （直接交给调用方）
              ▼                       ▼
   ESP8266_WaitResponse()    ESP8266_TCPRecvRaw()
   在 AT 文本里搜 OK          剥掉 +IPD → 交给 APP/mqtt.c
```

记住三件事，整个接收层就通了：**一个环形缓冲区、一个只进不退的写指针、
两个互斥的消费者**。

| 角色 | 代码 | 干什么 |
|---|---|---|
| 生产者 | DMA1_Channel6（`DMA_CIRCULAR`） | 只管往 `ESP8266_DmaBuf` 里写，永不停止 |
| 消费者 A | `ESP8266_WaitResponse()` | 等 AT 命令的**文本应答**，走 `RxDrain` → `RxBuf` |
| 消费者 B | `ESP8266_TCPRecvRaw()` | 收服务器发来的 **TCP 数据**，走 `RxPop` 直接给调用方 |

**为什么说这两个消费者"互斥"？** 因为同一时刻只有一条路径在收：
要么在"我说一句、模块答一句"（消费者 A），要么在"模块替服务器转话"
（消费者 B）。驱动里**没有任何锁** —— 靠的是**用的人不在同一时间用**：
`WaitResponse` 只在发完 AT 命令后调，`TCPRecvRaw` 只在 MQTT 报文的往返
期间调（`mqtt.c:164`、`mqtt.c:232`），两者都在同一个任务里顺序执行。

### 8.2 三个"为什么"

#### ① 为什么 DMA 要开成 CIRCULAR（环形）？

`usart.c:152` 里：`hdma_usart2_rx.Init.Mode = DMA_CIRCULAR;`

DMA 有两种模式：`NORMAL` 收满指定长度就停下、等谁来重新启动；
`CIRCULAR` 收满自动绕回开头接着收。**这里要的是"永不停机"** ——
AT 响应什么时候来不知道，服务器什么时候推数据也不知道，
不能给 DMA 留下"停下来"的机会。开成环形之后，
`HAL_UART_Receive_DMA()` 只在 `ESP8266_RxStart()` 里挂一次
（`esp8266.c:63`，`Init` 开头就调它），之后**到下一次重连为止都没人碰它** ——
重连时会先 `HAL_UART_DMAStop()` 再重开（`esp8266.c:59`，那行不能省，
理由见 `esp8266.c:46-58` 那段注释）。

代价是：环形缓冲区只有 256 字节，**如果连着一口气来 256 字节没人搬，
新数据就会绕回去把旧的盖掉**。115200 波特率下 256 字节 ≈ 22ms 就发完了，
所以这套设计隐含一条要求：**"至少每 20ms 得有人搬一次"**。
两个消费者都在超时循环里每 1ms 让一次 CPU，守的就是这个节奏
（`esp8266.c:33-35` 算过这笔账：1ms 只过来 11 个字节，256 有二十几倍余量）。

#### ② 为什么不用 IDLE 中断判"一帧收完了"？

这正是原第七章/第八章力推的方案，**最终没被采用**。
`esp8266.c:26` 那段注释写了理由，原文照抄：

> 为什么不用 IDLE 中断判"一帧收完了"?
>   那要多开一个 USART2 中断, 还得纠结"中断里能不能调 FromISR 的 RTOS API"
>   —— 一碰 RTOS, BSP 就破了"不认识 FreeRTOS"这条规矩(见 bsp_delay.h).
>   轮询的代价只是最多 1ms 的发现延迟, 而 AT 响应本身都是几十毫秒级的,
>   完全够用. 少一个中断, 少一堆麻烦.

翻译成人话，三条理由：

1. **BSP 层的规矩**：`BSP/` 下的驱动约定"不认识 FreeRTOS"（延时靠
   `BSP_DelayMs` 的弱/强符号顶替，见 `bsp_delay.h`）。一旦要在中断里
   调 `xSemaphoreGiveFromISR`，这条规矩就破了。
2. **权衡下来不划算**：轮询唯一的代价是最多 1ms 的发现延迟，
   而 AT 响应本身是几十毫秒级的 —— 省下这点时间没人看得见。
3. **少一个中断 = 少一类 bug**：中断优先级和 RTOS 优先级上限
   （`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`）的纠缠、
   中断里不能做的事……这些坑全都不用踩。

**注意这条跟"能不能处理 `+IPD`"没关系。** 只要有一个"永远在收"的 DMA，
数据就不会丢；判不判断"一帧收完"是另一回事 —— `+IPD` 是**按长度收**的，
根本不需要帧边界（见 8.6）。

#### ③ 为什么连 DMA 自己的中断也关掉？

`esp8266.c:74`：`__HAL_DMA_DISABLE_IT(ESP8266_UART.hdmarx, DMA_IT_TC);`

环形模式下，HAL 的"传输完成"回调本来也不干活
（`stm32f1xx_hal_uart.c:3047` 判了 `hdma->Instance->CCR & DMA_CCR_CIRC`，
是环形就直接跳过）。既然没活干，那这个中断就是纯浪费 ——
**我们靠轮询 `CNDTR` 知道进度，不需要任何中断来通知。**

补一句免得误会：`DMA1_Channel6_IRQn` 在 NVIC 里其实是**使能**的
（`dma.c:53`，优先级 5），`stm32f1xx_it.c:225` 里也有
`DMA1_Channel6_IRQHandler`。所以准确说法不是"没有中断"，
而是**没有任何中断会真正干活**。（`dma.c` 那段注释还写着
"给任务发信号量"——那是当年方案留下的说法，现在没有信号量了。）

### 8.3 写指针：`CNDTR` 就是现成的"写到哪了"

DMA 在环形模式下自己有一本账：`CNDTR`（剩余计数）随搬运递减，
绕回时自动重置。于是：

```
写指针 = 缓冲区大小 − CNDTR 剩余
```

`esp8266.c:82` 把这个式子包成了一个函数：

```c
static uint16_t ESP8266_RxHead(void)
{
    return (uint16_t)(ESP8266_DMA_BUF_SIZE -
                      __HAL_DMA_GET_COUNTER(ESP8266_UART.hdmarx));
}
```

**为什么这个式子成立？** 环形模式下 `CNDTR` 自己会回绕，
"搬了多少字节"和"写到哪个位置"就恒等了 —— 换成 `NORMAL` 模式，
收满之后 `CNDTR` 卡在 0，这个式子就废了（这也是必须用环形的第二个理由）。

**为什么读它不用加锁？** `CNDTR` 是单个 16 位寄存器，读一次就是原子的，
不会被 DMA 撕裂 —— 这点很关键：另一头 DMA 正在写内存，
我们这边绝不能读到一个"半截"的计数值。

### 8.4 三个搬运函数：读指针只有一条路能推

`ESP8266_RxPop()`（`esp8266.c:90`）是**唯一推进读指针 `ESP8266_DmaTail`
的地方**，别的函数都从它派生，各管一件事：

| 函数 | 位置 | 干什么 |
|---|---|---|
| `ESP8266_RxPop()` | `esp8266.c:90` | 从环形缓冲区取最多 `max` 字节交给调用方，返回实际取了多少（0 = 没新数据） |
| `ESP8266_RxDrain()` | `esp8266.c:112` | 把新字节搬进 `RxBuf`，给 `strstr` 搜 —— **消费者 A 专用** |
| `ESP8266_RxDiscard()` | `esp8266.c:123` | 把还没搬走的字节直接扔掉（清缓冲区用，免得为"扔"还先搬一遍） |

`ESP8266_RxDrain()` 里有一句注释值得抄下来（`esp8266.c:109`）：

> 空间不够时只搬得下多少算多少 —— 反正 WaitResponse 那边立刻会发现并
> 返回 ERR_BUF_FULL; 关键是读指针不能卡住, 卡住就永远追不上 DMA 了.

**"读指针不能卡住"是这套设计的死规矩**：环形缓冲区会绕圈，
读指针一旦落后超过一圈，还没读的数据就被 DMA 覆盖掉了。
所以宁可丢一点数据、报个错，也不让读指针停下来等。

### 8.5 `ClearRxBuf()` 为什么要清两处

第二章那条铁律 2 说"发命令前必须清空接收缓冲区"。用了 DMA 之后，
"清空"这个词变成了**两件事**（`esp8266.c:131`）：

```c
void ESP8266_ClearRxBuf(void)
{
    ESP8266_RxDiscard();                                /* ① DMA 环里还没搬走的 */
    memset(ESP8266_RxBuf, 0, sizeof(ESP8266_RxBuf));    /* ② 已经搬进 RxBuf 的 */
    ESP8266_RxLen = 0;
}
```

只清 ② 的话，下一次 `RxDrain` 又会把 ① 灌进来 —— 表现是"清了但没清干净"，
上一条命令的响应残渣照样能污染这一次的判断。**两处一起清，
"清空接收缓冲区"这个语义才完整。**

### 8.6 `+IPD` 是怎么被剥掉的

`ESP8266_TCPRecvRaw()`（`esp8266.c:605`）干的事：把串口上的
`+IPD,<len>:<payload>` 剥成裸 payload 交给上层。MQTT 层收到的
CONNACK / PINGRESP 就是这么来的（`mqtt.c:164` 等 CONNACK，
`mqtt.c:232` 等 PINGRESP）。

**为什么要留状态，不能"攒够一整包再剥"？**（`esp8266.c:565` 的注释解释了）

> 串口是流, 头有可能被分两次取出来: 头 7~11 字节, 115200 波特率下要
> 约 1ms 才发完, 正好跨过一次轮询。

所以状态机用两个变量接力：

| 变量 | 记什么 |
|---|---|
| `ESP8266_IpdHdr[12]` + `ESP8266_IpdHdrLen` | "头攒到哪了"，攒到 `':'` 才算完 |
| `ESP8266_IpdLeft` | "本包 payload 还欠多少字节" |

逐字节攒头时有几个细节，都是踩过才知道的：

- **遇到 `\r` 或 `\n` 就把头状态清零重来**（`esp8266.c:631`）——
  合法头里不可能有换行，但半截的头（比如模块复位时发了个 `+IPD` 就没下文了）
  不会一直占着状态，把后面真正的头挡在外面。
- **只认 `+` 开头**（`esp8266.c:642`）—— 模块在 `+IPD` 前面会先发一对
  `\r\n`，别把它当头的第一个字符攒进去，不然永远解析不出来；
  顺手也把 `CLOSED` 这类通知滤掉了。
- **攒满 12 字节还没见到 `':'` 就丢掉重来**（`esp8266.c:657`）。

**payload 是按长度盲取的，不做任何扫描** —— 所以 MQTT 数据里就算出现
`"+IPD,"` 字样，也不会被误判成包头。一次调用只交出一整包
（`esp8266.c:677`：一包收完就返回），半包、粘包交给上层按流处理。

### 8.7 对照第七章的三个局限，现在是什么状态

| 第七章说的 | 现在 |
|---|---|
| 7.1 接收是阻塞轮询，CPU 空转 | **不空转了**。字节由 DMA 搬；等待循环里没新数据就 `BSP_DelayMs(1)` 让出 CPU（`esp8266.c:283`）。代价：等待仍是"同步等"，发起命令的任务这几秒里出不来 |
| 7.1 空档期到达的数据直接丢 | **不丢了**。DMA 一直在收，哪怕 CPU 正在为 DHT11 关那 4ms 中断（`task_wifi.c:33` 记过这个坑） |
| 7.2 阻塞设计无法与 FreeRTOS 共存 | **解决了一半**。延时全换成 `BSP_DelayMs`（会让出 CPU）；"信号量"那条没用上，理由见 8.2 的② |
| 7.3 `+IPD` 没处理 | **已实现**，见 8.6 |

补一句旧实现到底为什么会丢字节：硬件层面叫**溢出错误
（ORE, Overrun Error）** —— USART 只有一个字节的接收寄存器，
里面的字节还没被 CPU 读走、下一个字节又到了，硬件只能**丢弃旧字节**
并置位 `ORE`。HAL 在忙等循环里还专门盯着它，一发现就中止本次接收
（`stm32f1xx_hal_uart.c:3202`）。这也是老笔记里
"一次 DMA 改造能全解决"的底气所在。

### 8.8 还剩下的一条风险：订阅推送会被 `WaitResponse` 卷走

这条**现在还没解决，只是暂时触发不了**，得记着：

收发两条路径虽然互斥，但**谁先抢到环形缓冲区是不受控的**。
在等 AT 应答的那段时间里（`WaitResponse` 正在把字节往 `RxBuf` 里搬、
拿 `strstr` 找 `OK`），如果服务器**主动推**数据过来，
那份数据会被当成 AT 文本一起卷进 `RxBuf` 搜掉 —— 然后就没了。

- 本项目只上报、不订阅，服务器没有"主动推"的机会，所以现在触发不了。
- **将来要做 MQTT 订阅（服务器主动下发指令），必须先改这里** ——
  要么让 `WaitResponse` 认得出 `+IPD` 并把它转交，要么改成"收完先存着、
  再交给上层分派"。

> **真正的解法不是"加个中断"。** 8.9 存档的那套方案解决的是
> "数据到了没人知道"，而这里缺的是"**这段数据是谁的**" ——
> 得让接收层先认出 `+IPD`、再决定交给谁，而不是让"搜 AT 文本"的路径
> 去抢同一批字节。**在那之前，接口上留个心比事后查三天强。**

### 8.9 未采用的方案存档：DMA + IDLE 中断 + 信号量

原第七、八章给的那套方案（`HAL_UARTEx_ReceiveToIdle_DMA()` +
IDLE 中断 + `HAL_UARTEx_RxEventCallback()` + 重新武装 + 信号量）
**一行都没有进代码**，代码骨架也不再抄在这里了（免得有人照着敲）。
这里只留两条**当年记下的、至今仍然有效**的信息，万一哪天要改回去：

**① USART2 全局中断根本没使能。** 这是当年记下的坑，现在依然如此：

| 中断 | `it.c` 里有处理函数吗 | NVIC 里使能了吗 |
|---|---|---|
| `DMA1_Channel6_IRQn` | ✅ 有（`stm32f1xx_it.c:225`） | ✅ 是，优先级 5（`dma.c:53`） |
| **`USART2_IRQn`** | ❌ **没有** | ❌ **没有**（`.ioc` 里也没勾） |

IDLE 中断走的是 `USART2_IRQHandler` 这条路，没使能就永远到不了 CPU，
现象是"DMA 在搬、但没人知道数据到了"，很容易怀疑到接线和波特率上。
真要改回去，勾 NVIC 请走 `.ioc`（CubeMX → USART2 → NVIC Settings），
别手改 `usart.c` / `it.c` —— 那两处会被 CubeMX 重新生成时覆盖。
优先级要 ≥ 5：能调 FreeRTOS `...FromISR` API 的中断，
优先级数值不能小于 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`（是 5）。

**② "重新武装"那一步现在不需要了 —— 这是老笔记里最容易照抄错的地方。**
当年写的是"本工程配的是 `DMA_NORMAL`，收到一条消息后整套机制自己关掉，
必须重新调一次 `HAL_UARTEx_ReceiveToIdle_DMA`"。**那个前提已经没了**：
`usart.c:152` 现在是 `DMA_CIRCULAR`，环形模式下 IDLE 不终止接收，
一次启动就不用管。

**结论：别照抄老方案。** 真要做异步接收，先看现有的环形缓冲实现
（[详解/02-ESP8266接收架构与+IPD剥离](09-ESP8266接收架构与+IPD剥离.md)），
在它上面加"通知"比推倒重来省事得多。

### 8.10 什么时候不需要这一套

**不要为了用 DMA 而用 DMA，也不要为了"高级"把环形缓冲区搞得更大。**
下面这些情况，旧那套逐字节轮询反而更省心：

| 情况 | 为什么轮询够用 |
|---|---|
| 数据量小、不频繁 | 一天发几条，CPU 占用无关紧要 |
| 单任务系统 | 没有别的任务会被拖慢 |
| 对实时性要求低 | 10ms 级的轮询粒度完全可接受 |
| **学习 / 验证阶段** | **轮询代码简单、好调试** —— 出问题直接 `printf` 看缓冲区 |
| RAM 紧张 | DMA 要多占一个缓冲区（本项目 20KB RAM，256B 尚可） |

**本项目的选择是"够用就好"**：
接收用上 DMA 是为了不丢字节（DHT11 关中断那 4ms 是真的会丢），
但**没有**顺手把中断、信号量、异步那一整套都加上 ——
因为 AT 响应是几十毫秒级的东西，1ms 的轮询延迟真的没人看得见。

**工程上最贵的从来不是写代码，是调试。**
代码复杂度每增加一点，调试成本就上升一截 —— 不要过早优化。

## 九、一句话总结

> 这套驱动把复杂的 AT 协议收敛成了一个统一模式：
> **"发一串字符，等一串字符，超时就放弃"**。
> 所有具体命令都只是这个模式的不同参数。
> 简单、可调试、够用 —— 也正因如此，它在需要高并发或低功耗时会碰到天花板。

唯一"长大"了的一块是**接收**：命令层以上还是上面这套请求-应答，
但底下那条 DMA 环形队列 + `+IPD` 剥离状态机（第八章）已经不算小了。
它换来的东西很实在 —— **哪怕 CPU 正在关中断跑 DHT11 的 4ms 位流，
串口来的字节也一个都不会丢。**

> 最后再说一遍：第七章那三个"局限"和它们的解法（DMA + IDLE 中断）
> **没有被采用**，真实实现是第八章那条路。老内容留着是当历史看的，
> 别照着它改代码。
