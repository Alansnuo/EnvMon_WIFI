## 4.1 这块代码要解决什么问题

### 一句话

**采集任务每 2 秒读一次 DHT11 丢进队列；通信任务从队列取数据，拼成 JSON
发到 OneNET —— 发不出去就重连，一直重连到成功为止。**

一个要**长期挂着**的环境监测设备，和"跑一次演示"的要求完全不同：

| 演示的要求 | 挂机的要求 |
|---|---|
| 连上就行 | **断了要能自己爬起来** |
| 数据发出去就行 | **发不出去不能把采集拖死** |
| 跑 5 分钟 | 跑几天，热点走远、手机休眠、来电话都得扛住 |

`task_wifi.c:224-226` 把这层认识写在了注释里：

> 对一个要长期挂着的环境监测设备这是致命的 —— 而本项目连的
> 还是**手机热点** (走远了、手机休眠、来电话都可能断), 断线是常态不是
> 意外, 必须能自己爬起来.

**"断线是常态"这个前提决定了整个结构**——所以才有一个专门的外层
`for(;;)` 循环用来重连（§4.3.3）。

### 三个必须分开的关注点

| 关注点 | 归谁 | 为什么不能混 |
|---|---|---|
| **拿数据**（读传感器） | `task_dht11.c` | 换传感器只改这个文件 |
| **发数据**（联网 + 上报） | `task_wifi.c` | 换平台只改这个文件 |
| **把两边接起来** | 队列 `g_xDht11Queue` | 两边互不知情，中间是数据不是函数调用 |

`task_dht11.c:9-11` 的边界声明：

```
职责边界:
  本任务只管"拿数据", 不管"往哪发" —— 数据丢进 g_xDht11Queue 就完事.
  发送逻辑是 task_wifi.c 的事. 这样换传感器 / 换上报方式互不影响.
```

**这条边界是靠"队列"而不是"函数调用"实现的**，这一点很重要：
如果是 `TaskDht11` 直接调 `MQTT_Publish`，那么**采集任务就会被网络超时卡住**
（`TCPSend` 最坏要 10 秒），采集周期立刻不准。

### 约束

| 约束 | 从哪来 | 影响 |
|---|---|---|
| **采集任务不能被网络拖住** | `xQueueSend` 超时必须给 0 | 队列满了**丢数据**，不是等（§4.5） |
| **收数据不能无限等** | 服务器 90 秒没收到报文就断 | `xQueueReceive` **必须带超时**（§4.3.4） |
| **任务栈很贵** | 512 字 = 2048 字节，从 10KB 堆里切 | 报文缓冲要放 `.bss`（[详解 03](10-mqtt报文拼装.md) §3.4） |
| **printf 不可重入** | 两个任务都在打 | 日志可能插花（[详解 01](08-启动流程与CubeMX初始化.md) §1.7.4） |
| **属性名大小写敏感** | OneNET 物模型 | 写错**平台不报错，直接断链** |

### 本文不讲什么

- MQTT 报文怎么拼、剩余长度怎么算 —— [详解 03](10-mqtt报文拼装.md)
- AT 指令怎么发、`+IPD` 怎么剥 —— [详解 02](09-ESP8266接收架构与+IPD剥离.md)
- 任务怎么建、优先级怎么排的道理 —— 《从零入门 02》
- OneNET 控制台怎么配 —— 《MQTT 接入笔记》

## 4.2 整体结构

### 两个任务 + 一条队列

```
App_Init()                        (调度器启动之前, app_main.c:48-72)
 │
 ├─ DHT11_Init()                  传感器初始化, 内部有 1 秒延时
 │      上电稳定要 1 秒, 放调度器前走掉更干净 (task_dht11.c:13-14 说明了理由)
 │
 ├─ xQueueCreate(4, 2)            ← g_xDht11Queue, 4 个槽, 每槽 2 字节
 │
 ├─ TaskWifiCreate()              优先级 3, 栈 512 字
 └─ TaskDht11Create()             优先级 2, 栈 256 字
        │
        └─ vTaskStartScheduler()  以后由调度器接管

────────────────────────── 以下在调度器里 ──────────────────────────

TaskDht11 (prio 2)                        TaskWifi (prio 3)
─────────────────                         ─────────────────
for (;;)                                  for (;;) ← 外层: "重连"
{                                         {
  DHT11_Read()  ← 关中断约 4ms              while (WifiConnect() == 0)
     │                                          vTaskDelay(5000)
  成功 → count++                             ← 阶段 1: 联网
     printf("[DHT11] #N ...")
     xQueueSend(q, &dht, 0) ──┐              failStreak = 0
        │                     │              while (failStreak < 3) ← 内层: 上报
        └─ 队列满 → 丢弃       │              {
          打 "sample dropped" │                xQueueReceive(q, &dht, 30s) ──┐
                              │                   │                        │
  vTaskDelay(2000)            │                有数据 → snprintf(JSON)     │
}                             │                       → MQTT_Publish()   ←─┘
                              │                超时   → MQTT_Ping()
                              ▼
                        g_xDht11Queue  (4 槽 × 2 字节 DHT11_Data)
                        [][][][]  满 4 个 = 8 秒的缓冲
```

**关键：两个任务之间只有队列这一个接触面。** 没有信号量、没有事件组、
没有全局标志位。队列本身就是唯一的同步原语——
它的"满"和"空"分别是两个任务的天然节流阀。

### 常量表

| 名字 | 值 | 定义在 | 含义 / 改了会怎样 |
|---|---|---|---|
| `APP_PRIO_WIFI` | **3** | `app_main.h:24` | 通信任务优先级（越高越优先） |
| `APP_PRIO_DHT11` | **2** | `app_main.h:25` | 采集任务优先级 |
| `APP_STACK_WIFI` | **512 字** = 2048 B | `app_main.h:33` | 通信任务栈。**从 FreeRTOS 堆里切** |
| `APP_STACK_DHT11` | **256 字** = 1024 B | `app_main.h:34` | 采集任务栈 |
| `APP_DHT11_PERIOD_MS` | **2000** | `app_main.h:37` | 采集周期。**DHT11 规定 ≥ 1 秒** |
| `APP_DHT11_QUEUE_LEN` | **4** | `app_main.h:45` | 队列长度 → **8 秒的缓冲深度**（§4.5 的关键数字） |
| `WIFI_RETRY_DELAY_MS` | 5000 | `task_wifi.c:54` | 联网失败后隔多久重试 |
| `WIFI_PING_INTERVAL_MS` | **30000** | `task_wifi.c:59` | `CFG_MQTT_KEEPALIVE_S * 500` = 60 × 500 |
| `WIFI_MAX_CONSEC_FAIL` | **3** | `task_wifi.c:69` | 连续失败几次就重连 |
| `CFG_MQTT_KEEPALIVE_S` | 60 | `app_config.h:69` | 服务器 1.5 倍（90 秒）没动静就断 |
| `CFG_MQTT_TIMEOUT_MS` | 10000 | `app_config.h:72` | 等 CONNACK / PINGRESP 的超时 |

> ⚠️ **`WIFI_PING_INTERVAL_MS = (CFG_MQTT_KEEPALIVE_S * 500)` 这个 `*500`**
> 极易看错。它不是"500 毫秒"，是**"秒 → 毫秒（×1000）再取一半"**，
> 也就是 Keep Alive 的一半 = **30 秒**。写成 `* 1000` 就是整整 60 秒——
> 那时候一旦队列空下来，**服务器会在 90 秒时断开，而设备刚好在 60 秒发一次心跳**，
> 只剩 30 秒余量，网络一抖就掉线。**别改这个 500。**

## 4.3 逐段详解

### 4.3.1 `WifiConnect()` —— 六件事，五处提前返回

`task_wifi.c:131-196`。这是一个**线性流水线**，每一步失败就立刻返回 0：

```c
static uint8_t WifiConnect(void)
{
    char ip[20];

    printf("Initializing ESP8266...\r\n");
    if (ESP8266_Init() != ESP8266_OK)
    {
        printf("ESP8266 Init Failed!\r\n");
        return 0;
    }
    printf("ESP8266 Initialized OK!\r\n");
    ...
```

**六件事的顺序和各自的失败后果：**

| # | 调用 | 成功标志（串口） | 失败时提前返回？ | 失败意味着 |
|---|---|---|---|---|
| 1 | `ESP8266_Init()` | `ESP8266 Initialized OK!` | ✅ **是** | 模块不响应：接线、供电、RST 脚 |
| 2 | `ESP8266_SetWiFiMode(STA)` | `WiFi Mode: STA` | ✅ 是 | 模块活着但不认这条命令 |
| 3 | `ESP8266_ConnectWiFi()` | `WiFi Connected!` | ✅ 是 | **热点问题**（密码 / 黑名单 / 不在跟前） |
| 4 | `ESP8266_GetIPAddress()` | `IP Address: 192.168.x.x` | ❌ **不是** | 只是拿不到 IP，不影响后续 |
| 5 | `ESP8266_TCPConnect()` | `TCP Connected!` | ✅ 是 | DNS / 端口 / 外网不通 |
| 6 | `MQTT_Connect()` | `[MQTT] CONNECTED - ...` | ✅ 是 | **鉴权**（Token / Client ID） |

**第 4 步是唯一的例外**（`task_wifi.c:163` 的注释）：

```c
    /* 取 IP 地址. 拿不到不算失败, 不影响后面的采集 */
    if (ESP8266_GetIPAddress(ip, sizeof(ip)) == ESP8266_OK)
    {
        printf("IP Address: %s\r\n", ip);
    }
    else
    {
        printf("Get IP Failed!\r\n");
    }
```

**为什么要留着它？** 它**纯粹是给人看的**——`IP Address` 那一行是判断
"WiFi 关联成功了吗"最直接的证据，比 `WiFi Connected!` 更硬
（IP 都有了说明 DHCP 也过了）。

**为什么允许它失败？** 因为 `AT+CIFSR` 这条命令在不同 ESP8266 固件版本上
输出格式不一样（v1.x 和 v2.x 差别很大），驱动做了兼容解析
（`esp8266.c:700` 的 `ESP8266_GetIPAddress`）——**解析失败不代表网络有问题**。
为了一个"给人看的"信息而中止整个连接流程，不值。

#### `ESP8266_Init()` 兼作"整模块硬复位"

这是整个恢复机制的核心。`task_wifi.c:233-239` 的注释：

```
这一段顺带就是"把模块整个复位": WifiConnect() 第一步是
ESP8266_Init(), 而 Init 里拉了 RST 引脚 (见 esp8266.c). 所以不管
模块是卡死了、socket 半开着、还是只是 WiFi 掉了, 走一遍这里都能
回到干净状态 —— 不用再写单独的清理代码.
```

**这是"一种药治三种病"的省事做法**：

| 故障 | 不清状态的话要做什么 | `ESP8266_Init()` 做什么 |
|---|---|---|
| WiFi 掉了 | 重新 `AT+CWJAP` | 硬复位 → 全部重来 |
| socket 半开 | `AT+CIPCLOSE` + `CIPSTART` | 同上 |
| 模块内部状态乱了（跑久了会） | **没有好办法** | 同上 |

**代价**是每次重连多花约 2 秒（复位延时 + 等模块启动）。
用 2 秒换"不用写清理代码"，对一个每 2 秒采一次数据的设备来说很划算——
反正重连期间数据本来也在丢（§4.5）。

> **为什么"模块跑久了内部会攒状态"是真的？** ESP8266 固件是
> 一个带 TCP/IP 协议栈的小操作系统，长期运行会累积 socket 状态、
> 内存碎片、半开连接。**定期整个复位反而更稳**——
> 这是很多商业设备"每天自动重启一次"的同一个理由。

#### 两个失败分支会打印模块的原始应答

```c
    if (ESP8266_ConnectWiFi(CFG_WIFI_SSID, CFG_WIFI_PASSWORD) != ESP8266_OK)
    {
        printf("WiFi Connect Failed! ESP8266 response:\r\n");
        printf("%s\r\n", (char *)ESP8266_GetRxBuf());
        /* 顺序不能反: 扫描会把 RxBuf 冲掉, 得先把原始应答打完 */
        WifiDiagScan(CFG_WIFI_SSID);
        return 0;
    }
```

`ESP8266_GetRxBuf()` 把驱动内部的 `RxBuf`（512 字节）暴露出来，
**直接当成字符串打出去**。这是"把模块自己说的话原封不动给用户看"——
比"翻译成人话"更有用，因为**翻译可能译错，原文不会说谎**。

**那句注释 `顺序不能反` 很重要**：`WifiDiagScan` 会发 `AT+CWLAP`，
那是一条新的 AT 命令，`SendCmd` 开头会 `ESP8266_ClearRxBuf()`
（[详解 02](09-ESP8266接收架构与+IPD剥离.md) §2.7 代价一）。
**先打印、后扫描**，否则打出来的是扫描的输出而不是失败的应答。

### 4.3.2 `WifiDiagScan()` —— 把"扫得到"和"连得上"分开

`task_wifi.c:97-126`。**只在 `ConnectWiFi` 失败的分支里跑**，
正常运行时一次都不执行（`CWLAP` 最坏要 **15 秒**——
`ESP8266_SCAN_TIMEOUT`，`esp8266.h:18`——不能进主流程）。

三类结论，分别对应三种病因：

| `ESP8266_ScanAP` 返回 | 打印 | 病因推断 |
|---|---|---|
| `ESP8266_OK`（名单里有） | `FOUND, RSSI = -XX dBm` + **原文** | **被拒绝了**，不是连不上 |
| `ESP8266_ERR_WIFI`（名单里没有） | `NOT in the scan list` | 热点关了 / 走远了 / 模块天线有问题 |
| 其他（扫描本身没应答） | `the scan itself got no answer` | **模块级问题，优先怀疑供电** |

**"扫得到但连不上"是本项目最坑的一条**，`task_wifi.c:84-90` 的注释直接点了名：

```
"扫得到但连不上"最容易看错 —— 它像模块坏了, 其实多半是热点**主动拒绝**。
已经踩过的坑, 按可能性排:
  1) 手机把这个板子拉黑了(MAC 黑名单 / "已阻止的设备")
  2) 热点客户端数满了, 或者开了"仅允许已添加的设备"
  3) 密码值不对
第 1 条最坑: 黑名单只拒绝关联, **不挡 beacon** —— 所以扫描照样扫得到、
信号还能满格。看到"满格却连不上"先翻热点的黑名单, 别怀疑模块。
```

**技术上为什么黑名单不挡 beacon**：WiFi 的 beacon 帧是 AP **广播**的
（SSID、信道、加密方式都在里面），任何在范围内的设备都能收到——
这就是"扫描"能列出热点列表的原理。而"关联"（association）是**点对点**的，
AP 可以在这一步拒绝特定的 MAC 地址。**两者是完全独立的机制**，
所以 MAC 黑名单对扫描结果**毫无影响**。

#### 为什么要把"模块看到的那一条原文"打出来

`task_wifi.c:92-94`：

```
还要把名单里那一条的**原文**打出来. 因为查名字用的是 strstr, 是子串
匹配 —— 热点真名比配置里长的话(比如后面多了个 "的iPhone"), 这里照样
报"找到了", 但 CWJAP 拿短名字是连不上的. 原文里才看得见真实全名.
```

**这是一个很细的坑**，值得展开：

`ESP8266_ScanAP(ssid, ...)` 内部用 `strstr` 在扫描结果里找 `ssid`。
如果配置里写的是 `MyPhone`，而热点真名是 `MyPhone的iPhone`：

- **扫描**：`strstr("...MyPhone的iPhone...", "MyPhone")` → **命中** → 报 `FOUND`
- **关联**：`AT+CWJAP="MyPhone","..."` → 名字**精确匹配**，找不到 → 失败

于是诊断报告说"找到了，是被拒绝的"，而**真相是名字写短了**——
按报告的结论去翻黑名单，会白翻。

**把原文打出来，全长一眼就看到了。** 所以那段打印里还有三句引导：

```c
            printf("[WiFi] Compare the name above with what CWJAP sends.\r\n");
            printf("[WiFi] If it is longer or differs, that IS the bug -\r\n");
            printf("[WiFi] the search here is substring, the join is exact.\r\n");
```

> **"the search here is substring, the join is exact"** —— 这一句是整个函数
> 最值钱的一句。它把"为什么诊断说找到了但连不上"这个矛盾解释完了。

### 4.3.3 外层循环 —— "重连"这件事本身

`task_wifi.c:219-249`：

```c
    for (;;)
    {
        while (WifiConnect() == 0)
        {
            printf("[WiFi] connect failed, retry in %d s\r\n",
                   WIFI_RETRY_DELAY_MS / 1000);
            vTaskDelay(pdMS_TO_TICKS(WIFI_RETRY_DELAY_MS));
        }
        printf("[WiFi] online, waiting for sensor data\r\n");
        ...
```

**外层 `for(;;)` 就是"重连"**。内层上报循环一旦判断链路死了就会退出，
**退回到这里，把联网流程整个重跑一遍**——包括 `ESP8266_Init()` 里的硬复位。

`task_wifi.c:222-226` 说明这一层是**后加的**：

```
以前没有这层: 连上之后要是断了, 上报循环会一直刷失败信息, 刷到手动
复位为止. 对一个要长期挂着的环境监测设备这是致命的
```

**"以前没有这层"**——这句话说明了一个设计演进的教训：
**"能连上"和"断了能自己好"是两个不同的需求**，第一个做完不会自动有第二个。

#### `vTaskDelay(5000)` 而不是 `HAL_Delay(5000)`

如果用 `HAL_Delay`，这 5 秒里 **CPU 会被这个任务占着空转**
（`HAL_Delay` 是忙等，[详解 01](08-启动流程与CubeMX初始化.md) §1.7.3）。
而 `vTaskDelay` 把任务挂起，**调度器立刻切去跑采集任务**。

**这就是"WiFi 任务优先级比采集高，但不会饿死采集"的原因**
（`task_wifi.c:28-31`）：

```
优先级说明: 本任务比采集任务高 (APP_PRIO_WIFI > APP_PRIO_DHT11),
  因为网络有超时约束, 晚一步就可能超时重传. 高优先级不会饿死采集 ——
  本任务绝大多数时间都阻塞在 vTaskDelay / xQueueReceive 上, 处于
  "阻塞态"而不是"就绪态", 调度器根本不看它.
```

**"就绪态"和"阻塞态"的区别是理解 FreeRTOS 调度的关键**：
调度器只在**就绪态**的任务里挑优先级最高的那个。
一个任务在 `vTaskDelay` 或 `xQueueReceive` 里等着时，**它不在就绪队列里**，
优先级再高也不参与竞争。

> **所以"高优先级任务不能让出 CPU 就饿死别人"这个担心是对的**——
> 防的办法不是降优先级，而是**让它该阻塞的时候真的阻塞**。
> `task_wifi.c` 里所有等待都是 `vTaskDelay` / `xQueueReceive`，
> 没有一处忙等。这就是它敢用优先级的底气。

### 4.3.4 内层循环 —— 上报与心跳

`task_wifi.c:258-320`。循环条件是**连续**失败计数：

```c
        failStreak = 0;
        while (failStreak < WIFI_MAX_CONSEC_FAIL)
        {
            if (xQueueReceive(g_xDht11Queue, &dht,
                              pdMS_TO_TICKS(WIFI_PING_INTERVAL_MS)) == pdPASS)
            {
                /* 有数据 → 拼 JSON → MQTT_Publish */
                ...
                if (MQTT_Publish(CFG_MQTT_PUB_TOPIC, payload))
                {
                    failStreak = 0;
                    ...
                }
                else
                {
                    failStreak++;
                }
            }
            else
            {
                /* 超时醒来 = 30 秒没数据 → 发心跳 */
                if (MQTT_Ping())
                {
                    failStreak = 0;
                    ...
                }
                else
                {
                    failStreak++;
                }
            }
        }
```

#### `xQueueReceive` 的超时就是心跳的节拍器

**这是整个循环结构里最巧的地方。** 超时值 = `WIFI_PING_INTERVAL_MS` = 30 秒，
而 30 秒 = Keep Alive 的一半。

于是同一个 `xQueueReceive` 调用**同时承担了两个职责**：

| 情况 | 返回 | 做什么 |
|---|---|---|
| 30 秒内有数据 | `pdPASS` | 上报数据（**顺带就满足了 Keep Alive**，不用发心跳） |
| 30 秒内没数据 | `pdMS_TO_TICKS` 超时 | **醒来发心跳** |

**"任何报文都会重置服务器那边的计时器"**——这是 MQTT 协议规定的：
Keep Alive 的意思是"**客户端承诺至少每隔这么久发点东西**"，
PUBLISH 和 PINGREQ 都算。

> ⚠️ **所以心跳不是"周期发"，是"没事干的时候才发"。**
> 数据流不断的话，**一次 `PINGREQ` 都不会发**——这很违反直觉，
> 但是对的。`task_wifi.c:308-309` 的注释写明了这一点。
>
> **为什么要这样而不是"每隔 30 秒无条件发一次心跳"？**
> 因为那是**多余的报文**（占带宽、占 ESP8266 的处理时间）。
> 用一个超时既实现了"等数据"又实现了"到点发心跳"，代码还更短。

**如果给 `portMAX_DELAY` 会怎样？** 队列一直空着的话，任务**永远醒不过来**，
服务器在 90 秒时把设备踢下线，而设备这边还在傻等队列——
**平台上显示"离线"，串口上什么都没有**。`task_wifi.c:259-262` 的注释
专门警告了这一点。

#### `failStreak` 用连续计数而不是累计

```c
        /* 退出条件写在 while 上: 连续失败到阈值就掉出去重连. 用**连续**计数
         * 而不是累计计数 —— 只要成功一次 failStreak 就归零, 所以偶发抖动
         * 不会触发重连, 只有"怎么试都不行"才会. */
```

**"连续"的威力**：假设每 10 次上报里有 1 次失败。累计计数的话，
30 次上报（60 秒）就会触发一次重连；连续计数的话，
**只要失败不同时发生，永远不触发**。

**这正是想要的行为**：单次失败可能只是网络抖了一下，
而重连要复位模块 + 重新关联 + 重走 MQTT，前后**十几秒到几十秒**。
**宁可多试两条，也别一惊一乍。**

#### 阈值 3 的来历

`task_wifi.c:66-68`：

```
3 怎么来的: 上报路径 2 秒一条, 3 次 = 6 秒就反应过来, 够快. 心跳路径
30 秒一次, 最长要 90 秒才触发 —— 但那条路只在采集停了才走得到, 正常
运行时队列里永远有数据, 轮不到它.
```

| 走哪条路 | 单次耗时 | × 3 = 发现断线要多久 |
|---|---|---|
| **上报**（队列有数据） | ~2 秒（队列节拍） | **约 6 秒** ✅ |
| **心跳**（队列空着） | ~30 秒（超时） | **约 90 秒** ⚠️ |

**心跳路径慢 15 倍**，但这个"慢"在正常运行时用不到——因为
DHT11 每 2 秒就投一条数据，队列基本上永远不空。

> **什么时候队列会空？** 三种：
> ① `TaskDht11` 挂了（`DHT11_Read` 一直失败，`task_dht11.c:64` 打 `Read Error!`）
> ② 传感器被拔了
> ③ 有人把 `APP_DHT11_PERIOD_MS` 改成比 30 秒还大
>
> 前两种情况下设备还是"活着"的（能发心跳、平台上显示在线），
> **只是没有数据**。这其实是合理的——链路是好的，坏的只是传感器。

#### `printf` 打出来的 `failStreak` 恒为 3

```c
        printf("[WiFi] %u failures in a row - link is dead, reconnecting\r\n",
               (unsigned)failStreak);
```

这一句在 `while` 循环**退出之后**执行。而它只在
`failStreak >= WIFI_MAX_CONSEC_FAIL` 时才退出循环，
**所以打出来的值永远是 3。**

**这个 `%u` 看起来在报告"失败了多少次"，实际是个常量。**
不是 bug（信息量没丢——"3 次"就是阈值本身），但**别指望它能显示"这次特别严重，失败了 7 次"**——不会的，到 3 就退出了。

#### 失败分支刻意不打印

```c
                else
                {
                    failStreak++;
                    /* 不在这儿打印: 真断线时会连着打好几条, 刷屏没意义.
                     * 结果统一由循环外面那句 "link is dead" 汇报. */
                }
```

**这个决定影响了排查方式**：《从零入门 06》§6.7 专门加了警告块，
因为老笔记里说"看 `upload FAILED` 刷屏"——**那行已经没有了**。

**排查思路不受影响**（还是"先关 MQTTX、再查主题、再查属性名"），
但**别再去找单条的失败日志**。看到 `link is dead, reconnecting`
就说明前面连着失败了 3 次。

### 4.3.5 上报路径 —— JSON 拼装

`task_wifi.c:285-290`：

```c
                (void)snprintf(payload, sizeof(payload),
                    "{\"id\":\"%lu\",\"version\":\"1.0\",\"params\":{"
                        "\"Temp\":{\"value\":%d.0},"
                        "\"Hum\":{\"value\":%d.0}"
                    "}}",
                    (unsigned long)(++msgId), dht.temperature, dht.humidity);
```

#### 五个容易写错的地方

| 细节 | 为什么 | 写错的后果 |
|---|---|---|
| **`Temp` / `Hum` 首字母大写** | 必须和控制台"功能定义"**一字不差，大小写敏感** | 平台**不报错，直接断链** |
| **`%d.0` 而不是 `%d`** | 属性在平台上定义是**浮点**类型 | 类型不符，平台不收 |
| **`\"` 转义** | C 字符串里的双引号 | 不转义编译不过（比较幸运） |
| **`%lu` + `(unsigned long)` 强转** | `msgId` 是 `uint32_t`，在 32 位下是 `unsigned int`，**用 `%lu` 就要显式转** | 格式串和参数类型不匹配，**在 AC5 下可能打出垃圾** |
| **`version":"1.0"`** | OneNET 物模型要求的固定字段 | 不收 |

#### ⚠️ 为什么不用 `%f`

`task_wifi.c:282-284` 的注释给的理由是**"省 flash"**：

```
值写成 "%d.0" 而不是用 %f: DHT11 本来只给整数, 但属性在平台上
定义的是**浮点**类型, 整数可能被判类型不符. 补个 .0
就同时满足两边, 又不用把 float 版 printf 链进来 (省 flash).
```

**"省 flash" 这个理由其实站不住**——本工程 Flash 只用了 19.2KB / 64KB
（[详解 01](08-启动流程与CubeMX初始化.md) §1.9），根本不缺。

**真正的原因是：MicroLIB 的 `printf` 根本没有浮点格式化。**
`%f` 在 MicroLIB 下**打不出东西**（不是"能打但占空间"）。

**所以这个写法不是优化，是必然。** 同一份逻辑在
[详解 01](08-启动流程与CubeMX初始化.md) §1.7.2 也讲了一遍。

#### `dht.temperature` 是 **`uint8_t`**

`BSP/dht11/dht11.h` 里：

```c
typedef struct
{
    uint8_t humidity;
    uint8_t temperature;
} DHT11_Data;
```

**DHT11 的小数位在驱动层就被丢掉了。** 传感器的完整数据是
"湿度整数 + 湿度小数 + 温度整数 + 温度小数 + 校验和"（《从零入门 05》§5.1），
但 DHT11 的小数部分**永远是 0**（这是芯片本身的精度限制，不是代码的问题），
所以驱动只保留了整数部分，结构体就 2 个字节。

**这也是队列元素只有 2 字节的原因**（`app_main.h:45` 附近）——
4 个槽才 8 字节。

> **以后换成 DHT22 / SHT30 这类有真实小数的传感器**：
> 结构体要改成 `float` 或 `int16_t`（×10 存），
> 而 `%f` **不能用**（MicroLIB），得写成 `%d.%d` 手动拆。

#### `(++msgId)` 会"跳号"

`msgId` 是 `task_wifi.c:214` 的 `static uint32_t msgId = 0;`，
自增发生在 `snprintf` 的参数求值里——**也就是在知道 `MQTT_Publish`
成不成功之前**。

所以一个上报失败也会消耗一个 id，平台上看到的 id 序列会有缺口。

**这有害吗？没有。** OneNET 用 `id` 做请求-响应配对和去重，
**缺口不影响任何一方**。真正要紧的是：

- ✅ **不能重复** —— `++msgId` 保证单调递增，不会重复
- ✅ **重连后不能归零** —— 它是 `static`，**不随重连重置**。
  如果哪天有人"清理"成局部变量，重连后 id 从 1 重新开始，
  平台可能把新消息当成旧的重复消息丢掉

> **一句话：跳号无害，归零致命。** 别把 `static` 去掉。

#### `payload[192]` 会不会溢出？

```c
    char       payload[192];            /* OneNET 物模型的 JSON 报文 */
```

当前 JSON 是 **80 字符**（`id` 1 位时），加 4 位 id 是 83。
**`snprintf` 保证不会写溢出**（它最多写 `sizeof(payload)-1` 个字符 + `'\0'`），
所以即使超了也只会**静默截断**。

**但截断的 JSON 是畸形的**，平台会拒收（而且可能直接断链）。
所以增加属性时**要同时加这个 192**。

**顺带一提：`(void)` 强转**——`snprintf` 返回的是"本来想写多少字节"，
调用方不用，加 `(void)` 显式忽略，避免编译器警告。

### 4.3.6 栈余量 —— `uxTaskGetStackHighWaterMark`

`task_wifi.c:251-256`：

```c
        printf("[WiFi] stack free = %lu words\r\n",
               (unsigned long)uxTaskGetStackHighWaterMark(NULL));
```

**`NULL` 表示"我自己"**（当前任务），返回的是**历史最低剩余量**——
也就是"这个任务曾经最深用到哪里"。

**单位是"字"，不是字节**（1 字 = 4 字节）。所以日志里的
`stack free = 370 words` 意思是 **370 × 4 = 1480 字节还没用**，
而任务栈总共 512 字 = 2048 字节 → **实际用掉 142 字 = 568 字节**。

**这个函数要开宏才能用**：`INCLUDE_uxTaskGetStackHighWaterMark = 1`
（`FreeRTOSConfig.h:688`，注释写着"查任务栈余量要用, 见适配笔记 3.5"）。

#### 怎么读这个数

| 打印值（字） | 判断 |
|---|---|
| > 100 | 宽裕 |
| 50 ~ 100 | 偏紧，加东西之前先算 |
| **< 50**（= 200 字节） | **危险**，立刻调大 `APP_STACK_WIFI` |

**为什么放在进上报循环之前打印**？`task_wifi.c:252-254` 的解释：

```
联网阶段是全场最吃栈的 (ESP8266 驱动里有 char cmd[128],
mqtt.c 里有拼包 + printf), 所以在进循环之前先报一次.
```

**关键：`uxTaskGetStackHighWaterMark` 读的是"历史最低"，
所以在联网阶段之后读，拿到的就是联网阶段那个最低点**——
正好是最想知道的那个数。（如果放在任务开头读，读到的还是 0 使用量。）

**打印时机很讲究**：这一句只在**每次联网成功之后**执行一次，
不会刷屏。注释最后写"调够了自己删掉这行"。

> **什么时候需要重新看这个数？**
> - 加新属性（JSON 变长，`snprintf` 内部缓冲要用更多栈）
> - 改 `MQTT_PKT_MAX`（[详解 03](10-mqtt报文拼装.md) §3.6）
> - 往 `WifiConnect` 里加新的 AT 命令
> - 改 `ESP8266_TX_BUF_SIZE`（`esp8266.h`，影响 `SendCmd` 里那个 `char cmd[128]`）

## 4.4 关键设计决策

### 决策一：用队列而不是直接函数调用

| | |
|---|---|
| **决策** | `TaskDht11` 只 `xQueueSend`，不知道数据去哪了 |
| **理由** | 网络操作最坏要 10 秒（`TCPSend` 两次 5 秒超时）。直接调用的话**采集周期会被网络拖得完全不准** |
| **不这么做** | 采集节奏被网络支配：连着失败几次，采集周期就从 2 秒变成 10 秒、20 秒……而 DHT11 恰恰要求**两次读取间隔 ≥ 1 秒**，时序乱了读数也不准 |

### 决策二：WiFi 优先级 (3) **高于** 采集 (2)

| | |
|---|---|
| **决策** | `app_main.h:24-25`：`APP_PRIO_WIFI = 3`，`APP_PRIO_DHT11 = 2` |
| **理由** | 网络有**超时约束**（`TCPSend` 等 5 秒、等 CONNACK 等 10 秒），慢一步就可能超时失败。采集只是周期采样，晚几毫秒完全无所谓 |
| **不这么做** | 采集优先的话，`DHT11_Read()` 那 4 毫秒关中断期间……其实**已经不影响串口了**（DMA 在搬，[详解 02](09-ESP8266接收架构与+IPD剥离.md) §2.1）。真正的代价是**网络响应变慢**，在高负载时更容易超时 |

> ⚠️ **《FreeRTOS 驱动适配笔记》§3.7 建议的是相反的优先级**
> （DHT11 = 4 > 通信 = 2）。那个建议是**在"串口还是逐字节轮询"的旧代码
> 前提下**给的——那时候确实得先保证采集不被网络打断，否则串口丢字节。
> **换成 DMA 之后这个前提没了**，优先级也跟着反了过来。
>
> 而且 `app_main.h:23` 的注释**正好指向那一节**（"详见《FreeRTOS驱动适配笔记》3.7"），
> 所以读注释的人会被引到一份结论相反的文档去。**两处都要改。**

### 决策三：`xQueueSend` 超时给 0（满了就丢）

| | |
|---|---|
| **决策** | `task_dht11.c:57` `xQueueSend(g_xDht11Queue, &dht, 0)` |
| **理由** | 采集任务是**生产者**。被消费者拖住就本末倒置了——消费者卡住时应该丢数据，而不是把生产者也卡住 |
| **不这么做** | 给个非零超时的话，队列满时采集任务会**停下来等**。那么"通信任务卡住"会传染成"采集也停了"——**一个故障变成两个**。给 `portMAX_DELAY` 更是会让采集任务彻底死等 |

**代价**：队列满时数据真丢了，而且**丢的是新数据**（不是覆盖旧的）。
`task_dht11.c:59` 会打 `[DHT11] queue full, sample dropped`。
这个代价在 §4.5 里算得很清楚。

### 决策四：`MQTT_Connect` 失败也算整个 `WifiConnect` 失败

| | |
|---|---|
| **决策** | `task_wifi.c:190-193`：`MQTT_Connect()` 返回 0 时 `return 0` |
| **理由** | TCP 通了只说明"电话拨通了"。**平台上那个"在线/离线"看的就是 MQTT 会话建没建起来**（`task_wifi.c:188-189` 的注释） |
| **不这么做** | TCP 通了就往下走的话，鉴权失败会被当成"连上了"——然后上报循环里每次 `Publish` 都失败，**3 次后重连，重连再"成功"，再失败**……陷入"看起来在重连但永远连不上"的循环，而且每轮都要花十几秒 |

**这条决策让失败**尽早**暴露**：鉴权问题在第 6 步就报出来
（`[MQTT] CONNACK refused: code 4, ...`），而不是等到第一次上报。

### 决策五：`vTaskDelay` 而不是 `HAL_Delay`（全部等待点）

| | |
|---|---|
| **决策** | `task_wifi.c:247` 重试延时、`:270` 队列接收；`task_dht11.c:70` 周期延时 |
| **理由** | `vTaskDelay` 把任务挂起，调度器切去跑别的；`HAL_Delay` 忙等占着 CPU |
| **不这么做** | WiFi 任务优先级 3 > 采集 2。用 `HAL_Delay(5000)` 的话，**这 5 秒里采集任务一次都跑不了**（高优先级任务占着 CPU 不让出）——采集周期直接变成 5 秒以上 |

> BSP 层用的是弱/强符号方案（`BSP/bsp_delay/` + `APP/app_delay.c`），
> 详见 [详解 01](08-启动流程与CubeMX初始化.md) §1.8 和 `app_delay.c` 的文件头。

### 决策六：重连 = 重跑整个 `WifiConnect`（含硬复位）

见 §4.3.1 末尾。核心是**用"多花 2 秒复位"换"不用写任何清理代码"**。

### 决策七：失败分支不打印，循环外统一汇报

| | |
|---|---|
| **决策** | `task_wifi.c:298-303` 失败时静默 |
| **理由** | 真断线时会连着失败好几条，每条都打就刷屏了，反而看不见关键信息 |
| **不这么做** | 串口被 `upload FAILED` 刷屏，`link is dead` 那句被淹没——**而那一句才是有信息的**（它说"连续 3 次了，我要重连了"） |

**代价**：调试时看不到"从第几条开始失败的"。
如果这个信息需要，可以改成"只在第一次失败时打一句"
（用 `failStreak == 1` 判断），既有信息又不刷屏。

## 4.5 已知局限与注意事项

| 局限 | 触发条件 | 现象 | 能自愈 | 修法 |
|---|---|---|---|---|
| **重连期间数据真丢** | `TaskWifi` 离开队列 > 8 秒 | `[DHT11] queue full` 刷屏 | 是（重连完就好） | 加大队列 / 减短重连耗时 |
| **重连后会先补发旧数据** | 队列里还有存货 | 平台上先出现 4 条旧读数 | 是 | 重连成功后先 `xQueueReset` |
| **心跳路径 90 秒才发现断线** | 采集停了 + 链路断了 | 平台上"在线但没数据" | 是（但慢） | 见下 |
| **`failStreak` 打印值恒为 3** | — | 日志信息量比看起来少 | — | 无（不是 bug） |
| **`msgId` 跳号** | 上报失败 | 平台上 id 不连续 | — | 无（无害） |
| **`payload[192]` 静默截断** | JSON 超过 191 字符 | 平台拒收 / 断链 | 否 | 加属性时一起加 |
| **`WiFi 密码` 明文在源码里** | — | 反编译可见 | — | 本规模不值得加密 |
| **`task_dht11.h:8` 注释过时** | 读注释的人 | 以为还有个启动任务 | — | 改注释 |
| **`app_main.h:12` 注释过时** | 同上 | 以为密码在 `task_wifi.h` | — | 改注释 |

### ⚠️ 展开说：「重连期间数据是延迟，不是丢失」**这句话是错的**

`task_wifi.c:241-242` 的原文：

```
这里卡住不影响采集: TaskDht11 是另一个独立任务, 照常每 2 秒采一次,
数据堆在队列里 (满了就丢). 所以重连期间数据是**延迟**, 不是丢失.
```

**前半句完全正确，后半句是错的。** 而且这句话**自己就自相矛盾**——
括号里那句"（满了就丢）"已经承认会丢，下一句又说"不是丢失"。

#### 算一下到底能撑多久

```
队列容量 = APP_DHT11_QUEUE_LEN = 4
采集周期 = APP_DHT11_PERIOD_MS = 2000 ms
        ↓
        4 × 2 秒 = 8 秒
```

**队列最多缓冲 8 秒。超过 8 秒，每 2 秒丢一条**，
并且 `task_dht11.c:59` 会打一句 `[DHT11] queue full, sample dropped`。

#### 而一次失败的 `WifiConnect` 要多久？

| 步骤 | 失败耗时上限 |
|---|---|
| `ESP8266_Init()`（复位 + 等 1 秒 + ATE0 + CWAUTOCONN） | 约 2 ~ 10 秒 |
| `ESP8266_SetWiFiMode()` | ≤ 5 秒 |
| `ESP8266_ConnectWiFi()`（CWQAP ≤ 5 s + **CWJAP ≤ 15 s**） | **≤ 20 秒** |
| `ESP8266_TCPConnect()`（CIPMUX ≤ 5 s + CIPSTART ≤ 10 s） | ≤ 15 秒 |
| `MQTT_Connect()`（`TCPSend` ≤ 10 s + 等 CONNACK 10 s） | ≤ 20 秒 |

**最常见的故障（WiFi 掉了）会在第 3 步失败**，累计约：

```
2 秒 (Init) + 5 秒 (Mode) + 5 秒 (CWQAP) + 15 秒 (CWJAP) ≈ 27 秒
```

**27 秒 ≈ 13 个采样周期，而队列只有 4 个槽。**
→ **约 9 条数据是真的丢了**，不是延迟。

这还只是**一次**失败的尝试。之后还有 `vTaskDelay(5000)`，
再失败一次就又是 27 秒——**每轮重连丢大约 13 条**。

#### 还有第二件事：重连后会先补发旧数据

重连成功后，队列里可能还囤着最多 **4 条、最老 8 秒前**的读数。
上报循环一进来就 `xQueueReceive`，**这些旧数据会先被发出去**。

对温湿度这种慢变量，8 秒前的读数和现在的差别不大，**实际影响很小**。
但从"数据正确性"的角度看，平台上前 4 条上报的**采集时刻和管理时刻对不上**。

#### 怎么修

| 方案 | 改动 | 代价 |
|---|---|---|
| **A. 改注释**（最小） | 把 `task_wifi.c:242` 改成"重连期间**会丢数据**——队列只有 4 个槽 = 8 秒" | 零成本，**建议至少做这个** |
| **B. 加大队列** | `APP_DHT11_QUEUE_LEN` 4 → 16（32 秒缓冲） | 多占 24 字节 RAM（`4 × 2 × 12` 约 100 字节含队列结构）。**能覆盖一次 CWJAP 超时** |
| **C. 重连后清队列** | 联网成功后 `xQueueReset(g_xDht11Queue)` | 不补发旧数据，但还是要丢 |
| **D. 缩短重连耗时** | 把 `ESP8266_WIFI_TIMEOUT` 从 15 秒降到 8 秒 | 网络慢时会误判失败 |

**方案的 B+C 组合是"该做的"**——队列加大到能覆盖一次重连，
重连成功后清掉存货只发新数据。但那需要先想清楚"到底允许多老的读数"
（一个环境监测设备，30 秒前的温度其实也还能用）。

> **本次只记录，未修改代码。** 但**注释必须改**——它现在会让人以为
> "不用管队列长度"，而下一次有人把 `WIFI_MAX_CONSEC_FAIL` 从 3 改成 10
> （重连更保守）时，丢的数据会**成倍增加**。

### 展开说：三处"启动任务"遗痕

`StartTask` 早就拆掉了（`app_main.c:30-33` 的注释说明了原因：它只是早期
为了让"联网成功后再建采集任务"而存在的，后来发现没必要），但**三个地方
的注释还留着它的影子**：

| 位置 | 现在说什么 | 实际是什么 |
|---|---|---|
| `task_dht11.h:8` | "由**启动任务**在联网成功后调用 (此时调度器已在跑)" | 现在是 `App_Init()` 直接调用，**在调度器启动之前** |
| `Core/Src/main.c:97` | `App_Init()` 内部是"DHT11 初始化 → 建数据队列 → **建启动任务**" | 现在是 `TaskWifiCreate()` / `TaskDht11Create()` 两个独立任务（`app_main.c:70-71`），**没有启动任务** |
| `app_main.h:12` | "WiFi 账号密码在 **task_wifi.h**" | 已经挪到 **`app_config.h:19-20`**（这条与"启动任务"无关，顺手一起记） |

这三处不影响功能，但会让读代码的人**找错地方**——
尤其前两条会让人以为"建任务是联网成功之后才发生的"，
从而误判启动顺序（真正的内容见 §4.3.3 和 `app_main.c` 的文件头）。

## 4.6 恢复路径全景表

这是本文最实用的一张表：**设备坏了会怎么自己好，要多久。**

| 故障 | 怎么被发现 | 发现耗时 | 恢复动作 | 总耗时 |
|---|---|---|---|---|
| **WiFi 掉了**（热点关了/走远） | 上报失败 ×3 | 约 6 秒 | 退外层 → `WifiConnect`（在第 3 步能连上就成功） | **6 秒 + 一遍联网（几秒~27 秒）** |
| **TCP 断了**（服务器断链） | 上报失败 ×3 | 约 6 秒 | 同上，`ESP8266_Init` 的硬复位会把 socket 清掉 | 同上 |
| **MQTT 会话被踢**（另一处用同 Client ID 登录） | 上报失败 ×3 或心跳失败 ×3 | 6 秒 / **90 秒** | 同上，重走 CONNECT | 同上 |
| **模块卡死**（跑久了内部状态乱） | 同上 | 6 秒 / 90 秒 | `ESP8266_Init()` **拉 RST 硬复位** | 同上 |
| **采集停了但链路好** | 心跳超时醒来 → 发 PING → **成功** | 每次 30 秒 | **不恢复**（链路没坏，只是没数据） | 永不 |
| **DMA 传输出错** | 上报一直超时 | 6 秒 / 90 秒 | 走上面的重连 → `RxStart()` 重挂 DMA | 同上（[详解 02](09-ESP8266接收架构与+IPD剥离.md) §2.8） |
| **开机就 WiFi 连不上** | 第一次 `WifiConnect` 失败 | 立即 | 外层 `while` 每 5 秒重试，**一直试** | 一直重试到好 |

### 三个"发现不了"的故障

这张表里**没有列**的，才是真需要人工介入的：

| 故障 | 为什么发现不了 | 表现 |
|---|---|---|
| **主题写错** | 平台**不报错，直接断 TCP**。而设备这边收到的 `SEND OK` 是 ESP8266 自己回的 | 第一条上报"成功"（`uploaded` 打了），后面全失败 → `link is dead` → 重连 → 循环 |
| **属性名大小写错** | 同上 | 同上 |
| **`MQTT_PKT_MAX` 不够**（主题+载荷 > 249） | `MQTT_Publish` 的四个失败分支**全部静默** | 同上（[详解 03](10-mqtt报文拼装.md) §3.3.6） |

**这三种的表现完全一样**：`link is dead, reconnecting` 循环，
平台上没有数据点。**分不清是哪一个，只能靠排查顺序**：

```
1. 先关 MQTTX（Client ID 冲突会不会是原因）
2. 拿同一串凭据去 MQTTX 连一遍（凭据对不对）
3. MQTTX 能连 → 用 MQTTX 往那个主题发一遍（主题对不对）
4. 都能 → 才是设备侧的问题（报文拼装 / 缓冲区）
```

**第 3 步是关键**：MQTTX 里手动往 `$sys/v9cSbzDFqr/test1/thing/property/post`
发一条 JSON，如果平台收到数据点了，说明主题是对的，
**那问题就在设备这侧的拼装或缓冲区**。

## 4.7 动手改这里

### 改上报周期

**改哪几行**：`app_main.h:37` 的 `APP_DHT11_PERIOD_MS`。

**连带要改的**：
- ⚠️ **不能小于 1000**。DHT11 自己的限制：两次读取间隔 ≥ 1 秒
  （`task_dht11.c` 引用、`从零入门 05` §5.2 讲了原因）
- 改大之后**队列的"8 秒缓冲"会跟着变**（§4.5 的账要重算）
- 改大到 30 秒以上，`xQueueReceive` 的超时会先触发 → **变成每次都发心跳**

**怎么验证**：串口看 `[DHT11] #N` 的时间间隔。

### 加一个新传感器（比如 BH1750 光照）

**照抄 `task_dht11.c` 建 `task_light.c`**，`task_light.c` 文件头已经列了步骤。

**关键决策是"数据通道怎么走"**，两种：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 另开一条队列** | `g_xLightQueue` | 两边都简单，互不影响 | 上报循环要改成**同时等两条队列**（`xQueueReceive` 只能等一条）→ 要么用**事件组**，要么轮询两条队列 |
| **B. 共用一条带来源标记的队列** | 结构体加个 `source` 字段 | 上报循环结构不变 | 队列元素变大；上报循环要 `switch (source)` 分派；两个传感器的**上报频率被绑在一起** |

`app_main.h:43-44` 说这个决定"等真要写的时候再定"。**倾向 A**：
队列语义清晰，`APP_DHT11_QUEUE_LEN` 那种参数可以各自调。
代价是要用**事件组**做"哪条队列有数据"的等待（`freertos/` 里有
`event_groups.c`，已经加进工程了）。

**连带要改的**：`App_Init()` 里加一句 `TaskLightCreate()`，
`app_main.h` 里加优先级和栈。

### 调任务栈大小

**改哪几行**：`app_main.h:33-34`。

**改大之前先看数**：串口那句 `[WiFi] stack free = N words`。
**N < 50 才需要改大。**

**改大之后必须重算 RAM**：任务栈是从 **FreeRTOS 堆（10240 字节）** 里切的，
不是从 `.bss`。[详解 01](08-启动流程与CubeMX初始化.md) §1.9 有完整账本。

```
APP_STACK_WIFI 512 字 = 2048 字节
APP_STACK_DHT11 256 字 = 1024 字节
合计 3072 字节, 占 FreeRTOS 堆的 30%
```

**改大到 1024 字**（WiFi）就吃掉 4096 字节 → 堆里只剩 6KB 给别的。
**如果 `xTaskCreate` 失败**，`task_wifi.c:204` 会打
`ERROR: xTaskCreate(WiFi) failed (heap too small?)` 然后进 `Error_Handler`
——那就是堆不够了。

**怎么验证**：改完重新烧录，看那句 `stack free` 有没有变大，
并确认没有出现 `xTaskCreate failed`。

### 调任务优先级

**改哪几行**：`app_main.h:24-25`。

**约束**（`app_main.h:15-19` 列了）：

```
configMAX_PRIORITIES = 5, 可用 0~4:
  4  → 定时器服务任务 (FreeRTOS 占用)
  3  → WiFi 任务
  2  → DHT11 采集任务
  0  → 空闲任务 (FreeRTOS 占用)
```

**所以能用的只有 1 和 2**（3 被 WiFi 占了，4 和 0 是系统的）。
把 DHT11 改成 1 就变成"低于所有任务"，一般没必要动。

### 让重连后不补发旧数据

**改哪几行**：`task_wifi.c:249` 之后（`printf("[WiFi] online, ...")` 之后）加一行：

```c
        xQueueReset(g_xDht11Queue);     /* 重连期间的积压已经过时, 丢掉 */
```

**连带要考虑的**：上面那条 `printf` 说的是 `online, waiting for sensor data`
——加了这行之后就真的只等新数据了。

**怎么验证**：断开热点 30 秒，再恢复热点。看平台上**恢复后的第一条**
是不是当前时间附近的读数（而不是 30 秒前的）。

### 改 Client ID / 换设备

**改哪几行**：`app_config.h:34`（`CFG_MQTT_CLIENT_ID`）
和 `:104`（主题里的设备名，**两处都要改**）。

**⚠️ 最容易忘的**：主题 `CFG_MQTT_PUB_TOPIC` 里**嵌着产品 ID 和设备名**：

```
$sys/v9cSbzDFqr/test1/thing/property/post
      └─产品ID─┘ └设备名┘
```

**只改 `CFG_MQTT_CLIENT_ID` 不改主题 → 主题和身份不匹配 → 平台静默断链。**
反过来说，`CFG_MQTT_USERNAME`（产品 ID）改的时候，主题里那一段也要跟着改。

**怎么验证**：**先在 MQTTX 上用新身份连一遍**（《从零入门 06》§6.6）。

### 工厂复位开关

**改哪一行**：`esp8266.h:30` 的 `ESP8266_FACTORY_RESET_ON_BOOT`（当前是 0）。

**改成 1 会怎样**：`ESP8266_Init()` 里会发 `AT+RESTORE`，
把模块恢复出厂设置（清掉保存的 WiFi、CWAUTOCONN 等）。

**什么时候用**：怀疑模块里存了**旧的 WiFi 凭据**导致行为诡异时。
**注意**：`AT+RESTORE` 会**清掉波特率设置**，如果模块被人改成过
非 115200，恢复出厂后反而连不上——那时候要手动用 `AT+UART` 改回来。

**平时保持 0**：每次开机都复位会给模块的 Flash 增加写入次数。

## 4.8 一句话总结

**采集任务每 2 秒读一次传感器丢进队列（满了就丢），通信任务先联网、
再一边从队列取数据上报、一边在没事干的时候发心跳，连续失败 3 次就
把整个联网流程重跑一遍——包括拉 RST 硬复位模块。**

三件最容易被误解的事：

1. **心眺不是周期发的，是"队列空着才发"的。** 数据流不断的话，
   一个 `PINGREQ` 都不发——而这是对的，
   因为 PUBLISH 也算"有动静"。
2. **`WIFI_PING_INTERVAL_MS = CFG_MQTT_KEEPALIVE_S * 500` 里的 `*500`
   是"取 Keep Alive 的一半"，别改成 `*1000`。**
3. **`task_wifi.c:242` 那句"重连期间数据是延迟，不是丢失"是错的。**
   队列只有 4 个槽 = **8 秒缓冲**，而一次失败的 `WifiConnect`
   要 **27 秒左右**——**每轮重连丢大约 13 条数据**。这句话必须改。
