## 4.1 MQTT 是什么 —— 不算命、不看视频

MQTT 是**物联网最常用的通信协议**。它跟 HTTP（网页用的）是平级的 ——
都是应用层协议，都跑在 TCP 之上。

打个比方：

```
HTTP 像"你去图书馆借书"：    你每次都要说"我要借这本书"，图书馆每次回答
MQTT 像"订报纸送到家"：      你订一次，以后报纸天天自己来
```

**MQTT 最大的特点**：
- 轻量：最小的报文只有 **2 个字节**（PINGREQ）
- 发布/订阅模式：发数据的人不关心谁收，收的人不关心谁发的
- 有 Keep Alive（心跳）机制，能发现断线

## 4.2 三个角色

```
┌──────┐  发布    ┌───────────┐  订阅    ┌──────┐
│设备  │─────────│  Broker  │─────────│  App  │
│(STM32)│  主题     │ (OneNET)  │  主题     │(手机)│
└──────┘         └───────────┘         └──────┘
```

- **设备**（Publisher）：发布消息的人，这里是 STM32
- **Broker**（消息代理/服务器）：中转站，这里是 OneNET
- **App**（订阅者）：收消息的人，可以是手机 App、控制台

设备发布消息时带着一个**主题**（Topic），Broker 把消息转发给所有订阅了这个主题的人。

## 4.3 本项目用的是哪种 MQTT

**MQTT 3.1.1，QoS 0，无订阅。**

- 版本 3.1.1：最通用的版本，几乎所有平台都支持
- QoS 0（最多发一次）：发了就不管了，服务器不确认。效率高但不可靠
- 无订阅：我们只上报，不收指令

**代价**：`SEND OK` 只代表 ESP8266 把数据发到了网络上，不代表 OneNET 收下了。
想确认只能去 OneNET 控制台看数据点。

## 4.4 MQTT 报文长什么样

MQTT 报文是**二进制**的，不是文本的（和 AT 指令不同）。

### CONNECT（建立连接）

这是设备发给服务器的第一条消息。逐字节拆解：

```
 字节位置    值          含义
 ──────────────────────────────────────────────
 [0]        0x10         报文类型: 0x10 = CONNECT
 [1]        0x9B        剩余长度 低7位=27, 高位续位=1
 [2]        0x01        剩余长度 续位=0, 实际值=155
 ── 可变头 ──
 [3-4]      0x00 0x04   "MQTT" 字符串长度 = 4
 [5-8]      4D 51 54 54  "MQTT"
 [9]        0x04        协议级别: 4 = MQTT 3.1.1
 [10]       0xC2        连接标志: 用户名(0x80)+密码(0x40)+清理会话(0x02)
 [11-12]    0x00 0x3C   Keep Alive = 60 秒
 ── 载荷 ──
 [13-14]    0x00 0x05   Client ID 长度 = 5
 [15-19]    74 65 73 74 31  "test1"
 [20-21]    0x00 0x0A   用户名长度 = 10
 [22-31]    76 39 63 53 62 7A 44 46 71 72  "v9cSbzDFqr"
 [32-33]    0x00 0x7C   密码长度 = 124
 [34-157]   <124 字节 Token>
 ──────────
 整包: 158 字节
```

> 这张表按 `app_config.h` 里那串 Token 的**实际长度 124 字节**算出来。跑起来时
> 串口会打 `[MQTT] CONNECT 158 bytes` —— **两个数字对不上就说明表抄错了**
> （或者 Token 换过了，那长度也会跟着变）。

**新手最容易犯错的地方：剩余长度（Remaining Length）**

剩余长度不是简单的第 2 字节。它的编码规则：

```c
// 每字节低 7 位是数据，最高位表示"后面还有"
// 155 的编码过程：
155 = 128 + 27
  低 7 位 = 27 = 0b 0011011  → 0x1B  最高位置1 → 0x9B  (表示后面还有)
  剩余   = 155 / 128 = 1       → 0x01  最高位置0       (表示结束了)
// 结果: 0x9B 0x01
```

> **如果你算错了剩余长度，服务器解析不出来，直接断开连接，而且不回任何报错。**
> 这是 MQTT 拼装里最容易踩的坑。

### PUBLISH（发数据）

```
[0]        0x30         报文类型: 0x30 = PUBLISH (QoS 0)
[1]        <剩余长度>
 ── 可变头 ──
[2-3]      0x00 len    主题长度
[4-...]    <主题>       字符串
 ── 载荷 ──
[...]      <数据>       JSON 字符串（payload）
```

QoS 0 没有报文标识符，主题后面直接就是载荷。

### PINGREQ（心跳保活）

```
[0]        0xC0         报文类型: 0xC0 = PINGREQ
[1]        0x00         剩余长度 = 0
```

就 2 个字节，MQTT 最短的报文。服务器收到后回 2 字节 `0xD0 0x00`。

## 4.5 OneNET 鉴权：Token 是怎么回事

**OneNET 不用用户名+密码登录，而是用 Token。** 这不是一串随机字符，
是用**设备密钥**算出来的签名。

Token 的格式：

```
version=2018-10-31
&res=products%2Fv9cSbzDFqr%2Fdevices%2Ftest1      ← 资源路径
&et=1821308308                                    ← 过期时间（Unix 秒）
&method=sha1                                       ← 签名算法
&sign=9Cyhm1fn76GI5cURLVvT6AV4XCg%3D              ← 签名
```

签名是怎么算出来的：

```
sign = base64( HMAC-SHA1( 设备密钥, "{et}\n{method}\n{res}\n{version}" ) )
     = base64( HMAC-SHA1( 密钥, "1821308308\nsha1\nproducts/...\n2018-10-31" ) )
```

**⚠️ 签名覆盖了 `et` / `method` / `res` / `version` 这四个字段。
四个里任何一个是手改的，sign 立刻失效。** 而平台只回一个含义模糊的
`CONNACK code 4`，看起来像密码错了。

本项目就栽在这上面：抄写时 `et` 多打了一个 1（18211308308 应该是
1821308308），sign 是对着正确的 et 算的，所以验签不过。

> **排查窍门**：et 是 Unix 时间戳（秒），**正常情况下永远是 10 位**。
> 11 位换算到两千年以后 —— 必是打错了。

## 4.6 MQTTX —— 你的调试利器

MQTTX 是 PC 上的 MQTT 客户端软件。**调试时一定要用它**。

### 怎么用 MQTTX 排查问题

1. 新建一条连接，填入：
   - Client ID: `test1`
   - 用户名: `v9cSbzDFqr`
   - 密码: （从 `app_config.h` 复制整串 Token）
   - 服务器: `mqtts.heclouds.com:1883`

2. 点"连接"

3. **连不上** → 凭据问题（查 et 位数、检查 Client ID/用户名有没有搞反）
   - MQTTX 连不上的，代码肯定连不上，**别去改固件**
4. **连得上** → 代码或硬件的问题

### ⚠️ 重要：Client ID 冲突

OneNET 同一时刻**一个 Client ID 只能有一个在线**。所以：
- MQTTX 和板子都用 `test1`
- **测板子之前必须断开 MQTTX**
- 否则板子连上 → MQTTX 再连 → 板子被踢 → 你以为是代码问题

## 4.7 代码中 MQTT 层的分工

`APP/mqtt.c` 只管**拼报文 + 等应答**，不管业务：

```c
uint8_t MQTT_Connect(void);      // 拼 CONNECT → 发 → 等 CONNACK
uint8_t MQTT_Publish(topic, payload);  // 拼 PUBLISH → 发
uint8_t MQTT_Ping(void);         // 拼 PINGREQ → 发 → 等 PINGRESP
```

`task_wifi.c` 做业务决策：
```c
if (xQueueReceive(...) == pdPASS)
{
    snprintf(payload, ..., "{\"Temp\":{\"value\":%d.0},...}");
    MQTT_Publish("$sys/v9cSbzDFqr/test1/thing/property/post", payload);
}
```

MQTT 层不知道温湿度是什么，JSON 长什么样也不关它的事。
它只知道"把这段字节填进 PUBLISH 报文发出去"。

## 4.8 主题和 JSON 是配套的一对

**换了产品类型，主题和 JSON 要一起换：**

| 产品类型 | 主题 | JSON |
|---|---|---|
| **物模型**（本项目） | `$sys/{产品ID}/{设备名}/thing/property/post` | `{"id":"1","version":"1.0","params":{"Temp":{"value":27.0}}}` |
| 数据流 | `$sys/{产品ID}/{设备名}/dp/post/json` | `{"datastreams":[{"id":"temp","datapoints":[{"value":27}]}]}` |

注意：属性名（Temp / Hum）**必须和控制台"功能定义"里的写法一字不差**，
大小写敏感。平台不收的时候**不会报错，直接断链**。

## 4.9 Keep Alive（心跳）

CONNECT 报文的 Keep Alive 字段 = 60 秒。服务器在 1.5 倍（90 秒）内
没收到任何报文就主动断开。

所以设备必须：
- 30 秒内没数据上报时，主动发 PINGREQ（Keep Alive 的一半）
- 收到 PINGRESP = 链路还活着
- 收不到 → 连续 3 次 → 判定断线 → 重连

> **这决定了任务结构**：`xQueueReceive` 不能设 `portMAX_DELAY`，
> 必须设超时，超时了就去发心跳。详见笔记②。
