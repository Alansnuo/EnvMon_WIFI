## 3.1 这块代码要解决什么问题

### 一句话

**把"我要发一条消息到某个主题"翻译成字节，把"收到的字节"翻译成"发生了什么"。**

`mqtt.h:9-14` 把边界写得很清楚：

```
职责边界: 本层只做"翻译" ——
    要发什么  → 翻译成字节
    收到字节  → 翻译成"发生了什么"
所以它不知道温湿度是什么, 也不知道 JSON 长什么样
```

**具体表现**：`MQTT_Publish(topic, payload)` 两个参数**都是字符串**，
`mqtt.c` 从头到尾**没有一次提到 `Temp` / `Hum` / JSON 关键字**。
那些在 `task_wifi.c:285-290`。换平台时改的是那边，这边一个字不用动。

### 三个必须解决的问题

| 问题 | 为什么难 | 在哪解决 |
|---|---|---|
| **剩余长度要写在长度之前** | 报文头里的"我还剩多少字节"是**先写**的，但那个值要**算完载荷才知道** | §3.5 `Mqtt_Wrap` |
| **剩余长度是变长编码** | 127 占 1 字节，128 就变 2 字节，16384 变 3 字节 | §3.4 `Mqtt_PutRemainingLen` |
| **收到半包怎么办** | 串口是流，4 字节的 CONNACK 可能分两次到 | §3.7 的 `while (rxLen < 4)` |

### 约束

| 约束 | 从哪来 | 影响 |
|---|---|---|
| **不能把 256 字节放栈上** | 任务栈只有 512 字（2048 B） | 拼装缓冲区必须是 `static` → **本文件不可重入**（§3.10） |
| **没有浮点 printf** | MicroLIB（[详解 01](08-启动流程与CubeMX初始化.md) §1.7.2） | 属性值只能拼成字符串，`mqtt.c` 完全不碰数值格式化 |
| **不知道底层是 TCP 还是别的** | 分层 | 但实际还是 `#include "esp8266.h"` —— 见 §3.11 |

### 本文不讲什么

- MQTT 协议本身（订阅、QoS 1/2、遗嘱、保留消息）—— 《从零入门 04》
- OneNET 的 Token 怎么算 —— 《从零入门 04》§4.5
- `ESP8266_TCPSend` / `TCPRecvRaw` 内部 —— [详解 02](09-ESP8266接收架构与+IPD剥离.md)
- JSON 长什么样、什么时候发 —— [详解 04](11-任务层-上报循环.md)

## 3.2 整体结构

### 数据流

```
task_wifi.c                        mqtt.c                        esp8266.c
────────────                       ──────                        ─────────
xQueueReceive()
  → snprintf(payload, JSON)
  → MQTT_Publish(topic, payload) ──┐
                                   │  Mqtt_PutString(topic)   ← 2字节长度 + 主题
                                   │  memcpy(payload)         ← 原样拷进去
                                   │  Mqtt_Wrap(..., 0x30)    ← 补固定头 + 挪位
                                   │        │
                                   │        ▼
                                   │  s_MqttTxBuf[256]  ←──── static, 全文件共用一个
                                   │        │
                                   └────────┴─→ ESP8266_TCPSend()  ──→ AT+CIPSEND
                                                                        + 裸数据

MQTT_Ping()  ──── 直接写 s_MqttTxBuf[0]=0xC0, [1]=0x00 ──┘

MQTT_Connect() ── 手写可变头 ─→ 三段载荷 ─→ Mqtt_Wrap(..., 0x10)
                     │
                     └─→ ESP8266_TCPRecvRaw(rx, 4) ←── 半包由 while 循环兜
                                                            (详解 02 §2.5.5)
```

**关键点：所有报文都经过同一个 `s_MqttTxBuf[256]`。**
这是"不可重入"的根源，也是"256 字节够不够"这个问题的唯一依据（§3.10）。

### 函数职责

| 函数 | 行号 | 对外 | 职责 |
|---|---|---|---|
| `Mqtt_PutString` | 40-51 | static | 写一个"2 字节长度 + 内容"的 MQTT 字符串 |
| `Mqtt_PutRemainingLen` | 55-69 | static | 写剩余长度（7 位续位编码），返回占了几字节 |
| `Mqtt_Wrap` | 73-92 | static | **补固定头 + 把 body 往前挪**，返回整包长度 |
| `Mqtt_ConnackReason` | 97-108 | static | 把 CONNACK 返回码翻成人话 |
| `MQTT_Connect` | 112-192 | ✅ | 拼 CONNECT → 发 → 等 CONNACK |
| `MQTT_Publish` | 194-217 | ✅ | 拼 PUBLISH → 发 |
| `MQTT_Ping` | 219-239 | ✅ | 拼 PINGREQ → 发 → 等 PINGRESP |

**四个 static 里，前三个是"拼包工具链"，第四个是"错误码字典"。**
对外只有三个函数，正好对应 MQTT 里三种"设备主动发起"的动作。

|---|---|---|---|

| 值 | 报文 | 方向 | 谁写的 |
|---|---|---|---|
| `0x10` | CONNECT | 设备→服务器 | `MQTT_Connect`（`mqtt.c:148`） |
| `0x20` | CONNACK | 服务器→设备 | 校验 `rx[0]`（`mqtt.c:176`） |
| `0x30` | PUBLISH (QoS 0) | 设备→服务器 | `MQTT_Publish`（`mqtt.c:211`） |

> 跑起来时串口会打 `[MQTT] CONNECT 158 bytes`，那是唯一的活口核对点。

## 3.3 逐段详解

### 3.3.1 `Mqtt_PutString()` —— 2 字节大端长度 + 内容

`mqtt.c:40-51`：

```c
static uint16_t Mqtt_PutString(uint8_t *dst, uint16_t room, const char *s)
{
    uint16_t n = (uint16_t)strlen(s);

    if ((uint32_t)n + 2U > (uint32_t)room) { return 0; }

    dst[0] = (uint8_t)(n >> 8);
    dst[1] = (uint8_t)(n & 0xFFU);
    memcpy(&dst[2], s, n);

    return (uint16_t)(n + 2);
}
```

**MQTT 里所有字符串都是"长度 + 内容"**（协议名、Client ID、用户名、密码、主题
全都是这个格式），长度是 **2 字节大端**（高字节在前）。

`n >> 8` 取高字节、`n & 0xFF` 取低字节 —— 这就是大端。**写成 `dst[0]=n & 0xFF`
就是小端，服务器会解析出完全不同的长度**，然后直接断链（而且不报错）。

#### 为什么"返回 0"能当错误码

`mqtt.c:38` 的注释解释了：

> 返回值含那 2 个字节; 装不下返回 0 (最短的合法返回值是 2, 所以 0 能当错误码).

**最短的合法字符串是空串**（`n = 0`），返回值是 `0 + 2 = 2`。
所以 `0` 是一个**不可能出现的正常返回值**，可以安全地当错误码用。

这是个很省事的设计：一个返回值同时表达"写了几字节"和"有没有成功"，
调用方只要 `if (n == 0)` 就行了。

#### 那个 `room` 检查

```c
    if ((uint32_t)n + 2U > (uint32_t)room) { return 0; }
```

**两边都强制转成 `uint32_t` 再比较**，这是防溢出的。

`n` 是 `uint16_t`，最大 65535，`n + 2` 在 `uint16_t` 下不会溢出。
但 `room` 也是 `uint16_t`，调用方传的是 `MQTT_PKT_MAX - pos`。
**如果 `pos > MQTT_PKT_MAX`（某个调用方算错了），`MQTT_PKT_MAX - pos` 会下溢出成
一个巨大的 `uint16_t`**——这个检查就形同虚设了。

转 `uint32_t` 之后，减法本身仍然是在 `uint16_t` 下算的（在调用方那边），
所以**这个转换其实防不住那一种溢出**。它真正防的是 `n + 2` 那一边。

> **所以：`room` 的正确性依赖调用方**。目前三处调用
> （`mqtt.c:133` / `:138` / `:143` / `:202`）都传的 `MQTT_PKT_MAX - pos`，
> 而 `pos` 只增不减、每次增加前都检查过，所以不会越界。
> **加新的字符串字段时，照抄这个模式，别自己算 room。**

### 3.3.2 `Mqtt_PutRemainingLen()` —— 7 位续位编码

`mqtt.c:55-69`：

```c
static uint8_t Mqtt_PutRemainingLen(uint8_t *dst, uint16_t len)
{
    uint8_t n = 0;
    uint8_t b;

    do
    {
        b   = (uint8_t)(len % 128U);
        len = (uint16_t)(len / 128U);
        if (len > 0) { b |= 0x80U; }
        dst[n++] = b;
    } while (len > 0);

    return n;
}
```

**规则**：每个字节**低 7 位**是数据，**最高位（0x80）表示"后面还有"**。
所以从 0 到 268435455 只需要 1 到 4 个字节。

#### 三个分界点

| 值 | 编码 | 几个字节 | 说明 |
|---|---|---|---|
| 0 ~ **127** | `7F` | 1 | 低 7 位装得下，最高位 0 |
| **128** ~ **16383** | `80 01` | 2 | 128 是第一个要 2 字节的值 |
| **16384** ~ 2097151 | `80 80 01` | 3 | 16384 = 128² 是第一个要 3 字节的值 |

用 **128** 走一遍循环：

```
第 1 轮: b = 128 % 128 = 0
         len = 128 / 128 = 1
         len > 0 → b |= 0x80 → b = 0x80
         dst[0] = 0x80

第 2 轮: b = 1 % 128 = 1
         len = 1 / 128 = 0
         len == 0 → 不加 0x80 → b = 0x01
         dst[1] = 0x01

len == 0 → 退出。返回 n = 2。
结果: 80 01  ✅
```

用 **155**（本项目 CONNECT 的实际值）走一遍：

```
155 % 128 = 27, 155 / 128 = 1 → b = 27 | 0x80 = 0x9B
1 % 128 = 1,   1 / 128 = 0    → b = 0x01
结果: 9B 01  ✅  和《从零入门 04》§4.4 算的一致
```

#### 为什么用 `do...while` 而不是 `while`

因为 **`len = 0` 也是一个合法输入**（PINGREQ 的剩余长度就是 0），
它必须编码成 `00`，占 **1 个字节**——不能输出 0 个字节。

`while (len > 0)` 的话，`len = 0` 时循环一次都不进，返回 `n = 0`，
报文就少了一个字节，固定头变成只有 1 字节。`do...while` 保证**至少写一次**。

> `MQTT_Ping` 里没用这个函数（它直接手写 `s_MqttTxBuf[1] = 0x00`），
> 因为 0 的编码就是 `00`，比较直白。**但如果你要加一个"载荷长度可能为 0"的新报文，
> 记得这个函数能正确处理。**

#### 参数是 `uint16_t`，所以最多 3 字节

MQTT 协议规定剩余长度最大 4 字节（28 位，约 256MB）。但这个函数的 `len` 是
`uint16_t`，最大 65535 → 最多编出 **3 字节**。

**这没问题**，因为 `MQTT_PKT_MAX = 256` 保证了 bodyLen ≤ 251。
但要注意 `Mqtt_Wrap` 里 `MQTT_BODY_OFFSET = 5` 是**按 4 字节留的**，
比实际需要多留 1 字节——这是保守设计，不是 bug（§3.4）。

### 3.3.3 `Mqtt_Wrap()` —— 全文件最巧的一处

`mqtt.c:73-92`：

```c
static uint16_t Mqtt_Wrap(uint16_t bodyLen, uint8_t type)
{
    uint8_t n;

    if ((uint32_t)MQTT_BODY_OFFSET + (uint32_t)bodyLen > (uint32_t)MQTT_PKT_MAX)
    {
        return 0;
    }

    n = Mqtt_PutRemainingLen(&s_MqttTxBuf[1], bodyLen);

    /* body 本来写在 MQTT_BODY_OFFSET 处, 而剩余长度实际只占 n 字节
     * (1 + n < MQTT_BODY_OFFSET), 所以整体往前挪.
     * 源和目的重叠, 必须用 memmove 不能用 memcpy. */
    memmove(&s_MqttTxBuf[1 + n], &s_MqttTxBuf[MQTT_BODY_OFFSET], bodyLen);

    s_MqttTxBuf[0] = type;

    return (uint16_t)(1 + n + bodyLen);
}
```

#### 问题：先有鸡还是先有蛋

MQTT 报文的**固定头**是 `[报文类型][剩余长度]`，而"剩余长度"的值 = **它后面的所有字节数**。

所以想写固定头，必须先知道 body 有多长；而 body 还没拼完，又不知道有多长。

**两种解法**：

| 解法 | 做法 | 代价 |
|---|---|---|
| A. 算两遍 | 先空跑一遍算出长度，写固定头，再拼一遍 | 长度计算的逻辑写两处，**两处不一致就是灾难** |
| B. **先拼后挪** | 把 body 拼在偏移 5 处，量出长度，再把固定头补到前面，body 往前挪 | 多几次内存搬动 |

本文件选了 **B**。`mqtt.c:8-13` 的文件头注释解释了理由：

> 挪这几下的代价, 换的是"长度只在一处算出来" —— 不会出现两处算得
> 不一致、服务器解析失败直接断开这种极难查的问题.

**这是个很值钱的取舍**：A 方案的 bug 症状是"服务器不回任何东西直接断链"
（和 Token 错了、主题错了长得一模一样），而且只在**某几个长度下**才发作
（比如只有 id 是 4 位数的时候算错）。B 方案多搬 ≤ 200 字节，
在 72MHz 的芯片上花不到 1 微秒。

#### 为什么偏移是 5

`MQTT_BODY_OFFSET = 5` = **1 字节报文类型 + 最多 4 字节剩余长度**。

MQTT 协议允许剩余长度最多占 **4 字节**，所以 5 是"照协议最坏情况留的"。

**但实际上最多只用 3 字节**（§3.3.2，因为参数是 `uint16_t`），
而且本项目 `MQTT_PKT_MAX = 256` 把 bodyLen 卡在 251 以下 → **实际永远只用 2 字节**。

所以那 1 个字节（偏移 5 和偏移 4 的差别）是白留的。
**留着是对的**——万一以后 `MQTT_PKT_MAX` 改成 4096，3 字节就出现了；
改成 2MB 的话 4 字节也出现了，而那时候偏移还是 5，不用改。

#### `memmove` 是必须的，不是"保险起见"

**这一点可以严格证明，不靠"可能重叠"这种含糊说法。**

设：
- **源**起点 = `MQTT_BODY_OFFSET` = **5**
- **目标**起点 = `1 + n`，其中 `n ∈ {1, 2, 3}` → 目标起点 **∈ {2, 3, 4}**
- 搬运长度 = `bodyLen`（真实报文里至少 10 字节）

所以 **目标起点永远小于源起点（≤ 4 < 5），而且两者距离最多 3 字节。**
只要 `bodyLen > 3`（永远成立），**源区域 `[5, 5+bodyLen)` 就有一部分落在
目标区域 `[1+n, 1+n+bodyLen)` 之内 —— 必然重叠。**

方向还是**向前**（目标在前、源在后）。`memcpy` 处理重叠是**未定义行为**，
AC5 的实现通常会按"从前向后"整字拷贝——
那样在目标位置**还没被覆盖之前**，源位置可能已经被前一轮的字写入改掉了，
结果是**搬过去的数据带着自己的一部分**，报文里出现重复片段。
服务器剩余长度解析失败，**直接断链，不回任何东西**。

**换成 `memcpy` 就是一个必然发作、但极难定位的 bug。**

#### 挪动的距离是**变化的**

这是这一节最值得记住的一点。看 `n` 在不同报文里的值：

| 报文 | bodyLen | `n` | 目标起点 `1+n` | 挪动距离 `5-(1+n)` |
|---|---|---|---|---|
| CONNECT（155） | 155 | **2** | 3 | **2** |
| PUBLISH，`id` 1 位（123） | 123 | **1** | 2 | **3** |
| PUBLISH，`id` 6 位（128） | 128 | **2** | 3 | **2** |

> 数字怎么来的：CONNECT 的 body = 10（可变头）+ 7（Client ID）+ 12（用户名）
> + 126（密码）= **155**。
> PUBLISH 的 body = 2 + 41（主题）+ JSON。
> JSON 用 `id="1"` 是 80 字符 → body = **123**；`id="4267"` 是 83 → 126；
> `id="426712"` 是 85 → **128** → 刚好跨过 127/128 那条线，`n` 从 1 变 2。

**所以"往前挪几个字节"是运行期才知道的**——这就是为什么必须先
`Mqtt_PutRemainingLen` 算出 `n`，再用 `memmove(dst = 1+n)` 挪。
**写死"挪 2 个字节"在 `msgId` 涨到 6 位数（连续跑约 55 小时后）就会开始出错。**

> 这条边界是活的：`msgId` 从 1 开始，每 2 秒 +1。到 100000 需要 200000 秒 ≈ 55.5 小时。
> 也就是说**设备连续跑两天多，报文长度就会跨过那条线**。
> 代码正确处理了它（因为 `n` 是算出来的），但这个细节值得知道——
> 如果哪天有人"优化"成写死的偏移，bug 会在**运行两天后**才出现。

### 3.3.4 `Mqtt_ConnackReason()` —— 唯一把错误码翻成人话的地方

`mqtt.c:97-108`：

```c
static const char *Mqtt_ConnackReason(uint8_t code)
{
    switch (code)
    {
        case 0x01: return "unacceptable protocol version (need 3.1.1, level=4)";
        case 0x02: return "client id rejected";
        case 0x03: return "server unavailable";
        case 0x04: return "bad username or password (Token expired?)";
        case 0x05: return "not authorized";
        default:   return "unknown";
    }
}
```

**返回值是 `const char *` 指向字符串字面量**——不占 `.bss`、不占栈，
放在 Flash 的只读区。这是嵌入式里处理"错误码 → 描述"的标准做法。

**所有字符串都是纯英文**——不是风格问题，是**硬约束**：

> ⚠️ AC5（ARM Compiler V5）**按 GBK 读源文件**。字符串字面量里写中文会触发
> `warning #870-D`，而且更麻烦的是——**这些字符串会通过 `printf` 打到串口**，
> 而串口助手按 UTF-8 显示时会变乱码（`濂堜綍…` 那种）。
> **本工程所有 `printf` 的格式串和内容串必须全英文。**

#### 这个函数为什么值钱

全项目**唯一**一处把"平台的错误码"翻译成"人话"的地方。

它直接对应 `app_config.h:44-55` 记的那次事故：

```
本项目就栽在这上面 (2026-09-20): 抄写时 et 里多打了一个 '1' ——
1821308308 写成了 18211308308 —— 而 sign 是对着前者算的, 于是验签不过。
```

**当时的日志是什么？** 就是这一行（`mqtt.c:185-186`）：

```
[MQTT] CONNACK refused: code 4, bad username or password (Token expired?)
```

`code 4` 的字面意思是"用户名或密码错误"——**但密码一个字都没错**，
错的是 Token 里的 `et` 字段。**平台的报错在骗人**，
而这个函数把"最可能的原因（Token 过期）"括号里写出来了——这就是它的价值。

> **看到 `code 4` 的第一反应不该是"去改密码"**，而是：
> ① `et` 是不是 11 位（正常永远 10 位）→ ② Client ID / 用户名有没有搞反
> → ③ 拿同一串 Token 去 MQTTX 复现。
> 详见《从零入门 06》§6.7。

`0x01` 那条也值得留意：`unacceptable protocol version (need 3.1.1, level=4)`。
如果哪天 `mqtt.c:124` 的协议级别写错（比如写成 0x05 想"升级到 5.0"），
服务器回的就是这个码——**它会明确告诉你需要 level 4**。

### 3.3.5 `MQTT_Connect()` —— 三段拼装 + 等 CONNACK

`mqtt.c:112-192`。结构是**拼可变头 → 拼载荷三段 → Wrap → 发 → 等 4 字节**。

#### 可变头（`mqtt.c:119-128`）

```c
    s_MqttTxBuf[pos++] = 0x00;                  /* 协议名长度 高字节 */
    s_MqttTxBuf[pos++] = 0x04;                  /* 协议名长度 低字节 */
    memcpy(&s_MqttTxBuf[pos], "MQTT", 4);
    pos = (uint16_t)(pos + 4);

    s_MqttTxBuf[pos++] = 0x04;                  /* 协议级别 4 = MQTT 3.1.1 */
    s_MqttTxBuf[pos++] = 0x80U | 0x40U | 0x02U; /* 用户名 | 密码 | 清理会话 */

    s_MqttTxBuf[pos++] = (uint8_t)(CFG_MQTT_KEEPALIVE_S >> 8);
    s_MqttTxBuf[pos++] = (uint8_t)(CFG_MQTT_KEEPALIVE_S & 0xFF);
```

**协议名长度和大端**：`0x00 0x04` 是"长度 4"的大端写法。
`"MQTT"` 那 4 个字节直接用 `memcpy` 拷（**不是** `Mqtt_PutString`，
因为长度已经手写在前两行了）。

**协议级别 `0x04`**：4 = MQTT 3.1.1。**写 3 是 3.1（老版本），写 5 是 MQTT 5.0**。
OneNET 要 4。

**连接标志 `0x80 | 0x40 | 0x02 = 0xC2`** —— 展开成二进制：

```
位:  7 6 5 4 3 2 1 0
值:  1 1 0 0 0 1 0 0
     │ │       │ └── bit0 保留 (必须 0)
     │ │       └──── bit1 Clean Session = 1  ← 0x02
     │ └──────────── bit6 Password Flag = 1  ← 0x40
     └────────────── bit7 User Name Flag = 1 ← 0x80
```

**`Clean Session = 1`** 很重要：每次连接都要求服务器**丢弃上一次的会话状态**。
对本项目正合适——我们不订阅任何东西，没有要保留的状态。
**代价是每次掉线重连都要重走完整的 CONNECT 流程**，没有"续上"的可能。

**如果用 `Clean Session = 0`**：服务器会记住你订阅过什么，重连时能恢复。
**但那样 CONNACK 的第 3 个字节（会话标志）就可能返回 1**，
而下面那句检查要跟着改。本项目用 1，所以省了这层麻烦。

**Keep Alive 大端写入**：`CFG_MQTT_KEEPALIVE_S = 60` → `0x00 0x3C`。
**如果写成小端**（`0x3C 0x00`），服务器会认为 Keep Alive = 15360 秒，
于是**它 6 个多小时都不会断你**——测试时看起来"一切正常"，
但这个错误会掩盖真实的断链检测问题。

#### 载荷三段（`mqtt.c:130-146`）

```c
    /* --- 载荷. 三段顺序是 MQTT 规定死的:
     *     Client ID → Will Topic → Will Message → 用户名 → 密码
     *     我们没用遗嘱, 所以中间三段空着, 直接排 Client ID / 用户名 / 密码 --- */
    n = Mqtt_PutString(&s_MqttTxBuf[pos], (uint16_t)(MQTT_PKT_MAX - pos),
                       CFG_MQTT_CLIENT_ID);
    if (n == 0) { return 0; }
```

三段各调一次 `Mqtt_PutString`，**每段都检查 `n == 0`**。

顺序不是随便定的，是 MQTT 协议**规定死的**：
`Client ID → Will Topic → Will Message → 用户名 → 密码`。
**中间两段（遗嘱）因为标志位没置而省略**——服务器的解析器会根据
连接标志的 bit2（Will Flag）决定要不要读这两段。

**所以如果哪天加了遗嘱**：必须在 `0x02` 那个标志字节里加上 `| 0x04`，
然后**在 Client ID 和用户名之间插入两段**。只插载荷不加标志位，
服务器会把 Will Topic 当成用户名来解析——**鉴权失败，报 code 4**。

#### 等 CONNACK（`mqtt.c:159-188`）

```c
    while (rxLen < 4)
    {
        got = ESP8266_TCPRecvRaw(&rx[rxLen], (uint16_t)(sizeof(rx) - rxLen),
                                 CFG_MQTT_TIMEOUT_MS);
        if (got == 0)
        {
            printf("[MQTT] no CONNACK (timeout) - check Remaining Length\r\n");
            return 0;
        }
        rxLen = (uint16_t)(rxLen + got);
    }
```

**`while` 循环是为了兜半包。** `TCPRecvRaw` 返回 0 只代表"这次没拿到"，
不代表出错——它可能只拿回来 2 个字节（[详解 02](09-ESP8266接收架构与+IPD剥离.md) §2.5.5）。
**重复调用直到凑够 4 个字节**，这是驱动层契约的另一端。

> **`MQTT_Ping` 里的 `while (rxLen < 2)`（`mqtt.c:230`）是同一个套路。**
> **这两处和 `TCPRecvRaw` 的返回值语义必须一起理解**，改一边就要想另一边。

**超时了打的那句话指向哪里？** `check Remaining Length`：

服务器收到一个**长度字段算错**的 CONNECT 时，它**解析不出来，直接断开 TCP，
一个字节都不回**。所以"超时且没有任何回包"这个症状，
**最大的嫌疑是长度算错**，而不是网络不通（网络不通的话
`ESP8266_TCPConnect` 那步就失败了，根本走不到这里）。

**读懂这个区分很重要**：
- TCP 都连不上 → 网络 / 域名 / 端口问题
- TCP 连上了，但 CONNECT 发出去后**毫无回音** → 报文拼装问题（十有八九是长度）
- 有回音，但是 `20 02 00 04` → 鉴权问题

#### 三个校验（`mqtt.c:176-188`）

```c
    if (rx[0] != 0x20 || rx[1] != 0x02)
    {
        printf("[MQTT] unexpected reply %02X %02X (expected 20 02)\r\n",
               rx[0], rx[1]);
        return 0;
    }

    if (rx[3] != 0x00)
    {
        printf("[MQTT] CONNACK refused: code %u, %s\r\n",
               rx[3], Mqtt_ConnackReason(rx[3]));
        return 0;
    }
```

| 字节 | 检查 | 含义 |
|---|---|---|
| `rx[0]` | `== 0x20` | 报文类型必须是 CONNACK |
| `rx[1]` | `== 0x02` | 剩余长度必须是 2（CONNACK 固定就是 2） |
| `rx[2]` | **不检查** | 会话标志 |
| `rx[3]` | `== 0x00` | 返回码，0 = 接受 |

**`rx[2]` 故意不检查，理由很硬**：它是"Session Present"标志。
本项目 `Clean Session = 1`，**协议规定服务器必须把它置 0**。
检查一个恒为 0 的字节没有意义。

> **反过来说**：如果哪天把 Clean Session 改成 0（比如为了做订阅），
> **`rx[2]` 就变成有信息量的了**——0 表示"服务器没有你的旧会话，
> 你的订阅都没了，得重新订阅"；1 表示"会话还在，订阅还在"。
> 做订阅的时候必须检查它，否则会**收不到消息却不知道为什么**。

**`rx[2]` 那个字节没有名字**：代码里从头到尾没提它，只写了"会话标志"
在注释里。这是有意的——不检查的东西不配拥有变量名。

### 3.3.6 `MQTT_Publish()` —— 最短的一个，语义最容易误读

`mqtt.c:194-217`：

```c
uint8_t MQTT_Publish(const char *topic, const char *payload)
{
    uint16_t pos = MQTT_BODY_OFFSET;
    uint16_t plen, len, n;

    if (topic == NULL || payload == NULL) { return 0; }

    /* 可变头: QoS 0 没有报文标识符那 2 个字节, 主题后面直接就是载荷 */
    n = Mqtt_PutString(&s_MqttTxBuf[pos], (uint16_t)(MQTT_PKT_MAX - pos), topic);
    if (n == 0) { return 0; }
    pos = (uint16_t)(pos + n);

    plen = (uint16_t)strlen(payload);
    if ((uint32_t)pos + (uint32_t)plen > (uint32_t)MQTT_PKT_MAX) { return 0; }
    memcpy(&s_MqttTxBuf[pos], payload, plen);
    pos = (uint16_t)(pos + plen);

    len = Mqtt_Wrap((uint16_t)(pos - MQTT_BODY_OFFSET), 0x30);
    if (len == 0) { return 0; }

    /* QoS 0: "成功"只表示 ESP8266 回了 SEND OK, 平台收没收到不知道.
     * 要确认得去平台上看数据点. */
    return (ESP8266_TCPSend(s_MqttTxBuf, len) == ESP8266_OK) ? 1U : 0U;
}
```

#### QoS 0 的"可变头"只有主题

对比 CONNECT，这里少了两样东西：

| | CONNECT | PUBLISH (QoS 0) |
|---|---|---|
| 协议名 + 版本 | 有 | **没有** |
| 连接标志 / Keep Alive | 有 | **没有** |
| **报文标识符** | 没有 | **QoS 0 也没有** |

**QoS 1/2 的 PUBLISH 有个 2 字节"报文标识符"（Packet Identifier）**，
主题长度之后、载荷之前。**QoS 0 省略它**。

**如果错写成 QoS 1 的格式**（主题后面多写 2 字节）：
服务器会把那 2 字节的第一个字节当成 JSON 的第一个字符 `{`，
从此**整个载荷偏移 2 字节**，解析出一堆垃圾——而且**不会报错**，
只是平台上看不到数据点。

#### `payload` 不检查长度？其实检查了

注意 `payload` 走的是 `memcpy` 而不是 `Mqtt_PutString`——
因为**载荷不带长度前缀**（长度信息已经在固定头的剩余长度里了）。

但它**仍然检查了边界**：

```c
    if ((uint32_t)pos + (uint32_t)plen > (uint32_t)MQTT_PKT_MAX) { return 0; }
```

`pos` 是主题写完之后的位置（含那 5 字节偏移），`plen` 是载荷长度。
**加起来超过 256 就返回 0**，不写。

#### ⚠️ 四种失败都是**完全静默的**

`MQTT_Publish` 有 **4 个 `return 0`**，**一个 `printf` 都没有**：

| 失败点 | 原因 |
|---|---|
| `topic == NULL \|\| payload == NULL` | 调用方传了空指针 |
| `Mqtt_PutString` 返回 0 | **主题太长**，装不下 |
| `pos + plen > MQTT_PKT_MAX` | **载荷太长**，装不下 |
| `Mqtt_Wrap` 返回 0 | 整包容不下（同一个约束） |
| `TCPSend != ESP8266_OK` | 发送失败（这个在驱动层会打日志） |

而**上层也不打印**（`task_wifi.c:298-303` 刻意留空，理由见下面引的注释）：

```c
                else
                {
                    failStreak++;
                    /* 不在这儿打印: 真断线时会连着打好几条, 刷屏没意义.
                     * 结果统一由循环外面那句 "link is dead" 汇报. */
                }
```

**于是"主题太长 / 载荷太长"这个失败会造成**：
串口上**什么都没有**，只看到 `[WiFi] uploaded:` 那句**不再出现**了，
而重连日志**也不会出现**（因为 `failStreak` 会累加但……不，它会累加，
3 次之后就报 `link is dead` 并重连）。

所以症状是：**"设备不报错了，但一直在重连，平台上看不到数据"**。
去查会怀疑网络、怀疑平台——**实际是本地缓冲区装不下**。

#### 还剩多少余量

**约束是这一个式子**（三处检查其实是同一个）：

```
5 (偏移) + 2 (主题长度字段) + 主题长度 + 载荷长度  ≤  256
即：主题长度 + 载荷长度 ≤ 249
```

当前实际：

| 项 | 长度 | 来源 |
|---|---|---|
| 主题 | **41** | `CFG_MQTT_PUB_TOPIC`（`$sys/v9cSbzDFqr/test1/thing/property/post`） |
| 载荷（`id` 1 位） | **80** | `task_wifi.c:285-290` 的 JSON |
| 载荷（`id` 4 位） | 83 | `msgId` 涨到 1000 之后 |
| **合计** | **121 ~ 124** | |
| **余量** | **约 125 字节** | |

**125 字节意味着什么？**

- 加一个属性（比如 `"Light":{"value":85.0},`）≈ **+25 字节** → **最多加 4 个**
- 或者产品 ID / 设备名变长：`v9cSbzDFqr`(10) 和 `test1`(5) 每加 1 个字符，
  主题加 1 → 载荷不变，一样吃余量
- 换个平台（比如阿里云主题通常 60+ 字符）→ 直接吃掉 20 字节

> **想加第 5 个属性时就会撞墙。** 撞墙的症状是上面说的"静默失败 + 循环重连"。
> 解决办法见 §3.11"想加大报文"。

### 3.3.7 `MQTT_Ping()` —— 2 个字节 + 只看第一个字节

`mqtt.c:219-239`：

```c
uint8_t MQTT_Ping(void)
{
    uint8_t  rx[MQTT_RX_MAX];
    uint16_t rxLen = 0, got;

    /* PINGREQ 是最短的报文: 只有 2 字节固定头, 没有可变头和载荷 */
    s_MqttTxBuf[0] = 0xC0;
    s_MqttTxBuf[1] = 0x00;

    if (ESP8266_TCPSend(s_MqttTxBuf, 2) != ESP8266_OK) { return 0; }

    while (rxLen < 2)
    {
        got = ESP8266_TCPRecvRaw(&rx[rxLen], (uint16_t)(sizeof(rx) - rxLen),
                                 CFG_MQTT_TIMEOUT_MS);
        if (got == 0) { return 0; }
        rxLen = (uint16_t)(rxLen + got);
    }

    return (rx[0] == 0xD0) ? 1U : 0U;
}
```

**PINGREQ 是 MQTT 里最短的报文**：2 字节，`C0 00`（类型 + 剩余长度 0）。
服务器回 `D0 00`（PINGRESP），也是 2 字节。

**它绕过了 `Mqtt_Wrap`**，直接手写这 2 个字节——因为
`Mqtt_Wrap` 的前提是"body 已经写在偏移 5 处"，而 PINGREQ 根本没有 body。
**手写更清楚，也更省事。**

**只检查 `rx[0] == 0xD0`，不检查 `rx[1] == 0x00`。**
PINGRESP 的剩余长度**必然是 0**（协议规定它没有可变头和载荷），
所以第二个字节没有信息量。

> 和 `MQTT_Connect` 检查 `rx[1] == 0x02` 对比一下：
> 那里检查了，因为 `0x02` 是个具体的值；这里 `0x00` 是唯一可能。
> **这个不一致不是疏忽，是两个报文的实际约束不同。**

**心跳为什么这么重要**：服务器在 **1.5 × Keep Alive**（= 90 秒）内
没收到任何报文就主动断开。所以设备必须在 30 秒内至少发一次东西。
**`WIFI_PING_INTERVAL_MS = CFG_MQTT_KEEPALIVE_S * 500 = 30000`**——
这个 `*500` 是"秒 → 毫秒 再取一半"，很容易看错，[详解 04](11-任务层-上报循环.md) §4.5 会展开。

## 3.4 关键设计决策

### 决策一：长度只算一处（先拼后挪）

| | |
|---|---|
| **决策** | body 先写在偏移 5，量出长度后用 `memmove` 把固定头补上（`mqtt.c:73-92`） |
| **理由** | 长度计算只写一遍 → 不可能出现"两处算得不一致" |
| **不这么做** | 算两遍的方案里，只要某一处漏了某个字段（比如忘了算主题长度那 2 字节），就会在**某些特定长度下**才发作。症状是"服务器不回任何东西直接断链"，和 Token 错、主题错完全一样，**极难定位** |

多搬 ≤ 251 字节的代价：72MHz 下一次 `memmove` 约几百纳秒，**每 2 秒一次**。

### 决策二：拼装缓冲区放 `.bss` 不放栈

| | |
|---|---|
| **决策** | `static uint8_t s_MqttTxBuf[256]`（`mqtt.c:33`） |
| **理由** | 任务栈只有 **512 字 = 2048 字节**（`app_main.h` 的 `APP_STACK_WIFI`）。256 字节放栈上就是 **1/8 的任务栈**，而且是在"联网 + 拼包 + printf"这个全场最吃栈的时刻 |
| **不这么做** | 栈溢出 → 踩到相邻任务的栈或 FreeRTOS 的堆 → **随机 HardFault**，或者更糟：**静默的数据损坏**，几小时才发作一次 |

代价是**本文件不可重入**，见 §3.10。

### 决策三：错误码翻译成英文短句而不是数字

| | |
|---|---|
| **决策** | `Mqtt_ConnackReason()` 返回 `const char *` 指向 Flash 里的字符串 |
| **理由** | 现场调试时串口上直接看到"Token expired?"比看到"code 4"强太多。字符串在 Flash 只读区，**不占 RAM** |
| **不这么做** | 只打 `code 4` 的话，每次都要回去翻笔记才知道 4 是什么——**而笔记里 4 的解释还是错的**（见 §3.11） |

### 决策四：三个对外函数，不做通用化

| | |
|---|---|
| **决策** | 只暴露 `MQTT_Connect` / `MQTT_Publish` / `MQTT_Ping` |
| **理由** | 正好是设备需要做的三件事。加一个 `MQTT_Subscribe` 或通用 `MQTT_Send(type, ...)` 都只是多一层间接 |
| **不这么做** | 做一个通用报文发送器（参数是报文类型 + 标志 + 载荷）会让调用方需要懂 MQTT 标志位——**把协议的复杂度泄漏到业务层**，正好违背 §3.1 说的边界 |

> `mqtt.h:18-22` 也承认了另一处**没做**的解耦：
> "严格说这让本层知道了底层是 ESP8266……这个规模的项目不值得"。
> 这是**明确的取舍，不是疏忽**。

## 3.5 已知局限与注意事项

| 局限 | 触发条件 | 现象 | 能自愈 | 修法 |
|---|---|---|---|---|
| **发布失败完全静默** | 主题+载荷 > 249 字节 | 不报错，但一直重连，平台上没数据 | 否 | §3.11"想加大报文" |
| **不可重入** | 两个任务同时用 MQTT | 报文互相覆盖，发出**畸形包** | 否 | §3.10 |
| **`rx[2]` 未检查** | 改用 Clean Session = 0 | 无法区分"会话还在"和"订阅丢了" | 否 | 做订阅时补上 |
| **`MQTT_RX_MAX = 32` 但只用 4** | 收到超过 4 字节的应答 | 多出来的字节被静默丢弃 | — | 无订阅时不可能发生 |
| **无 QoS 1/2、无遗嘱、无保留消息** | — | — | — | 本项目用不上 |
| **依赖 `ESP8266_TCPSend` 接口** | 换通信模块 | 要改 `mqtt.c` 的 include 和两处调用 | — | 抽端口层（不值得） |
| **`Mqtt_PutString` 的 `room` 依赖调用方** | 调用方算错 `MQTT_PKT_MAX - pos` | 边界检查失效 → 缓冲区越界 | 否 | 照抄现有调用模式 |

### 展开说：不可重入的真实边界

`mqtt.c:15-18` 的文件头注释说：

> 拼装缓冲区是 static, 不是局部变量. …… 代价是本文件不可重入 ——
> 本项目只有一个任务用 MQTT, 够用.

**"不可重入"具体意味着什么？** 说清楚边界，比笼统地说"不安全"有用得多：

| 场景 | 安全吗 | 说明 |
|---|---|---|
| 两个任务**各自独立**调用 MQTT（时间上错开） | ✅ **安全** | `s_MqttTxBuf` 是"用一下就走"，不跨调用保存状态 |
| 两个任务**同一时刻**都在 MQTT 调用栈里 | ❌ **不安全** | 后进的把先进的报文覆盖掉，发出去的是两半拼起来的畸形包 |
| 在中断里调 MQTT | ❌ 不安全 | 同上，而且 `s_MqttTxBuf` 不是 volatile，缓存一致性也没保证 |
| 一个任务调用时被高优先级任务抢占，但**高优先级任务不碰 MQTT** | ✅ 安全 | 这是当前的实际状态 |

**当前谁在用 MQTT？** 只有 `TaskWifi`（`task_wifi.c:190` 的 `MQTT_Connect`、
`:292` 的 `MQTT_Publish`、`:310` 的 `MQTT_Ping`）。`grep -rn "MQTT_" APP/` 里
没有别的任务。

**什么时候会破？** `mqtt.h:20-22` 自己指出了那条路：

> 真要用订阅就得改架构 —— 现在所有接收都是"发完等回", 订阅是服务器
> 主动推, 得有个独立的收报文循环

**"独立的收报文循环"如果是一个新任务，而它也要发 `PINGREQ` 或者
处理 `SUBACK`，那就破了不可重入的假设。**

**真要加第二个任务时怎么办？** 三种，从简到繁：

1. **加互斥锁** —— `MQTT_*` 函数开头/结尾包 `xSemaphoreTake/Give`。
   文件要 `#include "FreeRTOS.h"`，破坏了"协议层不依赖 RTOS"的分层
   （但 `mqtt.c` 本来就已经 `#include "esp8266.h"`，见 `mqtt.h:16-18` 的自我批评）
2. **每个任务一份缓冲区** —— 缓冲区作为参数传进来，或者开两份 static。
   多占 256 字节 RAM（[详解 01](08-启动流程与CubeMX初始化.md) §1.9 的账本：**不宽裕**）
3. **收报文循环不发文** —— 新任务只负责收和解析，所有发送仍由 `TaskWifi` 串行做。
   **这样就不用锁**——但 `s_MqttTxBuf` 仍然只有一份，两个任务还是会撞

> **本次只记录，未修改代码。** 现在只有 `TaskWifi` 一个调用者，是安全的。

### 展开说：`Mqtt_ConnackReason` 的码表**和某些笔记不一致**

`mqtt.c` 的函数里列的是 **CONNACK 返回码**，但 `AT+CWJAP` 的
**WiFi 连接错误码**是**另一套数字**，两者的含义完全不同：

| 码 | CONNACK 返回码（`mqtt.c` 用的） | `AT+CWJAP` 错误码（AT 指令用的） |
|---|---|---|
| 1 | unacceptable protocol version | **连接超时** |
| 2 | client id rejected | **密码错误** |
| 3 | server unavailable | **找不到该 AP** |
| 4 | bad username or password | **连接失败（被 AP 拒绝）** |

**两套都从 1 数到 4，但含义毫无关系。**
《ESP8266 知识点与 AT 指令》里 CWJAP 的 1 和 4 曾经写反过
（已在任务 1 中修正）。

**看日志时先分清是哪一套**：
- `[MQTT] CONNACK refused: code 4` → **Token / 鉴权**问题
- `WiFi Connect Failed!` 后面的 `+CWJAP:4` → **热点主动拒绝**（黑名单、客户端满）

后者正是 `task_wifi.c:97` 的 `WifiDiagScan()` 存在的理由。

## 3.6 动手改这里

### 加一个新属性（比如光照）

**改哪几行**：`task_wifi.c:285-290` 的 `snprintf`，加一段
`"\"Light\":{\"value\":%d.0},"`，同时在 `app_config.h` 或控制台里
**确认属性名和大小写**。

**连带要改的**：
- `task_wifi.c:213` 的 `char payload[192]` **要一起加大** ——
  当前 JSON 是 80 字节，加 3 个属性就到 155 了，离 192 只剩 37
- `MQTT_PKT_MAX`（`mqtt.c:29`）**当前有余量**（§3.3.6 算了：约 125 字节），
  加 1~4 个属性不用动。**加第 5 个就要动它**
- 加完属性后 `MQTT_PKT_MAX` 若超过 256，`s_MqttTxBuf` 跟着变大 →
  **记得回来核对 RAM 账**（[详解 01](08-启动流程与CubeMX初始化.md) §1.9）

**怎么验证**：串口看 `[WiFi] uploaded:` 有没有继续打。
**如果平台上看不到数据但串口一直在打 `uploaded`** → 是属性名/主题问题（平台静默断链）。
**如果 `uploaded` 根本不打了、而且开始循环重连** → 是缓冲区装不下（本节的问题）。

### 加大报文缓冲区

**改哪几行**：`mqtt.c:29` 的 `MQTT_PKT_MAX`。**只改这一个数就行**——
代码里所有边界检查都引用它，没有第二个地方藏着 256。

**连带要改的**：
- `Mqtt_Wrap` 里 `MQTT_BODY_OFFSET = 5` **不用改**：它按协议最坏情况
  （4 字节剩余长度）留的，`MQTT_PKT_MAX` 改到 2MB 都还够
- `s_MqttTxBuf` **不用改**：它是 `[MQTT_PKT_MAX]` 定义的
- ⚠️ **RAM**：`s_MqttTxBuf` 在 `.bss` 里，加多少就是加多少 RAM。
  从 256 加到 512 就吃掉 256 字节，**得从别处减**

**怎么验证**：`build.log` 里的 `ZI-data` 应该正好增加你加的量。
**这笔账很好对**——加 256 字节，`ZI-data` 就该从 12828 变成 13084。
对不上说明还有别的地方也变了。

### 加一个"发布失败"的日志

**改哪几行**：`MQTT_Publish` 的 4 个 `return 0`，每个前面加一句 `printf`。

**要注意的**：`task_wifi.c:300-303` **刻意不在失败时打印**（怕断线时刷屏）。
所以在 `MQTT_Publish` 里加日志要**区分原因**：

```c
    if (n == 0)
    {
        printf("[MQTT] topic too long (%u bytes)\r\n", (unsigned)strlen(topic));
        return 0;
    }
```

**只在"装不下"这类本地错误上打**——那种情况不会刷屏
（配置改错了就会一直错，一眼就能看出来）。
**`TCPSend` 失败那条不要在这里打**，留给上层的 `link is dead` 汇总。

**怎么验证**：故意把主题改长到超过 249 字符，编译烧录，
应该立刻看到 `topic too long` 而不是"静默重连"。

### 接一个新平台（比如阿里云 / EMQX）

**要改的**：
1. `app_config.h` 换 `CFG_MQTT_HOST` / `PORT` / 三个凭据宏 / `CFG_MQTT_PUB_TOPIC`
2. `task_wifi.c:285-290` 换 JSON 格式（各平台的物模型格式都不一样）
3. **`ConnectWiFi` 之前那步 TCP 端口**：如果平台要 TLS，得换 `8883` +
   `AT+CIPSTART="SSL",...` —— **ESP8266 内存吃紧**，见 §3.7 的"可能的方向"
4. **`mqtt.c` 一个字都不用改**（除非新平台要求 MQTT 5.0，那就得改协议级别 `0x04`）

**怎么验证**：**先在 MQTTX 上用新凭据连一遍**。
这是本项目的核心排查方法（《从零入门 06》§6.6）——
一次就能把"凭据错"和"代码错"分开。

### 加订阅

**这不是"改几行"，是架构改动。** 障碍**不在 `mqtt.c`**：

| 要做的事 | 在哪做 | 为什么难 |
|---|---|---|
| 拼 SUBSCRIBE 报文（`0x82`） | `mqtt.c` | **简单**——套 `Mqtt_PutString` 就行 |
| 解析 SUBACK（`0x90`） | `mqtt.c` | **简单** |
| **收到推送时能拿到数据** | `esp8266.c` | ❌ **难**——见下 |
| **发送命令时不把推送丢掉** | `esp8266.c` | ❌ **难**——见下 |

**真正的两道坎都在驱动层**（[详解 02](09-ESP8266接收架构与+IPD剥离.md) §2.7）：

1. **`ESP8266_SendCmd` 每次开头都清缓冲区**（`esp8266.c:300`）——
   服务器随时可能推数据过来，而这边每发一条命令就把在途的推送扔掉
2. **`WaitResponse` 会把 `+IPD` 卷进 `RxBuf` 当文本搜**——
   推送数据一旦被 drain 进 `RxBuf`，`TCPRecvRaw` **永远看不到它了**

**再加上 `rx[2]` 要开始检查**（§3.3.5）、**`CLOSED` 通知要被解析出来**
（`esp8266.c:642` 现在静默滤掉）。

**所以正确的顺序是**：先改 `esp8266.c` 把"一个流两个消费者"的模型理顺，
再回头加 `mqtt.c` 的 SUBSCRIBE。**反过来做会白干一场。**

## 3.7 一句话总结

**`mqtt.c` 干的是"翻译"：把调用方给的字符串拼成 MQTT 字节、把收到的字节
翻译成"发生了什么"——它不知道温湿度是什么，也不知道 JSON 长什么样。**

三个值得记住的：

1. **长度只算一处** —— 先拼 body 再 `memmove` 补固定头。
   那个 `memmove` **必须**是 `memmove`（源和目标必然重叠，且方向向前），
   而且**挪动的距离是运行期变化的**（剩余长度占 1 还是 2 字节，取决于报文多大）。
2. **`MQTT_PKT_MAX = 256` 是发布能力的硬上限** —— 主题 + 载荷 ≤ 249。
   当前用掉 121~124，**余量约 125 字节，够加 4 个属性**。
   超了不会报错，只会"静默地一直重连"。
3. **`code 4` 不代表密码错** —— 它是"验签没过"，头号嫌疑是 Token 里
   手改过的 `et` 字段。而 `Mqtt_ConnackReason` 是唯一把这句话说出来的地方。
