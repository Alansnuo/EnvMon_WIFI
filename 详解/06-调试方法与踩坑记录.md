# ⑥ 调试方法与踩坑记录 —— 哪一步、怎么测、测什么

> 适用人群：代码烧好了但不知道数据有没有上去 / 出了问题不知道
> 从哪一层开始查 / 想避免我们踩过的 15 个坑
>
> 本篇教你"分层排查"的方法论，和一张可抄的排查决策树。

---

## 6.1 最重要的原则：分层举证

串口打出 `[WiFi] 3 failures in a row - link is dead, reconnecting`，你从哪里开始查？

**千万不能从上往下查** —— 从应用层开始，可能性太多了：
是主题不对？是 TCP 断了？是模块死了？是 WiFi 掉了？还是 MQTT 报文拼错了？

正确顺序是**从下往上查**，每一层用自己的"举证工具"确认是好的，
再怀疑上一层：

```
④ 数据到平台了吗？ → 去 OneNET 控制台看数据点
③ MQTT 连上了吗？ → 看 CONNACK
② TCP 通了吗？   → 看 "TCP Connected!"
① WiFi 通了吗？   → 看 "WiFi Connected!"
  模块活了吗？    → 串口有没有打印 "ESP8266 Initialized OK!"
  硬件基本盘？    → 串口有没有 "DHT11 Sensor Ready!"
```

**不要跳步。** 如果你跳过①直接查③，可能折腾半天发现WiFi密码错了。

具体每一步查什么，见 6.4 的决策树。

## 6.2 必备工具

| 工具 | 用途 | 获取方式 |
|---|---|---|
| **串口助手** | 看 STM32 的打印日志 | SSCOM、Putty、MobaXterm 等 |
| **MQTTX** | PC 端测试 MQTT 连接 | [mqttx.app](https://mqttx.app/) |
| **OneNET 控制台** | 看设备是否在线、数据点、物模型 | [open.iot.10086.cn](https://open.iot.10086.cn/) |

串口助手设置：**115200 波特率，8 位数据，1 位停止位，无校验**。

## 6.5 踩过的坑一表

这是本项目在 2026-09-20 一天里踩过的所有坑的核心总结：

| 现象 | 你以为 | 实际上是 |
|---|---|---|
| `CONNACK code 4: 用户名或密码错误` | 密码写错了 | Token 验签不过（`et` 多了一个数字） |
| `SEND OK` | 平台收下了 | ESP8266 自己回的，平台可能已经断链 |
| 串口突然只打 `link is dead` | 网络抖了一下 | 逐条失败不再打印，这一句是连着失败 3 次的汇总 |
| 扫得到热点、信号满格 | 热点在跟前 | 被拉黑了（黑名单不挡 beacon） |
| 第一条上报成功，后面全 FAILED | 网络偶尔抖 | 主题不对，平台直接断 TCP |
| 串口显示 `濂堜綍…` | 编码错了，固件存了乱码 | 字节是对的，串口助手显示的问题 |
| IDE 红线报"未定义标识符" | 代码有错 | IDE 快照过期，编译器 0 错误 |

**共同特点**：每一层的报错都在骗你。照着报错查只会越查越远。

## 6.6 排查方法论

### 方法一：拿同一串凭据去 PC 端复现

设备出问题，**先别动固件代码**。把设备上用的那串 Token 原封不动抄到 MQTTX：

```
PC 端也失败 → 凭据 / Token / 主题 / 属性名的问题，别碰固件
PC 端成功   → 这才轮到查代码和硬件
```

这一步一次就能把"设备、代码、硬件"全部排除，比猜什么都快。
本项目两个死结（Token、主题）都是靠这个定性的。

### 方法二：只看最终结果

**判断"成功"的唯一标准：OneNET 控制台上出现数据点。**

- 不是 "设备在线"（那只是 CONNACK 过了）
- 不是 `SEND OK`（那是模块的回执）
- 不是串口的 `uploaded`（那只是 `TCPSend` 返回了 OK）

中间的每一环说自己成功了，都不算数。

## 6.7 MQTT 的调试技巧

**CONNACK code 4—— 最常见、也最骗人**

```
处理步骤：
1. 先确认：et 是 10 位还是 11 位？
   → 11 位 = 多打了数字，重新生成 Token 即可
2. 再确认：Client ID = 设备名，用户名 = 产品 ID？
   → 搞反了鉴权过不去，而且报的还是 code 4
3. 最后：拿 Token 去 MQTTX 试
   → MQTTX 也连不上 = 凭据问题
   → MQTTX 能连上 = 报文拼装问题
```

**上报失败（连着失败 3 次 → `link is dead`）**

> ⚠️ **逐条的失败现在不打印了。** 真断线时会连着失败好几条，每条都打就刷屏了，
> 所以失败分支是静默的（`task_wifi.c:300-303`），只在退出上报循环时统一汇报一句
> `[WiFi] N failures in a row - link is dead, reconnecting`。
> 排查思路不变，只是别再去串口里找单条的 `upload FAILED` —— 那行已经没有了。

```
处理步骤：
1. 先关掉 MQTTX（Client ID 冲突）
2. 确认主题：物模型产品用 thing/property/post，不是 dp/post/json
3. 确认属性名：Temp / Hum 跟控制台一字不差
4. 去控制台看有没有数据点
```

## 6.8 模块和供电的坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 串口无输出，或输出了不到一半 | 波特率不对 / TX/RX 接反 | 检查接线 |
| `AT` 有时有应答有时无 | 供电塌陷 | 用万用表测 3.3V，空载 3.3V，连模块后会不会掉到 3.0V 以下 |
| 第一回能连，复位后就死 | `HAL_UART_DMAStop` 没写 | 见笔记③ 3.9 |
| 扫得到但连不上 | 手机黑名单 | 去手机热点设置页找"已阻止的设备" |

## 6.9 调试时要注意的"人为因素"

1. **MQTTX 必须断开再测板子** — Client ID 冲突，谁后上线谁踢谁
2. **不要手改 Token** — 改一个字符就要重新算 sign，平台只回 code 4
3. **`%2F` 和 `/` 都能过鉴权** — 不要花时间纠结这个
4. **`mqtts.heclouds.com` 的 `s` 不代表加密** — 1883 就是明文
5. **IDE 的红线可能是假的** — 以编译器的 0 Error(s) 为准
