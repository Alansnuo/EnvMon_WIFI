## 〇、先建立全局观

### 0.1 函数调用关系

```
                        APP/task_wifi.c                 APP/mqtt.c
                              │                              │
   ┌──────────┬───────────────┼────────────┬─────────────────┤
   ↓          ↓               ↓            ↓                 ↓
Init()  SetWiFiMode()   ConnectWiFi()  ScanAP()   TCPSend()  TCPRecvRaw()
   │          │               │            │           │          │
   ├─ RxStart()               │            │           │          │
   ├─ Reset()                 │            │           │          │
   ├─ Test() ─────────────────┤            │           │          │
   ├─ SendCmd(ATE0)           │            │           │          │
   └─ SendCmd(CWAUTOCONN=0)   │            │           │          │
                              └────────────┘           │          │
                                                       ↓          │
                              ┌─────────────────────────────┐     │
                              │  ESP8266_SendCmd()          │     │
                              │    ├─ ClearRxBuf()          │     │
                              │    ├─ HAL_UART_Transmit() ← 发    │
                              │    └─ ESP8266_WaitResponse()← 收  │
                              └─────────────────────────────┘     │
                                          │                        │
                                          ↓                        ↓
                                   ESP8266_RxDrain()       ESP8266_TCPRecvRaw()
                                    （DMA → RxBuf）         （DMA → 调用方 buf）
                                          └───────────┬────────────┘
                                                      ↓
                                               ESP8266_RxPop()  ← 唯一推进读指针处
                                                      ↑
                                      ESP8266_DmaBuf[]  ← DMA 自己往里写
```

**关键结构**：所有 AT 命令最终都汇入 `SendCmd` → `WaitResponse` 这一条主干。

**但"读串口"这件事已经不在主干上了**：字节是 DMA 在环形模式下自己搬进
`ESP8266_DmaBuf[]` 的，CPU 只负责从里面取。取的人有两个 —— `RxDrain`（搬进
`RxBuf` 供 `WaitResponse` 做 AT 响应匹配）和 `TCPRecvRaw`（剥掉 `+IPD` 包装，
把裸数据交给 MQTT 层）。**现在驱动里没有一处 `HAL_UART_Receive` 了。**

| 位置 | 作用 |
|---|---|
| `WaitResponse:241` | AT 响应的消费点：`RxDrain` 批量搬进 `RxBuf` 后 `strstr` 匹配 |
| `TCPRecvRaw:605` | 服务器数据的消费点：`RxPop` 直接搬进调用方缓冲区 |
| `SendCmd:306` | 写串口点之一：发 AT 命令 |
| `TCPSend:542` | 写串口点之二：发裸数据 |
| `Reset:323/326`（由 `Init` 调） | 唯一的 GPIO 操作点 |
| `RxStart:44`（由 `Init` 调） | 唯一的 DMA 启动点 |

**只要这几个点没问题，整个驱动就没问题。** 调试时盯住这几处即可。

### 0.2 头文件提供的地基

```c
#define ESP8266_UART          huart2        // 用哪个串口
#define ESP8266_RST_PIN       GPIO_PIN_1    // RST 引脚 PB1
#define ESP8266_RST_PORT      GPIOB
```

**为什么用宏而不是直接写 `huart2`？**

因为 USART 可能改（比如从 USART2 换到 USART3）。用宏的话，
**改一行就够了**，不用在整个 `.c` 文件里搜索替换。
这是嵌入式驱动适配不同硬件时的标准做法 —— 把"和硬件绑定的东西"
全部集中到头文件顶部。

`extern UART_HandleTypeDef huart2;` 写在 `esp8266.c:5`，
而宏定义中**没有 `extern`** —— 宏只是文本替换，`ESP8266_UART` 展开后就是
`huart2`，正好对上外部声明。

同一个头部里还集中了另外两类"和硬件/节奏绑定"的东西（`esp8266.h:14-35`）：
**超时宏**（`ESP8266_TIMEOUT` / `WIFI_TIMEOUT` / `TCP_TIMEOUT` / `TX_TIMEOUT` /
`SCAN_TIMEOUT`）和**缓冲区大小宏**（`ESP8266_RX_BUF_SIZE` 512 /
`ESP8266_DMA_BUF_SIZE` 256 / `ESP8266_TX_BUF_SIZE` 256）。后文用到哪个再展开讲
（`ESP8266_TX_BUF_SIZE` 其实没人用 —— 见第七节 #8）。

## 一、基础设施层：接收缓冲区与 DMA 环形缓冲

### 1.1 为什么要 static

```c
// esp8266.c:10-11
static uint8_t ESP8266_RxBuf[ESP8266_RX_BUF_SIZE];
static uint16_t ESP8266_RxLen = 0;
```

**知识点｜C 语言的 `static` 在文件作用域下改变的是"链接属性"**：
加 `static` 后，这两个符号不再导出到全局符号表，别的 `.c` 文件**无法直接
`extern` 引用**它们。这叫**内部链接**。

**为什么要这样做？**

如果 `RxBuf` 是全局的，任何文件都能写 `extern uint8_t ESP8266_RxBuf[];`
然后随手改它 —— 缓冲区状态就失控了。设为 `static` 后，**唯一能修改它的
只有本文件内的函数**，外部只能用提供的访问接口。

这就是 C 语言里最常用的"封装"手法：**内部链接 + 访问函数**。

### 1.2 三个访问函数

```c
// esp8266.c:131-140  —— 清空
void ESP8266_ClearRxBuf(void)
{
    /* 两处都要清, 语义才是"清空接收缓冲区":
     *   ① DMA 环形缓冲区里还没搬走的那部分
     *   ② 已经搬进 RxBuf 的那部分
     * 只清②的话, 下次 Drain 又会被①灌进来, 看起来就像"清了但没清干净". */
    ESP8266_RxDiscard();
    memset(ESP8266_RxBuf, 0, sizeof(ESP8266_RxBuf));
    ESP8266_RxLen = 0;
}

// esp8266.c:146-149  —— 读长度
uint16_t ESP8266_GetRxBufLen(void)
{
    return ESP8266_RxLen;
}

// esp8266.c:155-158  —— 读指针
uint8_t* ESP8266_GetRxBuf(void)
{
    return ESP8266_RxBuf;
}
```

**注意 `ClearRxBuf` 现在是"三件事"**：先 `ESP8266_RxDiscard()` 把 DMA 环形
缓冲区里**还没搬走**的字节扔掉，再 `memset` 清 `RxBuf`，最后长度归零。

**为什么要扔两处？** 因为现在有**两个缓冲**（见 1.4）：DMA 的环形缓冲
（`ESP8266_DmaBuf`）和解析用的直线缓冲（`ESP8266_RxBuf`）。只清后者的话，
下一次 `RxDrain` 立刻又会把环形缓冲里的旧字节灌进来 —— 现象就是
"**明明清了，`strstr` 却还是匹配到了上一条命令的 `OK`**"。

**`ClearRxBuf` 里的 `memset` 是全篇最容易忽视、但最关键的一行。**

**知识点｜`strstr` 要求字符串必须以 `'\0'` 结尾。**
串口收到的是**裸字节流**，天然不带结尾符。如果缓冲区里从头到尾没有
`'\0'`，`strstr` 会一路往后读 —— 读到栈上或别的变量里，直到碰巧遇到
一个 0 字节才停下。

后果分两种：
- **轻**：匹配到了不该匹配的内容 → 逻辑误判（"假 OK"）
- **重**：读到未映射的内存 → HardFault 死机

**`memset` 全清零一次性解决了这个问题**：整个缓冲区全变 `'\0'`，
之后每写一个字节才有一个非零。而写入上限卡在 `SIZE-1`（见 2.⑥），
**最后一个字节永远是 `'\0'`**，`strstr` 永远不会越界。

**代价**：每次清空要写 512 字节。在 72MHz 的 M3 上约几微秒，
相比动辄几十毫秒的 AT 交互完全可忽略。

**`sizeof(ESP8266_RxBuf)` 而不是 `512`** —— 这样缓冲区大小改了，
`memset` 自动跟着变，不会漏改。

### 1.3 为什么需要 `GetRxBuf`

```c
// task_wifi.c:155-156 里的用法
printf("WiFi Connect Failed! ESP8266 response:\r\n");
printf("%s\r\n", (char *)ESP8266_GetRxBuf());
```

**这是驱动里最有价值的一个接口。**

AT 命令失败时，模块其实**说清楚了失败原因**：

| 模块回复 | 真实原因 |
|---|---|
| `+CWJAP:1` `FAIL` | **连接超时**（热点多半不在范围内） |
| `+CWJAP:2` `FAIL` | **密码错误** |
| `+CWJAP:3` `FAIL` | 找不到目标 AP |
| `+CWJAP:4` `FAIL` | **连接失败 —— 热点主动拒绝**（最常见是手机热点的 MAC 黑名单/"已阻止的设备"） |

但如果驱动只返回一个 `ESP8266_ERR_TIMEOUT`，你就只看到"失败了"，
完全不知道是密码错还是信号差 —— **只能靠猜**。

把原始响应暴露出来，一行 `printf` 就能看到模块的原话。
**这是嵌入式调试最实用的一条经验：永远保留原始错误信息，不要只上报错误码。**

> ⚠️ 这张表**以前写反了**：老版本把 `:1` 写成"找不到 SSID"、`:4` 写成
> "连接超时"。官方定义是 1 = 连接超时、4 = 连接失败（被拒）。
> 这两个恰好是最容易搞混的一对 —— 一个要往"热点太远"方向查，
> 一个要往"热点不让连"方向查，**查错方向能白查一轮模块**。
> 项目里的做法是：`CWJAP` 失败后立刻打原始应答，再跑一次
> `WifiDiagScan()`（`task_wifi.c:97`，内部调 `ESP8266_ScanAP`）扫一遍周边热点 ——
> 名单里有它 = 被拒绝，名单里没有 = 够不着。这一条见《踩坑笔记》。

### 1.4 接收层的地基：DMA 环形缓冲

这一层是**驱动重写时新加的**，也是整份笔记里"旧代码 → 新代码"变化最大的
地方。它解决的问题一句话就能说清：

> **STM32F1 的 USART 只有 1 个字节的接收寄存器，没有 FIFO。
> CPU 只要晚来几毫秒读，字节就没了。**

以前 `WaitResponse` 是逐字节 `HAL_UART_Receive(...,1,10)` 死等，虽然慢好歹
一直在读；但工程里 `DHT11_Read()` 有约 4ms 的关中断，那 4ms 里来的字节
**没人搬就直接丢了**。所以老工程只能"先连完 WiFi，再建采集任务"，两个阶段
不能重叠。

现在的做法（`esp8266.c:13-126`）：

```c
/* 启动 DMA 接收. 只在 Init 里调一次; 之后 DMA 永远在环形模式里转.
 * 前提: MX_DMA_Init() 和 MX_USART2_UART_Init() 都已经跑完
 *       (hdmarx 是在 USART2 的 MspInit 里用 __HAL_LINKDMA 挂上的). */
static ESP8266_Status ESP8266_RxStart(void)
{
    /* 先停掉上一次的接收, 再重开. 这一步不能省.
     *
     * HAL_UART_Receive_DMA() 要求 huart->RxState == HAL_UART_STATE_READY,
     * 否则直接返回 HAL_BUSY —— 见 stm32f1xx_hal_uart.c 里那个 if/else。
     * 第一次调用 RxState 是 READY, 没问题; 但 ESP8266_Init() 会被上层
     * 反复调用 (连不上就重试), 第二次进来时 RxState 还停在 BUSY_RX
     * (DMA 一直在环形模式里跑, 从没结束过), 于是这里返回失败,
     * Init() 立刻退出 —— 连模块都不复位了。
     *
     * 症状很有迷惑性: 第一次失败之后**永远**失败, 而且从第二次起报的是
     * "ESP8266 Init Failed!", 看起来像模块坏了或者接触不良,
     * 其实只是漏了这一行。HAL_UART_DMAStop() 会把 RxState 复位成 READY
     * (它内部调的 UART_EndRxTransfer 里有一句), 重开就能成功。 */
    (void)HAL_UART_DMAStop(&ESP8266_UART);

    ESP8266_DmaTail = 0;

    if (HAL_UART_Receive_DMA(&ESP8266_UART, ESP8266_DmaBuf,
                             ESP8266_DMA_BUF_SIZE) != HAL_OK)
    {
        return ESP8266_ERR_AT;
    }

    /* 关掉 DMA 传输完成中断.
     * 环形模式下 HAL 的回调本来也什么都不做 —— stm32f1xx_hal_uart.c:3047 判了
     * (hdma->Instance->CCR & DMA_CCR_CIRC), 环形就直接跳过.
     * 既然没活干, 那这个中断就是纯浪费, 关掉.
     * 我们靠轮询 CNDTR 计数器知道进度, 不需要任何中断通知. */
    __HAL_DMA_DISABLE_IT(ESP8266_UART.hdmarx, DMA_IT_TC);

    return ESP8266_OK;
}
```

**知识点｜`HAL_UART_Receive_DMA` + CIRCULAR 模式 = 硬件自主搬运。**
DMA 在环形模式下**永远不停机**地往 `ESP8266_DmaBuf` 里写，写到头自动回绕。
CPU 在不在忙、中断关没关，都不影响它 —— 那 4ms 采集期的字节照样落进内存。

**怎么知道它写到哪了？** 读 DMA 的剩余计数 `CNDTR`：

```c
/* DMA 当前的写指针.
 * 环形模式下 CNDTR 会自己回绕, 所以 "缓冲区大小 - 剩余计数"恒等于写位置.
 * CNDTR 是单个 16bit 寄存器, 读一次就是原子的, 不会被 DMA 撕裂. */
static uint16_t ESP8266_RxHead(void)
{
    return (uint16_t)(ESP8266_DMA_BUF_SIZE -
                      __HAL_DMA_GET_COUNTER(ESP8266_UART.hdmarx));
}
```

**知识点｜环形缓冲的经典风险是"写指针追上读指针"。** 这里写指针是 DMA，
读指针是 `ESP8266_DmaTail`。追不上的依据是**余量**：轮询间隔最多 1ms，
115200 波特率下 1ms 也就过来 11 个字节，而环有 256 字节 —— 二十几倍余量。
这就是 `esp8266.h:34` 那句注释"只需装下两次搬运之间的突发"的意思。

**为什么不用 IDLE 中断判"一帧收完了"？** 那要多开一个 USART2 中断，还得纠结
"中断里能不能调 `...FromISR` 的 RTOS API"——一碰 RTOS，BSP 就破了"不认识
FreeRTOS"这条规矩。轮询的代价只是最多 1ms 的发现延迟，而 AT 响应本身都是
几十毫秒级的。

**从环里取字节的四个函数**（都 `static`，外部看不见）：

| 函数 | 位置 | 干什么 |
|---|---|---|
| `ESP8266_RxHead` | `esp8266.c:82` | 算出 DMA 写到哪了 |
| `ESP8266_RxPop` | `esp8266.c:90` | 从环里取最多 `max` 字节给 `dst` —— **唯一推进读指针的地方** |
| `ESP8266_RxDrain` | `esp8266.c:112` | `RxPop` 搬进解析缓冲区 `RxBuf`（给 `WaitResponse` 用） |
| `ESP8266_RxDiscard` | `esp8266.c:123` | 把没搬走的直接扔掉（`ClearRxBuf` 用，免得为了"扔掉"还先搬一遍） |

**注意 `RxPop` 有**两个**消费者**：`RxDrain`（AT 响应 → `RxBuf`）和
`TCPRecvRaw`（TCP 数据 → 调用方缓冲区）。**同一份字节流，两条出口**，
各自把读指针往前推 —— 谁都不会看到对方已经取走的数据。

## 二、核心引擎：`ESP8266_WaitResponse`

这是全篇最重要的函数，**只有 48 行，但承载了整个驱动的可靠性**。

```c
ESP8266_Status ESP8266_WaitResponse(const char *expected, uint32_t timeout)
{
    uint32_t startTick = HAL_GetTick();

    while ((HAL_GetTick() - startTick) < timeout)
    {
        /* 把 DMA 收上来的字节搬进来. 一次搬一批, 比原来"一个字节判一次
         * strstr"高效得多, 语义没变 —— 凑齐 expected 就返回. */
        if (ESP8266_RxDrain() > 0)
        {
            // 先判响应, 再判缓冲满。顺序不能反: 若最后一个字节恰好凑齐响应,
            // 先判满就会把成功误报成失败。
            // RxBuf 末尾恒为 '\0'(由 ClearRxBuf 清零, 且 RxLen 到 SIZE-1 就停),
            // strstr 不会越界。
            if (strstr((char *)ESP8266_RxBuf, expected) != NULL)
            {
                return ESP8266_OK;
            }

            // 检查是否收到错误响应
            if (strstr((char *)ESP8266_RxBuf, "ERROR") != NULL ||
                strstr((char *)ESP8266_RxBuf, "FAIL") != NULL)
            {
                return ESP8266_ERR_AT;
            }

            if (ESP8266_RxLen >= ESP8266_RX_BUF_SIZE - 1)
            {
                return ESP8266_ERR_BUF_FULL;
            }

            /* 有数据就立刻再读一轮, 不延时 —— 响应可能还在往下吐 */
        }
        else
        {
            /* 没有新字节: 让出 CPU.
             * BSP_DelayMs 在任务里是 vTaskDelay(挂起本任务), 在裸机或
             * 调度器启动前是 HAL_Delay(忙等) —— 机制见 bsp_delay.h.
             *
             * 这一行就是"忙等饿死低优先级任务"那个毛病的解法:
             * 现在这条循环会让出 CPU, 而 DMA 保证字节一个不丢,
             * 两件事各归各的, 不再互相牵制. */
            BSP_DelayMs(1);
        }
    }

    return ESP8266_ERR_TIMEOUT;
}
```

**骨架没变**（"收字节 → 匹配 → 超时"），**换掉的只有"收字节"那一段** ——
从"自己逐字节去读串口"改成了"问 DMA 要一批"。逐段拆解：

### ① `HAL_GetTick()` 取时间戳

**知识点｜`HAL_GetTick()` 返回的是系统上电以来的毫秒数**，
底层是 SysTick 中断每 1ms 累加一次。

**为什么不用 `HAL_Delay`？** 因为 `HAL_Delay` 是"死等固定时间"，
而这里需要的是"**最多**等 N 毫秒，提前满足就提前返回"。
两者语义完全不同。

### ② `(HAL_GetTick() - startTick) < timeout` —— 无符号回绕安全

**知识点｜这是嵌入式中处理时间差的经典写法，顺序不能反。**

**为什么不能写成 `HAL_GetTick() < startTick + timeout`？**

`HAL_GetTick()` 是 32 位无符号数，约 49.7 天回绕一次。
假设 `startTick = 0xFFFFFF00`，`timeout = 5000`：

| 写法 | 计算 | 结果 |
|---|---|---|
| `HAL_GetTick() < startTick + timeout` | `startTick + 5000` 溢出 → `0x12B8` | 当前 tick 只要 > 0x12B8 就**立刻超时** ❌ |
| `(HAL_GetTick() - startTick) < timeout` | 无符号减法，`0x100 - 0xFFFFFF00 = 0x200` | 正确 ✅ |

**无符号减法天然处理回绕**：只要实际时间差小于 2³² 的一半，
`当前 - 起点` 的结果就是正确的时间差。

> 这类 bug 在板子连续跑几十天后才会出现，**测试时几乎不可能发现**，
> 但产品出货后必然爆发。养成写 `(now - start) < timeout` 的习惯。

### ③ `ESP8266_RxDrain()` —— 从 DMA 环里批量搬一批

```c
if (ESP8266_RxDrain() > 0)
```

**`RxDrain` 干的事**（`esp8266.c:112-119`）：把 DMA 环形缓冲区里**所有**
还没搬走的字节一次性 `RxPop` 进 `RxBuf`，返回搬了多少个；返回 `0` 表示
"这次没新数据"。

```c
static uint16_t ESP8266_RxDrain(void)
{
    uint16_t room  = (uint16_t)(ESP8266_RX_BUF_SIZE - 1 - ESP8266_RxLen);
    uint16_t moved = ESP8266_RxPop(&ESP8266_RxBuf[ESP8266_RxLen], room);

    ESP8266_RxLen = (uint16_t)(ESP8266_RxLen + moved);
    return moved;
}
```

**"就地写入"和"先自增再判断"这两条老规矩都还在**，只是从 `WaitResponse`
里下移到了 `RxDrain` 里：`RxPop` 直接把字节写进 `RxBuf[RxLen]` 往后数
（不需要临时变量再拷贝），`RxLen` 的自增由 `RxDrain` 最后一行负责。
所以 `WaitResponse` 只看得到"这一批搬进来多少字节"，看不到"第几个字节"——
`strstr` 仍然是对整块 `RxBuf` 做匹配，**匹配逻辑一个字没改**，
这也是这次重写最省心的地方。

**为什么改成"批量"？** 老版本每收 1 个字节就调一次 `HAL_UART_Receive`
再调一次 `strstr`，收满 512 字节要循环 512 次，全是函数调用开销。现在一批
搬完只匹配一次。**内核没变（边收边匹配、凑齐就返回），变的只是"收"的粒度。**

**`room = SIZE - 1 - RxLen`**：最多搬到 `RxBuf` 只剩一个字节为止 ——
那一个字节是留给 `'\0'` 的（见 1.2）。**搬不下就少搬几个，绝不越界**；
反正下一轮马上就会撞上 `ESP8266_ERR_BUF_FULL` 返回。

**`else` 分支里的 `BSP_DelayMs(1)` 是这次重写最值钱的一行。**
老版本在空数据时忙等 10ms，一条 `AT+CWJAP` 能把低优先级任务饿死十几秒；
现在没数据就 `BSP_DelayMs(1)` —— 在任务里它是 `vTaskDelay`，**主动让出 CPU**，
1ms 后再来看。CPU 占用从"接近 100% 空转"变成接近 0，而字节有 DMA 兜着，
一个都不会丢。两件事各归各的，不再互相牵制。

> ⚠️ **`ESP8266_RX_POLL_MS` 这个宏已经不存在了。** 老笔记里它是"单字节
> 轮询超时 10ms"，现在连宏带用法一起删掉了。新的节拍是 `BSP_DelayMs(1)`
> 里的那个 `1`，**含义也变了**：它不再表示"收不到就放弃"，只是"让出 CPU
> 的最小时间单位"。总超时精度从 10ms 级变成了 1ms 级（顺带变准了）。

### ④ 先判响应

```c
if (strstr((char *)ESP8266_RxBuf, expected) != NULL)
{
    return ESP8266_OK;
}
```

**知识点｜`strstr(haystack, needle)` 在大字符串里找子串**，
找到返回指针，找不到返回 `NULL`。

**为什么用 `strstr` 而不是逐行比对？**

看一个真实的 `AT+CWJAP` 响应：

```
WIFI CONNECTED\r\n
WIFI GOT IP\r\n
\r\n
OK\r\n
```

- `OK` **不在第一行**
- 中间夹着两条**主动上报**（模块自己冒出来的，不是你命令的回复）
- 还夹着一个空行

如果用"逐行匹配"，就得写状态机识别 `\r\n`、跳过空行、忽略主动上报 ——
代码量翻好几倍。而 `strstr` 在**整块文本**里找 `"OK"`，
**天然穿透所有这些格式差异**。

这就是"单缓冲 + strstr"方案（见《思路笔记》4.1）的实战理由：
**AT 响应格式不规整，子串查找比结构解析更皮实。**

**`(char *)` 强制转换**：`ESP8266_RxBuf` 是 `uint8_t[]`（因为串口是字节流），
而 `strstr` 要 `char*`。在 ARM 上两者都是 1 字节，转换是安全的。

> ⚠️ **一个隐患**：如果命令的**回显**没关，你发的 `AT+CWJAP="x","OK123"` 
> 会原样回显，里面就有 `"OK"` —— `strstr` 立刻误判成功！
> **这就是为什么 `Init` 里必须发 `ATE0`**（详见 4.2）。

### ⑤ 判错误响应

```c
if (strstr((char *)ESP8266_RxBuf, "ERROR") != NULL ||
    strstr((char *)ESP8266_RxBuf, "FAIL") != NULL)
{
    return ESP8266_ERR_AT;
}
```

**知识点｜AT 协议里 `ERROR` 和 `FAIL` 是两种不同的失败：**

| 响应 | 含义 | 例子 |
|---|---|---|
| `ERROR` | **语法/参数错**，命令根本没被执行 | 缺引号、缺 `\r\n`、参数越界 |
| `FAIL` | **语法对，操作失败** | 连接被拒、密码错、SSID 不存在 |

驱动把它们**统一归为 `ESP8266_ERR_AT`**，是因为对上层来说
"这条命令没成功"就够了。但调试时区分它们很有价值 —— 所以配合
`ESP8266_GetRxBuf()` 打印原文（见 1.3）。

**为什么不匹配 `"busy p..."`？** 因为它表示"上一条命令还在处理"，
是**可重试**的瞬时状态，不是错误。当前驱动没有重试机制，
所以它最终会走到 ⑦ 的 `ESP8266_ERR_TIMEOUT`。

### ⑥ 再判缓冲满

```c
if (ESP8266_RxLen >= ESP8266_RX_BUF_SIZE - 1)
{
    return ESP8266_ERR_BUF_FULL;
}
```

**`SIZE - 1` 而不是 `SIZE`** —— 那留出来的 1 个字节就是给 `'\0'` 的
（见 1.2）。

**为什么这一条必须排在 ④⑤ 后面？** 这是全篇最微妙的一个点：

> **反例**：假设 `expected = "OK"`，缓冲区大小 512。
> 第 511 个字节（下标 510，`RxLen` 自增后变 511）恰好是 `'K'`，
> 前面第 510 个字节是 `'O'`。
>
> 此刻 `RxLen == 511 == SIZE - 1`，**同时满足"缓冲满"和"匹配成功"**。
>
> - 先判满 → 返回 `ESP8266_ERR_BUF_FULL`（**明明成功了却报失败**）
> - 先判响应 → 返回 `ESP8266_OK` ✅

这类 bug 只在**特定长度**下偶发（差 1 个字节就没事），
调试时改一下数据长度它就消失了 —— **极难定位**。

**原则：先判"成功"，再判"失败"。** 成功的判断不应被资源限制抢先否决。

### ⑦ 超时返回

```c
return ESP8266_ERR_TIMEOUT;
```

**知识点｜超时不是"错误"，而是"信息不足"。**
失败可能有很多原因（模块死机、信号差、命令错、线松了），
驱动只知道"在 `timeout` 毫秒内没等到想要的回复"。

所以超时值**本质上是对最坏情况的估计**（见《思路笔记》4.5）：
命令越快，超时越短，失败时就能越早发现。

## 三、命令层：`ESP8266_SendCmd`

```c
ESP8266_Status ESP8266_SendCmd(const char *cmd, const char *expected, uint32_t timeout)
{
    // 清空接收缓冲区
    ESP8266_ClearRxBuf();

    // cmd 允许为空串/NULL: 此时只等响应(见 ESP8266_TCPSend 的用法)。
    // 注意: 空串不能直接丢给 HAL_UART_Transmit —— Size==0 时它返回 HAL_ERROR。
    if (cmd != NULL && *cmd != '\0')
    {
        if (HAL_UART_Transmit(&ESP8266_UART, (uint8_t *)cmd, (uint16_t)strlen(cmd),
                              ESP8266_TX_TIMEOUT) != HAL_OK)
        {
            return ESP8266_ERR_AT;
        }
    }

    return ESP8266_WaitResponse(expected, timeout);
}
```

**只有十几行，但体现了三条设计原则。** 这个函数从老版本到现在**一行逻辑
都没改**（改的只是注释和格式）。

### ① 为什么每次都要清空缓冲区

**这是"请求-应答"模式的第二铁律**（第一铁律是必须超时）。

**不清空会怎样？** 假设上一条 `AT` 成功了，缓冲区里还留着 `"AT\r\nOK\r\n"`。
现在发 `AT+CWJAP=...`，模块还在慢慢连路由器（要十几秒），
但因为 `strstr` 在**整个缓冲区**里找 `"OK"`，
**上一条命令残留的 `OK` 立刻被匹配上** —— 函数瞬间返回成功。

结果是：**WiFi 根本没连上，程序却以为连上了**，
后面所有 TCP 操作全部失败，而且错误现象指向完全无关的地方。

**这个 bug 的可怕之处在于结果是"成功"** —— 它不会报错，
只会让程序带着错误的状态一路走下去。

对比一下 `WaitResponse` 和 `SendCmd` 的职责划分：

| 函数 | 清缓冲区 | 发数据 | 等响应 |
|---|---|---|---|
| `SendCmd` | ✅ | ✅ | ✅ |
| `WaitResponse` | ❌ | ❌ | ✅ |

**`WaitResponse` 故意不清缓冲区** —— 因为它用在两步式的第二步
（见 5.6），此时缓冲区里还存着第一步的 `>` 提示符，
**必须保留上下文**。清空的责任交给 `SendCmd` 在发命令之前做。

### ② 为什么允许 cmd 为空

```c
if (cmd != NULL && *cmd != '\0')
```

**知识点｜`HAL_UART_Transmit()` 在 `Size == 0` 时直接返回 `HAL_ERROR`。**

原代码的写法是 `ESP8266_SendCmd("", "SEND OK", ...)` —— 传空串。
它**能跑**，但纯属巧合：因为 HAL 在 `Size==0` 时什么也没发（返回错误），
而代码忽略了返回值，所以"碰巧"变成了"只等不发"。

**这属于依赖未定义行为的巧合。** 一旦：
- HAL 库升级改了行为（比如开始返回 `HAL_OK`）
- 或者有人加了返回值检查

就会突然出错，而且**改动的人根本想不到会影响到发送数据的功能**。

所以现在显式写清楚：

```c
if (cmd != NULL && *cmd != '\0')   // 空串就跳过发送，语义明确
```

**`cmd != NULL && *cmd != '\0'` 是 C 语言判空字符串的标准写法**：
`cmd != NULL` 防空指针，`*cmd != '\0'` 防空串。
两个都必须有 —— 只判 `*cmd` 的话，传 `NULL` 会直接段错误。

> 📌 **源码里这句注释已经过时了**：`esp8266.c:302` 写的是
> "cmd 允许为空串/NULL: 此时只等响应**(见 ESP8266_TCPSend 的用法)**"，
> 但 `TCPSend` 现在已经改成直接调 `ESP8266_WaitResponse("SEND OK", ...)`
> （`esp8266.c:550`），**全工程再没有一处用空 cmd 调 `SendCmd` 了**。
> 也就是说这段"允许空 cmd"的分支现在是**纯粹的防御性兼容**，
> 保留无害，但别照着注释去找用法 —— 找不到的。

### ③ `strlen(cmd)` 算长度

```c
HAL_UART_Transmit(&ESP8266_UART, (uint8_t *)cmd, (uint16_t)strlen(cmd),
                  ESP8266_TX_TIMEOUT);
```

**知识点｜`HAL_UART_Transmit` 的第三个参数是"要发多少字节"，
不是"字符串"。** 它**不会自动停止在 `'\0'`** —— 传多大的长度就发多少字节。

所以必须用 `strlen` 精确算出长度。如果写死一个大数，
会把栈上后面的垃圾数据一起发出去。

**前提**：传进来的 `cmd` **必须是合法 C 字符串**（以 `'\0'` 结尾）。
好在所有调用方都用 `snprintf` 或字符串字面量，满足这个前提。

**`HAL_UART_Transmit` 是阻塞发送** —— 115200 波特率下，发 30 字节约 2.6ms，
CPU 在这期间干等着。`ESP8266_TX_TIMEOUT = 1000ms` 是保护：
万一串口硬件故障（比如 TX 脚被短路），不至于永久卡死。

### ④ 交给 `WaitResponse` 收尾

**这就是分层的好处**：`SendCmd` 完全不懂 AT 协议。
它不知道发的是 `AT+CWJAP` 还是 `AT+RST`，也不知道要等 `OK` 还是 `CONNECT`
—— 这些都作为参数传进来。

**新增一条 AT 命令时，这一层一行都不用改。**

## 四、初始化：`ESP8266_Init` 与 `ESP8266_Reset`

### 4.1 `ESP8266_Reset` —— 硬复位

```c
ESP8266_Status ESP8266_Reset(void)
{
    // 拉低RST引脚进行复位
    HAL_GPIO_WritePin(ESP8266_RST_PORT, ESP8266_RST_PIN, GPIO_PIN_RESET);
    BSP_DelayMs(100);
    // 释放RST引脚
    HAL_GPIO_WritePin(ESP8266_RST_PORT, ESP8266_RST_PIN, GPIO_PIN_SET);
    // 等待ESP8266启动
    BSP_DelayMs(1000);

    return ESP8266_OK;
}
```

> 📌 老版本这里写的是 `HAL_Delay()`，现在是 `BSP_DelayMs()`
> （见 `BSP/bsp_delay/bsp_delay.h`）：**裸机时它等价于 `HAL_Delay`（忙等），
> 上了 FreeRTOS 就变成 `vTaskDelay`（挂起本任务、让出 CPU）** ——
> 靠的是"强符号覆盖弱符号"两份实现（`BSP/bsp_delay.c` 弱定义 +
> `APP/app_delay.c` 强定义）。所以驱动里那句 1000ms 的等待，
> 在任务里**不会**白占 CPU 一秒。`esp8266.c` 里所有延时都走这个函数。

**知识点｜复位的两种方式：**

| | 硬复位（本项目） | 软复位 `AT+RST` |
|---|---|---|
| 方式 | 拉低 RST 引脚 | 发串口命令 |
| 依赖串口 | **不依赖** | 依赖 |
| 能救活假死模块 | **通常可以** | 可能不行 |
| 需要额外引脚 | 需要 | 不需要 |

**为什么选硬复位？** 因为 `Init` 面对的正是**状态未知**的模块：
可能上次运行崩溃了、可能刚热插拔、可能串口协议错乱了。
此时发 `AT+RST` 本身就是"假设串口是通的"—— 而这恰恰是不确定的。

**硬复位是唯一不依赖任何软件状态的手段**，这也是为什么
`project.ioc` 里专门占用了 **PB1** 这个引脚。

**100ms 是什么依据？** ESP8266 手册规定 RST 低电平保持时间
**最小 200µs**。100ms 远超这个要求，属于"给足余量"——
反正复位只在开机时做一次，多等 100ms 无所谓。

**1000ms 是什么依据？** 复位释放后，模块要加载固件、初始化射频，
**这段时间串口完全没有响应**。如果不等就开始发 `AT`，必然超时。
手册推荐等待时间在几百毫秒量级，1000ms 是保守取值。

### 4.2 `ESP8266_Init` —— 自适应流水线

现在的 `Init`（`esp8266.c:164-233`）一共 **8 步**，比老版本多了 3 步
（② 挂 DMA、⑥ 可选恢复出厂、⑧ 关自动重连）。骨架一览
（行号都是 `esp8266.c` 的）：

| # | 步骤 | 位置 | 干什么 |
|---|---|---|---|
| ① | 配 RST 引脚 | `:169-175` | 开 GPIOB 时钟 + PB1 配推挽输出 |
| ② | `ESP8266_RxStart()` | `:181` | **先把 DMA 接收挂上** ← 新 |
| ③ | `ESP8266_Reset()` | `:188` | 拉 RST 硬复位（内部已等 1000ms） |
| ④ | `BSP_DelayMs(1000)` | `:195` | 再等模块启动 |
| ⑤ | `ESP8266_Test()` | `:198` | `"AT\r\n"` → 期望 `"OK"` |
| ⑥ | `AT+RESTORE` | `:204-209` | **可选**：恢复出厂（开关默认 `0` = 关）← 新 |
| ⑦ | `ATE0` | `:213` | 关回显（**必须排在 ⑥ 之后**） |
| ⑧ | `AT+CWAUTOCONN=0` | `:230` | **关掉模块自作主张的自动重连** ← 新 |

每一步都查返回值、失败立刻 `return`；只有 ⑥ 和 ⑧ 是 `(void)` 忽略返回值的
—— 它们失败了不影响"模块可用"这个目标。

**结构特点：每一步都检查，失败立刻返回。**
这叫**快速失败（fail-fast）**——不在错误的前提下继续往下走。

对比"不检查"的写法：如果 ⑤ 失败了还继续发 `ATE0`，又会超时 5 秒，
最后返回的错误可能是 `ATE0` 的超时，而**真正的问题在 ⑤**——
错误信息被污染了，排查方向完全跑偏。

**② 的细节：为什么 DMA 要在复位**之前**挂上？**

```c
    /* 先把 DMA 接收挂上, 再复位模块 —— 复位后 ESP8266 吐的那串启动日志
     * 也会被收下来, 后面的 AT 测试能直接对上.
     * 更重要的是: 从这一刻起无论 CPU 在忙什么(哪怕在关中断跑 DHT11 的
     * 4ms 位流), 串口来的字节都由 DMA 搬进内存, 一个都不会丢. */
    status = ESP8266_RxStart();
    if (status != ESP8266_OK)
    {
        return status;
    }
```

顺序反了会怎样？复位后模块先吐一串启动日志、再回 `OK`，如果那会儿 DMA
还没挂上，这些字节就是**真丢了**（F1 的串口连 FIFO 都没有）——
现象是 `AT` 测试莫名其妙超时。**"先开接收，再动模块"，是这类驱动的通用顺序。**

> ⚠️ **`RxStart` 里第一行 `HAL_UART_DMAStop()` 不能省**（`esp8266.c:44-58`）。
> `HAL_UART_Receive_DMA()` 要求 `RxState == READY`：第一次调用没问题，
> 但 `ESP8266_Init()` 会被上层**反复调用**（连不上就重试），第二次进来时
> DMA 还在环形模式里转、`RxState` 停在 `BUSY_RX`，于是这里返回失败、
> `Init` 立刻退出 —— **连模块都不复位了**。症状很有迷惑性：
> 第一次失败之后**永远**失败，看着像模块坏了或者接触不良，
> 其实只是漏了这一行。`HAL_UART_DMAStop()` 内部会把 `RxState` 复位成
> `READY`，重开就能成功。

**① 的细节：`__HAL_RCC_GPIOB_CLK_ENABLE()`**

**知识点｜STM32 的外设时钟默认是关闭的**，省电。
不先开时钟就直接配置 GPIO，**所有寄存器写入都无效**——
`HAL_GPIO_Init` 会正常返回，但引脚毫无反应。

这是 STM32 新手最常踩的坑之一，而且**现象很迷惑**：
代码看着完全正确，就是不动。

（如果 `main.c` 里 CubeMX 生成的 `MX_GPIO_Init` 已经开过 GPIOB 时钟，
这一行是冗余的。但**驱动应该自包含** —— 不该依赖"调用者恰好开过时钟"。）

**`GPIO_MODE_OUTPUT_PP` = 推挽输出**：
能主动输出高电平和低电平。对比开漏输出（`GPIO_MODE_OUTPUT_OD`）
只能拉低、要靠外部上拉电阻拉高。

**RST 用推挽是对的** —— 我们要主动把引脚**拉低**才能复位，
开漏虽然也能拉低，但拉高要靠外部电阻，上升沿会变缓。

**⑦ 的细节：`ATE0` 关回显**

**知识点｜ESP8266 出厂默认回显是开着的：**

```
发送: AT
接收: AT        ← 回显：把你发的原样返回
      OK        ← 真正的响应
```

**不关回显会导致 `strstr` 误判**（见 2.④）：
你发的命令文本会混进缓冲区，如果命令里恰好包含 `OK`、`ERROR` 之类的
关键字，匹配结果就完全错了。

比如 `AT+CWJAP="Home","OK888888"` —— 密码里有 `OK`，
回显回来立刻被 `strstr(buf, "OK")` 命中，**WiFi 还没连就报成功**。

关掉之后缓冲区里只剩模块的真正回复，干净可靠。

**⑥ 的细节：可选的 `AT+RESTORE`**

```c
#if ESP8266_FACTORY_RESET_ON_BOOT
    /* 恢复出厂, 清掉模块自己存在 flash 里的那个 AP 配置。
     * 什么时候需要、用完怎么收场, 见 esp8266.h 里这个开关的说明。 */
    (void)ESP8266_SendCmd("AT+RESTORE\r\n", "ready", 15000);
    BSP_DelayMs(2000);              // 模块内部重启, 等它缓过来
#endif
```

**知识点｜模块的 flash 里存着"上次连过的 AP"，这是很多玄学问题的源头。**
密码改了、AP 没了，它还会在后台没完没了地重连，跟我们要发的 `AT+CWJAP`
抢同一套射频状态。`AT+RESTORE` 把这些旧账一次清干净。

注意三件事：
1. 它是**用宏开关包起来的**（`esp8266.h:30`，默认 `0`），因为这条命令要好几秒
2. 期望响应是 **`"ready"`** 而不是 `"OK"` —— RESTORE 后模块内部会重启，
   返回的是启动完成的 `ready`
3. **`ATE0` 必须排在它后面**：恢复出厂会把回显重新打开

> 📌 顺带一个无关但容易踩的点：RESTORE 会把串口波特率也恢复成出厂值
> 115200。本项目正好就是 115200，所以不受影响 —— 别的项目改过波特率
> 再开这个开关，会**当场失联**。

**⑧ 的细节：`AT+CWAUTOCONN=0` 关掉模块的自动重连**

```c
    (void)ESP8266_SendCmd("AT+CWAUTOCONN=0\r\n", "OK", ESP8266_TIMEOUT);
```

`AT+CWAUTOCONN` 默认是 1：一上电，模块就自己往 flash 里存的 AP 连。
那个 AP 要是密码改了或者不在了，它就在后台一直重试 —— 症状极有迷惑性：
**扫描能扫到、信号满格，但 `CWJAP` 就是失败**，而且响应里会先冒一条
`WIFI DISCONNECT`（后台重连失败留下的）。

**连接由我们全权负责**（见 5.3 里的 `CWQAP` + `CWJAP`），不需要它自作主张。
这条设置是持久化的，但每次开机重发一遍不费事，也省得依赖 flash 里存了什么。

**注意 ⑤ 和 ③④ 里的两次 1000ms 等待是重复的**（`Reset` 里已经等过 1000ms）。
合计约 2 秒。这不影响正确性，属于历史遗留的冗余等待 ——
可以删掉 ⑤ 前面的那句 `BSP_DelayMs(1000)`，保留也无害（只是开机慢 1 秒）。
**下面第七节会列出这类遗留问题。**

**一个刻意的职责划分**：`Init` 里**没有** `AT+CWMODE` 和 `AT+CWJAP`。

因为 `Init` 只负责"**让模块可用**"——能通串口、能认 AT、回显关掉。
至于"连哪个 WiFi、连哪台服务器"属于**业务配置**，
应该由上层决定（现在是 `APP/task_wifi.c` 的 `WifiConnect()`）——
因为可能要从 Flash 读配置、可能要支持配网。

**驱动的边界应该是"能力"，不是"策略"。**

## 五、业务接口层 —— 逐函数

### 5.1 `ESP8266_Test` —— 最小的业务函数

```c
ESP8266_Status ESP8266_Test(void)
{
    return ESP8266_SendCmd("AT\r\n", "OK", ESP8266_TIMEOUT);
}
```

**一行**。但它是整个分层设计的**最好证明**：
`AT` 命令、"OK" 响应、"5 秒超时"这三个业务信息，全部作为参数
传给一个**完全不懂 AT 协议**的 `SendCmd`。

**知识点｜`AT` 是"心跳"命令**：模块收到后不执行任何操作，直接回 `OK`。
用途就是**验证串口链路是否通畅**。

它是**分步排查的第一步**（见《知识点笔记》第 7.1 节）：
`AT` 都不回，后面全都不用试了。

**`"AT\r\n"` 里的 `\r\n`** —— 这是 AT 协议的硬性要求，**缺一不可**。
很多人第一次写驱动时忘了 `\r\n`，然后对着"模块无响应"排查半天。
**模块其实在等换行符。**

### 5.2 `ESP8266_SetWiFiMode`

```c
ESP8266_Status ESP8266_SetWiFiMode(ESP8266_WiFiMode mode)
{
    char cmd[24];

    // 用 snprintf 并传入实际缓冲区大小, 避免格式化结果溢出栈数组
    (void)snprintf(cmd, sizeof(cmd), "AT+CWMODE=%u\r\n", (unsigned)mode);

    // 若当前已是该模式, ESP8266 返回 "no change" 而非 "OK", 需一并视为成功
    if (ESP8266_SendCmd(cmd, "OK", ESP8266_TIMEOUT) == ESP8266_OK)
    {
        return ESP8266_OK;
    }
    if (strstr((char *)ESP8266_RxBuf, "no change") != NULL)
    {
        return ESP8266_OK;
    }
    return ESP8266_ERR_AT;
}
```

#### 5.2.1 知识点｜`no change` 不是错误

**这是 AT 协议里最容易误判的一个响应。**

如果设置的值和当前值**相同**，ESP8266 不回 `OK`，而是回 `no change`：

```
发送: AT+CWMODE=1
接收: no change        ← 注意：没有 OK
```

如果只等 `OK`，会走到 `WaitResponse` 的第 ⑦ 步返回 `ESP8266_ERR_TIMEOUT`
—— **明明设置成功了却报超时**。

所以这里额外检查一次 `no change`，视为成功。

**为什么不能直接在 `WaitResponse` 里把 `no change` 也算成功？**
因为 `no change` 只对**设置类**命令有意义。
如果 `AT+CWJAP`（连接路由器）回了 `no change`，那**绝不是成功**
—— 连 WiFi 是要执行动作，不是设置一个值。

**所以"no change 算不算成功"是业务层的知识，不能下沉到命令层。**
这正是分层的价值：通用逻辑在下，特例处理在上。

#### 5.2.2 知识点｜`AT+CWMODE` 的三种模式

| 值 | 模式 | 含义 | 本项目 |
|---|---|---|---|
| 1 | STA | **客户端**，连别人的路由器 | ✅ 用这个 |
| 2 | AP | 热点，自己是路由器 | — |
| 3 | STA+AP | 两者同时 | — |

这也解释了 `esp8266.h` 里的枚举：

```c
typedef enum {
    ESP8266_MODE_STA    = 1,
    ESP8266_MODE_AP     = 2,
    ESP8266_MODE_STA_AP = 3
} ESP8266_WiFiMode;
```

**枚举值直接等于 AT 参数值**（1/2/3），这样传参时可以直接
`snprintf("%u", mode)`，不需要写 `switch` 转换表。

#### 5.2.3 代码细节｜为什么用 `snprintf`

**知识点｜`snprintf` vs `sprintf`：**

| | 溢出风险 | 说明 |
|---|---|---|
| `sprintf(buf, fmt, ...)` | **无保护** | 超出就冲垮栈上相邻变量 |
| `snprintf(buf, size, fmt, ...)` | **有保护** | 超长时截断，最多写 `size-1` 字节 + `'\0'` |

**`AF+CWMODE=` 这种命令长度可控，理论上不会溢出。
但用 `snprintf` 是防御性编程的习惯** —— 万一以后有人改成
`AT+CWMODE=%s` 传用户输入，就不会出栈溢出漏洞。

`(void)` 前缀是**显式忽略返回值**。`snprintf` 返回"本应写入的长度"
（截断时大于 `size`），这里不需要，加 `(void)` 告诉编译器
"我知道有返回值，故意不用" —— 可以消除编译器的 warning。

**栈数组大小 24 的依据**：`"AT+CWMODE=3\r\n"` 是 13 字节，
留了近一倍余量，足够。

### 5.3 `ESP8266_ConnectWiFi`

```c
ESP8266_Status ESP8266_ConnectWiFi(const char *ssid, const char *password)
{
    char cmd[128];

    if (ssid == NULL || password == NULL)
    {
        return ESP8266_ERR_PARAM;
    }

    /* 先断开可能残留的关联, 再连。
     * 没连的时候 AT+CWQAP 就是个空操作, 但模块要是卡在"半连不连"的状态
     * (上一次失败留下的), 不先清干净会一直连不上 —— 而且表现得很像密码错,
     * 光看 +CWJAP:4 分不出来。失败无所谓, 忽略返回值。 */
    (void)ESP8266_SendCmd("AT+CWQAP\r\n", "OK", ESP8266_TIMEOUT);

    // SSID 最长 32 字节, 密码最长 63 字节, 加命令前缀约 113 字节, 128 够用。
    // 仍用 snprintf 兜底: 超长时截断, 而不是冲垮栈上的相邻变量。
    (void)snprintf(cmd, sizeof(cmd), "AT+CWJAP=\"%s\",\"%s\"\r\n", ssid, password);
    return ESP8266_SendCmd(cmd, "OK", ESP8266_WIFI_TIMEOUT);
}
```

**代码细节｜第一句 `AT+CWQAP` 是干什么的？**（老版本没有这一句）

`AT+CWQAP` = 断开当前 AP 关联。**没连的时候它就是个空操作**，
返回 `ERROR` 也无所谓 —— 所以这里 `(void)` 忽略返回值，不检查。

**那为什么还要发？** 因为模块可能卡在"**半连不连**"的状态：上一次 `CWJAP`
失败了、后台自动重连还在折腾、或者关联表里留着一半的垃圾。这时候直接发
`CWJAP` 会一直失败，**而且报出来的错码跟"密码错"长得一模一样** ——
光看 `+CWJAP:4` 根本分不出是密码不对还是状态不干净。

**先清干净再连，是跟外部模块打交道的一条通用经验**：
不要假设它处于"空闲"状态，先把它掰回你要的起点再谈下一步。
（对比 5.4 里每次连接前都发一次 `AT+CIPMUX=0` —— 同一个思路。）

> 配套的还有 `Init` 末尾那句 `AT+CWAUTOCONN=0`（见 4.2 ⑧）：
> 它管的是"**别让模块自己**去连"，这一句管的是"**把残留的**连清掉"。
> 两句合起来，`CWJAP` 的成功率才稳。

#### 5.3.1 知识点｜`AT+CWJAP` 的响应

成功时：

```
WIFI CONNECTED         ← 主动上报①
WIFI GOT IP            ← 主动上报②（DHCP 拿到 IP）

OK                     ← 同步响应
```

**注意 `OK` 前面有两行主动上报和空行** —— 这就是 2.④ 说的
"为什么必须用 `strstr` 而不是逐行匹配"的实例。

失败时返回带错误码的 `FAIL`（见《知识点笔记》4.2）：

| 返回 | 原因 |
|---|---|
| `+CWJAP:1` | **连接超时**（热点多半不在范围内） |
| `+CWJAP:2` | **密码错误** |
| `+CWJAP:3` | 找不到目标 AP |
| `+CWJAP:4` | **连接失败 —— 热点主动拒绝**（黑名单/"已阻止的设备"最常见） |

驱动统一返回 `ESP8266_ERR_AT`，但配合 `ESP8266_GetRxBuf()` 就能看到具体码。

> ⚠️ **`1` 和 `4` 别搞混 —— 这两个查错方向是相反的。**
> 这张表以前就写反了（把 1 写成"找不到 SSID"、4 写成"连接超时"）。
> 官方定义是：1 = 连接超时、四 = 连接失败（被拒）。
>
> 实际排查时：`+CWJAP:4` 且**扫描名单里能看到这个热点**，
> 基本就是**热点把它拒了**（手机热点里被拉黑 / 客户端满了 /
> 开了"仅允许已添加的设备"），不是模块的锅。项目里专门有个
> `WifiDiagScan()`（`task_wifi.c:97`）在失败分支跑一次 `AT+CWLAP`
> 来分这两类 —— 详见 §5.10 和《踩坑笔记》。

#### 5.3.2 代码细节｜转义引号

```c
"AT+CWJAP=\"%s\",\"%s\"\r\n"
```

**`\` 是 C 语言的转义符**。因为字符串本身用 `"` 包围，
里面要用 `"` 就必须写成 `\"`。

**最终发出去的字节**（不含反斜杠）：

```
AT+CWJAP="MyWiFi","12345678"\r\n
```

**知识点｜AT 协议要求字符串参数必须带双引号**：

| 写法 | 结果 |
|---|---|
| `AT+CWJAP="MyWiFi","12345678"` | ✅ |
| `AT+CWJAP=MyWiFi,12345678` | ❌ `ERROR` |

#### 5.3.3 为什么缓冲区是 128 字节

**这是有明确依据的**：

| 项 | 长度 |
|---|---|
| SSID 规范上限 | 32 字节 |
| 密码规范上限 | 63 字节 |
| `AT+CWJAP=""` + `,""` + `\r\n` 等固定部分 | 约 18 字节 |
| **合计** | **约 113 字节** |

128 有约 15 字节余量。**但注释里写了"仍用 snprintf 兜底"**——
因为 SSID/密码是**外部输入**（可能从 Flash 读出脏数据），
不能假设它们守规矩。

**这就是"知道边界，但不信任边界"的防御性编程。**

#### 5.3.4 超时为什么是 15 秒

```c
return ESP8266_SendCmd(cmd, "OK", ESP8266_WIFI_TIMEOUT);   // 15000ms
```

**因为连接路由器是所有 AT 操作里最慢的**：

1. 扫描信道，找这个 SSID
2. 认证（WPA2 握手，多次往返）
3. 关联
4. DHCP 请求 IP（又是几次往返）

信号差时可能十几秒。用默认的 5 秒会**频繁误报超时**，
甚至在信号边缘"有时成功有时失败" —— 这种间歇性故障最难查。

### 5.4 `ESP8266_TCPConnect`

```c
ESP8266_Status ESP8266_TCPConnect(const char *ip, uint16_t port)
{
    char cmd[128];
    ESP8266_Status status;

    if (ip == NULL)
    {
        return ESP8266_ERR_PARAM;
    }

    // 先确保单连接模式。CIPMUX 默认就是 0, 但若之前进过 AP 模式或执行过
    // CIPMUX=1, 残留在多连接模式下 CIPSTART 的语法不同, 会直接失败。
    status = ESP8266_SendCmd("AT+CIPMUX=0\r\n", "OK", ESP8266_TIMEOUT);
    if (status != ESP8266_OK)
    {
        return status;
    }

    (void)snprintf(cmd, sizeof(cmd), "AT+CIPSTART=\"TCP\",\"%s\",%u\r\n",
                   ip, (unsigned)port);
    return ESP8266_SendCmd(cmd, "CONNECT", ESP8266_TCP_TIMEOUT);
}
```

> 📌 形参叫 `ip`，但**传字符串就行** —— 项目实际传的是域名
> （`CFG_MQTT_HOST`，见 `task_wifi.c:179`），DNS 是模块自己解析的。
> 名字取得窄了点，不影响能力。

#### 5.4.1 知识点｜`AT+CIPMUX` 为什么必须先设 0

**`CIPMUX` 决定模块能否同时开多条 TCP 连接，而且它改变了
`AT+CIPSTART` 的语法**：

| CIPMUX | 模式 | `CIPSTART` 语法 |
|---|---|---|
| 0 | 单连接 | `AT+CIPSTART="TCP","ip",port` |
| 1 | **多连接** | `AT+CIPSTART=`**`<id>,`**`"TCP","ip",port` ← **多一个 id** |

**如果残留在多连接模式**，而代码用单连接语法去连 ——
模块会把 `"TCP"` 当成连接 id 解析，直接报错。

**为什么会残留？** `CIPMUX` 的值是持久的：
- 模块上电默认是 0
- 但如果之前跑过别的程序（或手动发过 `AT+CIPMUX=1`），它可能还是 1
- 而且 `ESP8266_Init()` **不会重置它**（硬复位不改变 AT 配置）

**所以每次连接前都发一次 `AT+CIPMUX=0` 兜底** ——
这是**幂等操作**（设成 0 时如果已经是 0，回 `OK` 或 `no change`，都算成功），
代价只是多一次往返，换来的是状态确定性。

> **设计原则：不要假设外部设备处于某个状态，主动把它设成你要的状态。**
> 这叫**幂等初始化**，是嵌入式与外部模块打交道的通用手法。

#### 5.4.2 知识点｜`AT+CIPSTART` 的响应是 `CONNECT` 不是 `OK`

```c
return ESP8266_SendCmd(cmd, "CONNECT", ESP8266_TCP_TIMEOUT);
```

成功时：

```
CONNECT

OK
```

**注意 `CONNECT` 在前，`OK` 在后。** 如果这里等的是 `"OK"`，
理论上也能匹配上 —— 但会**多等一个往返**，而且语义不准确。

更重要的是：**等 `CONNECT` 能在连接建立的第一时间返回**。
TCP 三次握手的完成信号就是 `CONNECT` 这一行。

**`ESP8266_TCP_TIMEOUT = 10 秒`** 的依据：
TCP 连接要经过 DNS 解析（如果传域名）+ 三次握手，
跨公网时延可能到几秒。比本地命令慢，但比 WiFi 关联快。

> ⚠️ **`CONNECT` 匹配的一个隐患**：`WIFI DISCONNECT` 这个主动上报里
> 也含 `CONNECT` 子串！不过在这条命令的上下文里，
> `WIFI DISCONNECT` 出现意味着网络刚断，此时连接本来就会失败，
> 实际影响很小。这类子串误匹配是 `strstr` 方案的固有代价 ——
> 更严谨的做法是匹配 `"CONNECT\r\n"`。

#### 5.4.3 代码细节｜`(unsigned)port`

```c
"AT+CIPSTART=\"TCP\",\"%s\",%u\r\n", ip, (unsigned)port
```

**知识点｜`uint16_t` 传给可变参数函数会触发"默认参数提升"**，
在 C 里会被提升为 `int`。虽然 `%u` 期望 `unsigned int`，
而 `uint16_t` 提升后是 `int` —— 正数时值相同，能正常工作。

显式写 `(unsigned)` 是**明确表达意图**：这里要的是无符号数。
可以消除编译器的格式警告，也让代码意图更清楚。

**端口 0~65535**，`uint16_t` 刚好覆盖，不会溢出。

### 5.5 `ESP8266_TCPDisconnect`

```c
ESP8266_Status ESP8266_TCPDisconnect(void)
{
    return ESP8266_SendCmd("AT+CIPCLOSE\r\n", "OK", ESP8266_TIMEOUT);
}
```

**一行**，又一次印证分层设计。

**知识点｜`AT+CIPCLOSE` 在不同模式下语法不同**：

| 模式 | 语法 |
|---|---|
| 单连接（CIPMUX=0） | `AT+CIPCLOSE` |
| 多连接（CIPMUX=1） | `AT+CIPCLOSE=<id>` |

因为 `TCPConnect` 里保证了 `CIPMUX=0`，所以这里可以不带参数。

**注意**：如果连接已经断了，`CIPCLOSE` 会返回 `ERROR`。
严格来说"断开一个已断开的连接"也应该算成功（幂等），
但当前实现会返回 `ESP8266_ERR_AT`。**这是可以改进之处。**

### 5.6 `ESP8266_TCPSend` —— 全篇最复杂的一个

```c
ESP8266_Status ESP8266_TCPSend(const uint8_t *data, uint16_t len)
{
    char cmd[24];
    ESP8266_Status status;

    if (data == NULL || len == 0)
    {
        return ESP8266_ERR_PARAM;
    }

    // 设置发送长度 ("AT+CIPSEND=65535\r\n" 共 19 字节)
    (void)snprintf(cmd, sizeof(cmd), "AT+CIPSEND=%u\r\n", (unsigned)len);
    status = ESP8266_SendCmd(cmd, ">", ESP8266_TIMEOUT);
    if (status != ESP8266_OK)
    {
        return status;
    }

    // 发送数据
    if (HAL_UART_Transmit(&ESP8266_UART, (uint8_t *)data, len,
                          ESP8266_TX_TIMEOUT) != HAL_OK)
    {
        return ESP8266_ERR_AT;
    }

    // 只等响应, 不再发命令。原来用 SendCmd("") 时, HAL_UART_Transmit 在
    // Size==0 时直接返回 HAL_ERROR, 那次调用其实是个空操作。
    return ESP8266_WaitResponse("SEND OK", ESP8266_TIMEOUT);
}
```

> 下面还是按老的 ①②③④ 编号讲（对应上面四段：参数检查 / 发长度 / 发数据 / 等回执），**代码里没有这些标记**。

#### 5.6.1 知识点｜`AT+CIPSEND` 的两步式交互

**这是 AT 协议里最特殊的一个命令 —— 它不是"一条命令一个响应"，
而是"一条命令 + 一段裸数据"。**

完整交互：

```
STM32 →  AT+CIPSEND=5\r\n          第一步：声明"我要发 5 字节"
ESP  →  \r\nOK\r\n>                模块回 '>' ，表示"准备好了，发吧"
STM32 →  HELLO                     第二步：裸数据，不是 AT 命令！
ESP  →  \r\nSEND OK\r\n            确认发送成功
```

**四个必须记住的点：**

| # | 规则 | 违反的后果 |
|---|---|---|
| 1 | `AT+CIPSEND=` 后面是**长度**，不是数据 | 模块把数据当长度解析 → `ERROR` |
| 2 | 必须**等到 `>`** 才能发数据 | 数据被当 AT 命令解析 → `ERROR` |
| 3 | 数据**不加引号、不加 `\r\n`** | 多发字节，长度对不上 → 数据被截断或污染 |
| 4 | 长度必须**完全准确** | 多了模块死等，少了数据被截断 |

**第 4 点最隐蔽**：`len` 是 `uint16_t`，最大 65535。
但 ESP8266 单次 `CIPSEND` **实际有上限**（受模块缓冲区限制，
通常约 2048 字节）。**当前代码没有检查这个上限** —— 见第七节。

#### 5.6.2 ② 为什么等的是 `">"` 而不是 `"OK"`

**知识点｜`>` 是 AT 协议的"数据模式提示符"**，
表示"模块已从命令模式切到数据模式，接下来收到的不当命令解析"。

**这是整个 AT 协议里唯一一个用单字符做响应的场景。**
单字符更容易被误匹配（比如响应里任何位置出现 `>`），
但 `CIPSEND` 的响应格式固定为 `\r\nOK\r\n>`，
`>` 总在最后，实际风险很低。

#### 5.6.3 ③ 数据发送 —— 唯一绕过 `SendCmd` 的写串口点

```c
HAL_UART_Transmit(&ESP8266_UART, (uint8_t *)data, len, ESP8266_TX_TIMEOUT);
```

**这里为什么不能调 `SendCmd`？** 因为 `SendCmd` 会先调 `ClearRxBuf()`
—— 而此刻缓冲区里存着**第一步收到的 `>`**，清掉就丢掉上下文了
（虽然这里其实不再需要它）。

更重要的是**语义**：`SendCmd` 是"发 AT 命令"，而这里是"发裸数据"。
**两者是完全不同的东西，不该用同一个函数。**

#### 5.6.4 ④ 为什么用 `WaitResponse` 而不是 `SendCmd("")`

**这是本次优化中最有价值的一处修复。**

原代码：

```c
return ESP8266_SendCmd("", "SEND OK", ESP8266_TIMEOUT);   // ❌ 依赖巧合
```

它**能跑**，但靠的是巧合：`HAL_UART_Transmit` 在 `Size==0` 时
返回 `HAL_ERROR`，等于什么也没发。也就是说，**"发一条空命令"
这个动作之所以没造成破坏，纯粹是因为 HAL 内部的一个边界判断。**

**为什么这是隐患？**

1. **语义完全错误** —— 读代码的人以为"发了个空命令"，实际上是个 no-op
2. **依赖未定义行为** —— HAL 从没承诺"Size==0 时返回错误"，
   这只是实现细节
3. **脆弱** —— 只要 HAL 升级改了行为，或者有人给 `SendCmd` 加了
   返回值检查（`if (status != HAL_OK) return ESP8266_ERR_AT;`），
   **发送数据功能会立刻坏掉**，而且改动者根本想不到影响在这里

改成：

```c
return ESP8266_WaitResponse("SEND OK", ESP8266_TIMEOUT);   // ✅ 语义明确
```

**函数名就说清楚了：只等，不发。** 这正是为什么 `WaitResponse`
要从 `SendCmd` 里**独立出来成为公开 API**（见 `esp8266.h:79`）。

> **通用经验：代码里每出现一处"靠巧合工作"的地方，
> 就是在给未来埋一颗定时炸弹。发现后立刻改成显式表达。**

#### 5.6.5 知识点｜`SEND OK` vs 其他响应

| 响应 | 含义 |
|---|---|
| `SEND OK` | 数据已交给 TCP 栈，发送成功 |
| `SEND FAIL` | 发送失败（通常是连接已断） |

**注意 `SEND OK` 里包含 `OK`**，所以理论上等 `"OK"` 也能匹配上。
但显式写 `"SEND OK"` 更**精确** —— 避免匹配到前面残留的 `OK`。

> ⚠️ **`SEND FAIL` 的漏判**：`WaitResponse` 里查的是 `"FAIL"` 子串，
> 而 `SEND FAIL` 里含 `FAIL` —— **所以能被正确捕获**（返回 `ESP8266_ERR_AT`）。
> 这一点是幸运的，但依赖了子串包含关系。更严谨的写法应该显式列出
> `"SEND FAIL"`。

### 5.7 `ESP8266_TCPRecvRaw` —— 收服务器发来的数据

> 📌 **这一节整节换过内容。** 老笔记讲的是
> `ESP8266_TCPReceive(uint8_t *buf, uint16_t len, uint32_t timeout)`，
> 结论是"这是整个驱动里最弱的一个函数"。**那个函数已经不存在了**，
> 取而代之的是 `ESP8266_TCPRecvRaw()`（`esp8266.c:605-683`，
> 声明在 `esp8266.h:163`）。老版本列的四个缺陷 ——
> `+IPD` 前缀污染 / 不知道长度 / 硬编码的 `10` / 不写 `'\0'` ——
> **现在全部解决**。怎么剥的、为什么这么剥，
> 另见《详解/09-ESP8266接收架构与+IPD剥离.md》。

#### 5.7.1 知识点｜TCP 数据是**主动上报**的

**这是整件事的由来。** 前面所有 AT 命令都是"我问 → 它答"，
但服务器推来的数据**没人问也会来**：

```
+IPD,5:HELLO        ← 服务器发来的数据，不请自来
```

| 项 | 说明 |
|---|---|
| `+IPD,` | 前缀，表示"收到 TCP 数据" |
| `5` | 数据长度（字节） |
| `:` | 分隔符 |
| `HELLO` | **真正的数据** |

**老 `TCPReceive` 的三个死穴，正是新函数要解决的三件事：**

1. **数据可能在调用之前就到了** —— 那时没人读串口，字节就丢了
   → 现在 DMA 一直在收（见 1.4），**什么时候来都不丢**
2. **数据被 `+IPD,5:` 污染** —— 老函数不做任何前缀剥离
   → 现在有状态机剥（见 5.7.2）
3. **不知道要收多少** —— 老函数的 `len` 是调用者猜的
   → 现在长度从 `+IPD,<n>` 里读出来，**不用猜了**

#### 5.7.2 代码｜状态机怎么剥 `+IPD`

```c
uint16_t ESP8266_TCPRecvRaw(uint8_t *buf, uint16_t max, uint32_t timeout)
{
    uint32_t startTick = HAL_GetTick();
    uint16_t copied = 0;
    uint16_t room, want, got;
    uint8_t  b;

    if (buf == NULL || max == 0) { return 0; }

    while ((HAL_GetTick() - startTick) < timeout)
    {
        /* ---------- 还没进到 payload 里: 逐字节攒 +IPD 头 ---------- */
        if (ESP8266_IpdLeft == 0)
        {
            if (ESP8266_RxPop(&b, 1) == 0)
            {
                /* 手上有货就先交出去, 别为了等一个头把已经拿到的数据押着 */
                if (copied > 0) { return copied; }
                BSP_DelayMs(1);
                continue;
            }

            /* 换行 = 一条消息的边界, 头状态清零重来.
             * 合法头 "+IPD,<数字>:" 里不可能出现 \r 或 \n, 所以这么做
             * 不会误伤; 但能保证半截的头 (比如模块复位发了个 "+IPD" 就
             * 没下文了) 不会一直占着状态, 把后面真正的头挡在外面. */
            if (b == '\r' || b == '\n')
            {
                ESP8266_IpdHdrLen = 0;
                continue;
            }

            /* 只认 '+' 开头的东西. 模块在 +IPD 前面会先发一对 \r\n
             * (AT 固件的习惯), 别把它当头的第一个字符攒进去 ——
             * 攒进去的话 ParseIpdLen 一看 hdr[0] 不是 '+' 就直接判失败,
             * 而 IpdHdrLen 已经清掉了, 于是下一轮再攒一遍 \r\n……
             * 数据永远解析不出来. 顺手也把 "CLOSED" 这类通知滤掉了. */
            if (ESP8266_IpdHdrLen == 0 && b != '+') { continue; }

            ESP8266_IpdHdr[ESP8266_IpdHdrLen++] = (char)b;

            if (b == ':')
            {
                /* 认完了: 长度写进 IpdLeft, 下一轮开始收 payload */
                if (ESP8266_ParseIpdLen(ESP8266_IpdHdr, ESP8266_IpdHdrLen,
                                        &ESP8266_IpdLeft) != 0)
                {
                    ESP8266_IpdHdrLen = 0;
                    continue;
                }
                ESP8266_IpdHdrLen = 0;      /* 不是 +IPD 头, 丢掉重来 */
            }
            else if (ESP8266_IpdHdrLen >= ESP8266_IPD_HDR_MAX)
            {
                /* 攒满了还没见到 ':' —— 比如 "CLOSED\r\n" 这类通知。
                 * 丢掉重来, 别让一段通知把状态机卡死。 */
                ESP8266_IpdHdrLen = 0;
            }
            continue;
        }

        /* ---------- 正在收 payload ---------- */
        room = (uint16_t)(max - copied);
        if (room == 0) { return copied; }       /* 装满了, 剩下的下次再来 */

        want = (ESP8266_IpdLeft < room) ? ESP8266_IpdLeft : room;
        got  = ESP8266_RxPop(&buf[copied], want);

        copied          = (uint16_t)(copied + got);
        ESP8266_IpdLeft = (uint16_t)(ESP8266_IpdLeft - got);

        /* 一包收完就返回: MQTT 按包解析, 攒两包混在一起反而要在上层拆 */
        if (ESP8266_IpdLeft == 0) { return copied; }

        if (got == 0) { BSP_DelayMs(1); }        /* 没新数据, 让出 CPU */
    }

    return copied;
}
```

**为什么要留状态，不能"攒够一整包再剥"？**

因为**串口是流，头有可能被拆成两半**：`+IPD,5:` 这几个字节在 115200 下
要发近 1ms，正好可能跨过一次搬运 —— 上一次只拿到 `+IP`，下一次才拿到
`D,5:`。所以必须记住"头攒到哪了"：

```c
#define ESP8266_IPD_HDR_MAX   12    /* "+IPD,65535:" 是 11 字符, 留 1 字节余量 */

static char     ESP8266_IpdHdr[ESP8266_IPD_HDR_MAX];    // 正在攒的 +IPD 头
static uint8_t  ESP8266_IpdHdrLen = 0;
static uint16_t ESP8266_IpdLeft = 0;                    // 本包 payload 还欠多少字节
```

**三个变量 = 一台两态状态机**：

| 状态 | 判据 | 干什么 |
|---|---|---|
| ① 攒头 | `ESP8266_IpdLeft == 0` | 逐字节往 `IpdHdr` 里塞；见到 `':'` 就调 `ParseIpdLen` 解析出长度 |
| ② 收数据 | `ESP8266_IpdLeft > 0` | **按长度盲取**，`RxPop` 一次搬一批，`IpdLeft` 减到 0 就收工返回 |

**四处"防卡死"的设计，值得单独看：**

1. **见到 `\r` / `\n` 就清空攒头状态** —— 合法头里不可能有换行，所以
   不会误伤；但能保证**半截的头**（模块复位时只发了 `+IPD` 就没下文了）
   不会永远占着状态，把后面真正的头挡在外面
2. **头必须以 `+` 开头** —— 模块在 `+IPD` 前面习惯先发一对 `\r\n`，
   要是把那对 `\r\n` 也攒进去，`ParseIpdLen` 一看 `hdr[0]` 不是 `+` 就判失败，
   而状态已经清了，下一轮再攒一遍 `\r\n`……**数据永远解析不出来**
   （顺手也把 `CLOSED` 这类通知滤掉了）
3. **攒满 12 字节还没见到 `:`** → 丢掉重来，防"一段长通知把状态机卡死"
4. **payload 是按长度盲取的，不做任何扫描** —— 所以 MQTT 数据里就算
   出现 `"+IPD,"` 字样，也不会被误判成包头。
   **"定长优先于扫描"** 是流协议解析里最稳的一条原则

#### 5.7.3 接口语义｜返回值从"状态码"变成了"字节数"

```c
 * @retval 实际收到的字节数; 0 = 超时内没有数据
```

老函数返回 `ESP8266_Status`（`OK` / `ERR_TIMEOUT`），**却不说收了多少** ——
调用者只能自己数，还得猜结尾在哪。新函数直接返回字节数：
**`0` 就是"这次没拿到"**，一个整数说清所有事。

**`'\0'` 也不是问题了**：`TCPRecvRaw` 交出的是**二进制协议数据**（MQTT 报文），
长度由返回值给出，**根本不该当字符串看**。所以它不写 `'\0'` 不是缺陷，
而是"这一层不管字符串语义"—— 写进去反而会跟 MQTT 报文字节撞车。
（AT 响应那条路依旧靠 `ClearRxBuf` + `RxLen` 上限保证末尾是 `'\0'`，见 1.2。）

**谁在用？** `APP/mqtt.c`，两处：
- `MQTT_Connect()` 等 4 字节 CONNACK（`mqtt.c:162-174`）
- `MQTT_Ping()` 等 2 字节 PINGRESP（`mqtt.c:230-236`）

都是"先算好要几个字节，循环收够为止" —— 正好是新接口配合得上的用法。

#### 5.7.4 与 `WaitResponse` 的对比

| | `WaitResponse` | `TCPRecvRaw` |
|---|---|---|
| 收进哪里 | 内部 `RxBuf`（经 `RxDrain`） | **调用者的 `buf`**（经 `RxPop`） |
| 怎么处理 | 在缓冲里 `strstr` 找 expected | 剥 `+IPD` 包装，交出裸数据 |
| 返回值 | `ESP8266_Status` | **收到的字节数** |
| `'\0'` 保护 | ✅ 缓冲区末尾恒为 `\0` | 不需要（二进制数据，按长度用） |
| 用途 | AT 命令响应 | 服务器推来的 TCP 数据 |

**两条出口都从同一个环里取字节**（见 1.4），但**语义完全不同**：
一个面向"文本 + 子串匹配"，一个面向"二进制 + 定长"。
**分成两个函数而不是加个参数，就是因为这个语义差异。**

#### 5.7.5 前提与限制（用之前得知道）

1. **只在 `CIPMUX=0`（单连接）下成立。** 多连接模式下的包头是
   `+IPD,<id>,<len>:`（多一个连接 id），而 `ESP8266_ParseIpdLen` 只认
   `+IPD,<len>:`，会解析失败。驱动里 `TCPConnect` 每次都先发
   `AT+CIPMUX=0`（见 5.4.1），**所以实际跑不到那个分支** ——
   但这是个"靠上游保证"的隐含前提，记在心上
2. **一次调用最多交出一整包。** 服务器一个 TCP 分段来多少就给多少，
   不跨包攒 —— 上层按流解析、自己处理半包（MQTT 那边就是这么做的）
3. **超时到了但手上已经有数据，也会先交出去**（`if (copied > 0) { return copied; }`）
   —— "别为了等一个头，把已经拿到的数据押着"

> **判断一个函数的"健康度"不能只看它现在能不能跑，
> 要看它的设计假设在当前需求下是否成立。** 老 `TCPReceive` 当年"能用"，
> 是因为项目只上报、不接收；现在 MQTT 要等 CONNACK / PINGRESP，
> 假设一变，函数就得跟着重写 —— 这次就是。
> 需求一变，隐藏的缺陷立刻爆发。

### 5.8 `ESP8266_GetStatus`

```c
ESP8266_Status ESP8266_GetStatus(void)
{
    return ESP8266_SendCmd("AT+CIPSTATUS\r\n", "OK", ESP8266_TIMEOUT);
}
```

**注意：这个函数的返回值几乎没有信息量** ——
它只告诉你"`AT+CIPSTATUS` 命令执行成功"，
**不告诉你连接状态到底是什么**。

状态信息在响应正文里（想要的话，得自己从 `ESP8266_GetRxBuf()` 里解析）：

```
STATUS:3
+CIPSTATUS:0,"TCP","192.168.1.100",8080,52341,0

OK
```

**知识点｜`STATUS:<n>` 的取值**（详见《知识点笔记》4.5）：

| `n` | 含义 |
|---|---|
| 0 | 未初始化 |
| 1 | 已初始化，未连 WiFi |
| 2 | 已连 WiFi，拿到 IP，无 TCP 连接 |
| 3 | **已建立 TCP 传输连接** |
| 4 | 连接已断开 |
| 5 | 未连接 AP |

**改进方向**：应该像 `GetIPAddress` 那样，把 `STATUS:` 后面的数字
解析出来，通过返回值或出参告诉调用者。现在的接口
**让调用者不得不再去 `strstr(ESP8266_GetRxBuf(), "STATUS:3")`** ——
把解析责任推给了上层，破坏了封装。

> 📌 现状补充：**全工程现在没有一处调用 `ESP8266_GetStatus()`**
> （`task_wifi.c` 判断链路死活用的是"连续失败 3 次"而不是查状态）。
> 它现在就是个**手动调试用的工具函数** —— 串口敲不上 AT 的时候，
> 有它在固件里可以直接在代码里调一次看结果。

### 5.9 `ESP8266_GetIPAddress` —— 兼容性处理的范例

```c
ESP8266_Status ESP8266_GetIPAddress(char *ip, uint8_t len)
{
    ESP8266_Status status;
    char *p;

    // len 至少为 2 才能容纳 1 个字符 + 结尾 '\0'
    if (ip == NULL || len < 2)
    {
        return ESP8266_ERR_PARAM;
    }

    status = ESP8266_SendCmd("AT+CIFSR\r\n", "OK", ESP8266_TIMEOUT);
    if (status != ESP8266_OK)
    {
        return status;
    }

    // 查找IP地址
    // AT固件 v1.x: +CIFSR:STAIP,"192.168.1.100"
    // AT固件 v2.x: 直接返回 192.168.1.100
    p = strstr((char *)ESP8266_RxBuf, "STAIP,\"");
    if (p != NULL)
    {
        p += 7;  // 跳过 "STAIP,\""
    }
    else
    {
        // 兼容不同固件版本, 直接定位第一个数字
        p = (char *)ESP8266_RxBuf;
        while (*p != '\0' && (*p < '0' || *p > '9'))
        {
            p++;
        }
    }

    if (*p != '\0')
    {
        uint8_t i = 0;
        while (*p != '\"' && *p != '\0' && *p != '\r' && *p != '\n' && i < len - 1)
        {
            ip[i++] = *p++;
        }
        ip[i] = '\0';
        return ESP8266_OK;
    }

    return ESP8266_ERR_AT;
}
```

#### 5.9.1 知识点｜AT 固件 v1.x 和 v2.x 的格式差异

**同一个 `AT+CIFSR` 命令，两个固件版本返回格式完全不同：**

**v1.x：**
```
+CIFSR:APIP,"192.168.4.1"
+CIFSR:APMAC,"1a:2b:3c:4d:5e:6f"
+CIFSR:STAIP,"192.168.1.100"      ← 要的是这个
+CIFSR:STAMAC,"aa:bb:cc:dd:ee:ff"

OK
```

**v2.x：**
```
192.168.1.100                    ← 直接就一行 IP
```

**这就是为什么要写两套解析逻辑。** 买模块时不知道固件版本，
写驱动时也**不该假设**用户烧的是哪个版本。

#### 5.9.2 ② 分段解析：`p += 7`

```c
p = strstr((char *)ESP8266_RxBuf, "STAIP,\"");
if (p != NULL) p += 7;
```

`strstr` 返回的是**匹配子串的起始位置**，也就是 `"STAIP,\""` 里
`'S'` 的位置。我们要的是**引号后面的 IP**，所以往后移动 7 个字符。

**为什么是 7？** 数一下 `STAIP,"` ：

```
S T A I P , "
1 2 3 4 5 6 7   ← 7 个字符
```

**注意这里用的是 `+= 7` 而不是 `+= strlen("STAIP,\"")`**。
值是对的，但**用字面数字是脆弱的** —— 如果以后处理的字符串变了，
7 就错了，而且不会报错，只会静默解析出错。更稳的写法：

```c
p += strlen("STAIP,\"");
```

#### 5.9.3 ③ 兜底：找第一个数字

```c
p = (char *)ESP8266_RxBuf;
while (*p != '\0' && (*p < '0' || *p > '9')) p++;
```

**这段是 v2.x 的兼容路径**：跳过所有非数字字符，停在第一个数字上。

`(*p < '0' || *p > '9')` 是**判断"不是数字"的惯用写法**。
**字符 `'0'`~`'9'` 在 ASCII 表里是连续排列的**（48~57），
所以用范围比较就能判断，比查表或调 `isdigit()` 更快。

**"跳过前缀直到找到目标"是一个很实用的解析手法** ——
不需要知道前缀长什么样，只要知道"目标从第一个数字开始"。

> ⚠️ **这个兜底的漏洞**：如果 v2.x 的响应里在 IP **之前**还有别的数字
> （比如固件版本号），就会定位到错误的位置。
> 这是"宽松解析"的固有代价 —— 用**容错性**换**精确性**。

#### 5.9.4 ④ 拷贝循环的五个终止条件

```c
while (*p != '\"' && *p != '\0' && *p != '\r' && *p != '\n' && i < len - 1)
```

**为什么要同时检查五种情况？**

| 条件 | 防的是什么 |
|---|---|
| `*p != '\"'` | v1.x 格式的**结束引号** |
| `*p != '\0'` | 缓冲区**末尾**（防越界） |
| `*p != '\r'` | v2.x 格式的**行尾** |
| `*p != '\n'` | 同上 |
| `i < len - 1` | **出参缓冲区写满**（留 1 字节给 `'\0'`） |

**这体现了"解析未知格式"的核心思路：不要把终止条件建立在
"我知道格式长什么样"上，而是把所有可能的终止情况都列出来。**

因为在两个固件版本之间，IP 后面跟的东西不一样（可能是 `"` ，
也可能是 `\r\n`）。**全都防住，两种格式就都能正确处理。**

**`i < len - 1` 而不是 `i < len`** —— 同样的道理（见 1.2）：
要给 `'\0'` 留位置。循环结束后：

```c
ip[i] = '\0';     // 手动补上结尾符
```

**必须手动补**，因为这个循环是逐字符拷贝的，不会自动加终止符。

#### 5.9.5 ① 参数校验 `len < 2`

```c
if (ip == NULL || len < 2) return ESP8266_ERR_PARAM;
```

**为什么是 2 不是 0？**

最小合法 IP 是 `"1"`（1 个字符 + 1 个 `'\0'` = 2 字节）。
如果 `len == 1`，那么 `len - 1 == 0`，循环条件 `i < 0` 永远为假，
循环体一次都不执行，最后 `ip[0] = '\0'` —— **返回一个空字符串但报成功**。

**调用者拿到空 IP 却以为成功了** —— 又是"静默错误"。
所以 `len < 2` 时直接拒绝，明确报参数错误。

### 5.10 `ESP8266_ScanAP` —— 失败现场的"取证"函数（新加的）

这个函数老版本里**没有**，是连着"热点主动拒绝"那次排查一起加进来的。
它扫一遍周边热点，回答一个问题：**"这个 SSID，模块到底看不看得见？"**

```c
    st = ESP8266_SendCmd("AT+CWLAP\r\n", "OK", ESP8266_SCAN_TIMEOUT);

    /* ERR_BUF_FULL 不当失败: 邻居热点太多时 512 字节装不下后半截名单, 但
     * 已经收上来的那部分照样能查。而且 +CWLAP 是按信号强度从强到弱排的 ——
     * 真要找的那个就在跟前的话, 必然排在名单最前面, 一定收进来了。 */
    if (st != ESP8266_OK && st != ESP8266_ERR_BUF_FULL)
    {
        return st;
    }

    p = strstr((char *)ESP8266_RxBuf, ssid);
    if (p == NULL)
    {
        return ESP8266_ERR_WIFI;        /* 扫完了, 名单里没有 */
    }
```

#### 5.10.1 知识点｜`AT+CWLAP` 和三个返回值的含义

| 返回 | 含义 | 下一步往哪查 |
|---|---|---|
| `ESP8266_OK` + `rssi` | 名单里**有**这个热点 | 热点活着、信号也有 → 多半是**被拒绝**（黑名单/客户端满） |
| `ESP8266_ERR_WIFI` | 扫完了，名单里**没有** | 热点关了/走远了/模块天线或供电有问题 |
| 其他 `ESP8266_ERR_*` | 扫描**本身**没应答 | 模块级的问题，优先怀疑 3.3V 供电 |

**这就是"扫描能不能扫到"作为诊断的价值**：它把"连不上"这个笼统的现象
一刀切成两类。详见 5.3.1 下面那张 `+CWJAP:4` 的说明和《踩坑笔记》。

`AT+CWLAP` 要几秒钟，所以给了独立的 `ESP8266_SCAN_TIMEOUT`（15 秒），
而且**只在失败分支调用**（`task_wifi.c:97` 的 `WifiDiagScan()`），
正常流程一次都不跑。

#### 5.10.2 知识点｜子串匹配的陷阱：找到 ≠ 找对

```c
    if (rssi != NULL)
    {
        /* 名字外层有引号, 所以从名字往后第一个逗号之后就是 RSSI */
        q = strchr(p, ',');
        *rssi = (q != NULL) ? ESP8266_ParseRssi(q + 1) : 0;
    }
```

`strstr((char *)ESP8266_RxBuf, ssid)` 是**子串**匹配 —— 这是这个函数
最大的一个坑，也是 `entry` 这个出参存在的唯一理由：

> 热点真名是 `"奈何神明耍诈的iPhone"`，而配置里写的是 `"奈何神明耍诈"`，
> `strstr` **照样报"找到了"** —— 但 `CWJAP` 拿这个短名字是**连不上**的。
> 于是你就看到一个自相矛盾的现象：**扫描说在，连接说不行。**

**所以必须把名单里那一条的原文抄回来**（`entry` 出参，往前退到 `'('`、
往后到行尾、掐掉 `\r`），让人眼对比"模块看到的真名"和"我们发的名字"。
`task_wifi.c:109-113` 那几行 `printf` 就是这个用途。

> **教训：拿子串匹配当"相等"用，迟早会在某个名字上翻车。**
> 匹配可以用宽松的，但**结论要给到能让人类自己判断的原始信息**。

（`ESP8266_ParseRssi` 是配套的小工具：手写一遍十进制解析、支持负号，
为它引一个 `<stdlib.h>` 的 `atoi` 不划算 —— `esp8266.c:396-415`。）

## 六、数据流全景

把上面的零件串起来，看一次完整的**传感器数据上报**从开始到结束。

> 📌 **这一段整段重写过。** 老笔记画的是"`main()` 里一个大循环，边采集边
> 上报"的**裸机结构**。现在 `main.c` 里**没有任何采集循环**了 ——
> 结构是 `App_Init()` 建队列建任务 → `vTaskStartScheduler()` →
> `TaskWifi` / `TaskDht11` 两个任务各跑各的。

```
【开机阶段】main.c
main()
 ├─ HAL_Init() / SystemClock_Config()            72MHz
 ├─ MX_GPIO_Init() / MX_DMA_Init() / MX_USART2_UART_Init()   115200 8N1
 ├─ App_Init()                                   ← APP/app_main.c
 │   ├─ DHT11_Init()
 │   ├─ xQueueCreate(g_xDht11Queue)              采集 → 通信 的数据通道
 │   ├─ TaskWifiCreate()     优先级 APP_PRIO_WIFI
 │   └─ TaskDht11Create()    优先级 APP_PRIO_DHT11

【TaskWifi / 阶段1：联网】APP/task_wifi.c  WifiConnect()

     ├─ GPIOB 时钟 + PB1 配推挽输出
     ├─ RxStart()   → DMA 环形接收挂上（此后字节一个不丢）
     ├─ Reset()     → RST 拉低 100ms → 拉高 → 等 1000ms
     ├─ 等 1000ms
     ├─ Test()            → "AT\r\n"        → 期望 "OK"     [5s]
     ├─ [可选] RESTORE    → "AT+RESTORE\r\n"→ 期望 "ready"  [15s]
```

### 6.1 三个阶段的特点

| 阶段 | 耗时 | 失败概率 | 失败后果 |
|---|---|---|---|
| **初始化** | 约 2.5 秒 | 低（除非硬件问题） | 直接不可用 |
| **组网** | 5~20 秒 | **高**（信号、密码） | 不可用，需重试 |
| **上报** | 几十毫秒 | 中（网络抖动） | 丢一条数据，可重发 |

**注意组网阶段占了绝大部分时间，而且失败概率最高。**
所以必须有**重试机制** —— 现在的做法是（`task_wifi.c`）：

| 场景 | 恢复路径 |
|---|---|
| 开机连不上 | 外层 `while (WifiConnect() == 0)` + `vTaskDelay(5000)`，**一直试** |
| 连上之后断线 | 上报连续失败 3 次 → 退出内层循环 → **退回外层重跑整个联网流程** |

重连就是重跑一遍 `WifiConnect()` —— 它第一步是 `ESP8266_Init()`，
而 `Init` 会拉 RST 引脚复位模块。所以**模块卡死、socket 半开、只是 WiFi 掉了，
走同一条路都能救回来**，不需要单独的清理流程。

**为什么联网期和采集期现在可以同时跑？**（老版本必须"先联网完，再建采集任务"）

因为老版本收串口是逐字节轮询，`DHT11_Read()` 里有约 4ms 关中断，
那期间 USART2 收到的字节**没人搬就丢了**（F1 的串口连 FIFO 都没有）。
现在字节由 DMA 搬 —— 硬件干活，跟 CPU 关不关中断没关系，
**约束消失了**，那个"启动任务"也就没必要存在了。

### 6.2 所有超时一览

| 命令 | 超时宏 | 值 | 为什么 |
|---|---|---|---|
| `AT` / `ATE0` / `CWMODE` / `CWQAP` / `CWAUTOCONN` | `ESP8266_TIMEOUT` | 5s | 本地执行，瞬间完成 |
| `CWJAP` | `ESP8266_WIFI_TIMEOUT` | **15s** | 扫描+认证+DHCP，最慢 |
| `CIPSTART` | `ESP8266_TCP_TIMEOUT` | **10s** | 握手+DNS |
| `CIPSEND` 等 `>` | `ESP8266_TIMEOUT` | 5s | 本地，快 |

| `CWLAP`（排查用） | `ESP8266_SCAN_TIMEOUT` | **15s** | 扫一圈周边热点，就这么慢 |
| 串口发送 | `ESP8266_TX_TIMEOUT` | 1s | 纯硬件，出问题说明串口坏了 |

## 八、一句话总结

> 这个驱动的骨架是**一个函数**（`WaitResponse`）——
> "要一批字节、匹配、超时"，整个 AT 协议都被收敛进这个循环里。
> （"字节从哪来"已经不归它管了：DMA 在环形缓冲里自己收，见 1.4。）
>
> 外面套一层 `SendCmd`（加"发命令"和"清缓冲"），
> 再外面是十几个一行到十几行的业务函数（提供具体命令和响应）。
>
> 还有**一条与主干并行的支路**：`TCPRecvRaw` —— 同一份字节流的另一个出口。
> 它不匹配、不找子串，只负责把 `+IPD` 包装剥掉、把定长的二进制数据交出去。
> **一个驱动要同时伺候"文本协议"和"二进制协议"，这条分叉就是必须的。**
>
> **三层各有明确职责**：底层只管字节，中层只管收发，上层只管协议。
> 这样新增 AT 命令时中间层一行都不用改 —— 这就是分层的全部价值。
>
