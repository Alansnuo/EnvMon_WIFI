## 一、两套代码根本不是一回事

必须先说清楚，否则照抄参考工程的代码会一路错到底。

| | 参考工程（面包板可用） | 目标工程 `EnvMon_WIFI` |
|---|---|---|
| 库 | 标准外设库 SPL（`stm32f10x_gpio.c` 那套） | HAL（CubeMX 6.15.0 生成） |
| 结构 | 裸机 `while(1)` 大循环 | FreeRTOS V11.3.1，`heap_4` |
| 云 | 机智云 Gizwits，`gizwits_protocol.c` 跑在 MCU 上 | 机智云**不在 MCU 上**；ESP8266 用自带 AT 固件的 MQTT 指令直连 OneNET |
| 延时 | `Delay_ms()` / `Delay_us()`，忙等 | `BSP_DelayMs()`，调度器起来后是 `vTaskDelay`（见下文机制三） |
| 引脚写法 | `PBout(5)`、`GPIO_SetBits()`、`GPIO_WriteBit()` | `HAL_GPIO_WritePin()`，或直接写 `BSRR`/`BRR` |
| ESP8266 口 | USART2 @ **9600**（透传，跑机智云协议） | USART2 @ **115200**（跑 AT 指令） |

**结论**：参考工程可以整篇照抄的只有**功能引脚宏定义**和**协议/时序逻辑**；所有 GPIO 操作、延时、初始化函数都要按 HAL 重写一遍。本套笔记里给出的代码都是**已经按 HAL 重写过的**，直接可编译。

## 三、九个移植决策（本节是整份笔记的结论，逐条在分篇里展开）

### 1. OLED：从 PB0/PB1 改到 PB8/PB9

参考工程 `OLED.h` 里是

```c
#define OLED_SCL   GPIO_Pin_1
#define OLED_SDA   GPIO_Pin_0
#define OLED_PROT  GPIOB
```

你的板子走的是 PB8/PB9，两个宏改成 `GPIO_PIN_8` / `GPIO_PIN_9` 即可。驱动本体（软件 I2C + SSD1306 命令序列）一个字都不用动。

参考工程里 PB6~PB9 原本是 4 个按键，**你的板子没有按键**，所以不冲突。详见 [02-OLED显示屏移植.md](02-OLED显示屏移植.md)。

### 2. BH1750：从 PB4/PB5 改到 PB6/PB7，顺便删掉 JTAG 重映射

参考工程 `BH1750.h` 里是 SCL=PB4、SDA=PB5，并且 `Init_BH1750()` 里有一句

```c
GPIO_PinRemapConfig(GPIO_Remap_SWJ_JTAGDisable, ENABLE);
```

**这句是为了解放 PB4**（PB4 是 JTAG 的 NJTRST）。换成 PB6/PB7 后，PB6/PB7 不是 JTAG 脚，**这句可以直接删掉**——留着也不出错（禁的是 JTAG，SWD 的 PA13/PA14 还在，你还要用它下载），删掉是更符合"最短能跑通"的做法。

⚠️ 额外提醒：GY-302 之间是 I2C，**必须上拉**。GY-302 小板自己带 4.7 kΩ 上拉，不用外加。

详见 [01-BH1750光照传感器移植.md](01-BH1750光照传感器移植.md)。

### 3. LED：从 PWM 调光改成两个普通 GPIO，而且**是低电平点亮**

参考工程 `LED.h` 是 `PB14` + `TIM1 CH2` 的 PWM 调光（能显示 0/30/60/100% 亮度）。你的板子上是**两个独立的普通 LED，只有 2 个脚，没有 PWM 通路**，所以：

- `LED.c` / `LED.h` / `PWM.c` 这一整套（`LED_Init`、`LED_PWM_KEY`、`ledluminance`）**全部作废**，别移植；
- 新写两个 GPIO 输出即可。

看网表：

```
'$1N75' ; D2.1 R11.2      3V3 ; ... R11.1 ...
'$1N74' ; D3.1 R1.2       3V3 ; ... R1.1 ...
```

电流路径是 `3V3 → R11 → D2 → PC14`，也就是**阳极接 3V3、阴极接 MCU**，所以：

> **PC14 / PC15 输出低电平（`GPIO_PIN_RESET`）时 LED 亮，输出高电平时灭。**

这点和参考工程（`GPIO_ResetBits` 灭灯）是**反的**，第一次点亮大概率会搞反。

⚠️ 另一个坑：PC13/PC14/PC15 在 STM32F1 上属于**低驱动能力引脚**，数据手册限定单脚灌电流不能超过 3 mA。所以 R1/R11 取 **1 kΩ** 左右比较稳妥（3V3 − 2 V ≈ 1.3 mA），别用 220 Ω。

⚠️ PC14/PC15 同时是 **LSE 晶振脚**（OSC32_IN/OSC32_OUT）。`EnvMon_WIFI` 的 `SystemClock_Config()` 只用 HSE、`.ioc` 里也没开 LSE，所以拿来当普通 GPIO 是安全的；但**以后要上 RTC 或者用 32.768 kHz 晶振就没位置了**。

⚠️ **这条在题目4 里是要还的**：题目4 要求 OLED 显示"当前时间"，而 STM32F1 自带的 RTC 只能用 LSE，也就是只能用 PC14/PC15——正好被这两个 LED 占着。三条出路（上电计时 / ESP8266 网络对时 / 外挂 I2C RTC 芯片）见 [06 篇第三节](06-题目4缺口补齐-按键时间播报PWM云端.md)。

⚠️ **PWM 调光也一样**：PC14/PC15 没有任何定时器通道，硬件 PWM 出不来。但**软件 PWM（定时中断翻转 GPIO）完全可以**——03 篇里"硬件上就是断的"那句结论下得太满，更正见 [06 篇第六节](06-题目4缺口补齐-按键时间播报PWM云端.md)。

详见 [03-LED指示灯移植.md](03-LED指示灯移植.md)。

### 4. 蜂鸣器：从 PA0 改到 PC13，只改两个宏

参考工程 `Buzzer.h` 的 `Buzzer = GPIO_Pin_0` / `Buzzer_PROT = GPIOA`，改成 `GPIO_PIN_13` / `GPIOC`。`Buzzer_ON()` 里是 `GPIO_SetBits`（**高电平开**），和你的板子一致（U4.3 接 3V3，U4.2 是信号脚），逻辑不用反。PC13 同样受 3 mA 限制，不过蜂鸣器模块的信号脚是驱动三极管基极，电流很小，没问题。

### 5. 天问语音：**必须占 USART1（PA9/PA10）**，和 printf 打架

网表里 `PA9 ; U1.6 U5.13`、`PA10 ; U1.7 U5.14`——**你的板子把天问模块硬接在 USART1 上了**。而 `EnvMon_WIFI` 当前的 USART1 是调试 printf 口（`fputc` 重定向到 `huart1`）。

这是**板级布线决定的硬冲突，软件改不了**（除非飞线或改板）。三条出路：

1. **【推荐】共享 USART1。** 天问的通信是单工为主（MCU 发命令、模块发应答），而 printf 只发不收：
   - `PA9`（MCU TX）同时喂给 `天问的 RX` 和（接调试助手时）`助手的 RX`——两个都是输入，不冲突；
   - printf 只输出 ASCII，而天问的协议要求帧头 `0x55 0xAA`，`0xAA` 不是 ASCII 字符，**printf 的输出永远不会被误判成一帧**，安全；
   - 代价：调试助手只能**单向监听** PA10，**不要接助手的 TX**（会和模块 TX 一起顶在 USART1 的 RX 上，互相打架）。
2. 放弃 printf，USART1 专供天问。
3. 飞线到 PB10/PB11（USART3，网表里引出来了但悬空）——要动硬件。

注意 `EnvMon_WIFI` 里 **USART1 没开 NVIC 中断**（`Core/Src/usart.c` 的 `HAL_UART_MspInit` 里只有 USART2 有 `HAL_NVIC_EnableIRQ`），接收要自己加，见 04 篇。

详见 [04-天问语音模块移植.md](04-天问语音模块移植.md)。

### 6. ESP8266：PA2/PA3 已经对了，**但 PB1 那个脚的身份存疑**

好消息：你的板子 `U2.4 ← PA2`、`U2.8 → PA3`，和 `EnvMon_WIFI` 现在的 USART2（PA2=TX / PA3=RX）**完全一致**，波特率 115200 也不用改，这部分零工作量。

坏消息：`PB1 ; U1.34 U2.6`。ESP-01S 只有 8 个脚，其中 U2.5、U2.7 都接了 3V3（电源），剩下 U2.6 只能是 **EN(CH_PD) / RST / GPIO0 / GPIO2** 之一。而 `BSP/ESP8266/esp8266.h` 里写的是

```c
#define ESP8266_RST_PIN  GPIO_PIN_1
#define ESP8266_RST_PORT GPIOB
```

`ESP8266_Init()` 会把它**拉低 100 ms 再放开**。如果 U2.6 实际不是 RST：

- 是 **CH_PD/EN** → 拉低=整颗芯片断电，放开=重新上电启动。**效果上碰巧和复位差不多，能用**，但它是"掉电启动"而不是"复位"，时序余量更小，建议改成上电后一直拉高，靠 `AT+RST` 软复位。
- 是 **GPIO0** → ⚠️ **最危险**。GPIO0 在上电瞬间为低会进 **Flash 下载模式**，模块直接不跑程序，表现为"怎么都连不上"。必须确认。

**`2.电路图/电路图.pdf` 我没能打开**（本机缺 `pdftoppm`），所以这一条是**根据 ESP-01S 封装惯例推断的，没有目视核对过**。请你自己打开原理图确认 U2.6 的丝印/网络名。确认方法：拿万用表量 U2.6 对地电阻，或直接看原理图上那根线连到模块的哪个脚名。

详见 [05-ESP8266移植-两套方案对比.md](05-ESP8266移植-两套方案对比.md)。

### 7. TDS 模块（U3）：和 DHT11 撞 PB12

`PB12 ; U1.1 U3.2`，而 `EnvMon_WIFI` 里 `DHT11_PIN = GPIO_PIN_12`，`MX_GPIO_Init()` 也把 PB12 配成了开漏输出。**同一根线不可能既是 TDS 的数据脚又是 DHT11 的数据脚。**

⚠️ **再仔细看一遍 `$PACKAGES` 段：你的板子上根本没有 DHT11 这个器件，PB12 上挂的是 TDS（U3）。** 也就是说 DHT11 是**要你自己接的**，而它唯一顺理成章的位置已经被占了。

如果目标是题目4（要 DHT11、不要 TDS），那就**把 U3 拆掉或不焊**，数据线接 PB12。详见 [06 篇第五节](06-题目4缺口补齐-按键时间播报PWM云端.md)。

## 四、三个共通机制（每篇都要用，先在这里讲一次）

### 机制一：`BSP_DelayMs()` 的强弱符号覆盖

`BSP/bsp_delay/bsp_delay.c` 里是 `__weak` 的 `BSP_DelayMs()`（内部调 `HAL_Delay` 忙等），`APP/app_delay.c` 里是强定义（调度器已跑就 `vTaskDelay`，没跑就 `HAL_Delay`）。链接器自动选强的。

**对移植的意义**：驱动里**永远写 `BSP_DelayMs()`，绝不要直接写 `HAL_Delay()` 或 `vTaskDelay()`**。这样驱动代码在调度器之前（`App_Init()` 里）和之后（任务里）都能用，不用改一个字。

### 机制二：微秒延时——工程里**没有**现成的，要自己加

参考工程的 `Delay_us(5)` 是 SPL 的忙等。`EnvMon_WIFI` 目前**只有 `dht11.c` 内部一份 `static` 的 DWT 微秒延时**，没对外暴露。

BH1750 的软件 I2C 每半个时钟要 5 μs 延时，**没有它根本跑不通**。所以 01 篇的第一步就是往 `BSP/bsp_delay/` 里加一个公用的：

```c
/* bsp_delay.h */
void BSP_DelayUs(uint32_t us);   /* 忙等微秒, 只给总线时序用(<=几 ms) */
```

实现用 Cortex-M3 内核自带的 **DWT 周期计数器**（`DWT->CYCCNT`），理由和 DHT11 里那段注释一样：不占 SysTick、不占任何 TIM、和 FreeRTOS 零冲突。注意 DHT11 里那份是 `static` 的，两份各自初始化 DWT 是幂等的（都只是置 `DEMCR.TRCENA` 和 `DWT->CTRL`），**不冲突**，不用去改 `dht11.c`。

⚠️ `BSP_DelayUs()` 是**忙等**，只能用在几微秒到几百微秒的总线时序上；毫秒级一律用 `BSP_DelayMs()`，否则会把 CPU 白占着不放给别的任务。

### 机制三：FreeRTOS 的任务优先级和栈

`FreeRTOSConfig.h` 里的关键数字：

```c
#define configMAX_PRIORITIES        5      /* 可用优先级 0~4 */
#define configMINIMAL_STACK_SIZE    128    /* idle 任务, 单位是字(4字节) */
#define configTICK_RATE_HZ          1000
#define configTOTAL_HEAP_SIZE       10240  /* 字节 */
#define configTIMER_TASK_PRIORITY   (configMAX_PRIORITIES - 1)   /* = 4 */
```

当前占用情况：

| 用途 | 优先级 | 栈（字） | 栈（字节） |
|---|---|---|---|
| 定时器服务任务 | 4 | 128 | 512 |
| WiFi 任务 | 3 | 512 | 2048 |
| DHT11 任务 | 2 | 256 | 1024 |
| idle | 0 | 128 | 512 |
| 队列 `g_xDht11Queue` | — | 4×2 + 开销 | ~50 |

**合计约 4.2 KB / 10 KB**，还有一半余量。所以再挂 **OLED 任务（优先级 1，栈 256 字）** 和 **语音任务（优先级 1，栈 256 字）** 是放得下的，大概到 6.3 KB。

**优先级别乱填**：WiFi 是 3，采集任务别超过 3。OLED 刷屏是慢速外设（整屏 1 KB 数据按位发送，耗时几十毫秒），**优先级给最低（1）**，让它只捡空闲时间刷，否则会把 WiFi 和采集饿死。

**别忘了一句**：`configTOTAL_HEAP_SIZE` 是 `heap_4` 的总池子，加任务后如果 `xTaskCreate` 返回 `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY`，就是这个池子不够，不是栈写错了。

## 五、本套笔记的读法

每篇都是固定三段：

1. **作用原理**——这个模块是干什么的、靠什么物理/协议原理工作；
2. **代码原理**——参考工程的代码为什么这么写，哪几行是关键，哪里其实写错了；
3. **怎么移植到 PCB**——引脚改哪几行、工程里加哪些文件、`App_Init()` 里加哪句、怎么验证。

带 ⚠️ 的是**已知有问题或者我也没核实过**的地方，别跳过。
