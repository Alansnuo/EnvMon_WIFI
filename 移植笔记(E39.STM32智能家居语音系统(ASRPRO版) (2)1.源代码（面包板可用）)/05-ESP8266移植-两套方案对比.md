# 05 ESP8266 联网移植：两套方案对比

**定位**：同一个 ESP8266，参考工程把它当"透传模块"跑机智云协议栈，`EnvMon_WIFI` 把它当"AT 指令模块"直连 OneNET 物模型。**两条路都对，但代码量、可调试性、烧录方式完全不同**。本篇把两套都讲清楚，再给结论。

**读之前先补**：[00-总纲](00-总纲-PCB引脚表与移植决策.md)（第二节引脚表、第三节第 6 条「PB1 身份存疑」）。

**参考文件**：参考工程 `Gizwits/gizwits_protocol.c`、`gizwits_product.c`、`System/Usart.c`、`Utils/`；目标工程 `BSP/ESP8266/esp8266.c`、`esp8266.h`、`APP/app_json.c`、`APP/task_wifi.c`、`APP/app_config.h`

> **题目4 必做2 还要"当前时间"**，而这块板子上没有 RTC。最省事的办法是让 ESP8266 网络对时（`AT+CIPSNTPCFG` / `AT+CIPSNTPTIME?`），它复用本篇已经在跑的 USART2。见 [06 篇第三节](06-题目4缺口补齐-按键时间播报PWM云端.md)。
>
> **题目4 选做1 说的是 EMQX / 阿里云 IoT**，不是 OneNET。好消息：本篇这套用的是**通用 AT MQTT 指令**，换 EMQX 一行驱动代码都不用改。阿里云**不建议**（要 HMAC-SHA1，AT 固件算不了）。见 [06 篇第七节](06-题目4缺口补齐-按键时间播报PWM云端.md)。

## 一、作用原理

### 先分清「模块」和「模块里的固件」

ESP8266 是一颗带 WiFi 收发能力的 SoC（**它自己也是一颗 MCU**，主频 80/160 MHz，还带 Flash）。大家说的"ESP8266 模块"（ESP-01S）通常指**芯片 + Flash + 天线 + 电平转换**做成的 8 脚小板。你的网表里 `U2` 就是它。

关键认识：**模块出厂时里面烧的固件，决定了你能怎么用它**。常见两种：

| 固件 | 谁提供的 | 对外什么样 |
|---|---|---|
| **AT 固件** | 乐鑫（Espressif）官方 | 一串 `AT+xxx` 文本命令，MCU 用 printf 的方式驱动它 |
| **GAgent 固件** | 机智云 | 二进制协议，MCU 侧要跑 `gizwits_protocol.c` 才能对话 |

**两套方案的差别，80% 就是这个固件。** 不是"两种写法"，是"两块硬件其实是同一块、但里面的软件不同"。所以选方案之前先问自己：手头这块 ESP-01S **现在烧的是哪个**？

判断方法：接 USB-TTL，波特率 115200，随便发一句 `AT`。
- 回 `OK` → **AT 固件**，走方案 A；
- 什么都不回（或者回一堆乱码二进制）→ 可能是 GAgent 固件，或者波特率不对（GAgent 常见 9600）。

### 方案 A：AT 指令 + OneNET 物模型

ESP8266 里跑 AT 固件，**MCU 用文本命令遥控它**。整个通信链路是：

```
MCU ──(USART2, 115200)──> ESP8266 ──(WiFi/TCP)──> mqtts.heclouds.com:1883
     "AT+MQTTPUB=0,\"$sys/.../post\",\"{\"...\"}\",0,0"
```

**MCU 侧要做的事**：① 用 AT 指令配 WiFi、配 MQTT、连服务器；② 自己拼 JSON 报文；③ 发出去。就这些。

`EnvMon_WIFI` 里这套**已经写好并跑通了**，本篇主要是带你读懂它。

### 方案 B：GAgent 固件 + 机智云协议栈

ESP8266 里跑 GAgent 固件，**模块自己会连机智云**——它认得云端、会维持心跳、会断线重连、能接收云端下发的数据点。MCU 只跟它做一件事：**通过串口交换"数据点"**。

```
MCU ──(USART2, 9600, 私有二进制)──> ESP8266/GAgent ──(WiFi)──> 机智云
     gizwits_protocol.c 打包的字节流
```

**MCU 侧要做的事**：跑一整套 `gizwits_protocol.c`（**62 KB 源码**的协议栈），定义数据点结构体 `dataPoint_t`，处理配网、心跳、时间戳、握手、加密。

这就解释了参考工程为什么有 `Gizwits/` 那一堆文件——**它不是"驱动 ESP8266"，它是在 MCU 上重新实现了一遍机智云的通信协议**。

### 两条路的成本在哪

| | 方案 A | 方案 B |
|---|---|---|
| 复杂的东西在哪 | 在 ESP8266 的 AT 固件里（乐鑫写的） | 在 MCU 的协议栈里（机智云写的） |
| MCU 侧代码量 | 约 10 KB 源码 | `gizwits_protocol.c` 一个文件就 62 KB |
| 你要理解的东西 | AT 指令集 + JSON | 二进制协议格式（或者干脆不理解，当黑盒用） |
| 模块要不要刷固件 | 用出厂固件即可 | **必须刷成 GAgent**，把原厂 AT 固件冲掉 |

⚠️ **这一条是方案 B 最大的隐性门槛**：刷固件要把 ESP8266 的 **GPIO0 拉低**再上电（进 Flash 下载模式），用 USB-TTL + 乐鑫烧录工具。**没有 USB-TTL 转换器就做不了方案 B**。而且刷完之后模块**再也不是 AT 模块了**，想回方案 A 得再刷回来。

## 二、代码原理

### 方案 A 的代码（`EnvMon_WIFI` 现有实现，5 个文件）

#### 结构总览

```
BSP/ESP8266/esp8266.h/.c   驱动: AT 指令收发 + 收发缓冲管理
APP/app_json.c             报文: 拼 JSON, 值变化才发
APP/task_wifi.c            任务: 连一次网, 然后循环上报
APP/app_config.h           配置: WiFi 账号 + OneNET 三元组
```

#### `esp8266.h` 里的关键宏

```c
#define ESP8266_UART   huart2                  /* USART2: PA2=TX, PA3=RX */
#define ESP8266_RST_PIN  GPIO_PIN_1            /* ⚠️ 见第 3 步: U2.6 身份待核实 */
#define ESP8266_RST_PORT GPIOB
```

波特率 115200（在 CubeMX 里配 USART2），和 AT 固件默认值一致。

#### 收发为什么这么设计（本驱动最值得学的部分）

`esp8266.c` 顶部有一句注释，把设计动机写得很清楚：

> 非用 DMA 不可：F1 的串口只有 1 字节接收寄存器，而 DHT11 要关中断约 4 ms，用 RXNE 中断收的话那 4 ms 里的字节必丢。

展开说：
- **AT 指令的应答很长**（`AT+CWJAP` 连上路由器会吐几十上百字节），而 **F1 的 USART 接收寄存器只有 1 字节深**，CPU 晚来一步就丢一个字节；
- 更糟的是 `dht11.c:147` 会 `__disable_irq()` 关中断约 4 ms，**这期间任何 RXNE 中断都进不来**；
- 所以接收走 **DMA1_Channel6 循环模式**——DMA 是硬件搬运，**不需要中断参与**，关中断也照收不误。

对应的代码：

```c
/* 收: 循环 DMA + 轮询 CNDTR 算写了多少 */
ESP8266_RxStart()  → HAL_UART_Receive_DMA(&ESP8266_UART, s_DmaBuf, ESP8266_DMA_BUF_SIZE)
ESP8266_RxHead()   → ESP8266_DMA_BUF_SIZE - __HAL_DMA_GET_COUNTER(...)
ESP8266_RxPop()    → 从 DMA 环形缓冲抄到自己的环形缓冲(处理回绕)
ESP8266_RxDrain()  → 把新收到的字节喂给 strstr 用
```

**注意有两个"环"**：DMA 的环形缓冲（`ESP8266_DMA_BUF_SIZE` 256 字节）+ 驱动自己维护的接收缓冲。抄这一层是因为 DMA 缓冲区随时在回绕，直接在上面 `strstr` 会读到半新半旧的内容。

DMA 启动时还**故意关掉了两个中断**：

```c
__HAL_DMA_DISABLE_IT(&hdma_usart2_rx, DMA_IT_TC);    /* 不用 DMA 传输完成中断 */
__HAL_UART_DISABLE_IT(&ESP8266_UART, UART_IT_ERR);   /* 不用串口错误中断 */
```

理由：**这个驱动的接收模型是"轮询 CNDTR"，不是"中断通知"**。开着 TC 中断反而会在每次缓冲满时打断任务，而任务本来就会定时来捞数据。关掉更简单，也没有丢数据的风险。

**发送**走 `HAL_UART_Transmit_IT`（中断发送），所以 **USART2 的 NVIC 必须开**——`Core/Src/usart.c` 的 `HAL_UART_MspInit` 里 USART2 那段有 `HAL_NVIC_EnableIRQ(USART2_IRQn)`，**这个不能删**。

> 对比 04 篇的天问：天问用 RXNE 中断（6 字节短帧，丢了重说一遍就行）；ESP8266 用 DMA（几十到几百字节，丢一个字节整条 AT 应答就废了）。**同样是串口收数据，帧长决定了选哪种方式**，不要互相套用。

#### `ESP8266_Exec()`：一个 AT 指令从发出到判定的完整流程

```
1. 检查长度 < ESP8266_AT_CMD_MAX（288 字节，AT 指令不能太长）
2. ClearRxBuf()          ← memset 清接收缓冲
3. HAL_UART_Transmit_IT() 发出去
4. 等 gState == HAL_UART_STATE_READY（发送完成），超时 ESP8266_TX_TIMEOUT
5. 主循环:
     RxDrain()                                   ← 收新字节
     找到期望的 ack 字符串  → 返回 OK
     找到 "ERROR" 或 "FAIL" → 返回失败
     缓冲满                → 返回失败
     总超时                → 返回失败
```

⚠️ **`ClearRxBuf()` 用 `memset` 清零而不是只挪指针**，因为第 5 步靠 `strstr` 找子串——`strstr` 需要 `'\0'` 结尾。如果只挪索引不清零，上一次的残留会混进来导致误判。

⚠️ **`ate0` 那条不能省**（`ESP8266_Init` 里发了 `ATE0`）。AT 固件默认回显（你发什么它原样吐回来），回显会让 `strstr` 在错误的时机命中——比如你发 `AT+MQTTCONN=...` 想等 `+MQTTCONNECTED`，结果自己的回显里带 `AT+MQTTCONN` 先命中了别的判断。关掉回显一劳永逸。

⚠️ **`AT+CWAUTOCONN=0` 也是故意的**：关掉"上电自动连上次的 AP"。不关的话模块可能自己去连一个你不知道的热点，然后报文全丢在那边，现象是"程序说发出去了但云端没数据"。

#### 四条 AT 指令组，对应 `app_config.h` 的哪个字段

| 驱动函数 | 发的指令 | 字段来源 |
|---|---|---|
| `ESP8266_ConnectAP()` | `AT+CWMODE=1` / `AT+CWQAP` / `AT+CWJAP="%s","%s"` | `CFG_WIFI_SSID` / `CFG_WIFI_PASSWORD` |
| `ESP8266_MQTT_SetParam()` | `AT+MQTTUSERCFG=0,1,"%s","%s","",0,0,""` | `CFG_MQTT_CLIENT_ID` / `CFG_MQTT_USERNAME` |
| 〃 | `AT+MQTTPASSWORD=0,"%s"` | `CFG_MQTT_PASSWORD` |
| 〃 | `AT+MQTTCONNCFG=0,%u,0,"","",0,0` | `CFG_MQTT_KEEPALIVE_S` |
| `ESP8266_MQTT_ConnectBroker()` | `AT+MQTTCONN=0,"%s",%u,0` | `CFG_MQTT_HOST` / `CFG_MQTT_PORT` |
| `ESP8266_MQTT_Publish()` | `AT+MQTTPUB=0,"%s","%s",0,0` | `CFG_MQTT_PUB_TOPIC` + 报文 |

`AT+MQTTUSERCFG` 里那个 `scheme = 1` 表示 **MQTT over TCP**（不是 TLS）。OneNET 的 1883 端口就是明文 TCP，所以是 1；如果用 8883 加密端口才改成 2。

⚠️ **为什么密码要单独发 `AT+MQTTPASSWORD`**：OneNET 的 Token 长度**超过了 AT 固件里 `AT+MQTTUSERCFG` 的密码字段上限（64 字节）**，塞不进去会被截断，导致连不上（现象是 `AT+MQTTCONN` 返回 `ERROR` 或一直等不到 `+MQTTCONNECTED`）。分开发就绕过了这个限制。

⚠️ **`AT+MQTTCONN` 等的确认串是 `"+MQTTCONNECTED"`，不是 `"CONNECTED"`。** 因为 AT 固件在连接过程中还可能吐出 `WIFI CONNECTED` / `WIFI GOT IP` 之类的字符串，用短串会**提前命中**，误判成"MQTT 连上了"。`esp8266.h` 的函数注释里专门写了这条。

#### 报文：`app_json.c` 的两件事

**第一件：拼 OneNET 物模型的 JSON。** OneNET 要求这个格式：

```json
{"id":"1","version":"1.0","params":{"Temp":{"value":25.0},"Hum":{"value":60.0}}}
```

代码里是一个 `snprintf` 套出来的，参数部分在 `s_Params[64]`：

```c
"\\\"Temp\\\":{\\\"value\\\":%d.0}\\,\\\"Hum\\\":{\\\"value\\\":%d.0}"
```

⚠️ **这里每一层反斜杠都是必要的，不是写多了**。两层原因叠在一起：
1. **C 源码层**：字符串字面量里的 `\"` 表示"一个双引号字符"。所以源码写着 `\\\"`，实际字符串里是 `\"`（反斜杠 + 引号）。
2. **AT 指令层**：`AT+MQTTPUB=0,"topic","payload",0,0` 是**逗号分隔、引号括起**的指令格式。payload 里的**每个双引号前面必须加反斜杠**，每个**逗号前面也要加反斜杠**——否则 AT 固件的解析器会把它们当成参数的结束/分隔符，把 payload 从中间切断。

所以最终发到模块线上的字节里，逗号是 `\,`、引号是 `\"`。**这就是 `app_json.c` 里那些看起来像乱码的反斜杠的全部意义**。

**第二件：值变化才发。** `AppJson_Report()` 把这次拼好的参数和**上一次发成功的** `s_Sent` 比对，一样就直接返回 0 不发；不一样才发，并且只在发送成功后才由 `AppJson_Commit()` 把 `s_Params` 拷进 `s_Sent`。

⚠️ 这个"发送成功才 Commit"的顺序很关键。如果先 Commit 再发、发失败了，本地会以为"已经告诉云端了"，**那份数据就永远补不上了**。代码里的顺序是对的，别改。

#### `task_wifi.c`：连一次，然后一直上报

```c
WifiConnect() = Init → ConnectAP → MQTT_SetParam → MQTT_ConnectBroker
TaskWifi()    = while (WifiConnect() == 0) { 等 5 秒重试 }   ← 连不上就一直重试
                然后进内循环: 收 DHT11 队列 → 拼报文 → 发布 → 成功就 Commit
```

重试策略是 `WIFI_RETRY_DELAY_MS = 5000`（连不上等 5 秒再来）和 `WIFI_MAX_CONSEC_FAIL = 3`（连续 3 次发布失败，认为链路已经废了，退回外层重连 WiFi）。

⚠️ **只有 `TaskWifi` 允许碰 ESP8266。** 别的任务（光照、语音、OLED）想上报数据，**只能往队列里丢**，由 WiFi 任务统一发。两个任务同时往 USART2 写，AT 指令会被撕碎，模块收到半条指令就吐 `ERROR`，之后所有指令都跟着错位。

⚠️ **本工程只发布，不订阅。** 所有 AT 指令里没有任何 `AT+MQTTSUB`，云端下发的数据没有人接。如果按 01 篇的建议加了光照上报，也是"发上去"，不是"读回来"。这是有意的设计（见 01 篇第 5 步）。

### 方案 B 的代码（参考工程，讲原理不照抄）

#### 文件清单——这就是"MCU 侧协议栈"的全部体重

| 文件 | 大小 | 作用 |
|---|---|---|
| `Gizwits/gizwits_protocol.c` | **62 KB** | 协议栈本体：打包/解包、心跳、时间同步、握手、P0 模式配网 |
| `Gizwits/gizwits_protocol.h` | 27 KB | 协议常量、结构体、宏 |
| `Gizwits/gizwits_product.c` | 12 KB | **用户层**：事件处理 + 串口读写回调 |
| `Utils/dataPointTools.c` | — | 数据点取值/赋值 |
| `Utils/ringbuffer.c` | — | 收发环形缓冲 |
| `Utils/gagent_md5.c` | — | 握手用的 MD5 |
| `Utils/common.c` | — | 通用工具 |
| `System/Usart.c` | — | USART2 初始化 + 中断收字节 |

加起来是**方案 A 的十倍左右**。而且 `Utils/` 里那几个文件是**协议栈的依赖**，不是可选项——少一个就链接不过。

#### 三层结构

```
gizwits_product.c   ← 你改这里
      ├─ gizwitsEventProcess()   云端下发的每条指令 → 一个 case
      ├─ userHandle()            传感器值 → currentDataPoint
      ├─ userInit()              数据点初始化
      ├─ gizTimerMs() / gizGetTimerCount()   毫秒计数(协议栈要算超时)
      └─ uartWrite()             MCU → 模块的字节发送
gizwits_protocol.c  ← 你不用改(也基本改不动)
      └─ 定时调 gizwitsHandle(&currentDataPoint) 完成所有通信
```

数据点是**结构体**（`dataPoint_t currentDataPoint`），你只管往字段里写值：

```c
void userHandle(void)
{
    currentDataPoint.valuetemperature = sensorData.temp;
    currentDataPoint.valuehumidness   = sensorData.humi;
    currentDataPoint.valuelux         = sensorData.lux;
    ...
}
```

云端的指令反过来，走 `gizwitsEventProcess()`：

```c
case EVENT_LED:
    currentDataPoint.valueLED = dataPointPtr->valueLED;
    ledluminance.ledDutyRatio = currentDataPoint.valueLED;
    TIM_SetCompare2(TIM1, ledluminance.ledDutyRatio);   /* 真正干活 */
    break;
```

**看懂这套结构的意义**：它和本篇方案 A 的 `AppJson_Report()` **在做同一件事**（把本地值告诉云端），只是方案 A 是"你自己拼 JSON"，方案 B 是"往结构体里赋值，协议栈帮你打包"。方案 B 好用，代价是协议栈的 100 KB 源码和它占的 RAM。

#### 一个很有意思的细节：`uartWrite()` 里的 `0xFF → 0x55`

```c
if (i >= 2 && buf[i] == 0xFF)
{
    USART_SendData(USART2, 0x55);      /* 补发一个 0x55 */
    while (USART_GetFlagStatus(USART2, USART_FLAG_TC) == RESET);
}
```

**这是 GAgent 协议的转义规则**：字节流里第 3 个字节之后（前 2 字节是帧头）出现的每个 `0xFF` 后面都要补一个 `0x55`，接收端反过来去掉。

为什么？因为——**这点和 04 篇的天问模块一模一样**——协议需要"帧头/帧尾"在字节流里唯一可辨。天问用的是 `0x55 0xAA` 做帧头（靠"`0xAA` 不是 ASCII"来保证 printf 不伪帧）；GAgent 用的是"`0xFF` 必须成对出现"这类约定（`0xFF` 开头就是命令帧）。

**两套转义都是为了同一件事**：在**没有帧边界**的串口字节流里，让"数据里恰好出现了跟标志位一样的字节"不再产生歧义。方案 A 的 `\,` / `\"` 转义（`app_json.c`）是同一个思想在文本层的版本——AT 指令用逗号和引号分词，payload 里的逗号引号就必须转义。

> 类比记住：**串口没有"包"这个概念，只有一串字节。** 谁想在里面划出边界，谁就得定一套转义规则，然后把两侧都写对。三套实现（天问 `0x55 0xAA`、GAgent `0xFF 0x55`、OneNET `\,` `\"`）本质是一回事。

#### 配网方式：airlink

参考工程里有一句 `gizwitsSetMode(WIFI_AIRLINK_MODE)`——**手机 App 通过路由器广播把 SSID/密码"喊"给模块**，模块听懂了就自己去连。**MCU 代码里不存 WiFi 密码**。

方案 A 是**硬编码**：`CFG_WIFI_SSID` / `CFG_WIFI_PASSWORD` 就写在 `app_config.h` 里，编译进固件。

这个差别带来的后果比看起来大：
- 方案 B **换 WiFi 不用重新烧固件**，换个手机 App 操作一遍就行；
- 方案 A **换 WiFi 要改代码重新编译烧录**。

对"自己玩的一块板子"来说方案 A 完全够用；如果是给别人用的产品，方案 B 的配网体验是刚需。

## 三、怎么移植到 PCB

### 第 1 步：先确定你走哪条路（可能是本篇最重要的一步）

**先量一件事**：你这块 ESP-01S **现在烧的是什么固件**。

```
接 USB-TTL: 模块 VCC→3V3, GND→GND, TXD→TTL的RX, RXD→TTL的TX, CH_PD→3V3
串口助手 115200, 发 AT + 回车
```

| 现象 | 固件 | 该走的方案 |
|---|---|---|
| 回 `OK` | AT 固件 | **方案 A**（`EnvMon_WIFI` 已经能跑） |
| 无回复 | 试 9600 再发一次；还是无回复说明是 GAgent 或别家的 | 方案 B，或重刷 AT 固件 |
| 回一堆乱码二进制 | GAgent | 方案 B，或重刷 AT 固件 |

⚠️ **`EnvMon_WIFI` 现在这套是方案 A，而且已经跑通了**（`task_wifi.c` / `app_json.c` / `esp8266.c` 都在，`app_config.h` 里账号也填好了）。所以**如果你只是想让它联网，什么都不用改**——方案 A 这条路已经在终点了。

**下面两节，方案 A 讲"怎么核实和验证"（因为代码已存在），方案 B 讲"如果非要用机智云，要搬哪些东西"。**

### 第 2 步（方案 A）：核实三处硬件配置

**① USART2 的 NVIC 必须开着。** `HAL_UART_Transmit_IT` 靠中断发字节，`Core/Src/usart.c` 的 `HAL_UART_MspInit` 里 USART2 那段应该有：

```c
HAL_NVIC_SetPriority(USART2_IRQn, n, 0);
HAL_NVIC_EnableIRQ(USART2_IRQn);
```

**② DMA1_Channel6 要配成 USART2_RX 的循环模式。** 在 `.ioc` 里 `USART2 → DMA Settings` 看有没有 `USART2_RX ← DMA1 Channel 6, Circular`。少了这条，`HAL_UART_Receive_DMA` 会返回错误，**接收一个字节都收不到**。

**③ 波特率 115200。** AT 固件默认 115200。如果你之前为了别的原因改过 USART2 的波特率，改回来。

### 第 3 步（方案 A）：⚠️ 核实 PB1 —— U2.6 到底是什么脚

这是**本篇唯一没被验证过的硬件项，务必自己确认**。

网表：`PB1 ; U1.34 U2.6`。`bsp/esp8266/esp8266.h` 里把它当成复位脚：

```c
#define ESP8266_RST_PIN  GPIO_PIN_1
#define ESP8266_RST_PORT GPIOB
```

`ESP8266_Init()` 的行为是**拉低 100 ms 再放开**：

```c
HAL_GPIO_WritePin(ESP8266_RST_PORT, ESP8266_RST_PIN, GPIO_PIN_RESET);
BSP_DelayMs(100);
HAL_GPIO_WritePin(ESP8266_RST_PORT, ESP8266_RST_PIN, GPIO_PIN_SET);
BSP_DelayMs(1000);
```

但 U2.6 不一定是 RST。ESP-01S 只有 8 个脚，U2.5 / U2.7 已确认接 3V3（电源），剩下 U2.6 只能是**这四个之一**：

| U2.6 实际是 | 拉低 100 ms 的后果 | 该怎么办 |
|---|---|---|
| **RST** | 复位，代码是对的 | 不用改 |
| **CH_PD / EN** | 相当于整颗芯片断电再上电。**碰巧能用**，但这是"掉电启动"不是"复位"，时序余量小 | 改成上电后**一直拉高**，需要复位时发 `AT+RST` |
| **GPIO0** | ⚠️ **最危险**。GPIO0 在上电瞬间为低 = 进 Flash 下载模式，**模块根本不跑程序**，现象是"怎么都连不上" | 上电后**立刻拉高**并保持，绝不能有低电平窗口 |
| **GPIO2** | GPIO2 上电时要为高，拉低同样会进不了正常启动 | 同上，保持高 |

**怎么确认**：打开 `2.电路图/电路图.pdf` 看那根线的网络名（`CH_PD` / `RST` / `GPIO0` / `GPIO2` 一般会标），或者拿万用表打 U2.6 对地/对 3V3 的阻值。

> ⚠️ **我打不开那份 PDF**（本机缺 `pdftoppm`），所以上面这张表是**按 ESP-01S 的封装惯例推断的，没有目视核对**。你必须自己确认一次。

⚠️ **顺便说**：这条和方案 B 的"刷固件要拉低 GPIO0"是同一件事的两面。**如果 U2.6 真是 GPIO0，方案 B 刷固件反而方便（现成的下载控制脚）**；但如果代码里让它上电为低，模块就永远起不来。

### 第 4 步（方案 A）：验证

按顺序，**每步过了再做下一步**：

**① 只验 AT 通道。** 在 `App_Init()` 里 `ESP8266_Init()` 之后打印它的返回值：

```c
if (ESP8266_Init() == ESP8266_OK) { printf("ESP AT OK\r\n"); }
else                              { printf("ESP AT FAIL\r\n"); }
```

- **FAIL**：先查 TX/RX 有没有接反（`PA2`→模块的 **RXD**，`PA3`←模块的 **TXD**，**交叉接**）；再查 USART2 的 DMA/NVIC；再确认波特率；最后怀疑 U2.6（第 3 步）。
- 模块上电时串口会吐一段启动日志（`ready` 之类），**能看到就是通的**（这是最省事的判断）。

**② 只验连 WiFi。** `ESP8266_ConnectAP()` 返回 OK 就说明 SSID/密码对、信号够。

- **FAIL**：`AT+CWJAP` 失败一般是密码错、SSID 是 5G（ESP8266 只支持 2.4 G）、或者信号太弱。**SSID/密码在 `APP/app_config.h` 里，中文 SSID 也可以**（AT 固件支持 UTF-8）。注意密码不能含未转义的 `"` 和 `,`。

**③ 只验 MQTT。** `ESP8266_MQTT_ConnectBroker()` 返回 OK（内部等的是 `+MQTTCONNECTED`）。

- **FAIL 且回 `ERROR`**：多半是三元组不对。OneNET 的三元组（产品 ID / 设备名 / Token）**必须和设备对得上**，Token 还有**有效期**（`app_config.h` 里那个 Token 的 `et=` 参数就是过期时间戳）。**Token 过期是"上个月还好好的、这个月连不上"的最常见原因**——去 OneNET 控制台重新生成一个。
- **一直等不到 `+MQTTCONNECTED`（超时）**：检查 `CFG_MQTT_HOST` 是不是 `mqtts.heclouds.com`、端口 1883。

**④ 全链路。** 恢复 `TaskWifi`，看 OneNET 控制台的**设备在线**和**物模型数据**。

- **在线但没有数据**：`AppJson_Report()` 的"值变化才发"在起作用——温湿度没变就不发。**吹口气让温度变一下**，或者把这段逻辑临时改成每次都发来验证通道。
- **有数据但平台显示格式错**：多半是 `app_json.c` 的转义被改动了。**那串 `\\\"` / `\\\,` 一个都不能删**（见第二节）。

### 第 5 步（方案 B）：如果确实要用机智云

**先把代价说清楚**：MCU 侧要多背约 100 KB 源码和相应的 RAM（`gizwits_protocol.c` 内部有多个静态缓冲）；STM32F103C8 只有 **64 KB Flash / 20 KB RAM**，把这套塞进去**很可能放不下**——参考工程大概率跑在更大容量的型号上。**移植前先用 Keil 编译一次看 `.map` 的 ROM/RAM 占用，放不下就别开始。**

如果放得下，要搬的东西：

1. **整个 `Gizwits/` 目录** + `Utils/` 里被引用的那几个文件（`common.c`、`dataPointTools.c`、`ringbuffer.c`、`gagent_md5.c`）；
2. **`System/Usart.c` 改写成 HAL**——参考工程那段是 SPL 的 `USART_SendData` 轮询 `USART_FLAG_TC`，在 FreeRTOS 下会**忙等把 CPU 占住**，必须换成 `HAL_UART_Transmit`（阻塞版可以，因为只有 WiFi 任务碰它）；
3. **波特率要改**：参考工程 USART2 是 9600，那是 **GAgent 固件的波特率**。刷成 GAgent 后，`EnvMon_WIFI` 现在的 115200 就不对了。
4. **给 ESP8266 刷 GAgent 固件**——这是绕不过去的一步（GPIO0 拉低 + USB-TTL + 乐鑫烧录工具）。
5. **删掉现在这套方案 A 的代码**：`BSP/ESP8266/esp8266.c`（AT 指令）、`APP/app_json.c`（JSON 拼装）全部作废，因为报文封装交给协议栈了。`task_wifi.c` 也要重写——从此不需要 `WifiConnect()`，协议栈自己管连接，`TaskWifi` 只剩一件事：**周期调 `gizwitsHandle(&currentDataPoint)` + 把传感器值写进 `currentDataPoint`**。

⚠️ **注意 `gizwitsHandle()` 必须被周期调用**（它内部靠"距离上次调用多少毫秒"推进状态机），周期要稳定。在 FreeRTOS 里就放在 `TaskWifi` 的循环里，**周期不能飘**——所以这个任务别设成最低优先级，也别让别的任务把它饿太久。

### 两套方案速查对照

| | 方案 A（`EnvMon_WIFI` 现状） | 方案 B（参考工程） |
|---|---|---|
| 模块固件 | AT 固件（出厂即可） | **GAgent（必须自己刷）** |
| 串口波特率 | 115200 | 9600 |
| MCU 侧源码 | 约 10 KB（3 个文件） | 约 100 KB（7+ 个文件） |
| Flash / RAM | 很省 | **F103C8 可能放不下** |
| 要理解的东西 | AT 指令 + JSON 转义 | 二进制协议（或当黑盒） |
| 配网 | 硬编码在 `app_config.h` | airlink（手机 App 广播） |
| 换 WiFi | 改代码重烧 | App 里操作一遍 |
| 云端 | OneNET（物模型 + JSON） | 机智云（数据点） |
| 方向 | **只发不收** | 收发都有（云端能下发指令） |
| 断线重连 | 自己写（`task_wifi.c` 的外层 while） | 协议栈内置 |
| 可调试性 | **高**：全是可读的 ASCII AT 指令 | 低：二进制，要抓包解析 |
| 云端绑定 | 松：换 MQTT 服务器 = 改字符串 | 紧：绑死机智云 |
| 额外硬件 | 无 | **USB-TTL 转换器**（刷固件用） |

### 结论

**你的板子 + `EnvMon_WIFI` 就该用方案 A，而且已经用上了。** 理由按重要性排：

1. **它已经在跑了**，`task_wifi.c` / `app_json.c` / `esp8266.c` 都在工程里，账号也配好了。方案 B 要从零搬 100 KB 协议栈，还得先搞 USB-TTL 刷固件。
2. **F103C8 放不下方案 B**。64 KB Flash 装 62 KB 的协议栈源码（编译后虽然会小一些，但加上 HAL、FreeRTOS 和你的应用，余量非常紧），风险不值得冒。
3. **这块板子是只上报的场景**（温湿度 + 光照），不需要云端下发指令。方案 B 的"协议栈内置重连 / airlink 配网"这些好处，在这个场景下换不回那 100 KB 的成本。
4. **调试成本差一个量级**。方案 A 出问题时你打开串口助手就能看到 `AT+CWJAP` 返回了什么；方案 B 出问题你得对着二进制猜。

**方案 B 什么时候才对**：要给别人用（配网体验是刚需）、需要云端反向控制设备、或者你根本没有 AT 固件的模块手上只有 GAgent 的。前两条你现在都不满足。
